= Caching and Resource Lifecycles
:toc:
:toclevels: 2

Resources follow their owners, not one global cache switch: Core retains bounded
lookup state; each window retains query/display state; application services share
artwork and processing outputs; the renderer and font backend own their own
allocations. This chapter defines what is retained, what invalidates it, and when
the owner can release it. Entry and payload limits are not process-RSS limits,
and releasing an application reference need not immediately reclaim GPU memory.

Query stamps and revision domains are defined in
link:21_ipc.adoc#_query_results_and_pagination[IPC]. Signal meaning and continuity
belong to link:23_visuals.adoc[Visualization Rendering Design], layout/interaction
contracts to link:24_layout.adoc[GUI layout], and GPU admission/API guarantees
to link:25_gpu_rendering.adoc[GPU rendering]. The sections below retain the
invalidation consequences needed to reason about resource use without repeating
those mechanisms.

== Query projection retention

List/tree retention is independent of `visualizations.cache`. A projection key
combines normalized query identity and its query-owned stamp, not page offsets,
limits, cursors, or expected revisions. A matching stamp authorizes query reuse;
bitrate-bearing payload stamps include the committed bitrate revision. A consumer
generation decides whether the result still serves current intent. Neither check
can substitute for physical-worker completion.

=== Core-owned lookup retention

The interactive Store keeps a track-ID LRU of at most twice
`interface.page_size`: 128 tracks at the default 64, at most 512 at the supported
maximum 256. Hits refresh age; misses are not cached. Reducing page size trims
immediately. Core metadata changes invalidate affected entries; playback
statistics patch cached scalars. A successful source-conditional bitrate commit
patches an existing cached Track's value/certainty pair without inserting a miss.
Scan publication clears this cache only for library-display impacts; no-change
scans and masked raw-metadata edits retain it.
This bounds entries, not track-string bytes, and is neither a whole-library
snapshot nor a GUI page cache. Read-only export does not use it.

Library track/display pages retain one latest exact filtered count, keyed by
normalized filters and optional root. A separate scalar slot retains the
duplicate-group total. A sixteen-entry LRU of scalar totals covers Other,
directory children, albums and album members, Queue, and playlist entries; keys
include the relevant filters and collection identity, never page offsets or rows.
The read-query owner reuses counts across pinned snapshots while the owning
data-domain revisions remain valid. Cache ownership advances only after the
pinned snapshot passes publication validation. Read-only mode alone is not an
invalidation rule. Writable scalar-count caches check SQLite's local-change
counter and on-demand `PRAGMA data_version` so independent commits cannot leave
stale totals. Explicit writer transactions bypass count caches, avoiding rollback
leakage. Read-query caches invalidate only their affected data domains; unrelated
Queue/playlist changes and no-change scans retain library totals. There is no
timer-based external-commit polling or collection-sized row cache.

The background read owner leaves its Track-cache capacity at zero; it does not
share the interactive Store's LRU. Bitrate revision changes retain count caches:
bitrate is neither a filter nor an ordering/count input. Single-Track reads and
page SQL remain separate paths; pages are not assembled through per-ID LRU reads.

Root aggregation and directory child relations remain request-local; persistent
album summaries are transactionally maintained database projections, not an
evictable page cache.
Their query costs and invariants are in
link:21_ipc.adoc#_transactional_inputs_and_bounded_storage_queries[IPC storage queries].

=== Window-local query retention

The window and feature owners share one GUI snapshot cache. Changed-state
projection and revision comparison occur under the same Core read lock; unchanged
reads reuse the snapshot. Each consumer retains its own last-processed revision,
so another consumer's refresh cannot hide a change. Completion/timeout checks use
current revisions, not a submission-time snapshot. A publication with unchanged
state-section tokens does not invalidate the GUI root; audio frames still have
their independent processing path.

Bitrate revision changes retire retained display payloads for demand-driven
reload while preserving selection, counts, and navigation geometry. There is no
bitrate history, replay cache, or track-to-view reverse index. Old responses fail
the same query-stamp admission as other stale data. See
link:21_ipc.adoc#_query_results_and_pagination[IPC query results].

==== Demand, cancellation, and physical retirement

Feature owners reconcile configuration and revision keys even while hidden;
actual reads require demand. An open Add to playlist chooser independently
demands summaries. Hiding retires pending reads immediately, without waiting for
another Core publication or paint, but preserves accepted rows, selections, and
Details drafts. Unchanged album keys retain bounded pages and failures; covers
have separate owners.

Every submitted read holds its physical slot until its actual Core reply or
reply-channel disconnection. Replacement, cancellation, hiding, and a logical
timeout can revoke publication rights but cannot release that slot. Only matching
completion releases it and re-drives the latest eligible demand; old completions
cannot clear replacement requests or publish feedback. Hidden demand waits for
reveal. This is handoff, not retry of a current failure or polling of a task.
Owner epochs let Core skip obsolete queued GUI reads before Store access; already
dispatched SQL is not interrupted, another owner's work is not cancelled, and
writes are never replayed.

GUI submission has a two-second deadline and response presentation a 12-second
deadline. A response timeout stops current loading feedback and shows its error,
but the reader still owns the slot and discards any late payload. Explicit retry
also waits for that retirement. This GUI policy does not alter IPC, non-GUI
deadlines, or command acknowledgements. Transport errors carry no payload stamp
and are not evidence of a changed collection; successful payloads still require
current data and intent.

Debounced directory/playlist/Details reads recheck demand before submission.
Abandoned timers release only their own unsubmitted reservations, not submitted
slots or accepted data. Album searches, Playlist pages, and explicit Details
retain the latest demand's absolute quiet deadline across redispatch, hiding,
and completion; replacement renews it. The window's explicit-action confirmation
barrier is independent of Details drafts and selection owners: late reads/save
acknowledgements cannot restore retired intent. Interaction rules are described
in link:24_layout.adoc[GUI layout].

==== Payloads, failures, and retained geometry

[cols="1,2",options="header"]
|===
|Buffer |Retention bound
|Album, Playlist catalog/entry, Queue pages
|The larger of eight pages or visible pages plus three; failed offsets have the
same separate bound.
|Library tree pages and failures
|One shared LRU bound: the larger of sixteen pages or current demand, including
unverified ancestry. Expansion/selection identities are separate from payloads.
|===

Tree branch bookkeeping follows live ownership: cached pages, demand, pending
requests, expanded descendants and their ancestors, selection, focus, and
navigation. Otherwise-unowned collapsed branches are reclaimed rather than kept
for every directory ever visited. Reopening one loads its count again; hidden
descendant expansion choices and selected anchors remain intact.

Expansion snapshots belong only to the inactive view; switching consumes the
destination snapshot rather than retaining a duplicate of its active branches.
Sparse branch, page, stale-ancestry, selection-anchor and selected-identity hash
tables shed high-water capacity when their live contents shrink substantially,
retaining bounded reuse slack instead of reallocating on every deselection or collapse.
Branch collection borrows live identities and runs when ownership changes, not
for unchanged viewport demand alone.

A data revision forgets counts and drops obsolete pages, failures, and positional
pins, but retains nonempty scroll geometry until a current result supplies its
total. Previously empty results gain a loading position so additions remain
discoverable. Flat-list/album query changes discard old geometry; tree filter
changes preserve expansion choices while invalidating facts. Retained geometry
cannot authorize counts, ranges, or navigation; tree ranges also need current
ancestor counts. Unfiltered Queue state can supply a current total immediately;
filtered Queue needs its own result.

Page-size changes clear boundary-dependent pages, failures, and reservations,
not current totals, geometry, or identity selections. Hiding/logical cancellation
preserve accepted data and retained failures. A current failed page needs explicit
retry until eviction or changed demand makes it eligible again. Accepted errors
consume reservations, not successful-data publication. Queue identity-reconciliation
failures retain occurrences but leave positions unavailable until successful
retry or a new single selection; cancelling a replacement cannot validate them.
Selected-playlist summary failures are retained by selection/catalog stamp;
catalog invalidation forgets the count until a current lookup or page restores it.
All retries use existing reader lanes and physical gates.

Placeholders retain geometry while loading text waits 150 ms; failures/retry
affordances remain immediate. One cancellable earliest-deadline wake per view
belongs to current requests and retires on completion/cancellation/hiding. A
replacement Queue search starts its own delay only when submitted, not while
waiting for the old worker. Viewport demand is deferred past prepaint so accepted
local forest pages can invalidate their placeholder frame. These presentation
rules do not validate stale pages or alter metadata/operation safety semantics.

==== History-derived retention

History owns one sorting index per immutable source/sort choice and cached
column measurements per source, resolved font, and text size. Search, scrolling,
and playback do not rebuild static widths. Only the replacement playback-time
label is remeasured; two widest stored-time measurements preserve exact sizing
when its row is excluded, including ties, without a per-row measurement cache.
Typography/source changes rebuild measurements. Tree page acceptance similarly
indexes borrowed identities once for selection revalidation; viewport demand
binary-searches intersecting preorder segments instead of rescanning all retained
expansions. These caches are independent of visualization caching.

== Processing output retention

The processing service, not a window or its query cache, owns scratch, retained
PCM, and auditions. Graph PCM is capped at 2 GiB per run; graph and ordinary jobs
share a 4 GiB output budget and at most four retained audition results. The selected
audition is pinned; output that cannot coexist within the budget fails publication
rather than evicting that audition. Export jobs publish durable files without
occupying audition slots or evicting retained runs, whether copying cached PCM or
rendering another port. Their scratch is retired after publication, and their
receipts share the latest 32 terminal statuses. Those statuses may outlive audition
files, so a terminal status alone does not authorize audition. Native source
rendering also has the RIFF 4 GiB scratch limit. Cancellation/closed views do not
prove worker retirement. Workflow and source/output validity are specified in
link:27_audio_processing.adoc#_tasks_retention_and_audition[Audio processing].

Retirement is nonblocking on Core: one bounded reclamation worker deletes rejected
and evicted results. Retiring bytes remain charged until deletion succeeds, and
stem mixes count toward the same output budget. A subsequent processing worker
waits for prior reclamation before preparing more PCM. An audition result that
must wait for reclamation remains cancellable and is revalidated before publication.
Export publication also rechecks cancellation and source identity before its
no-clobber commit; it does not admit temporary PCM into the audition budget.
A deletion failure retains ownership and charge and fails later preparation
rather than allowing more PCM
to accumulate. Shutdown joins work and reclamation; retained audition files live
until final service destruction after playback retirement.


== Visualization caching

=== Scope and contract

`visualizations.cache` trades retained graphics memory for less repeated rendering
work. It does not change audio analysis, waveform samples, spectrum levels,
palette mapping, or playback state. Settings and display controls are documented
in link:01_config.adoc[Configuration and layout]; signal continuity and rendering
rationale are explained in link:23_visuals.adoc[Visualization Rendering Design].

The policy covers Waveform display columns and numerical publications, Spectrum body
geometry, and Spectrogram numerical column publications. Audio Visualizer styles are independent:
radial styles do not retain reusable graphics, stereo analysis styles retain
numerical publications in revocable GPU slots, and generative styles retain
simulation state. The setting does not control those resources, album artwork,
or font caches.

Disabling the cache bypasses reusable graphics, not the underlying audio data
or Spectrogram history. Peak hold, smoothing, and display calculations retain
the same meaning. Re-enabling it requires an initial rebuild before reuse
resumes. Submitted publications remain alive while their scenes reference them.

Still Mode is a destructive suspension, not another cache policy: it stops
visualization demand and discards results as well as derived graphics. Its
analysis, waveform-coverage, and late-result invariants are authoritative in
link:23_visuals.adoc#_still_mode[Visualization Rendering Design]. Graphics that
have already been submitted still follow the retirement boundary below.

=== Reuse and invalidation

==== Waveform

Waveform shares immutable column data and numerical GPU publications among panels
with the same source/display identity and effective values; changes fork only
the affected owner. Effective column count is the smaller of drawable width and
available bins. Source revision, amplitude mapping, or effective count triggers
aggregation; only changed mapped values or palette replace the publication.
Raw-width changes preserving that count, height, and cursor movement reuse it.

A full scan's request generation remains its display identity across rolling PCM
updates; replacement scans stay distinct even with the same source revision.
Keys do not retain full-preview snapshots. Unchanged pooled values retain their
publication, all-unknown data creates none, and known silence remains drawable.
Cache-off recomputes derived values without retaining publications or discarding
source samples. Packed columns transfer to GPUI without a second column copy;
the renderer owns upload reuse and completion-aware retirement, not application
image queues. Signal aggregation and coverage semantics are in
link:23_visuals.adoc#_waveform[Waveform].

==== Spectrum

Spectrum retains body geometry and frequency mappings per panel, so differently
sized panels do not replace each other's state. New levels reuse mappings;
unchanged effective body levels also reuse geometry. Envelope reinitialization,
panel geometry, frequency grouping, or display mapping invalidates that reuse.
Background/grid/label repaint and separately drawn Peak markers do not discard
the body. Bars/Outline/LED retain rectangle publications, Line/Solid retain Path
publications; LED segments do not require individual CPU contours.

Cache-off releases the reusable body, not signal envelopes or the shared palette.
Suspension retains the final immutable body, normalized peak markers, and display
labels for each current layout panel, independently of rebuilding caches. Envelopes,
frequency mappings, and scratch are released. Restoration draws that presentation
until a current drawable result replaces it; semantic invalidation discards it.
Envelope and palette semantics are in link:23_visuals.adoc#_spectrum[Spectrum rendering].

==== Spectrogram

Spectrogram retains frequency history and numerical GPU field tiles of at most
32 columns. Changed buckets rebuild their tile; scrolling changes placement.
Palette, range, frequency mapping, and sampling-size changes rebuild affected
publications without discarding compatible history. FFT-size/window changes
discard history because its analysis meaning changed; changing the Before/After
signal selection also discards incompatible history. History duration/rate changes
resize retention and start a new pooling interval; appearance changes and unrelated
Spectrum settings do not rebucket audio. Pooling semantics are defined in
link:23_visuals.adoc#_spectrogram[Spectrogram].

Drawable panels share one history sized for the largest requested plot width,
capped by history seconds times analysis FPS, with at least two columns.
Sampling height uses the largest drawable panel's height times the configured
sampling scale, with a floor at the visible source-frequency count, then caps it
by configured rows and the startup shared GPU budget. Resizing preserves newest
chronological columns; narrow/wide panels do not fight to resize shared history
while painting.

Prepaint retains panel measurements until bounds/visibility changes. A too-small
panel retires only its own drawable-size request, leaving drawable siblings
authoritative. If all active panels are too small, history shrinks to its newest
two columns and sampling height becomes zero; unchanged small frames do not
reallocate it. Enlargement restores measured demand and normal accumulation
without losing those columns. This size-only transition does not change analysis
demand; drawable geometry is specified in link:24_layout.adoc[GUI layout].

When no Spectrogram panel is visible, including when the window is hidden,
CPU history, pooling/scroll state, and derived working storage are released.
Each current layout panel may retain only the immutable tiles and normalized
placements in its last actual drawing, not the full historical column store.
Other analysis views can continue updating without accumulating hidden history.
Restoration shows that frozen drawing until fresh analysis produces a replacement;
it does not replay frames received while hidden. This is independent of the cache setting.

=== Resource boundaries

Caches are local to current panel owners or bounded shared history, not an
unbounded record of earlier render states. Hiding a window releases visualization
working state, Spectrogram history and stereo/generative simulation resources,
while bounded final drawings follow the suspension rules above. Base waveform
previews retain their independent bounded lifetime; see
link:23_visuals.adoc#_waveform[Waveform].
Waveform numerical payloads grow with effective display-column count and panel
count, not panel pixel area: four f32 values (16 bytes) per column, at most 1024
columns per panel, plus the shared paired-color palette and publication metadata.
Height and placement are shader inputs and do not require new numerical uploads.
Spectrum uses at most 2000 display slots, further limited by drawable width.
Bars and LED store at most one rectangle per visible slot; LED density increases
fragment work rather than the number of stored body rectangles.
Spectrogram numerical publication memory grows with bounded history capacity and
capped sampling height, in addition to the frequency data needed to preserve history.

The renderer's shared GPU-material admission budget additionally covers charged
buffer capacity, including retained upload generations; it is not a cap on CPU
payloads, textures, or total GPU memory. Rivu sets
`interface.gpu_material_budget_mb` when creating its GUI and retains that startup
value for Spectrogram sampling until restart. Byte, allocation, draw-record and
in-flight limits, including pressure behavior, are documented in
link:25_gpu_rendering.adoc#_internal_led_vertical_slice[GPU rendering].

These are CPU and renderer resources: publication payload alone does not describe
total process or GPU memory. Removed panel entries are pruned. Suspension retains
only final drawing data: radial styles have at most 32 levels and rotation, stereo
styles keep their immutable fixed-size field, fractals keep their bounded segment
publication rather than their simulation, and Oscilloscope retains at most 2048
normalized stereo sweep points (16 KiB), never its PCM owner. There is no general
screenshot cache. Destroying the window releases all these publications.
GPU uploads may remain charged until completion and a later renderer preparation,
or renderer destruction; hiding does not promise immediate VRAM release.

The GUI staging frame releases optional Density, Spatial Spectrum, metrics, and
band-energy payloads when their last display demand disappears; losing all
analysis demand also discards the spectrum copy. Reuse requires the same
publication, generation, FFT settings, and display token. Retained final drawing
data is not analysis staging and cannot seed restored history or simulation.
Source/seek identity and analysis settings govern semantic invalidation even while
hidden or paused. The continuity contract belongs to
link:23_visuals.adoc[Visualization Rendering Design].

The audio worker's processed Before tap owns a separate stereo FIFO for
source-aligned input awaiting output admission. Its frame count is bounded by
the graph's retained latency plus one converted PCM fragment, not by panel dimensions
or `visualizations.cache`. Capture-identity changes and inactive analysis discard
both its samples and allocation; refill checks retire it even when output admits
no new PCM. Exhausting the output span also releases it. This is distinct from
the bounded analysis ring and waveform preview retention. Admission, continuity,
and signal-selection rules are defined in
link:23_visuals.adoc#_pcm_admission[PCM admission].

Density keeps one 256 by 256 accumulation field and three fixed immutable
snapshot slots: 1 MiB of cell storage per active analyzer, excluding rendering and
small control allocations. A publication materializes into a uniquely held slot;
the shared frame, GUI staging, and Density's source model share that payload
without copying its cells. GPU publication additionally copies the changed numeric
field into one immutable snapshot shared by its panels. Spatial Spectrum retains
its separate decaying field. If slow consumers retain all three worker slots, the
worker coalesces the whole publication rather than allocating, blocking, or pairing old Density
with newer metrics. Accepted sample time and accumulated signal continue;
publication resumes when a slot becomes available. Losing Density demand
releases its pool and consumer references without stopping a surviving
Spatial Spectrum consumer.

Density/Spatial use revocable dynamic GPU slots rather than retained field images.
One Density publication contains 256 KiB of numeric cells; one Spatial publication
contains 128 KiB. Each style shares a 4 KiB palette across publications and panel
placements. Unchanged fields and paint/resize do not republish. Hiding clears the
slot and source model, including references used by cached scenes; previously
captured frames may finish safely. Renderer-owned buffers remain bounded and are
reclaimed on a later draw after completion, or on renderer destruction, not by an
application retirement callback or a forced cleanup frame. These are payload counts,
not total process memory or physical VRAM limits.

=== Design tradeoffs

Caching avoids repeated aggregation, geometry construction, and publication,
not scene submission or rendering. Changed Line/Solid bodies still need curves
and tessellation; changed rectangle/field bodies still need bounded payloads.
Cache-off trades less retained graphics state for rebuilding that work without
altering analysis or playback. Bounded shared immutable publications avoid a
second geometry representation; further consolidation needs workload evidence,
not assumed hit rates or submission counts.

== Native metadata admission

Native playback, probes, and full-waveform reads retain tags but skip embedded
visuals before their payload buffers are allocated. Artwork extraction owns a
separate budget: its encoded single-image limit defaults to 16 MiB and follows
`interface.artwork_file_limit_mb` (1–64 MiB, applied after restart). Its aggregate
visual-frame allowance is twice that limit; encoded staging admits three times
the sum of that limit and 64 KiB of framing allowance. Base64 and unsynchronised
pictures check decoded size before allocating their payload buffers.
Text admission is capped at 1 MiB per encoded item and a 4 MiB aggregate charge
that includes decoding/copy allowance and per-operation overhead. At most 4096
admission operations are allowed, including frames, decoded strings, and packet
fragments; this is not an exact retained-tag count. Other metadata readers keep
the fixed 24 MiB encoded-staging allowance; nested metadata is limited to eight
levels. Oversized metadata is skipped without rejecting otherwise decodable audio;
these limits do not guarantee complete tags or chapters for such files.

One opened native source owns its remaining allowance across probing, packet
reads, and seeks. Artwork extraction owns a separate probe allowance. Synchronous
parser scopes share that allowance with nested readers and restore the previous
scope on return or unwind; they never span an asynchronous wait or thread hop.
The pinned Symphonia 0.6.1 metadata and container patches under `vendor/` enforce
admission before frame, chunk, attachment, or metadata-packet allocation rather
than relying on a check after decoding the complete payload.

Matroska DocType and CodecId are structural identifiers, independent of the
exhaustible metadata allowance. Their encoded payloads have a separate 1 KiB
limit. Oversized declarations are format errors rejected before payload reading
or allocation, not skipped metadata or truncated identifiers.

These are metadata admission bounds, not total process-memory or I/O-time
limits. Audio packets, codec state, FFmpeg reads, and decoded image pixels have
separate costs. The encoded-image admission limit does not bound decoded pixels.

== Artwork lookup retention

Artwork has three different retention layers: the application lookup identifies
source results, encoded files persist on disk, and each window owns decoded
display images. Releasing one layer does not imply reclamation of the others.

=== Application-session lookup

Artwork lookup is independent of visualization caching. One application-session
manager is shared by MPRIS and every graphical window, including reopened and
reloaded windows. Cache-only reads return only completed real covers, without
media I/O or waiting for a probe. The GUI uses its embedded SVG default directly,
without track lookup entries or exported default-image files. MPRIS lazily exports
its PNG fallback on the existing background publisher; its cache-only metadata
getter never creates that file or retries a failed export. Blocking loads run on
GPUI's existing background executor and the MPRIS publisher, not new artwork
threads. Source extraction accepts only regular files. Nonblocking opening rejects
FIFOs without waiting for a writer, and the opened file is checked before probing.
Regular-file probing and filesystem I/O can still block those background callers.

The GUI keeps one active load and only the latest pending selection. Completions
are matched by track ID, fingerprint, and source path before updating the selected preview or
publishing MPRIS metadata; a late result can warm the cache, never replace a
newer identity. MPRIS signals metadata after artwork becomes available, including
an initial cold load without another playback update.

The Album artwork panel initiates acquisition only while visible. Hiding it
clears queued demand without cancelling a submitted shared load; completion may
warm the cache but cannot start another hidden lookup. Revealing it acquires the
latest track. Other consumers, including MPRIS, retain their own acquisition demand.
A path change updates the panel's source snapshot and retires the previous cover
even when track ID and fingerprint are unchanged; it does not reset track rotation.

The content key is track ID plus source fingerprint. Resident requests for the
same content share one probe outside the lookup lock. In-flight loads retain the
lookup, while GUI and MPRIS consumers retain its published file directly. Either
keeps that version resident.
A changed fingerprint creates a new version without discarding an old version
still in use. The GUI retires replaced results after the next window-frame
boundary; MPRIS retains its published result until replacement or shutdown, and
its property getter retains the returned result until the next read or shutdown.
There is no separate file lease counter or session-wide visited-file registry.

Successful embedded covers remain reusable after a path move that preserves
track ID and fingerprint. Directory covers, misses, and source/probe failures
belong to the attempted source path: a different path retries discovery while
repeated demand at an unchanged path stays completed. A request sharing an
unfinished probe at another path waits for that result, then retries its own path
unless the shared result was an embedded cover.

Lookup retention targets 64 entries. FIFO eviction selects only idle results;
active results can temporarily exceed that target. Idle overflow is trimmed on
subsequent loads. Cache-only reads neither insert entries nor probe on misses.
Revisiting an evicted identity requires another source probe. Late completions
cannot replace a newer identity, even when both resolve to identical image bytes.

An album worker carries its completed result lease into the GUI callback. The
callback delivers real covers directly to still-visible demand with the same
track ID, fingerprint, and path; shared-cache pressure cannot turn that result
into a missing cover before delivery. Hidden or obsolete completion cannot
retain a display owner or start another hidden demand.

Album grids separately remember only explicit negative completions for their
current visible source identity and path. Those cards keep their generated SVG
fallback. Evicting an idle negative result from the shared cache does not restart
that visible lookup, even when visible negatives exceed 64. Positive results
remain owned by their existing views, not another lookup cache. Scrolling out of
demand, changing source identity or path, hiding the grid, or closing its window
releases these negative records; the shared 64-entry retention target is unchanged.

=== Encoded files and maintenance

Encoded images use immutable content-derived paths under `artwork/cache`.
Disk names use the first 128 bits of BLAKE3 as 32 lowercase hexadecimal characters:
the first two form a bucket directory and the remaining 30 form the filename.
For example, originals use `ab/<30-hex>.png` and thumbnails use
`ab/<30-hex>-256.webp`, `-512.webp`, or `-1024.webp`. Runtime content identity
retains the full hash. Existing originals are compared with the incoming bytes
before reuse; mismatches fail without overwriting the existing file.
Identical bytes reuse an existing file, independent of track identity; files
provide paths for GPUI and URLs for external MPRIS consumers. Embedded and directory
images share byte-sniffed, content-hash storage. Each encoded image is limited by
the session's active `interface.artwork_file_limit_mb` (default 16 MiB, range
1–64 MiB). The manager captures it at startup; changing or drafting the setting
does not change admission until restart. Published artwork leases carry that
immutable limit through GUI reads, independently of decoded-image budgets. A
shared content path alone cannot authorize reuse under a different encoded policy;
both successful decodes and remembered failures are policy-keyed.
Directory discovery checks only the source's immediate directory and exact
`cover`, `folder`, or `front` stems; full candidate rules are documented in
link:04_playback.adoc#_mpris_and_artwork[MPRIS and artwork].
There is no automatic file-count or total-byte budget, startup directory inventory,
or automatic cleanup. No persistent track-to-image index is restored after restart:
the first source probe discovers the image hash, then reuses its file if present.

Static GUI covers also generate lossless WebP thumbnails on demand, with longest
edges of 256, 512, or 1024 physical pixels. Originals remain unchanged; GIF and
animated WebP keep their original frame path. Thumbnail filenames include only
the source's shortened hash and numeric size tier, without a processing-version
or encoding-policy suffix. Future processing-rule changes require explicit cache
invalidation. Small originals are not enlarged or duplicated into equivalent
tiers. Background loads coalesce same-source decoding and publish complete files
atomically; missing or damaged thumbnails are regenerated. A disk-cache write
failure does not prevent display. Reuse does not rewrite a cached thumbnail or
refresh its age.
Thumbnail-file reads have their own fixed 8 MiB safety cap, independent of the
source's encoded admission limit. Every reuse still admits the original source
under the active session policy before reading its disposable thumbnail.

Maintenance counts and cleans thumbnail files as well as originals. Unlike
resident source files, thumbnails are disposable even while a source lookup is
resident: displayed pixels do not depend on keeping the thumbnail file. Each
source has at most three generated tiers; this is not a global disk-capacity limit.

The MPRIS default export uses the same content-hash directory and is protected
once exported; later sessions can clean it when it is no longer resident.

Maintenance scans managed originals and thumbnails only within one level of
two-character lowercase-hex buckets, using the filename forms described above.
Files at the cache root and unrecognized names are excluded from statistics and
cleanup. It does not follow symlinks or descend into nested directories.

Only explicit link:01_config.adoc#_artwork_cache_maintenance[Settings maintenance]
enumerates disposable files. Statistics and cleanup use modification age, not
last-access age; normal reuse does not touch timestamps. Cleanup skips every
file referenced by a resident lookup result, including idle cached results and
active old versions. Multiple track identities may protect the same file.
Released results merely become evictable; neither release nor eviction performs
filesystem work. Disk usage can grow until the user requests maintenance, and
age-based cleanup does not enforce a global capacity limit.

Each blocking acquisition holds a shared maintenance gate through source opening,
extraction, cache-file publication, and lookup registration. Per-file cleanup
takes the exclusive gate before inspecting protection and deleting, so cleanup
can wait for a slow probe. Probing and filesystem I/O do not hold the lookup
mutex; render and MPRIS property reads remain cache-only and do not wait for the
maintenance gate. Maintenance ignores symlinks and unrelated names, reports
inspection/deletion failures, and leaves audio sources untouched.

=== Window-owned real-cover decoding

GUI previews keep decoded images separate from this session-wide lookup cache.
Within one window, metadata previews, album cards, and the large artwork panel
share one pending load or completed decode per immutable content path and active
encoded admission policy, even when different tracks reference the same bytes.
Background same-source sharing also keys the encoded policy and decoded budget;
neither admitted images nor remembered failures cross policy identities. Each
consumer retains its own lookup identity and source-file protection. Loading
starts only when a preview requests the image and runs the artwork-specific
bounded decoder on GPUI's background executor, not render-time file I/O.

Static-image demand uses the actual display size and window scale, rounded up to
the smallest sufficient tier; demands above 1024 use the original. Cover/cropped
surfaces also account for aspect ratio so the short edge retains enough pixels.
Visible consumers share the largest required tier. An upgrade retains the old
image until the replacement is ready; shrinking demand is debounced for 300 ms.
Cached consumers are invalidated after painting and acknowledge the new image
generation before old textures retire at a frame boundary. Ordinary within-tier
resizing does not decode again. Resizing uses premultiplied-alpha filtering to
avoid colored fringes without copying the full source image.

Replaced or hidden consumers retire through a window-owned queue after scene
replacement; removed panels need not paint again. Releasing one consumer cannot
cancel or unload another's image. Only the last retired consumer cancels the
pending load or removes the completed image from the renderer. Hiding Track
details or the large artwork panel retires its display owner and queued lookup
demand; a late shared lookup may warm the session cache but cannot restore a
hidden owner or start another hidden acquisition. Track details keeps its editor
draft independently. Window hide, close, or reload releases
current and retired display owners without waiting for another frame. Another
window owns an independent decode.

Revisiting an image after its last consumer retires decodes it again; there is
no idle decoded-image cache across selections or windows. A still-live consumer
can supply the shared decode. Each real-cover decode uses
`interface.artwork_decode_budget_mb` (default `64`, range `1`–`1024` MiB),
including cumulative BGRA pixels and conservative frame/vector overhead. The
budget includes every composited GIF/WebP animation frame; even tiny frames
incur an overhead charge. It applies per immutable content path per window, not
across all active/retired images or windows. Settings operation is described in
link:01_config.adoc#_desktop_settings[Desktop settings].

A committed budget change invalidates shared cover loads and completed failures,
retires completed pixels at the existing scene boundary, and refreshes all cover
consumers. Unchanged budgets retain their decodes. Pending old items are cancelled;
already-running synchronous decode work may finish, but cannot publish its old
result. Hidden windows flush retirement without waiting for another frame.
Re-decoding and scene retirement can temporarily overlap allocations; lowering
the budget is not instantaneous RSS reclamation. Settings drafts do not change
the active policy.

Before pixel decoding, dimensions must be nonzero and at most 4096 per side.
A separate 64 MiB workspace admission estimate charges four RGBA canvases
(at most 16 MiB per canvas), with additional checks for native static-pixel
conversion costs. GIF receives decoder allocation limits; WebP canvas, frame
rectangle and embedded VP8/VP8L dimensions are checked before pixel decode.
This estimate is not a hard codec-scratch, process-RSS or GPU-resource cap:
encoded input, codec state, transient buffers and renderer textures have separate
costs. Simultaneously live/retired owners and other windows add their own costs.

An over-budget or corrupt cover is rejected as a whole, logged, and replaced
with the existing default cover in metadata previews, album cards and the artwork
panel. No partial animation or silent first-frame fallback is published. Accepted
GIF/WebP animations retain all frames and original delays. Stable element IDs
retain their playback cursors; multiple artwork panels share decoded pixels but
not cursor state. GPUI handles final display scaling of the selected image tier.
Trusted decorations and generated default artwork keep their separate policies.
Encoded-file maintenance does not measure or reclaim decoded images; the
encoded-file limit is not a pixel budget.

=== Generated defaults and decorations

Album-artwork decorations load lazily for visible styles, with one shared decode
per style and window. Losing the last visible style consumer retires its image
and cancels pending decoding through the same window-frame boundary; window
hide or close flushes it immediately. A synchronous rasterization already running
may finish, but cannot publish after cancellation. An old scene cannot restart a
released decoration load. Reopening before retirement reuses the live owner;
reopening after retirement decodes anew. Decoration resolution and GPU rotation
are unchanged.

Generated default covers share a separate window-local cache across square
previews, cards, and circular artwork panels. GPUI background assets rasterize
the embedded SVG at twice the displayed physical square size, then Lanczos-filter
to the target size. Display scale and style-specific image size select immutable
keys; older completions cannot replace a newer size. Existing fitting, clipping,
and rotation remain unchanged. Warm frames share images without rasterization
or pixel-buffer copies, and a single asynchronous gate serializes generation.
The fixed 2:1 Lanczos3 reduction preserves vertical-then-horizontal floating-point
filtering and final byte rounding, but processes one intermediate row at a time.
Its floating-point row uses 32 bytes per target-side pixel, plus a linear-size
coefficient table, rather than 32 bytes per target-image pixel. Supersampled SVG
pixels and final BGRA output remain separate allocations; scratch is not cached.

This memory-only cache admits at most 16 pending/completed size keys and 32 MiB
of final BGRA pixels. Least-recently-used eviction cancels pending assets and
retires GPU images at the next window-frame boundary; temporary retired images
are outside the resident budget. Final sides are capped at 2048 physical pixels
(larger surfaces scale that image), bounding supersampling at 4096 pixels per side.
Only one generation uses raster/filter scratch memory at a time. The last shared
owner releases its assets and GPU images on window close or reload; other windows
have independent caches. More active sizes than these limits can regenerate
evicted images. Generation failures are logged and display `Artwork unavailable`.
Generated bitmaps remain in RAM/GPU memory and never create disk files; existing
media-cover/MPRIS disk paths and encoded-file maintenance are unchanged.


== Font and rendering resources

=== Native graphics preparation

Native window creation selects instance, surface and device together. Vulkan
hardware must configure the real surface successfully to avoid initializing GL.
If it cannot, GL hardware is tried before either backend's software adapters.
Each backend is initialized at most once per preparation; software fallback
reuses the prepared instance and surface. Device recovery rejects software
adapters, and additional windows reuse an existing healthy shared context's
originating instance rather than choosing a new backend.

=== Font data and glyphs

Font retention is independent of `visualizations.cache` and Still Mode.
Primary-font selection and fallback behavior are documented in
link:01_config.adoc[Configuration and layout]. Rivu resolves the primary family
at startup or when its saved setting changes, not during painting. On Linux,
primary-family matching and missing-character resolution share one backend-owned
Fontconfig configuration, initialized on first demand and retained for the text
system's lifetime. Configuration initialization failures are retained by that
same owner. The backend loads individual selected faces, preserving candidate
rank rather than preferring the face with the most coverage. Native shaping
fallback remains the final step.
A candidate that cannot be registered or loaded is logged and skipped without
discarding earlier successful candidates or changing the remaining order.
Fontconfig metadata is retained by the resolver; first-use matching and loading
can block text preparation. This does not promise lower total startup RSS or
latency: reduced font-file residency can be offset by matching metadata and caches.

Successful candidate results, including no coverage, share a 64-entry FIFO with
at most 64 KiB of aggregate request-key bytes and 1 MiB of aggregate candidate
storage (face-record sizes plus owned path capacities). Hits do not refresh FIFO
age. These are owned-storage accounting budgets, not a total allocation or RSS
limit: allocator overhead, Fontconfig metadata, externally held candidate results,
and loaded font data are not included. Oversized requests or results are returned
normally, without memoization or truncation; failed requests are not cached.
Keys include the original family, locale, weight, style, and the sorted, unique
Unicode scalars of the actual missing text. Reordering or repeating the same
scalars reuses candidates, not shaped layouts; shaping still receives the
original text and complete graphemes. Scalar keys are charged by their stored
`u32` bytes. Normalization reuses at most 64 KiB of separately retained scratch;
larger temporary scratch is released after the request. Repeated input does not
grow scratch in proportion to the original text length.
Changing base text size alone does not resolve font families again.

Icon text uses a separate symbol family; `embed-nerd-font` embeds one discovered
font file and registers it before GUI creation, not a subset or fallback chain.
This removes the runtime file dependency at the cost of executable bytes and
backend font storage. A patched text font can be much larger than a symbols-only
font; shaping and glyph rendering still need their own allocations. Font choice
and build/startup requirements belong to link:01_config.adoc[Configuration] and
link:../readme.adoc[README].

The backend owns font, shaping, glyph, and atlas caches. It may retain multiple
faces or fonts considered during fallback, not only those that supplied visible
glyphs. Parsed fonts and FontId assignments are not evicted, so switching fonts
may leave earlier font data resident. Raster-bounds memoization is capped at
32768 entries and clears on a successful distinct miss at that budget; bounds
are recomputed without changing font identity.

Glyph atlas reclamation starts above 8192 glyph entries after 120 frames with
sprite demand at no more than one-quarter of that count. Once the old frame is
discarded, every texture page referenced by the current replayable Scene is
protected, including color glyphs and textured Paths. Only glyphs on unprotected
pages are evicted; image and SVG owners remain responsible for their own tiles.
Whole-page protection preserves cached paint ranges but can retain unused
glyphs alongside live ones, so this is a high-water policy, not a hard byte cap.

Atlas insertion transfers owned pixel buffers into the renderer's pending-upload
queue. Required BGRA-to-RGBA conversion runs in place on that owner; borrowed
pixels are copied once because the queue must outlive the build callback.
Uploads remain deferred to frame preparation and can be discarded when their
texture retires before submission. This does not eliminate wgpu staging copies.

System font-file mappings can share kernel file pages, whereas parsed font and
glyph data also consume process memory. Font discovery alone is not a measure
of retained memory, and total process memory includes unrelated renderer
resources.

=== Settings view reuse

Settings owns its draft, inputs, navigation, and save feedback in a separate
GPUI entity. Playback and analysis updates do not invalidate that entity's
cached element tree. Settings interactions and relevant runtime changes do;
GPUI also invalidates reuse when bounds or inherited text style change.
This cache is independent of `visualizations.cache`, retains no settings
bitmap, and does not freeze background visualizations or eliminate window
composition.

=== Renderer buffers, atlases, and display lifecycle

Cached Paths and Scene replay share immutable vertex storage while keeping
draw order, masks, and other Path metadata independent. Editing a shared Path
uses copy-on-write. Painting still converts logical coordinates once into
scaled geometry; Scene insertion and replay do not copy those vertices again.
The renderer reuses its expanded vertex and Path-sprite upload buffers;
uploads copy the bytes before either buffer is cleared for the next batch.
Each buffer above 4096 elements shrinks after 120 successful frames at no more
than one-quarter utilization, retaining twice the observed peak with a
1024-element floor. Surface unconfiguration releases both buffers immediately.

Path tessellation reuses one idle vertex/index scratch pair per calling thread,
with a combined capacity limit of 1 MiB. Larger paths remain supported, but
their oversized scratch allocation is discarded after use. Each call owns its
checked-out buffers; nested calls cannot overwrite them, and failed calls
cannot leave geometry in the next lease. Final Path vertices have independently
owned storage reserved for the triangle count, so later scratch reuse does not
change submitted or cached Paths. Lyon's private tessellator workspace remains
per-call rather than becoming an unbounded retained cache. GPUI idle reclamation
also releases idle tessellation scratch on its calling thread; other threads'
scratch remains bounded and is released when those threads exit.

Ordinary Paths and multisampled GPU materials, including rectangles and segments,
share one renderer-owned resolve/MSAA scratch pair. Current demand is the
componentwise maximum of clipped raster extents; retained attachment capacity
may exceed it. Bounded slack absorbs small changes, fitting demand reuses the
pair, and sustained low demand reclaims capacity rather than replacing it on
every size change. Capacity stays within the physical viewport/device limit;
growth or a lower limit replaces it immediately. A frame with no raster demand
drops renderer ownership. Capacity slack does not enlarge raster or composition
bounds. Submitted GPU work retains replaced resources until completion;
reclamation neither destroys in-flight textures nor waits for the GPU. These
attachment bytes are separate from the GPU-material buffer budget. Exact
capacity and reclamation policy is authoritative in
link:25_gpu_rendering.adoc#_shared_local_multisample_scratch[Shared local multisample scratch].
Instance storage above its initial capacity shrinks after
120 successful frames at no more than one-quarter utilization, retaining twice
the observed peak rounded up to a power of two and never below initial capacity.
Discarded CPU Frame, Scene, and line-layout buffers reclaim high-water capacity
after 120 small uses of each buffer (normally 240 draws for double buffering).
The live frame and replay ranges remain untouched. These policies use existing
draws, not timers, and do not promise reclamation while drawing is inactive.

Atlas requests with nonpositive dimensions or dimensions beyond the device limit
are rejected before creating a page. A new page is committed only after its
first tile reservation succeeds, so failed reservations leave no empty GPU page
and do not consume reusable page slots.

After the window is destroyed, the application requests headless mode. A
successful transition releases the display connection and its shared GPU
context; a failed transition is logged, not treated as completed reclamation.
Reopening reconnects to the original display before creating a new window;
requests arriving during a connection switch are coalesced. A failed reconnect
leaves the application running so another open request can retry.

After a successful headless transition with no pending reopen request, the host
requests GPUI idle reclamation. GPUI waits until the current update's events and
deferred callbacks finish, then skips reclamation if a window has opened again.
Empty, inactive element and event arenas return excess chunks and allocation
records, retaining one 1 MiB chunk each. Live arena allocations are not invalidated.
Layout scratch capacity, cached font metrics and glyph bounds, and idle text
wrapper/run buffers are released; registered fonts and their identities remain.
Checked-out text wrappers stay usable and need not return to a discarded pool.
Reopening rebuilds these derived caches on demand. Reclamation adds no timer or
worker and does not wait for GPU completion or background work.

Playback, IPC, tray, MPRIS, and accepted business operations remain independent
of this transition. The GPUI event loop, executors, registered font system, and
business caches remain available; this is not full framework teardown. Allocator arenas,
thread-local state, and backend display bookkeeping can outlive a window or
display reconnect, so RSS is not a count of live rendering resources. No
allocator trim is performed, and closing the window does not promise
serve-level process memory.

The graphical host shares one immutable startup Localizer between its GUI
session and tray worker, including the parsed Fluent resources and fixed-message
cache. Closing or reopening the window does not rebuild these resources, and
saved language changes apply only after host restart. GUI-specific SharedString
adaptation remains window-owned; tray protocol payloads remain tray-owned.
