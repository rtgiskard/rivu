= Caching and Resource Lifecycles

Query projections, visualization graphics, artwork, and font/renderer resources
have different owners and retention policies. This document describes their
scheduling, cancellation, and release boundaries; no single cache switch or
window-memory total represents all of them. Query stamps and revision semantics
are authoritative in link:21_ipc.adoc#_query_results_and_pagination[IPC]; rendering
choices are explained in link:23_visuals.adoc[Visualization Rendering Design].

== Query projection retention

List and tree data are independent of `visualizations.cache`. Consumers use
link:21_ipc.adoc#_query_results_and_pagination[the query-owned stamp contract]
for dependency selection and result acceptance, and
link:21_ipc.adoc#_revisions_and_watching[IPC revisions] for state watching.
A projection key is normalized query identity plus its stamp, excluding page
offsets, limits, batch cursors, and expected revisions. Request generations
reject obsolete intent independently of data freshness.

Each window-local feature reconciles its own revision and configuration
dependencies, including while its panels are hidden, and owns the execution and
completion of its reads. Directory and root-count preparation, publication, and
physical-worker retirement are Library owner transitions. Logical cancellation
only changes publication rights; it cannot free a submitted worker slot.
Queued directory demand alone does not invalidate the view; local forest
publication and worker progress supply the notifications that resume rendering.

The forest page is synthesized locally from configured roots, not another
database query; root-count identity also includes those roots. Metadata-only
changes preserve the latest navigation target and modifiers; an already
dispatched full-row read drains before retrying against current metadata.
Duplicate source/target choices retain track identity across reference-only
refreshes; command eligibility is checked against current targeted member facts.
The duplicate-review owner applies start, cancellation, acknowledgement, and
completion transitions together with its query gates and dispatches its own
effects; Core owns relocation execution. Dismissal and window destruction request
cancellation without joining a worker. An acknowledgement arriving after dismissal
must cancel its accepted task rather than reopen or overwrite a newer review.

The Library browser owns search-count identity, accepted totals, per-root counts,
failure retention, and its single physical worker slot. Preparation reconciles
configured roots and the filtered query stamp before reserving that slot;
completion releases it before accepting only the current roots, query, stamp,
and generation. Changing demand or hiding retires old submissions without
releasing the slot early. A stale completion cannot publish counts or a failure;
visible demand resumes after it drains, while hidden demand waits until reveal.
Current failures require explicit retry or changed demand. The same Library
feature owns query execution and search-widget updates; no window-level query
dispatcher maintains a second copy of those transitions.
Aggregation counts duplicate and nested configured roots only once; this count
payload does not determine whether the configured-root viewport remains mounted.

Owners reconcile keys while hidden, but tree and Details reads require actual
panel demand. An open Add to playlist chooser also demands playlist summaries,
independently of the Playlists panel. An unchanged key retains bounded album pages
and page failures across hiding; covers are released independently.

The Playlists feature owns the paired page and request transitions: search,
selection changes, refresh, page-size changes, cancellation, and completion.
Page lifecycle mutation stays private to that owner; other consumers borrow
read-only page buffers and use explicit catalog or entry operations. A registered
request carries its own identity and optional executable read, so queued demand
can retain loading feedback without a second caller-supplied request kind.
Its dispatcher executes reads and applies presentation feedback without separate
window-level reservations or request validity. Retiring a page request does not
release its submitted worker; an old completion cannot clear a replacement
request. Selection-existence lookups remain independent of page-size changes.

Album, Playlist catalog/entry, and Queue buffers retain at most the larger of
eight pages or visible pages plus three; failed offsets have the same separate
bound. Library payloads and failure markers share a least-recently-used bound of
sixteen pages or current demand, including unverified ancestry, whichever is
larger. Expansion and selection identities are retained separately from row payloads.

Album member counts, pages, and whole-album queue actions use the existing
`tracks_album_members` index: exact direct-parent directory and effective album
title select the member range, followed by disc/track/title/ID ordering. They do
not scan a directory's descendant paths or merge child directories into an album;
root `/` remains its own direct-parent key. Unicode-whitespace-only album titles
remain ineligible, and member search filters only that album's indexed range.

Authoritative result counts are separate from retained scroll geometry. A data
revision forgets counts and drops obsolete pages, failures, and positional pins,
but retains nonempty geometry until a current result supplies its real total.
A previously empty result gains a loading position so later additions are
discoverable. Flat-list and album query identity changes discard their old
geometry; tree filter changes preserve expansion choices but invalidate affected
facts. Count displays and range/navigation operations cannot treat retained
geometry as current facts;
tree ranges also require current counts for stale ancestors before validating
their retained identities. Unfiltered Queue snapshots can supply authoritative
totals immediately, including zero; filtered queries require their own totals.

Page-size changes clear boundary-dependent pages, failures, and reservations,
not current counts, viewport geometry, or identity selections. Hiding and logical
cancellation release only pending reservations, preserving accepted data and
retained failures. For unchanged data and page boundaries, a retained failed page
requires explicit retry; eviction can make that page eligible for demand again.
An accepted error consumes its reservation rather than leaving a loading
placeholder; it is not a successful data publication.
Cancelling a generation cannot release a physical worker gate: completion owns
that release, and only the latest queued demand may then run. Metadata drafts/save baselines,
occurrence identities, unavailable state, and relocation operations remain
business-owned rather than being swallowed by a generic payload cache.

Explicit Details selections load through a track query. Playback-follow Details
use the Core's current-track snapshot; reloading playback does not start a second
track read or leave a query reservation behind.

The Details read coordinator owns query freshness, the latest quiet deadline,
coalesced demand, and the single reader slot. Preparing a read reserves the slot;
the quiet timer rechecks visibility, editing identity, and query freshness before
submission. An abandoned timer retires only its own reservation; submitted reads
retain the slot until completion. The edit session remains authoritative for
drafts and read/save acceptance, independently of query generations. Panel
activation also drives demand, so revealing Details can resume reads without a
new Core snapshot.

The window owns the latest explicit action and its confirmation barrier, separate
from the Details edit session and read coordinator. New input or cancellation
retires the previous action; a late range result or save acknowledgement cannot
restore it. Confirmation validates the frozen target again before changing the
selection or discarding the original draft. Selection owners prepare frozen
commits and dispatch their own reads; the window validates the current action
and routes acceptance back to the originating owner. Cancellation preserves a
submitted worker's gate until completion, even when a newer selection is waiting.

Root-count batches run one at a time. Tree reads share at most four physical
workers and four coalesced latest pending branch demands; unscheduled demand
owns no loading token. Completion re-drives current visible demand, while
discarded offscreen demand does not accumulate as a visited-branch backlog.
Debounced directory, playlist, and explicit Details demand is checked again
before submission. Abandoned unsubmitted demand releases its reservation without
becoming a failed page or discarding cached rows; submitted reads retain their
physical gate until completion.
Reusable owner epochs also accompany cancellable GUI reads into Core. Core skips
an obsolete queued read before accessing Store; cancellation never interrupts a
read that has passed dispatch, cancels another owner, or replays a write. Hiding
a window updates owner demand immediately, without waiting for another Core
publication or render, and retires pending page and explicit Details reads without
discarding retained rows or drafts. Completion still owns every submitted gate.
Album searches, Playlist pages, and explicit Details selections retain the latest
demand's absolute quiet deadline independently of a submitted worker. Replacement
renews that deadline; redispatch, hiding, and completion consume only its remaining
interval rather than starting another full delay.
Viewport demand is deferred past prepaint so locally accepted forest pages can
invalidate the frame that still contains their loading placeholders.

Album, Library tree, Playlist catalog/entries, and Queue page placeholders keep
their geometry while loading text waits 150 ms. Requests and existing debounce
start unchanged; failures and retry affordances remain immediate. Presentation
deadlines belong to current request owners, with one cancellable earliest-deadline
wake per view entity, retired on completion, cancellation, or hiding. This does
not retain invalid pages or change empty-result bootstrapping. Metadata and
selection/duplicate-operation progress retain their separate safety semantics.

Publication revisions and four state-section tokens are distinct from query
stamps and request generations. A publication with unchanged section tokens does
not invalidate the GUI root; independent audio frame processing still proceeds.

== Visualization caching

=== Scope and contract

`visualizations.cache` trades retained graphics memory for less repeated rendering
work. It does not change audio analysis, waveform samples, spectrum levels,
palette mapping, or playback state. Settings and display controls are documented
in link:01_config.adoc[Configuration and layout]; signal continuity and rendering
rationale are explained in link:23_visuals.adoc[Visualization Rendering Design].

The policy covers Waveform display columns and static images, Spectrum body
geometry, and Spectrogram history images. Audio Visualizer styles are independent:
radial styles do not retain reusable graphics, stereo analysis styles retain
their own result images, and generative styles retain simulation state. The
setting does not control those resources, album artwork, or font caches.

Disabling the cache bypasses reusable graphics, not the underlying audio data
or Spectrogram history. Peak hold, smoothing, and display calculations retain
the same meaning. Re-enabling it requires an initial rebuild before reuse
resumes. Temporary images still remain alive long enough for their submitted
scene to render safely.

Still Mode is a destructive suspension, not another cache policy: it stops
visualization demand and discards results as well as derived graphics. Its
analysis, waveform-coverage, and late-result invariants are authoritative in
link:23_visuals.adoc#_still_mode[Visualization Rendering Design]. Graphics that
have already been submitted still follow the retirement boundary below.

=== Reuse and invalidation

==== Waveform

Waveform separates display-column aggregation from static image caching.
Unchanged data and display mapping reuse the columns; incremental waveform
updates rebuild only affected image tiles. Playback cursor movement does not
invalidate the static waveform. Source, dimensions, amplitude mapping, and
palette changes rebuild the affected derived data.

==== Spectrum

Spectrum retains body geometry and frequency-band grouping per panel. Differently
sized panels do not replace one another's grouping. Repaints can reuse geometry,
including across analysis updates whose effective body levels are unchanged.
Envelope reinitialization and changes to panel geometry, frequency grouping, or
display mapping still invalidate reuse. Hold timing and Peak markers advance
independently of the cached body; Peak markers are drawn separately. Restoring a
hidden panel waits for a valid audio frame to initialize its envelopes before
drawing. The benefit depends on the workload, not on a fixed expected hit rate.
The shared palette ramp is independent of geometry caching; its bounded ownership
and retirement are described in link:23_visuals.adoc#_spectrum[Spectrum rendering].

==== Spectrogram

Spectrogram retains images for unchanged history columns. New audio updates the
recent columns while older columns remain reusable. Palette, display range,
frequency mapping, and image-size changes rebuild affected images so compatible
retained history is shown with the current settings. FFT-size or window changes
discard history rather than recoloring data with a different analysis meaning.

Visible Spectrogram panels share one bounded history sized for the largest
requested plot width, capped by configured history seconds multiplied by
analysis FPS, with a minimum capacity of two columns. Shared image resolution
follows the largest visible panel height and the configured row cap. Narrow and
wide panels therefore do not compete to resize it during painting. Capacity
changes preserve the newest chronological columns. Recoloring compatible
history does not discard its underlying frequency data.

When no Spectrogram panel is visible, including when the window is hidden,
its images are retired and CPU history and derived storage are released.
Other analysis views can continue updating without accumulating Spectrogram
history. Restoring demand starts with a new analysis publication, not the
frames received while hidden. This lifetime is independent of the cache setting.

=== Resource boundaries

Caches are local to current panel owners or bounded shared history, not an
unbounded record of earlier render states. Hiding a window releases Spectrogram
history and stereo/generative results; it does not necessarily drop the active
Spectrum panels' geometry or waveform previews. Base waveform storage is bounded
independently of its derived images; see link:23_visuals.adoc#_waveform[Waveform].
Derived image memory grows with panel dimensions and panel count.
Spectrum uses at most 2000 display slots, further limited by drawable width;
dense LED layouts contain substantially more geometry than simple curves.
Spectrogram image memory grows with bounded history capacity and capped image
height, in addition to the frequency data needed to preserve that history.

These are CPU and renderer resources: image payload alone does not describe
total process or GPU memory. Removed panel entries are pruned. Replaced images
and images from hidden or removed panels are retired through the window
lifecycle, without requiring those panels to paint again. Window closure
releases the remaining retained images.

The GUI staging frame releases optional density, spatial-spectrum, metrics, and
band-energy payloads as their last display demand disappears. Unchanged demand
keeps its buffers; losing all analysis demand also discards the shared spectrum
copy. Restoring demand waits for a publication with the current display token
and generation rather than restoring hidden results.

Density keeps one 256 by 256 accumulation field and three fixed immutable
snapshot slots: 1 MiB of cell storage per active analyzer, excluding images and
small control allocations. A publication materializes into a uniquely held slot;
the shared frame, GUI staging, and Density renderer then share that payload
without copying its cells. Spatial Spectrum retains its separate decaying
field. If slow consumers retain all three slots, the worker coalesces the
whole publication rather than allocating, blocking, or pairing old Density
with newer metrics. Accepted sample time and accumulated signal continue;
publication resumes when a slot becomes available. Losing Density demand
releases its pool and consumer references without stopping a surviving
Spatial Spectrum consumer.

An image cannot be dropped merely because the application has stopped reusing
it: a submitted scene can still reference it. Replaced cached waveform and
Spectrogram images retire at a subsequent window-frame boundary; transient
uncached images and uploaded stereo-analysis images survive a complete
intervening frame. Clearing uncached waveform graphics transfers submitted
tiles to retirement before discarding reusable data, so every upload retains
an explicit release owner. Retirement runs from the root window independently of panel
visibility. Final cleanup uses a frame callback without invalidating content,
including in Still Mode with analysis frame scheduling inactive. Uncached image creation
therefore cannot drive its own redraw loop. The last submitted scene retains its
images until replacement or window closure. This retains temporary memory longer
than immediate release, but keeps scene ownership valid.

=== Design tradeoffs

Caching avoids repeated aggregation, geometry construction, and image creation,
but does not eliminate scene submission or rendering. Spectrum painting still
scales Path coordinates and the renderer still expands vertices for upload;
sharing removes ownership copies, not those transformations. Spectrogram still
submits its visible images. Disabling reuse reduces retained graphics memory at
the cost of rebuilding that work.

Correct invalidation takes precedence over reuse: source or display changes
must not leave stale graphics, and cache-policy changes must not erase analysis
or playback state. The design favors bounded application-level caches and
shared immutable geometry over a second geometry representation. A combined
Spectrogram texture would change that boundary and should be justified by
profiling real workloads, not assumed hit rates or submission counts alone.

== Native metadata admission

Native playback, probes, and full-waveform reads retain tags but skip embedded
visuals before their payload buffers are allocated. Artwork extraction admits
images up to 8 MiB, with a separate 16 MiB aggregate visual-frame allowance.
Text admission is capped at 1 MiB per encoded item and a 4 MiB aggregate charge
that includes decoding/copy allowance and per-operation overhead. At most 4096
admission operations are allowed, including frames, decoded strings, and packet
fragments; this is not an exact retained-tag count. Nested metadata and encoded
image staging have finite allowances
as well. Oversized metadata is skipped without rejecting otherwise decodable
audio; these limits do not guarantee complete tags or chapters for such files.

One opened native source owns its remaining allowance across probing, packet
reads, and seeks. Artwork extraction owns a separate probe allowance. Synchronous
parser scopes share that allowance with nested readers and restore the previous
scope on return or unwind; they never span an asynchronous wait or thread hop.
The pinned Symphonia 0.6.1 metadata and container patches under `vendor/` enforce
admission before frame, chunk, attachment, or metadata-packet allocation rather
than relying on a check after decoding the complete payload.

These are metadata admission bounds, not total process-memory or I/O-time
limits. Audio packets, codec state, FFmpeg reads, and decoded image pixels have
separate costs. The encoded-image admission limit does not bound decoded pixels.

== Artwork lookup retention

Artwork lookup is independent of visualization caching. One application-session
manager is shared by MPRIS and every graphical window, including reopened and
reloaded windows. Cache-only reads return completed artwork or the bundled icon
without media I/O or waiting for a probe. Blocking loads run on GPUI's existing
background executor and the existing MPRIS publisher, not new artwork threads.
Cold source extraction accepts only regular files. Nonblocking opening rejects
FIFOs without waiting for a writer, and the opened file is checked before probing.
Regular-file probing and filesystem I/O can still block those background callers.

The GUI keeps one active load and only the latest pending selection. Completions
are matched by track ID and fingerprint before updating the selected preview or
publishing MPRIS metadata; a late result can warm the cache, never replace a
newer identity. MPRIS signals metadata after artwork becomes available, including
an initial cold load without another playback update.

The Album artwork panel initiates acquisition only while visible. Hiding it
clears queued demand without cancelling a submitted shared load; completion may
warm the cache but cannot start another hidden lookup. Revealing it acquires the
latest track. Other consumers, including MPRIS, retain their own acquisition demand.

The lookup key is track ID plus source fingerprint. Resident requests for the
same identity share one probe outside the lookup lock. Consumers hold the lookup
result itself, so loading, GUI, and MPRIS references keep that version resident.
A changed fingerprint creates a new version without discarding an old version
still in use. The GUI retires replaced results after the next window-frame
boundary; MPRIS retains its published result until replacement or shutdown, and
its property getter retains the returned result until the next read or shutdown.
There is no separate file lease counter or session-wide visited-file registry.

Successful probes, including a source with no usable embedded cover, remain
reusable after a path move that preserves track ID and fingerprint. Source-open
and probe failures instead belong to the attempted path: a different path retries
that content identity, while repeated demand at the unchanged failed path stays
completed. A request sharing an unfinished probe at another path waits for that
singleflight result, then retries its own path only if the shared probe failed.

Lookup retention targets 64 entries. FIFO eviction selects only idle results;
active results can temporarily exceed that target. Idle overflow is trimmed on
subsequent loads. Cache-only reads neither insert entries nor probe on misses.
Revisiting an evicted identity requires another source probe. Late completions
cannot replace a newer identity, even when both resolve to identical image bytes.

An album worker carries its completed result lease into the GUI callback. The
callback delivers real covers directly to still-visible demand with the same
track ID, fingerprint, and path; shared-cache pressure cannot turn that result
into a missing cover before delivery. Hidden or obsolete completion cannot
retain a display owner or start another hidden demand.

Album grids separately remember only explicit negative completions for their
current visible source identity and path. Those cards keep their generated SVG
fallback. Evicting an idle negative result from the shared cache does not restart
that visible lookup, even when visible negatives exceed 64. Positive results
remain owned by their existing views, not another lookup cache. Scrolling out of
demand, changing source identity or path, hiding the grid, or closing its window
releases these negative records; the shared 64-entry retention target is unchanged.

Encoded images use immutable content-hash filenames under `artwork/cache`.
Identical bytes reuse an existing file, independent of track identity; files
provide paths for GPUI and URLs for external MPRIS consumers. Each newly extracted
image is limited to 8 MiB. The bundled fallback is stored separately. There is
no automatic file-count or total-byte budget, startup directory inventory, or
automatic cleanup. No persistent track-to-image index is restored after restart:
the first source probe discovers the image hash, then reuses its file if present.

Only explicit link:01_config.adoc#_artwork_cache_maintenance[Settings maintenance]
enumerates disposable files. Statistics and cleanup use modification age, not
last-access age; normal reuse does not touch timestamps. Cleanup skips every
file referenced by a resident lookup result, including idle cached results and
active old versions. Multiple track identities may protect the same file.
Released results merely become evictable; neither release nor eviction performs
filesystem work. Disk usage can grow until the user requests maintenance, and
age-based cleanup does not enforce a global capacity limit.

Each blocking acquisition holds a shared maintenance gate through source opening,
extraction, cache-file publication, and lookup registration. Per-file cleanup
takes the exclusive gate before inspecting protection and deleting, so cleanup
can wait for a slow probe. Probing and filesystem I/O do not hold the lookup
mutex; render and MPRIS property reads remain cache-only and do not wait for the
maintenance gate. Maintenance ignores symlinks and unrelated names, reports
inspection/deletion failures, and leaves the fallback and audio sources untouched.

GUI previews keep decoded images separate from this session-wide lookup cache.
Within one window, metadata previews, album cards, and the large artwork panel
share one pending load or completed decode per immutable content path, even
when different tracks reference the same bytes. Each consumer retains its own
lookup identity and source-file protection. Loading starts only when a preview
requests the image and runs the artwork-specific bounded decoder on GPUI's
background executor, not render-time file I/O.

Replaced or hidden consumers retire through a window-owned queue after scene
replacement; removed panels need not paint again. Releasing one consumer cannot
cancel or unload another's image. Only the last retired consumer cancels the
pending load or removes the completed image from the renderer. Hiding the large
artwork panel retires its display owner; a late lookup may warm the session cache
but cannot restore that hidden owner. Window hide, close, or reload releases
current and retired display owners without waiting for another frame. Another
window owns an independent decode.

Album-artwork decorations load lazily for visible styles, with one shared decode
per style and window. Losing the last visible style consumer retires its image
and cancels pending decoding through the same window-frame boundary; window
hide or close flushes it immediately. A synchronous rasterization already running
may finish, but cannot publish after cancellation. An old scene cannot restart a
released decoration load. Reopening before retirement reuses the live owner;
reopening after retirement decodes anew. Decoration resolution and GPU rotation
are unchanged.

Generated default covers share a separate window-local cache across square
previews, cards, and circular artwork panels. GPUI background assets rasterize
the embedded SVG at twice the displayed physical square size, then Lanczos-filter
to the target size. Display scale and style-specific image size select immutable
keys; older completions cannot replace a newer size. Existing fitting, clipping,
and rotation remain unchanged. Warm frames share images without rasterization
or pixel-buffer copies, and a single asynchronous gate serializes generation.

This memory-only cache admits at most 16 pending/completed size keys and 32 MiB
of final BGRA pixels. Least-recently-used eviction cancels pending assets and
retires GPU images at the next window-frame boundary; temporary retired images
are outside the resident budget. Final sides are capped at 2048 physical pixels
(larger surfaces scale that image), bounding supersampling at 4096 pixels per side.
Only one generation uses raster/filter scratch memory at a time. The last shared
owner releases its assets and GPU images on window close or reload; other windows
have independent caches. More active sizes than these limits can regenerate
evicted images. Generation failures are logged and display `Artwork unavailable`.
Generated bitmaps remain in RAM/GPU memory and never create disk files; existing
media-cover/MPRIS disk paths and encoded-file maintenance are unchanged.

Revisiting an image after its last consumer retires decodes it again; there is
no idle decoded-image cache across selections or windows. A still-live consumer
can supply the shared decode. Each real-cover decode uses
`interface.artwork_decode_budget_mb` (default `64`, range `1`–`1024` MiB),
including cumulative BGRA pixels and conservative frame/vector overhead. The
budget includes every composited GIF/WebP animation frame; even tiny frames
incur an overhead charge. It applies per immutable content path per window, not
across all active/retired images or windows. Settings operation is described in
link:01_config.adoc#_desktop_settings[Desktop settings].

A committed budget change invalidates shared cover loads and completed failures,
retires completed pixels at the existing scene boundary, and refreshes all cover
consumers. Unchanged budgets retain their decodes. Pending old items are cancelled;
already-running synchronous decode work may finish, but cannot publish its old
result. Hidden windows flush retirement without waiting for another frame.
Re-decoding and scene retirement can temporarily overlap allocations; lowering
the budget is not instantaneous RSS reclamation. Settings drafts do not change
the active policy.

Before pixel decoding, dimensions must be nonzero and at most 4096 per side.
A separate 64 MiB workspace admission estimate charges four RGBA canvases
(at most 16 MiB per canvas), with additional checks for native static-pixel
conversion costs. GIF receives decoder allocation limits; WebP canvas, frame
rectangle and embedded VP8/VP8L dimensions are checked before pixel decode.
This estimate is not a hard codec-scratch, process-RSS or GPU-resource cap:
encoded input, codec state, transient buffers and renderer textures have separate
costs. Simultaneously live/retired owners and other windows add their own costs.

An over-budget or corrupt cover is rejected as a whole, logged, and replaced
with the existing default cover in metadata previews, album cards and the artwork
panel. No partial animation or silent first-frame fallback is published. Accepted
GIF/WebP animations retain all frames and original delays. Stable element IDs
retain their playback cursors; multiple artwork panels share decoded pixels but
not cursor state. GPUI still handles display scaling; Rivu does not resize
real-cover buffers or generate thumbnails. Trusted decorations and generated
default artwork keep their separate policies. Encoded-file maintenance does not
measure or reclaim decoded images; the encoded 8 MiB limit is not a pixel budget.

== Font and rendering resources

=== Font data and glyphs

Font retention is independent of `visualizations.cache` and Still Mode.
Primary-font selection and fallback behavior are documented in
link:01_config.adoc[Configuration and layout]. Rivu resolves the primary family
at startup or when its saved setting changes, not during painting. It leaves
missing-glyph fallback to the native GPUI/cosmic-text backend rather than
providing an explicit fallback list: that backend eagerly loads explicit
candidates. This avoids unnecessary application-directed loading and a local
font-backend fork, but does not enforce Fontconfig ordering beyond the primary
family.

Icon text selects a separate symbol family, independent of the UI text font.
Without `embed-nerd-font`, that family is `Symbols Nerd Font Mono`. With the
feature enabled, build-host Fontconfig discovery prefers `Symbols Nerd Font
Mono`, then `Symbols Nerd Font`, then other detected Nerd Font families. It
selects one font file and its family, embeds that file's bytes, and registers
them with GPUI before creating the GUI. Icon text uses the selected family;
embedding is not a font subset or a bundled fallback chain. If discovery cannot
find an installed Nerd Font, the build fails; if registration fails, GUI startup
fails. Build requirements belong in link:../readme.adoc[README].

Embedding removes the runtime dependency on that icon-font file, but trades
executable size and backend registration for availability. Selecting a patched
text font instead of a symbols-only font can embed much more data; backend
parsing, shaping, and glyph rendering still require their own storage.

The backend owns font, shaping, glyph, and atlas caches. It may retain multiple
faces or fonts considered during fallback, not only those that supplied visible
glyphs. Parsed fonts and FontId assignments are not evicted, so switching fonts
may leave earlier font data resident. Raster-bounds memoization is capped at
32768 entries and clears on a successful distinct miss at that budget; bounds
are recomputed without changing font identity.

Glyph atlas reclamation starts above 8192 glyph entries after 120 frames with
sprite demand at no more than one-quarter of that count. Once the old frame is
discarded, every texture page referenced by the current replayable Scene is
protected, including color glyphs and textured Paths. Only glyphs on unprotected
pages are evicted; image and SVG owners remain responsible for their own tiles.
Whole-page protection preserves cached paint ranges but can retain unused
glyphs alongside live ones, so this is a high-water policy, not a hard byte cap.

System font-file mappings can share kernel file pages, whereas parsed font and
glyph data also consume process memory. Font discovery alone is not a measure
of retained memory, and total process memory includes unrelated renderer
resources.

=== Settings view reuse

Settings owns its draft, inputs, navigation, and save feedback in a separate
GPUI entity. Playback and analysis updates do not invalidate that entity's
cached element tree. Settings interactions and relevant runtime changes do;
GPUI also invalidates reuse when bounds or inherited text style change.
This cache is independent of `visualizations.cache`, retains no settings
bitmap, and does not freeze background visualizations or eliminate window
composition.


=== Renderer buffers, atlases, and display lifecycle

Cached Paths and Scene replay share immutable vertex storage while keeping
draw order, masks, and other Path metadata independent. Editing a shared Path
uses copy-on-write. Painting still converts logical coordinates once into
scaled geometry; Scene insertion and replay do not copy those vertices again.
The renderer reuses its expanded vertex and Path-sprite upload buffers;
uploads copy the bytes before either buffer is cleared for the next batch.
Each buffer above 4096 elements shrinks after 120 successful frames at no more
than one-quarter utilization, retaining twice the observed peak with a
1024-element floor. Surface unconfiguration releases both buffers immediately.

The renderer allocates Path resolve/MSAA targets only when nonempty Path vertices
are drawn, and drops its references on a successful frame without Path drawing.
Restoring Path drawing rebuilds targets at the current physical size. Submitted
GPU work retains its resources; reclamation does not destroy in-flight textures
or wait for the GPU. Instance storage above its initial capacity shrinks after
120 successful frames at no more than one-quarter utilization, retaining twice
the observed peak rounded up to a power of two and never below initial capacity.
Discarded CPU Frame, Scene, and line-layout buffers reclaim high-water capacity
after 120 small uses of each buffer (normally 240 draws for double buffering).
The live frame and replay ranges remain untouched. These policies use existing
draws, not timers, and do not promise reclamation while drawing is inactive.

Atlas requests with nonpositive dimensions or dimensions beyond the device limit
are rejected before creating a page. A new page is committed only after its
first tile reservation succeeds, so failed reservations leave no empty GPU page
and do not consume reusable page slots.

After the window is destroyed, the application requests headless mode. A
successful transition releases the display connection and its shared GPU
context; a failed transition is logged, not treated as completed reclamation.
Reopening reconnects to the original display before creating a new window;
requests arriving during a connection switch are coalesced. A failed reconnect
leaves the application running so another open request can retry.

Playback, IPC, tray, MPRIS, and accepted business operations remain independent
of this transition. The GPUI event loop, executors, registered font system, and
business caches remain available; this is not full framework teardown. Allocator arenas,
thread-local state, and backend display bookkeeping can outlive a window or
display reconnect, so RSS is not a count of live rendering resources. No
allocator trim is performed, and closing the window does not promise
serve-level process memory.

The graphical host shares one immutable startup Localizer between its GUI
session and tray worker, including the parsed Fluent resources and fixed-message
cache. Closing or reopening the window does not rebuild these resources, and
After a successful headless transition with no pending reopen request, the host
requests GPUI idle reclamation. GPUI waits until the current update's events and
deferred callbacks finish, then skips reclamation if a window has opened again.
Empty, inactive element and event arenas return excess chunks and allocation
records, retaining one 1 MiB chunk each. Live arena allocations are not invalidated.
Layout scratch capacity, cached font metrics and glyph bounds, and idle text
wrapper/run buffers are released; registered fonts and their identities remain.
Checked-out text wrappers stay usable and need not return to a discarded pool.
Reopening rebuilds these derived caches on demand. Reclamation adds no timer or
worker and does not wait for GPU completion or background work.

saved language changes apply only after host restart. GUI-specific SharedString
adaptation remains window-owned; tray protocol payloads remain tray-owned.
