= Caching and Resource Lifecycles
:toc:
:toclevels: 2

Resources follow their owners, not one global cache switch: Core retains bounded
lookup state; each window retains query/display state; application services share
artwork and processing outputs; the renderer and font backend own their own
allocations. This chapter defines what is retained, what invalidates it, and when
the owner can release it. Entry and payload limits are not process-RSS limits,
and releasing an application reference need not immediately reclaim GPU memory.

Query stamps and revision domains are defined in
link:21_ipc.adoc#query-results-and-pagination[IPC]. Signal meaning and continuity
belong to link:23_visuals.adoc[Visualization Rendering Design], layout/interaction
contracts to link:24_layout.adoc[GUI layout], and GPU admission/API guarantees
to link:25_gpu_rendering.adoc[GPU rendering]. The sections below retain the
invalidation consequences needed to reason about resource use without repeating
those mechanisms.

== Startup work

Device discovery runs on the application's bounded blocking executor, independently
of queue restoration and request handling. Core publishes the result without
changing the selected output; the device list may initially be empty. Shutdown
acknowledgement can precede discovery completion, but process exit waits for it.

Saved layouts are read and parsed during desktop initialization. The persistence
writer starts when the GUI session accepts that data, before the first window is
constructed. Reopening starts a fresh desktop from the persisted layout; late
loads within a session cannot replace an edited workspace.

== Queue control and mutation working memory

SQLite owns complete queue order. Core retains only the current queue projection
and at most 4096 successful starts for navigation history. Navigation uses the
queue-order index; history reconciliation checks retained identities. Neither
queue size nor duplicate occurrence identity depends on page-cache limits.

Bulk edits retain their selection and affected positions, not a second complete
queue. Randomization temporarily retains a full ID permutation and releases it
on completion. External-file registration and insertion share transaction-local
SQL staging, preserving request order and repeats without a second resolved-ID
list. Failure rolls both changes back.

Queue clearing, including replacement from a playlist or album, batches at most
4096 occurrences per statement within one atomic transaction, bounding temporary
delete-plan IDs without exposing partial clears or replacements.
These bounds exclude SQLite page caches and transaction working memory. Freed
allocations may remain in the allocator; a lower post-restart RSS alone does not
establish a live-object leak.

== Query projection retention

List/tree retention is always enabled. A projection key combines normalized query
identity and its query-owned stamp, not page offsets,
limits, cursors, or expected revisions. A matching stamp authorizes query reuse;
bitrate-bearing payload stamps include the committed bitrate revision. A consumer
generation decides whether the result still serves current intent. Neither check
can substitute for physical-worker completion.

=== Core-owned lookup retention

Core's interactive track-ID LRU holds at most twice `interface.query_batch_size`:
128 entries by default, at most 512. Hits refresh age, misses are not retained,
and reducing the batch size trims immediately. Metadata edits invalidate affected
entries; statistics and committed bitrate updates patch them. Scans and file
admission invalidate reported data domains, or all entries if the impact is
uncertain. Background queries and export do not use this LRU. The limit counts
entries, not string bytes.

Count retention holds one duplicate-group total and a shared sixteen-entry LRU
for Library, Other, directory, album, album-member, Queue, and playlist-entry totals.
Filtered Library keeps only its latest scope, including the unfiltered full-library
total, within that shared limit. Keys include filters and collection identity, not
page boundaries. Counts survive snapshots only while
their data-domain revisions remain valid; publication must validate ownership
before advancing it. Playlist counts follow each playlist's lifetime. Unrelated
changes and bitrate-only updates preserve library totals; affected metadata
searches invalidate them.

Writable counts also detect independent SQLite commits and bypass reuse inside
writer transactions, preventing rollback leakage. There is no polling timer or
collection-sized row cache. Connections retain at most 64 parameterized statements;
values and offsets do not create new identities. Root aggregation is request-local
and shares work for identical normalized roots while preserving input order.
Persistent album summaries are transactional database projections, not evictable
pages. See link:21_ipc.adoc#transactional-inputs-and-bounded-storage-queries[IPC storage queries].

=== Window-local query retention

One window-local snapshot cache serves GUI feature owners. Background workers
merge authoritative state and revisions; unchanged reads reuse the snapshot.
Consumers track their own processed revisions, so one refresh cannot hide a change
from another. Completion and timeout decisions use current revisions. Unchanged
state-section tokens do not invalidate the GUI root; audio has a separate update path.

Layout publications define panel membership and active-tab demand. Playback
position changes do not rediscover the layout, but source/seek identity, playback
state, visibility, and waveform progress still govern whether retained data is
usable. Structural ownership belongs to link:24_layout.adoc[GUI layout].

Bitrate changes retire display payloads for demand-driven reload while preserving
selection, counts, and navigation geometry. They create no history or reverse
track-to-view index; old responses must pass the same query-stamp admission as
other data. See link:21_ipc.adoc#query-results-and-pagination[IPC query results].

==== Demand, cancellation, and physical retirement

Feature owners reconcile freshness while hidden but submit reads only for active
demand. Hiding revokes publication rights while preserving accepted rows and
selection. Details input, submitted saves, open playlist choosers, and cover
acquisition have separate lifetimes; retiring a read cannot retire an accepted write.

GUI and TUI query tracking separates three things: current query identity and
freshness, owner-scoped cancellation, and physical worker occupancy. Tracking
retains neither result rows nor execution slots. Cancellation reaches only the
corresponding Core request and does not invalidate another consumer's current data.

A submitted read holds its physical slot until reply or disconnection. Replacement,
hiding, cancellation, and logical timeout revoke publication but do not free that
slot. Physical retirement re-drives the latest eligible demand; old completions
cannot publish or clear replacement requests. Core skips obsolete queued reads
and cooperatively interrupts executing SQL, releasing its snapshot before the lease.

GUI admission allows two seconds and response presentation twelve seconds.
Timeout shows an error, cancels the read, and rejects late payloads; explicit retry
still waits for physical retirement. Transport errors have no payload stamp and
do not prove data changed. Command deadlines are independent.

`RevisionChanged` and owner-scoped `Cancelled` retire the obsolete read without
displaying a storage failure or immediately repeating identical demand. A changed
authoritative query stamp, changed demand, or explicit retry permits another read;
physical retirement still owns the execution slot. Genuine query failures remain
visible through the feature's normal error handling.

Album Browser publishes rows before querying an uncached unfiltered search total.
An auxiliary failure leaves rows usable and the counter unavailable; its physical
slot follows the same retirement rule.

[cols="1,3",options="header"]
|===
|Owner |Retained demand and execution boundary
|Library browser
|One root/search-count worker; configured-root rows are local data and remain
visible without counts. Root aggregates count each track once.
|Library tree
|At most four physical reads and four coalesced pending branch demands. Collapsing
discards queued subtree demand, not submitted slots; repeated demand does not
duplicate in-flight work or implicitly retry failure.
|Playlists and Queue
|The feature owns pages and request lifecycle; other consumers borrow read-only
buffers. Selection-existence reads are independent of page size, and position
validity is independent of operation progress.
|Details
|One read coordinator; explicit selections query Track, while playback-follow uses
Core's current-track projection. Inline text and field-specific save acceptance
have a separate owner; reads never overwrite the active input.
|Collection resolution
|Opening an album menu retains its identity, not all member IDs. Favorite,
Unfavorite, and New playlist use one cancellable paged reader only after selection.
Queue/Playlist copies submit versioned source identity for transactional Core
resolution and do not depend on the GUI ID-reader gate. The loading page keeps
menu-scope focus instead of restoring an unmounted submenu trigger. Cancellation
preserves the physical reader gate until its matching worker completes; retirement
notifies the window even when its logical result is stale.
|Duplicate review
|Stable selected identities survive reference refreshes, but commands require
current facts. A failed or timed-out status read does not release the relocation
task identity or automatically retry. Dismissal still requests cancellation without
joining the worker; late admission cannot reopen the review.
|===

Debounced reads recheck demand before submission; abandoned timers release only
unsubmitted reservations. Album, Playlist, and explicit Details reads preserve
their quiet deadline across hiding and redispatch, renewing it on replacement.
Late reads or saves cannot restore retired interaction intent. See
link:24_layout.adoc[GUI layout] for interaction ownership.

==== Payloads, failures, and retained geometry

[cols="1,2",options="header"]
|===
|Buffer |Retention bound
|Album, Playlist catalog/entry, Queue pages
|The larger of eight pages or visible pages plus three; failed offsets have the
same separate bound.
|Library tree pages and failures
|One shared LRU bound: the larger of sixteen pages or current demand, including
unverified ancestry. Expansion/selection identities are separate from payloads.
|===

Tree branch bookkeeping survives only while owned by cached pages, demand, pending
reads, expansion ancestry, selection, focus, or navigation. Otherwise-unowned
collapsed branches are reclaimed and reload counts on reopening. Switching views
transfers the inactive expansion snapshot rather than retaining duplicate active
branches. Hidden descendant expansion and selected anchors remain intact.

Sparse tree tables and Queue/Playlist/History selections shed high-water capacity
when live contents shrink substantially, retaining reuse slack instead of
reallocating on every deselection. This limits stale capacity, not live selection
size: selecting all still retains every selected identity.

A data revision forgets counts and drops obsolete pages, failures, and positional
pins, but retains nonempty scroll geometry until a current result supplies its
total. Previously empty results gain a loading position so additions remain
discoverable. Flat-list/album query changes discard old geometry; tree filter
changes preserve expansion choices while invalidating facts. Retained geometry
cannot authorize counts, ranges, or navigation; tree ranges also need current
ancestor counts. Unfiltered Queue state can supply a current total immediately;
filtered Queue needs its own result.

Page-size changes clear boundary-dependent pages, failures, and reservations, not
totals, geometry, or identity selections. Hiding and logical cancellation preserve
accepted data and failures. Current page failures require explicit retry until
eviction or changed demand makes them eligible again; retries use existing lanes.
Queue reconciliation failures retain occurrences but leave positions unavailable.
Selected-playlist summary failures remain scoped to selection/catalog freshness;
catalog invalidation forgets counts until a current result restores them.

Library matching counts depend on filters and data revisions, not row sort order.
The batched root-count owner supplies unfiltered root totals; matching-count reads
wait for its complete current snapshot rather than querying those totals again.
Unfiltered root and Other totals follow roots/structure freshness independently;
warm totals are reused across filter changes. Overlapping configured roots count
each track once. Sorting neither cancels a valid in-flight count nor refetches
unchanged totals.

Loading text waits 150 ms while placeholders retain geometry; errors and retries
are immediate. A cancellable per-view wake follows current requests and retires on
completion, hiding, or cancellation. Presentation delays never authorize stale data.

==== History-derived retention

History retains sort indexes by immutable source/sort choice and column widths
by source and typography. Search, scrolling, and playback reuse static
measurements; live time labels remain dynamic. Source or typography replacement
releases obsolete measurements, including while hidden. Tree pages similarly
retain selection indexes rather than traversing all expansions per viewport request.

=== Terminal projections

Foreground Details freshness is independent of its underlying list and page size.
Page, Details, and playlist-summary failures remain suppressed until their own
demand or freshness changes, or an explicit view transition resets them. Playlist
titles use a single-summary demand independent of entry batch size. Entry payload
refreshes, navigation, and search-locate cancellation do not retry an unchanged
failed title; a new title revision or reopening the view permits a retry.

Pages retain intrinsic column widths and fit them to the viewport on each draw;
Recent counts and time labels remain live. The TUI retains one help layout and
one Details layout, invalidated by width, language, key context, theme, or Details
source changes. Scrolling and playback reuse those styled lines.

== Processing output retention

The processing service owns immutable PCM and frozen run snapshots, independently
of windows and query caches. Active, retained and retiring PCM share a 512 MiB
allocation budget. Clones and slices share their backing reservation; the final
owner releases the charge. This does not cap decoder/DSP state, model weights,
Python inference workspace or total process RSS.

Native graphs can share immutable upstream PCM for unity-gain, zero-delay paths
without merging logical node identity or timing. Identical FIR filters share
kernels, never convolution history; spectral modes retain only the estimation
history they consume.

Successful admission of a non-export run retires unselected PCM and prepared
runners before the worker allocates. The selected audition stays pinned; capacity
exhaustion fails rather than evicting it or spilling to disk. At most four frozen
run snapshots support later graph recomputation. Availability is revoked when PCM
is retired, including in current/history status. The latest 32 terminal statuses
can outlive retained audio. Export jobs preserve their source handles, occupy no
audition slot and publish only a durable file and receipt.

One bounded reclamation worker releases rejected/replaced payloads off Core.
Workers wait for preceding retirement without blocking Core; charges persist
while playback, exports or aliases still own the PCM. Export publication rechecks
cancellation and source identity before its atomic no-clobber commit. Shutdown
joins workers; live audio survives until its final playback owner releases it.
Workflow, native streaming and neural memory boundaries are specified in
link:27_audio_processing.adoc#tasks-retention-and-audition[Audio processing].


[[visualization-caching]]
== Visualization caching

=== Scope and contract

Reusable visualization data is always cached within its owners' resource bounds.
Reuse does not change audio analysis, waveform samples, spectrum levels, palette
mapping, or playback state. Settings and display controls are documented in
link:01_config.adoc[Configuration and layout]; signal continuity and rendering
rationale are explained in link:23_visuals.adoc[Visualization Rendering Design].

The ownership layers have different retirement boundaries:

[cols="1,3",options="header"]
|===
|Owner |Retained data and boundary
|GUI analysis worker
|Reusable FFT machinery and bounded optional snapshot pools. Suspending capture
clears accepted input, not necessarily prepared allocation capacity; see
<<resource-boundaries,Resource boundaries>>.
|Window presentation owner
|The latest accepted staging frame, shared by visible consumers. Removing demand
releases the corresponding staging payloads; this is not a history cache.
|View models
|Waveform columns, Spectrum mappings, Spectrogram history, stereo publications,
and generative simulations. Suspension may replace working state with a bounded
final drawing; the per-view rules below distinguish those lifetimes.
|Renderer
|Uploads and submitted publications. A scene can retain a publication after the
view releases it; completion-aware retirement is independent of logical demand.
|===

Artwork and font caches have separate owners and lifetimes, independently
of visualization enablement.

Disabling visualizations suspends capture rather than merely changing cache policy: it stops
visualization demand and discards live-analysis results and derived graphics,
while retaining bounded waveform summaries. Its analysis, coverage and late-result invariants are authoritative in
link:23_visuals.adoc#visualization-enablement[Visualization Rendering Design]. Graphics that
have already been submitted still follow the retirement boundary below.

=== Reuse and invalidation

==== Waveform

Panels with matching source/display identity share immutable waveform columns and
GPU publications. Column count is bounded by drawable width and available bins.
Source revision, amplitude mapping, or effective count requires aggregation;
changed values or palette replace the publication. Height, position, cursor
movement, and width changes preserving effective count reuse it.

The GUI session owns at most 1024 summary bins, shared by all Waveform panels;
neither Core nor disk caches retain waveform summaries. Cached drawings retain
only identity tokens and cannot pin or restore obsolete summaries. Progressive
and full-load updates, unknown intervals and summary replacement follow
link:23_visuals.adoc#waveform[Waveform signal and lifetime rules].

Finite PCM sessions use bounded chunks, reusable framing storage and backpressure,
not whole-track PCM retention. Physical worker admission survives logical
cancellation until worker exit; see
link:21_ipc.adoc#finite-pcm-rendering[Finite PCM rendering]. The renderer separately
owns GPU upload retirement.

==== Spectrum

Spectrum panels with matching output and display settings share one immutable
body/peak presentation. Each panel retains its own entry, so resizing or removing
one does not invalidate another's drawing; shared output retires with its last owner.
Content identity includes plot size, grouping and appearance, not plot position:
local geometry is placed at paint time, so translation alone does not rebuild it.
Spectrum and Spectrogram share the selected GPU color map; range, size and style
do not change its identity. Waveform uses paired endpoints from the same map.
Body representation belongs to
link:25_gpu_rendering.adoc#consumer-cutover-contracts[GPU consumer contracts].

Suspension retains the final immutable body, normalized peak markers, and display
labels for each current layout panel. Envelopes, frequency mappings, and scratch
are released. Restoration draws that presentation until a current drawable result
replaces it; semantic invalidation discards it. Envelope and palette semantics are in
link:23_visuals.adoc#spectrum[Spectrum rendering].

==== Spectrogram

Spectrogram retains frequency history and numerical GPU tiles. Appearance,
frequency mapping and sampling-size changes rebuild affected publications without
discarding compatible history. FFT/window or signal changes discard incompatible
history; duration/rate changes resize retention and start a new pooling interval.
Unrelated Spectrum settings do not rebucket audio. Pooling semantics belong to
link:23_visuals.adoc#spectrogram[Spectrogram]; tile publication belongs to
link:25_gpu_rendering.adoc#spectrogram-column-fields[GPU column fields].
Panels share one immutable layer assembly for the effective history, display time
and sampling state. Each panel retains its accepted presentation independently;
scrolling can replace layer placement without rebuilding unchanged numerical tiles.
Hidden history updates invalidate working assembly ownership without rebuilding
it; another panel's retained output remains independently owned.

Shared Spectrogram history follows the largest drawable physical width, capped
by history seconds × analysis FPS, with at least two columns. Its logarithmic
frequency grid has at most 1024 rows and is further limited by the startup GPU
budget against full history capacity. Presentation targets one row per physical
pixel within that grid. Peak-preserving reduction avoids retaining raw FFT bins
per historical column; equivalent sampled rows share storage, but reprojection
cannot merge historically distinct peaks.
Hidden panels reuse their last measured dimensions; a configured history view
that has never been drawn starts with history seconds × analysis FPS columns.
This records the hidden interval without allocating a GPU presentation.

Sample storage is four bytes per distinct row per column plus a shared two-byte
index per logical row, excluding container overhead and allocator capacity. GPU
tiles retain the full presentation grid and are charged separately. Resizing
coalesces compatible chronological buckets and preserves gaps and configured time
span; painting does not resize history.

Panels update measured demand when size or visibility changes. A too-small panel
withdraws only its own request; when all are too small, shared history keeps two
columns without a drawable plot. Enlargement resumes normal retention from those
coarsened intervals. This does not change analysis demand; see
link:24_layout.adoc[GUI layout] for drawable geometry.

Configured Spectrogram panels retain bounded CPU history, pooling state and their
last sampling dimensions while hidden. Audio publications continue appending to
that history without assembling new GPU drawings. Restoration draws the latest
history instead of replaying hidden publications or restarting an empty window.
Removing the last configured Spectrogram panel, disabling visualizations or
destroying the window releases history and derived working storage.

[[resource-boundaries]]
=== Resource boundaries

Hiding releases instantaneous-view working state and stereo/generative simulation
resources while retaining bounded final drawings as described below. Configured
Spectrogram history and progressive Waveform collection continue independently of
visibility. GUI-worker analyzer capacity and base waveform previews have separate
lifetimes; see <<waveform,Waveform caching>>.
Waveform numerical payloads grow with effective display-column count and panel
count, not panel pixel area: four f32 values (16 bytes) per column, at most 1024
columns per panel, plus the shared paired-color palette and publication metadata.
Height and placement are shader inputs and do not require new numerical uploads.
Spectrum uses at most 2000 display slots, further limited by drawable width.
Bars and LED store at most one rectangle per visible slot; LED density increases
fragment work rather than the number of stored body rectangles.
Spectrogram numerical publication memory grows with bounded history capacity and
capped sampling height, in addition to the frequency data needed to preserve history.

Renderer admission is separate from CPU retention; its startup budget also limits
Spectrogram sampling. Accounting, limits and pressure behavior belong to
link:25_gpu_rendering.adoc#admission-and-retirement[GPU admission and retirement].

Removed panel entries are pruned. For instantaneous styles, window suspension
retains only final drawing data: radial styles keep at most 32 levels and rotation;
stereo styles keep their immutable fixed-size field; fractals keep bounded segments, not simulation; and
Oscilloscope keeps at most 2048 normalized stereo sweep points (16 KiB), never
its PCM owner. Pause and inactive fractal tabs instead retain the bounded scene
without running it. Layout removal, semantic invalidation and window destruction
release these publications. There is no general screenshot cache. Physical GPU
retirement is defined in
link:25_gpu_rendering.adoc#admission-and-retirement[GPU admission and retirement].

Analysis publications reuse the destination frequency, spectrum and requested
spatial buffers across same-sized updates, both in transport staging and window
staging. Immutable density, PCM and spectrogram snapshots keep shared ownership
of their bounded producer slots rather than copying their samples.

The GUI staging frame releases optional Density, Spatial Spectrum, metrics, and
band-energy payloads when their last display demand disappears; losing all
analysis demand also discards the spectrum copy. Reuse requires the same
publication, generation, FFT settings, and display token. Retained final drawing
data is not analysis staging and cannot seed restored history or simulation.
Source/seek identity and analysis settings govern semantic invalidation even while
hidden or paused. The continuity contract belongs to
link:23_visuals.adoc[Visualization Rendering Design].

Core retains one bounded native-channel PCM window shared read-only with GUI
clients. Output setup selects a native-channel stride and
`max(32, ceil((prefetch_frames + ceil(sample_rate / 5) + 32768) / 1024) + 2)`
active slots. The output prefetch has a separate 16 MiB sample limit; observation
headroom adds 200 ms and the maximum FFT span. At most 7407 slots and 8,213,300
float samples are addressable: 32,853,200 sample bytes plus bounded metadata and
alignment. The mapping reserves that maximum, but setup prefaults only configured
metadata and sample pages; previously faulted pages can remain resident after a
smaller configuration. Before output setup, the fallback is 32 slots of 1024 frames
and 18 channels (2.25 MiB of samples).

Capture appends contiguous fragments within logical blocks, with no publication
allocation. Neither IPC nor GUI transport retains another PCM queue; the GUI's
logical stereo analysis history remains separate. Slots are never pinned by
readers, so a stalled GUI cannot retain or extend Core storage. These are bounded
mapping/sample capacities, not process RSS limits. The transport contract belongs
to link:21_ipc.adoc#realtime-pcm-transport[Realtime PCM transport].

The processed Before tap's native-channel source-aligned FIFO is separate from the analysis ring
and waveform retention. Capture-identity changes, inactive analysis or exhaustion
of its output span release samples and allocation, including on refills admitting
no new PCM. Its capacity and admission contract are defined in
link:23_visuals.adoc#pcm-admission[PCM admission].

Density owns one 256 × 256 accumulation field and three immutable snapshot slots:
1 MiB of cell storage per active analyzer, excluding rendering and control state.
Worker, GUI staging, and source model share a slot's payload. If consumers pin all
three, Density is omitted from that publication rather than allocating or blocking;
other ready analysis continues. The renderer keeps the prior drawing and matching
readouts, never pairs old Density with newer metrics. PCM snapshots have the same
readiness rule. During active capture, losing Density or PCM demand releases the
corresponding analyzer pool without resetting surviving consumers or the shared
FFT window. During suspension those prepared pools can remain allocated until
active demand is reconciled again or the analyzer is replaced or destroyed;
their accepted samples and GUI staging are not retained as current input. The
five-slot PCM pool retains at most 160 KiB of stereo sample storage per analyzer.

Spectrogram full-bin analysis uses three reusable immutable slots, each holding
`analysis_fft_size / 2` calibrated dB values. Their sample storage totals 48 KiB
for FFT 8192 and at most 192 KiB for FFT 32768. Staging shares these arrays, not
copies; exhaustion omits only this optional payload. Removing the last configured
Spectrogram demand releases the analyzer pool and staging handle even while
paused; hiding alone does not. Existing external snapshots remain valid until
their owners release them.
This storage is separate from bounded logarithmic CPU history and GPU tiles;
the figures are payload capacities, not total process-memory limits.

Band-energy or Spectrogram demand also retains one reusable raw-power buffer:
`4 * analysis_fft_size / 2` bytes, at most 64 KiB. Losing both demands releases it
without resetting surviving analysis; base Spectrum, Density, PCM and Spatial-only
demand do not allocate it. Its values belong to the current FFT window, never a
retained Spectrogram publication.

Density and Spatial Spectrum retain revocable numerical GPU publications of
256 KiB and 128 KiB respectively, plus a shared 4 KiB palette per style.
Unchanged fields and resize reuse them; hiding clears application ownership.
Captured frames and device storage follow
link:25_gpu_rendering.adoc#admission-and-retirement[GPU retirement].


[[native-metadata-admission]]
== Metadata admission

Lofty exclusively owns descriptive tags and embedded artwork. It is used as an
unmodified upstream dependency, without application-specific cumulative text,
picture, object-count, or nesting budgets. Summary reads do not request pictures
or audio properties. Unsupported containers have no decoder-based metadata fallback.
Read-only conversion drops format-specific remainders used only for tag writeback;
explicit source edits retain native tag structures instead.

Lofty's public single-allocation limit is set to 128 MiB to accommodate the
configured cover sizes and container overhead. Embedded cover selection checks
the encoded image size after parsing: the default is 16 MiB, following
`interface.artwork_file_limit_mib` (1–64 MiB, applied after restart). Unusable
front covers do not hide other usable pictures. These limits do not bound total
parser memory; upstream readers may buffer a complete tag before selecting images.

Native audio decoding has a separate Symphonia metadata allowance and does not
publish descriptive tags. Playback and PCM rendering do not run
an additional Lofty tag pass. Native readers skip embedded visuals before payload
allocation. Their text admission is capped at 1 MiB per encoded item and a 4 MiB
aggregate charge, with at most 4096 admission operations, eight nesting levels,
and a 24 MiB encoded-staging allowance. One native source keeps its allowance
across probing, packet reads, and seeks; nested synchronous parsers share it.
Oversized metadata may be skipped while retaining otherwise usable audio.

Matroska DocType and CodecId are structural identifiers, independent of the
exhaustible metadata allowance. Their encoded payloads have a separate 1 KiB
limit. Oversized declarations are format errors rejected before payload reading
or allocation, not skipped metadata or truncated identifiers.

These are metadata admission bounds, not total process-memory or I/O-time
limits. Audio packets, codec state, FFmpeg reads, and decoded image pixels have
separate costs. The encoded-image admission limit does not bound decoded pixels.

== Artwork lookup retention

Artwork has three different retention layers: the application lookup identifies
source results, encoded files persist on disk, and each window owns decoded
display images. Releasing one layer does not imply reclamation of the others.

The optional `rivu-metadata` artwork service accepts source identity and path,
independently of track models. The application owns its shared manager, default
image, and background scheduling; windows own decoded display images.

=== Application-session lookup

One application-session manager serves MPRIS and all windows, including reopened
ones, independently of visualization enablement. Cache-only reads perform no
media I/O. Extraction runs on background executors and rejects non-regular sources;
even a regular-file probe can block. GUI defaults use the embedded SVG, while
MPRIS lazily exports a PNG fallback in the background.

Logical identity is track ID, fingerprint, and path. Concurrent CUE identities can
share physical probing of the same path/fingerprint without sharing completion
rights. A matching result may update a preview or MPRIS metadata; obsolete results
can warm lookup state but never replace newer demand. MPRIS publishes metadata
when a cold cover finishes without needing another playback update.

Each consumer holds one physical load until it actually retires, then rechecks
latest demand. Hiding the Artwork panel clears queued demand, not an already
submitted shared load; it cannot start hidden acquisition. Other consumers retain
independent demand. MPRIS continues transport and metadata notifications during
loading, but disabling or replacing the service waits for physical completion.
The material atmosphere follows the same physical-slot rule. Hiding or disabling
it releases display demand, not an in-flight lookup. Matching completion checks
the latest enabled track against the cache's resolved result, including cached
misses, before admitting another lookup.

In-flight probes and published results keep their logical versions resident, not
idle CUE aliases. Different fingerprints may coexist while old covers are in use.
GUI replacement retires after a frame boundary; MPRIS retains published results
until replacement/shutdown and returned properties until the next read/shutdown.
There is no visited-file registry.

Embedded covers can survive a move preserving track ID and fingerprint. Directory
covers, misses, and failures belong to the attempted path; a path change retries
discovery, even with unchanged ID/fingerprint, without resetting panel rotation.
Sharing an unfinished probe from another path requires retrying the current path
unless it yielded an embedded cover.

Lookup retention targets 64 entries. FIFO eviction selects idle results only;
active results may exceed the target, with overflow trimmed on subsequent loads.
Cache-only reads neither insert nor probe. Positive acquisition returns a lease
that prevents eviction before display installation. Consumers retain negative
completion for their current visible source even after shared-cache eviction,
preventing repeated misses; hiding or source changes releases that identity.

Album cards follow viewport demand and retain their own positive leases or
negative completions. Completion updates only cards demanding that source and
advances a bounded waiting queue. Waiting cards can acquire another consumer's
completed result without probing again; a shared cache hit alone is not display
ownership. MPRIS likewise forgets completed identity on a source change so returning
to an evicted source can reacquire after the physical slot retires.

=== Encoded files and maintenance

Encoded images use immutable content-derived paths under `artwork/cache`.
The first 128 bits of BLAKE3 form 32 lowercase hexadecimal characters: two name
the bucket, the rest the file. Originals use `ab/<30-hex>.<format>` with a
byte-sniffed `png`, `jpg`, `gif`, `webp`, `bmp`, `tiff`, or `ico` extension;
thumbnails use `ab/<30-hex>-<tier>.webp` for tiers 200, 256, 400, 560, or 1024.
Runtime identity retains the full hash. Existing originals are byte-compared:
identical content reuses the file regardless of track identity, while a mismatch
fails without overwriting it. Contents, not the source extension, determine format.
Files provide GUI paths and external MPRIS URLs.

Encoded admission uses `interface.artwork_file_limit_mib` (default 16 MiB,
range 1–64 MiB), captured at application startup. Published leases carry that
policy through GUI reads. Shared paths alone do not authorize reuse under another
policy; successful decodes and remembered failures are policy-keyed. Directory
candidate rules belong to link:04_playback.adoc#mpris-and-artwork[MPRIS and artwork].

There is no automatic disk-capacity limit, inventory, cleanup, or persistent
track-to-image index. After restart, probing rediscovers the hash before file reuse.

Static GUI covers generate lossless WebP tiers at 200, 256, 400, or 560 physical
pixels on demand; larger previews can also request 1024. Small originals are
never enlarged during generation. Animated GIF/WebP keep original frames.
Live same-content results share pixels, and complete files publish atomically;
missing or damaged thumbnails regenerate, and write failure does not prevent
display. Reuse neither rewrites files nor refreshes age. Maintenance also
recognizes previously generated 512-pixel files, but new loads do not generate them.

Tier names have no processing-version suffix, so future processing changes require
explicit invalidation. Thumbnail reads have a separate 8 MiB cap and still require
source admission under the encoded policy. Thumbnails remain disposable while a
source lookup is resident: displayed pixels do not depend on those files.
The MPRIS default export is protected once exported; later sessions can clean it
when no longer resident.

Only explicit link:01_config.adoc#artwork-cache-maintenance[Settings maintenance]
enumerates and cleans files. It recognizes originals and thumbnails in one level
of two-character lowercase-hex buckets, excluding cache-root files, unknown names,
symlinks, and nested directories. Statistics and cleanup use modification age,
not access age; reuse never refreshes timestamps.

Resident lookup results protect all their files, including idle results and active
old versions. Release makes results evictable; neither release nor eviction does
filesystem work. Cleanup is age-based, not a capacity guarantee, so disk use can
grow until requested. Acquisition excludes maintenance through probing and lookup
registration; cleanup checks protection under exclusive exclusion, and slow probes
can delay it. Cache-only reads do not wait. Maintenance never touches audio sources
and reports inspection/deletion failures.

=== Cached panel drawing

Album Browser and each large artwork panel use a GPUI cached view boundary.
When another panel redraws, unchanged views reuse their retained drawing state
instead of rebuilding their element trees. Input, model and image completions,
and geometry changes still invalidate the affected views. This retains per-view
drawing state, not another collection-sized row cache or decoded-image cache.
Artwork frame delivery is described under
link:23_visuals.adoc#artwork-composition-and-animation[Artwork composition and animation].

=== Window-owned real-cover decoding

Window consumers share pending or completed real-cover decoding by immutable
content path and encoded policy, while retaining independent lookup identities
and file protection. Background sharing also keys the decoded budget; neither
pixels nor remembered failures cross policy identities. Work starts on preview
demand using a bounded background decoder, never render-time file I/O.

Static previews select the smallest sufficient tier from actual physical display
size. Album-card demand is capped at 560 pixels, accepting display upscaling above
that size; independent large previews retain their 1024/original-image path.
Visible consumers of the same source share their largest required tier, so a
large preview can raise the shared image above the album-card cap. Upgrades retain
the old image until ready; smaller demand is debounced 300 ms. Old textures retire
only after consumers acknowledge scene replacement. Within-tier resizing does
not decode again.
The 64-by-64 material derivative requests source pixels only until its result is
ready, then retains its own cache without keeping a low-tier source alive. Other
cover consumers retain their independent source demands. When the last source
demand retires, source pixels release at the scene boundary without generating a
lower tier for the derivative. Switching back to a source-image material requests
the required tier again. Derivative observers remain registered for budget
invalidation but do not hold obsolete source generations.

One application-owned decode seat, shared by every window, serializes real-cover
reads, pixel decoding, thumbnail filtering, encoding, and publication on GPUI's
background executor. Its reusable workspace is released with the application.
Waiting consumers retain only request state, not encoded input or worker scratch;
retiring their load cancels the wait. Already-running synchronous work owns the
seat until it actually returns, even after its consumer stops waiting.

The seat retains at most 2 MiB each for source, thumbnail-input, and encoded-output
buffers, plus at most 240 KiB of reusable filtering workspace on x86-64. It keeps
no full intermediate image or idle original pixels. Oversized capacities are
discarded after completion, failure, or unwind. Filtering preserves premultiplied
alpha; delivered pixels have independent immutable ownership, and source sharing
uses weak display references. These retained-capacity bounds exclude active pixels,
codec state, GPU uploads, and process RSS.

Replaced or hidden display consumers retire after scene replacement; removed
panels need not paint again. Only the last retired consumer cancels a shared load
or unloads its image. Hiding Details or Artwork also clears queued lookup demand;
late completion cannot restore a hidden owner or start hidden acquisition.
Window hide, close, or reload flushes current and retired owners without another
frame. Other windows keep independent lifetimes.
Source release is terminal even for a scene-held image that was never painted:
an obsolete scene cannot restart its decode or keep its encoded-file protection
alive. Updating a path without changing track ID/fingerprint updates queued and
current lookup inputs, but does not reset artwork rotation or invent a transition.

Revisiting an image after its last consumer retires decodes it again; there is
no idle decoded-image cache across selections or windows. A still-live consumer
can supply the shared decode. Each real-cover decode uses
`interface.artwork_decode_budget_mib` (default `64`, range `1`–`1024` MiB),
including cumulative BGRA pixels and conservative frame/vector overhead. The
budget includes every composited GIF/WebP animation frame; even tiny frames
incur an overhead charge. It applies per immutable content path per window, not
across all active/retired images or windows. Settings operation is described in
link:01_config.adoc#desktop-settings[Desktop settings].

A committed budget change invalidates shared cover loads and completed failures,
retires completed pixels at the existing scene boundary, and refreshes all cover
consumers. Unchanged budgets retain their decodes. Pending old items are cancelled;
already-running synchronous decode work may finish, but cannot publish its old
result. Hidden windows flush retirement without waiting for another frame.
Re-decoding and scene retirement can temporarily overlap allocations; lowering
the budget is not instantaneous RSS reclamation. Settings drafts do not change
the active policy.

Pixel decoding requires nonzero dimensions no greater than 4096 per side. A
separate 64 MiB workspace estimate charges four RGBA canvases, at most 16 MiB each,
with additional native conversion checks. GIF allocation limits and WebP canvas,
frame, and embedded-codec dimension checks apply before decode. This estimate is
not a hard codec-scratch, process-RSS, or GPU cap; transient buffers, concurrent
live/retired images, and other windows have separate costs.

An over-budget or corrupt cover is rejected as a whole, logged, and replaced
with the existing default cover in metadata previews, album cards and the artwork
panel. No partial animation or silent first-frame fallback is published. Accepted
GIF/WebP animations retain all frames and original delays. Stable element IDs
retain their playback cursors; multiple artwork panels share decoded pixels but
not cursor state. GPUI handles final display scaling of the selected image tier.
Trusted decorations and generated default artwork keep their separate policies.
Encoded-file maintenance does not measure or reclaim decoded images; the
encoded-file limit is not a pixel budget.

=== Generated defaults and decorations

Decorations decode lazily once per visible style/window. The last consumer retires
them at a frame boundary; hide/close flushes immediately. Cancelled synchronous
work may finish but cannot publish, and old scenes cannot restart it. Reopening
reuses only owners that have not retired.

Default SVG covers use a separate window-local memory cache keyed by physical
size and style. Background rasterization is serialized; consumers share immutable
images, and obsolete sizes cannot replace newer demand.

This memory-only cache admits at most 16 pending/completed size keys and 32 MiB
of final BGRA pixels. Least-recently-used eviction cancels pending assets and
retires GPU images at the next window-frame boundary; temporary retired images
are outside the resident budget. Raster sides are capped at 2048 physical pixels
(larger surfaces scale that image). Only one generation uses rasterizer workspace
at a time. The last shared owner releases its assets and GPU images on window
close or reload; other windows have independent caches. More active sizes than
these limits can regenerate evicted images. Generation failures are logged and
display `Artwork unavailable`.
Generated bitmaps remain in RAM/GPU memory and never create disk files; existing
media-cover/MPRIS disk paths and encoded-file maintenance are unchanged.


== Font and rendering resources

=== Native graphics preparation

Native window creation selects instance, surface and device together. Vulkan
hardware must configure the real surface successfully to avoid initializing GL.
If it cannot, GL hardware is tried before either backend's software adapters.
Each backend is initialized at most once per preparation; software fallback
reuses the prepared instance and surface. Device recovery rejects software
adapters, and additional windows reuse an existing healthy shared context's
originating instance rather than choosing a new backend.

=== Font data and glyphs

Font retention is independent of visualization caching and enablement. Primary
family resolution runs at startup or saved-setting changes, not painting. Linux
matching and missing-character lookup share one lazily initialized Fontconfig
owner for the text system's lifetime, including retained initialization failure.
Faces load in candidate order; individual failures are logged and skipped, with
native shaping fallback last. First-use lookup may block text preparation.

Successful candidate lookups, including no coverage, use a 64-entry FIFO bounded
by 64 KiB of request keys and 1 MiB of candidate storage. Oversized results remain
usable without caching or truncation; failed requests are not cached. Keys include
family, locale, weight/style, and unique missing Unicode scalars, so reordered or
repeated scalars reuse candidates, not shaping. Normalization retains at most
64 KiB of scratch. Text-size changes alone do not resolve families again.

These bounds exclude Fontconfig metadata, externally held candidates, loaded
fonts, and allocator overhead; they promise neither total RSS nor startup latency.
Font selection belongs to link:01_config.adoc[Configuration and layout].

Icon text uses a separate symbol family; `embed-nerd-font` embeds one discovered
font file and registers it before GUI creation, not a subset or fallback chain.
This removes the runtime file dependency at the cost of executable bytes and
backend font storage. A patched text font can be much larger than a symbols-only
font; shaping and glyph rendering still need their own allocations. Font choice
and build/startup requirements belong to link:01_config.adoc[Configuration] and
link:../readme.adoc[README].

The backend owns font, shaping, glyph, and atlas caches. It may retain multiple
faces or fonts considered during fallback, not only those that supplied visible
glyphs. Parsed fonts and FontId assignments are not evicted, so switching fonts
may leave earlier font data resident. Raster-bounds memoization is capped at
32768 entries and clears on a successful distinct miss at that budget; bounds
are recomputed without changing font identity.

The cosmic backend keeps only the latest nonempty bounds-to-rasterize bitmap,
with at most 256 KiB of pixel-buffer capacity (a 256-by-256 RGBA bitmap). This is
an opportunistic handoff, not atlas residency: an atlas hit may never consume it.
The next bounds request releases it, including empty or failed requests. Matching
rasterization takes the bitmap; interleaved requests recompute evicted content
without changing pixels. Larger glyphs remain supported but are not retained,
so their bounds-to-rasterize path renders twice. The limit excludes scaler scratch,
caller-owned output pixels, atlas uploads and textures, and total process memory.

Glyph atlas reclamation starts above 8192 glyph entries after 120 frames with
sprite demand at no more than one-quarter of that count. Once the old frame is
discarded, every texture page referenced by the current replayable Scene is
protected, including color glyphs and textured Paths. Only glyphs on unprotected
pages are evicted; image and SVG owners remain responsible for their own tiles.
Whole-page protection preserves cached paint ranges but can retain unused
glyphs alongside live ones, so this is a high-water policy, not a hard byte cap.

Atlas uploads own their pixel buffers through deferred frame preparation; retired
textures can discard pending uploads. Font-file mappings may share kernel pages,
but parsed fonts, shaping, glyphs, and unrelated renderer resources have separate
costs. Font discovery is not a measurement of retained memory.

=== Settings view reuse

Settings owns its draft, inputs, navigation, and save feedback in a separate
GPUI entity. Playback and analysis updates do not invalidate that entity's
cached element tree. Settings interactions and relevant runtime changes do;
GPUI also invalidates reuse when bounds, content mask, inherited text style,
effective rem size, or paint-only group context changes. Active accessibility
rebuilds cached subtrees so nodes and actions remain registered, without changing
the caller-provided layout style.
This cache retains no settings bitmap and does not freeze background
visualizations or eliminate window composition.

=== Renderer buffers, atlases, and display lifecycle

Cached Paths and replayed Scenes share immutable vertices while draw order and
masks remain independent; editing uses copy-on-write. The renderer reuses expanded
vertex and Path upload buffers. Above 4096 elements, 120 frames at no more than
one-quarter use shrink them toward twice observed demand with a 1024-element
floor. Surface unconfiguration releases them immediately.

Tessellation retains one idle scratch pair per calling thread, capped at 1 MiB;
larger paths work but discard oversized scratch afterward. Checked-out scratch
cannot affect submitted Paths. GPUI idle reclamation releases its calling thread's
idle scratch; other threads retain only their bound until exit.

Ordinary Paths and multisampled GPU materials, including rectangles and segments,
share one renderer-owned resolve/MSAA scratch pair. Current demand is the
componentwise maximum of clipped raster extents; retained attachment capacity
may exceed it. Bounded slack absorbs small changes, fitting demand reuses the
pair, and sustained low demand reclaims capacity rather than replacing it on
every size change. Capacity stays within the physical viewport/device limit;
growth or a lower limit replaces it immediately. A frame with no raster demand
drops renderer ownership. Capacity slack does not enlarge raster or composition
bounds. Submitted GPU work retains replaced resources until completion;
reclamation neither destroys in-flight textures nor waits for the GPU. These
attachment bytes are separate from the GPU-material buffer budget. Exact
capacity and reclamation policy is authoritative in
link:25_gpu_rendering.adoc#shared-local-multisample-scratch[Shared local multisample scratch].
Instance storage above its initial capacity shrinks after
120 successful frames at no more than one-quarter utilization, retaining twice
the observed peak rounded up to a power of two and never below initial capacity.
Discarded CPU Frame, Scene, and line-layout buffers reclaim high-water capacity
after 120 small uses of each buffer (normally 240 draws for double buffering).
The live frame and replay ranges remain untouched. These policies use existing
draws, not timers, and do not promise reclamation while drawing is inactive.

Atlas admission rejects invalid or over-device-limit dimensions before allocation.
Failed first-tile reservation leaves no empty page or consumed page slot.
Device recovery clears old atlas tiles and adopts the replacement device's
texture-dimension limit before new requests.

Closing the last window exits the desktop process. GPUI display connections,
GPU contexts, font caches, worker buffers and allocator state retire with that
process rather than remaining in a windowless service. Submitted GPU work still
obeys backend retirement rules during teardown.

Playback, IPC, tray, MPRIS and accepted business operations belong to the separate
Core service and remain alive. Reopening starts a new desktop and rebuilds its
derived caches from current service state. Process exit releases desktop-owned
memory; this is not a promise about Core's retained business or audio caches.

GUI and tray have separate process-local startup Localizers. A saved language
change requires restarting the GUI for window strings and restarting the Core
service for tray protocol payloads.
