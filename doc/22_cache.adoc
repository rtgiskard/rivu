= Caching and Resource Lifecycles
:toc:
:toclevels: 2

Resources follow their owners, not one global cache switch: Core retains bounded
lookup state; each window retains query/display state; application services share
artwork and processing outputs; the renderer and font backend own their own
allocations. This chapter defines what is retained, what invalidates it, and when
the owner can release it. Entry and payload limits are not process-RSS limits,
and releasing an application reference need not immediately reclaim GPU memory.

Query stamps and revision domains are defined in
link:21_ipc.adoc#_query_results_and_pagination[IPC]. Signal meaning and continuity
belong to link:23_visuals.adoc[Visualization Rendering Design], layout/interaction
contracts to link:24_layout.adoc[GUI layout], and GPU admission/API guarantees
to link:25_gpu_rendering.adoc[GPU rendering]. The sections below retain the
invalidation consequences needed to reason about resource use without repeating
those mechanisms.

== Queue control and mutation working memory

SQLite owns the complete occurrence order. Core retains a scalar queue projection
and at most 4096 successful starts for navigation history, not a full queue-ID
array. Playback navigation resolves positions through the queue-order index;
history reconciliation checks only retained identities. Occurrence identity,
duplicate tracks, and queue size are independent of page-cache limits.

Bulk edits retain their submitted selection and affected positions, not a second
complete queue. Randomizing the entire queue temporarily materializes an ID
permutation; that buffer belongs to the operation and is released on completion.
These bounds do not cap SQLite page caches or transaction working memory.

Queue clearing deletes at most 4096 occurrences per prepared-statement execution
inside one SQLite transaction. This bounds the foreign-key delete plan's temporary
row-ID set without exposing partial clears: any failure rolls back all batches
and current-occurrence changes. Freed SQLite and Rust allocations can remain in
the allocator; a lower post-restart RSS alone does not establish a live-object leak.

== Query projection retention

List/tree retention is always enabled. A projection key combines normalized query
identity and its query-owned stamp, not page offsets,
limits, cursors, or expected revisions. A matching stamp authorizes query reuse;
bitrate-bearing payload stamps include the committed bitrate revision. A consumer
generation decides whether the result still serves current intent. Neither check
can substitute for physical-worker completion.

=== Core-owned lookup retention

Core's interactive track-ID LRU holds at most twice `interface.page_size`: 128
entries by default, at most 512. Hits refresh age, misses are not retained, and a
smaller page size trims immediately. Metadata changes invalidate affected entries;
playback statistics and committed bitrate changes patch existing entries. Scans
clear it only for display impacts. This bounds entries, not string bytes. The
background query owner and export do not populate this LRU or assemble pages from it.

Count retention stores scalars, not rows: one latest filtered library count, one
duplicate-group total, and a sixteen-entry LRU for Other, directories, albums,
album members, Queue, and playlist entries. Keys include normalized filters and
collection identity, never page boundaries. The read owner reuses them across
snapshots while their data-domain revisions remain valid, advancing cache
ownership only after snapshot publication validation. Unrelated collection changes,
no-change scans, and bitrate-only changes preserve library totals.

Writable count caches check local SQLite changes and on-demand `PRAGMA data_version`
for independent commits; writer transactions bypass them to avoid rollback leakage.
There is no polling timer or collection-sized row cache. Root aggregation and
directory relations are request-local; persistent album summaries are transactional
database projections, not evictable pages. See
link:21_ipc.adoc#_transactional_inputs_and_bounded_storage_queries[IPC storage queries].

=== Window-local query retention

The window and feature owners share one GUI snapshot cache. Changed-state
projection and revision comparison occur under the same Core read lock; unchanged
reads reuse the snapshot. Each consumer retains its own last-processed revision,
so another consumer's refresh cannot hide a change. Completion/timeout checks use
current revisions, not a submission-time snapshot. A publication with unchanged
state-section tokens does not invalidate the GUI root; audio frames still have
their independent processing path.

Workspace publishes panel membership and active-tab demand when layout structure
or panel options change. Visualizer and artwork owners reconcile their retained
consumers against that publication; ordinary playback position updates do not
rediscover the layout. Window visibility and Still Mode gate existing demand.
Source/seek identity, playback state and waveform progress remain dynamic inputs:
an unchanged panel set does not authorize retaining semantically obsolete data.
See link:24_layout.adoc[GUI layout] for structural ownership and update boundaries.

Bitrate revision changes retire retained display payloads for demand-driven
reload while preserving selection, counts, and navigation geometry. There is no
bitrate history, replay cache, or track-to-view reverse index. Old responses fail
the same query-stamp admission as other stale data. See
link:21_ipc.adoc#_query_results_and_pagination[IPC query results].

==== Demand, cancellation, and physical retirement

Feature owners reconcile configuration and freshness even while hidden, but submit
reads only for demand. Hiding immediately revokes pending publication rights while
preserving accepted rows, selections, and Details drafts. An open Add to playlist
chooser has independent demand; cover acquisition has separate owners.

GUI and TUI consumers use `QueryTracker` for query identity, freshness stamps, and
owner-scoped cancellation generations. It owns neither result rows nor worker
slots. `QueryTicket` carries submission validity into Core; cancelling a tracker
invalidates its tickets without invalidating an otherwise current cached payload.

Every submitted read holds its physical slot until the actual reply or channel
disconnection. Replacement, hiding, cancellation, and logical timeout cannot free
it. Matching retirement re-drives the latest eligible demand; old completions
cannot publish or clear replacement requests. Core can skip obsolete queued GUI
reads before Store admission, but cannot interrupt dispatched SQL or replay writes.

GUI admission allows two seconds and response presentation twelve seconds. Timeout
ends loading feedback and shows an error, discarding late payloads; explicit retry
still waits for physical retirement. Transport errors have no payload stamp and
do not prove collection changes. This policy does not alter IPC or command deadlines.

Album Browser publishes a page before requesting an uncached unfiltered search
total. Auxiliary failure leaves the rows intact and counter unavailable. The same
physical slot remains occupied until that query retires; hiding or replacement
revokes its publication rights without opening another slot.

[cols="1,3",options="header"]
|===
|Owner |Retained demand and execution boundary
|Library browser
|One root/search-count worker; configured-root rows are local data and remain
visible without counts. Root aggregates count each track once.
|Library tree
|At most four physical reads and four coalesced pending branch demands. Collapsing
discards queued subtree demand, not submitted slots; repeated demand does not
duplicate in-flight work or implicitly retry failure.
|Playlists and Queue
|The feature owns pages and request lifecycle; other consumers borrow read-only
buffers. Selection-existence reads are independent of page size, and position
validity is independent of operation progress.
|Details
|One read coordinator; explicit selections query Track, while playback-follow uses
Core's current-track projection. Draft/save acceptance has a separate owner.
|Collection resolution
|One cancellable paged reader for album-menu favorite actions. Whole-collection
Queue/Playlist copies instead submit versioned source identity for transactional
Core resolution, without a GUI collection-sized ID buffer.
|Duplicate review
|Stable selected identities survive reference refreshes, but commands require
current facts. Dismissal requests task cancellation without joining the worker;
late admission cannot reopen the review.
|===

Debounced reads recheck demand before submission. An abandoned timer releases only
its unsubmitted reservation. Album searches, Playlist pages, and explicit Details
preserve the latest demand's quiet deadline across hiding and redispatch; replacement
renews it. Confirmation barriers, drafts, and selections remain separate from read
lifetime, so late reads or saves cannot restore retired intent. See
link:24_layout.adoc[GUI layout] for interaction rules.

==== Payloads, failures, and retained geometry

[cols="1,2",options="header"]
|===
|Buffer |Retention bound
|Album, Playlist catalog/entry, Queue pages
|The larger of eight pages or visible pages plus three; failed offsets have the
same separate bound.
|Library tree pages and failures
|One shared LRU bound: the larger of sixteen pages or current demand, including
unverified ancestry. Expansion/selection identities are separate from payloads.
|===

Tree branch bookkeeping survives only while owned by cached pages, demand, pending
reads, expansion ancestry, selection, focus, or navigation. Otherwise-unowned
collapsed branches are reclaimed and reload counts on reopening. Switching views
transfers the inactive expansion snapshot rather than retaining duplicate active
branches. Hidden descendant expansion and selected anchors remain intact.

Sparse tree tables and Queue/Playlist/History selections shed high-water capacity
when live contents shrink substantially, retaining reuse slack instead of
reallocating on every deselection. This limits stale capacity, not live selection
size: selecting all still retains every selected identity.

A data revision forgets counts and drops obsolete pages, failures, and positional
pins, but retains nonempty scroll geometry until a current result supplies its
total. Previously empty results gain a loading position so additions remain
discoverable. Flat-list/album query changes discard old geometry; tree filter
changes preserve expansion choices while invalidating facts. Retained geometry
cannot authorize counts, ranges, or navigation; tree ranges also need current
ancestor counts. Unfiltered Queue state can supply a current total immediately;
filtered Queue needs its own result.

Page-size changes clear boundary-dependent pages, failures, and reservations, not
totals, geometry, or identity selections. Hiding and logical cancellation preserve
accepted data and failures. Current page failures require explicit retry until
eviction or changed demand makes them eligible again; retries use existing lanes.
Queue reconciliation failures retain occurrences but leave positions unavailable.
Selected-playlist summary failures remain scoped to selection/catalog freshness;
catalog invalidation forgets counts until a current result restores them.

Loading text waits 150 ms while placeholders retain geometry; errors and retries
are immediate. A cancellable per-view wake follows current requests and retires on
completion, hiding, or cancellation. Presentation delays never authorize stale data.

==== History-derived retention

History retains one sort index per immutable source/sort choice and column widths
per source, resolved font, and text size. Search, scrolling, and playback reuse
static measurements; only the replacement time label is remeasured. Source or
typography changes rebuild them, and source replacement releases obsolete
measurements even while hidden. Tree pages similarly retain selection indexes
rather than rescanning all expansions on viewport demand.

== Processing output retention

The processing service owns immutable PCM and frozen run snapshots, independently
of windows and query caches. Active, retained and retiring PCM share a 512 MiB
allocation budget. Clones and slices share their backing reservation; the final
owner releases the charge. This does not cap decoder/DSP state, model weights,
Python inference workspace or total process RSS.

Successful admission of a non-export run retires unselected PCM and prepared
runners before the worker allocates. The selected audition stays pinned; capacity
exhaustion fails rather than evicting it or spilling to disk. At most four frozen
run snapshots support later graph recomputation. Availability is revoked when PCM
is retired, including in current/history status. The latest 32 terminal statuses
can outlive retained audio. Export jobs preserve their source handles, occupy no
audition slot and publish only a durable file and receipt.

One bounded reclamation worker releases rejected/replaced payloads off Core.
Workers wait for preceding retirement without blocking Core; charges persist
while playback, exports or aliases still own the PCM. Export publication rechecks
cancellation and source identity before its atomic no-clobber commit. Shutdown
joins workers; live audio survives until its final playback owner releases it.
Workflow, native streaming and neural memory boundaries are specified in
link:27_audio_processing.adoc#_tasks_retention_and_audition[Audio processing].


== Visualization caching

=== Scope and contract

Reusable visualization data is always cached within its owners' resource bounds.
Reuse does not change audio analysis, waveform samples, spectrum levels, palette
mapping, or playback state. Settings and display controls are documented in
link:01_config.adoc[Configuration and layout]; signal continuity and rendering
rationale are explained in link:23_visuals.adoc[Visualization Rendering Design].

Waveform retains display columns and numerical publications, and Spectrogram
retains numerical column publications. Spectrum reuses frequency mappings but
rebuilds its body on each panel render. Radial Audio Visualizer styles do not
retain reusable graphics, stereo analysis styles retain numerical publications
in revocable GPU slots, and generative styles retain simulation state. Album
artwork and font caches have their own owners and lifetimes. Submitted
publications remain alive while their scenes reference them.

Still Mode is a destructive suspension, not another cache policy: it stops
visualization demand and discards results as well as derived graphics. Its
analysis, waveform-coverage, and late-result invariants are authoritative in
link:23_visuals.adoc#_still_mode[Visualization Rendering Design]. Graphics that
have already been submitted still follow the retirement boundary below.

=== Reuse and invalidation

==== Waveform

Waveform shares immutable column data and numerical GPU publications among panels
with the same source/display identity and effective values; changes fork only
the affected owner. Effective column count is the smaller of drawable width and
available bins. Source revision, amplitude mapping, or effective count triggers
aggregation; only changed mapped values or palette replace the publication.
Raw-width changes preserving that count, height, and cursor movement reuse it.

A scan generation remains its display identity across rolling PCM updates;
replacement scans stay distinct. The Waveform owner holds the full preview
directly and merges PCM into it without sharing mutable frame storage. Cached
paint closures retain only source/generation tokens and briefly borrow the current
owner for column pooling; they reject invalidated or replacement previews. Keys
do not pin preview snapshots. All-unknown data produces no publication, while
known silence remains drawable. The renderer owns upload reuse and
completion-aware retirement. Signal semantics are in
link:23_visuals.adoc#_waveform[Waveform].

==== Spectrum

Spectrum retains frequency mappings per panel, so differently sized panels do
not replace each other's state. New levels reuse compatible mappings; panel
geometry, frequency grouping, or display mapping changes rebuild them. Each panel
render rebuilds the body from current display levels, including on background,
grid, or label repaints. Bars/Outline/LED publish rectangles and Line/Solid publish
Paths; LED segments do not require individual CPU contours. Peak markers remain
separate from the body.

Suspension retains the final immutable body, normalized peak markers, and display
labels for each current layout panel. Envelopes, frequency mappings, and scratch
are released. Restoration draws that presentation until a current drawable result
replaces it; semantic invalidation discards it. This frozen presentation is not a
body-reuse cache. Envelope and palette semantics are in
link:23_visuals.adoc#_spectrum[Spectrum rendering].

==== Spectrogram

Spectrogram retains frequency history and numerical GPU field tiles of at most
32 columns. Changed buckets rebuild their tile; scrolling changes placement.
Palette, range, frequency mapping, and sampling-size changes rebuild affected
publications without discarding compatible history. FFT-size/window changes
discard history because its analysis meaning changed; changing the Before/After
signal selection also discards incompatible history. History duration/rate changes
resize retention and start a new pooling interval; appearance changes and unrelated
Spectrum settings do not rebucket audio. Pooling semantics are defined in
link:23_visuals.adoc#_spectrogram[Spectrogram].

Drawable panels share one history sized for the largest requested plot width,
capped by history seconds times analysis FPS, with at least two columns.
Sampling height uses the largest drawable panel's height times the configured
sampling scale, with a floor at the visible source-frequency count, then caps it
by configured rows and the startup shared GPU budget. Resizing preserves newest
chronological columns; narrow/wide panels do not fight to resize shared history
while painting.

Panels update measured demand when size or visibility changes. A too-small panel
withdraws only its own request; when all are too small, shared history keeps its
newest two columns and sampling height becomes zero. Enlargement resumes normal
retention without losing them. This does not change analysis demand; see
link:24_layout.adoc[GUI layout] for drawable geometry.

When no Spectrogram panel is visible, including when the window is hidden,
CPU history, pooling/scroll state, and derived working storage are released.
Each current layout panel may retain only the immutable tiles and normalized
placements in its last actual drawing, not the full historical column store.
Other analysis views can continue updating without accumulating hidden history.
Restoration shows that frozen drawing until fresh analysis produces a replacement;
it does not replay frames received while hidden.

=== Resource boundaries

Caches are local to current panel owners or bounded shared history, not an
unbounded record of earlier render states. Hiding a window releases visualization
working state, Spectrogram history and stereo/generative simulation resources,
while bounded final drawings follow the suspension rules above. Base waveform
previews retain their independent bounded lifetime; see
link:23_visuals.adoc#_waveform[Waveform].
Waveform numerical payloads grow with effective display-column count and panel
count, not panel pixel area: four f32 values (16 bytes) per column, at most 1024
columns per panel, plus the shared paired-color palette and publication metadata.
Height and placement are shader inputs and do not require new numerical uploads.
Spectrum uses at most 2000 display slots, further limited by drawable width.
Bars and LED store at most one rectangle per visible slot; LED density increases
fragment work rather than the number of stored body rectangles.
Spectrogram numerical publication memory grows with bounded history capacity and
capped sampling height, in addition to the frequency data needed to preserve history.

The renderer's shared GPU-material admission budget additionally covers charged
buffer capacity, including retained upload generations; it is not a cap on CPU
payloads, textures, or total GPU memory. Rivu sets
`interface.gpu_material_budget_mb` when creating its GUI and retains that startup
value for Spectrogram sampling until restart. Byte, allocation, draw-record and
in-flight limits, including pressure behavior, are documented in
link:25_gpu_rendering.adoc#_internal_led_vertical_slice[GPU rendering].

These are CPU and renderer resources: publication payload alone does not describe
total process or GPU memory. Removed panel entries are pruned. Window suspension
retains only final drawing data: radial styles have at most 32 levels and rotation,
stereo styles keep their immutable fixed-size field, fractals keep their bounded
segment publication rather than their simulation, and Oscilloscope retains at most
2048 normalized stereo sweep points (16 KiB), never its PCM owner. Pause and
inactive fractal tabs instead retain the existing bounded scene per style without
running it; layout removal and semantic invalidation release it. There is no
general screenshot cache. Destroying the window releases all these publications.
GPU uploads remain charged through completion. Hidden material residency is then
retired without requiring another frame; visible-idle drawings retain useful
uploads. This is not a promise of immediate VRAM release. Completion maintenance
and its bounded task lifetime are defined in
link:25_gpu_rendering.adoc#_admission_and_retirement[GPU rendering].

The GUI staging frame releases optional Density, Spatial Spectrum, metrics, and
band-energy payloads when their last display demand disappears; losing all
analysis demand also discards the spectrum copy. Reuse requires the same
publication, generation, FFT settings, and display token. Retained final drawing
data is not analysis staging and cannot seed restored history or simulation.
Source/seek identity and analysis settings govern semantic invalidation even while
hidden or paused. The continuity contract belongs to
link:23_visuals.adoc[Visualization Rendering Design].

The audio worker's processed Before tap owns a separate stereo FIFO for
source-aligned input awaiting output admission. Its frame count is bounded by
the graph's retained latency plus one converted PCM fragment, not by panel dimensions.
Capture-identity changes and inactive analysis discard
both its samples and allocation; refill checks retire it even when output admits
no new PCM. Exhausting the output span also releases it. This is distinct from
the bounded analysis ring and waveform preview retention. Admission, continuity,
and signal-selection rules are defined in
link:23_visuals.adoc#_pcm_admission[PCM admission].

Density owns one 256 × 256 accumulation field and three immutable snapshot slots:
1 MiB of cell storage per active analyzer, excluding rendering and control state.
Worker, GUI staging, and source model share a slot's payload. If consumers pin all
three, Density is omitted from that publication rather than allocating or blocking;
other ready analysis continues. The renderer keeps the prior drawing and matching
readouts, never pairs old Density with newer metrics. PCM snapshots have the same
readiness rule. Losing Density demand releases its pool without resetting a
surviving Spatial Spectrum consumer or the shared FFT window.

Density and Spatial Spectrum use revocable GPU slots: 256 KiB and 128 KiB per
numeric publication respectively, with a shared 4 KiB palette per style. Unchanged
fields and resize reuse them. Hiding clears slot/source ownership; captured frames
may finish safely. Renderer buffers retire after completion on a later draw or
renderer destruction, not an application cleanup frame. These are payload bounds,
not total memory or physical VRAM limits.

=== Design tradeoffs

Caching avoids repeated aggregation and publication for reusable Waveform and
Spectrogram data, not scene submission or rendering. Spectrum reuses frequency
mappings but rebuilds body geometry: Line/Solid need curves and tessellation,
while rectangle styles need bounded payloads. Bounded shared immutable
publications avoid a second geometry representation; further consolidation needs
workload evidence, not assumed hit rates or submission counts.

== Native metadata admission

Native playback, probes, and full-waveform reads retain tags but skip embedded
visuals before their payload buffers are allocated. Artwork extraction owns a
separate budget: its encoded single-image limit defaults to 16 MiB and follows
`interface.artwork_file_limit_mb` (1–64 MiB, applied after restart). Its aggregate
visual-frame allowance is twice that limit; encoded staging admits three times
the sum of that limit and 64 KiB of framing allowance. Base64 and unsynchronised
pictures check decoded size before allocating their payload buffers.
Text admission is capped at 1 MiB per encoded item and a 4 MiB aggregate charge
that includes decoding/copy allowance and per-operation overhead. At most 4096
admission operations are allowed, including frames, decoded strings, and packet
fragments; this is not an exact retained-tag count. Other metadata readers keep
the fixed 24 MiB encoded-staging allowance; nested metadata is limited to eight
levels. Oversized metadata is skipped without rejecting otherwise decodable audio;
these limits do not guarantee complete tags or chapters for such files.

One native source keeps its allowance across probing, packet reads, and seeks;
artwork probing has a separate allowance. Nested synchronous parsers share it.
The pinned Symphonia metadata/container patches enforce admission before payload
allocation, not after decoding complete metadata.

Matroska DocType and CodecId are structural identifiers, independent of the
exhaustible metadata allowance. Their encoded payloads have a separate 1 KiB
limit. Oversized declarations are format errors rejected before payload reading
or allocation, not skipped metadata or truncated identifiers.

These are metadata admission bounds, not total process-memory or I/O-time
limits. Audio packets, codec state, FFmpeg reads, and decoded image pixels have
separate costs. The encoded-image admission limit does not bound decoded pixels.

== Artwork lookup retention

Artwork has three different retention layers: the application lookup identifies
source results, encoded files persist on disk, and each window owns decoded
display images. Releasing one layer does not imply reclamation of the others.

=== Application-session lookup

One application-session lookup manager serves MPRIS and every graphical window,
including reopened windows, independently of visualization caching. Cache-only
reads never probe or perform media I/O. GUI defaults use the embedded SVG; MPRIS
lazily exports its PNG fallback on the background publisher. Extraction runs on
existing background executors and admits only regular sources, rejecting FIFOs
without waiting. Regular-file probing can still block its caller.

Each GUI consumer keeps one physical load; its selected track or viewport remains
the source of latest demand. Only matching physical completion frees that slot,
then the consumer rechecks current visible demand. Completions match track ID,
fingerprint, and source path before updating the preview or publishing MPRIS
metadata; a late result can warm the cache, never replace a
newer identity. MPRIS signals metadata after artwork becomes available, including
an initial cold load without another playback update.
MPRIS handles playback revisions while one physical artwork load remains in flight;
volume, transport and metadata notifications do not wait for its completion.
Disabling or replacing the service waits for that load to physically retire,
and late completion still cannot publish against a different source identity.
MPRIS retains its completed-load identity only while it matches the current source.
Clearing or changing selection forgets it even with another load in flight, so
returning to an evicted source reacquires its cover after the physical slot retires.

The Album artwork panel initiates acquisition only while visible. Hiding it
clears queued demand without cancelling a submitted shared load; completion may
warm the cache but cannot start another hidden lookup. Revealing it acquires the
latest track. Other consumers, including MPRIS, retain their own acquisition demand.
A path change updates the panel's source snapshot and retires the previous cover
even when track ID and fingerprint are unchanged; it does not reset track rotation.

Track ID plus source fingerprint identifies content. Resident concurrent requests
share one probe outside the lookup lock. In-flight work and published consumers
keep that version resident; a changed fingerprint can coexist with an old cover
still in use. GUI replacement retires after a frame boundary; MPRIS holds its
published result until replacement/shutdown and returned properties until the
next read/shutdown. No visited-file registry is retained.

Successful embedded covers remain reusable after a path move that preserves
track ID and fingerprint. Directory covers, misses, and source/probe failures
belong to the attempted source path: a different path retries discovery while
repeated demand at an unchanged path stays completed. A request sharing an
unfinished probe at another path waits for that result, then retries its own path
unless the shared result was an embedded cover.

Lookup retention targets 64 entries. FIFO eviction selects only idle results;
active results can temporarily exceed that target. Idle overflow is trimmed on
subsequent loads. Cache-only reads neither insert entries nor probe on misses.
Revisiting an evicted identity requires another source probe. Late completions
cannot replace a newer identity, even when both resolve to identical image bytes.

Cache-only acquisition returns cold, completed-negative, or a leased positive
result in one lookup. Consumers decide delivery and scheduling from that same
result, never a separate loaded-state check; eviction cannot reclaim a positive
result before it is installed in a view. Completed workers likewise deliver their
lease directly to matching visible demand. Hidden or obsolete completion cannot
restore a display owner or start hidden acquisition.

Album cards retain explicit negative completions only for their current visible
source identity/path, so eviction from the shared cache does not trigger repeated
probes. Leaving demand, hiding, or source changes release those records. Positive
covers remain owned by their views; neither changes the shared 64-entry target.
Viewport and album-page changes synchronize card demand with the shared cache.
An individual completion updates only cards demanding that source and advances
the bounded waiting queue; it does not rescan every visible card or re-read all
completed cache entries. A waiting card acquires any result completed by another
consumer before leaving the queue; a shared cache hit alone is not display ownership.

=== Encoded files and maintenance

Encoded images use immutable content-derived paths under `artwork/cache`.
Disk names use the first 128 bits of BLAKE3 as 32 lowercase hexadecimal characters:
the first two form a bucket directory and the remaining 30 form the filename.
For example, originals use `ab/<30-hex>.png` and thumbnails use
`ab/<30-hex>-256.webp`, `-512.webp`, or `-1024.webp`. Runtime content identity
retains the full hash. Existing originals are compared with the incoming bytes
before reuse; mismatches fail without overwriting the existing file.
Identical bytes reuse an existing file, independent of track identity; files
provide paths for GPUI and URLs for external MPRIS consumers. Embedded and directory
images share byte-sniffed, content-hash storage. Each encoded image is limited by
the session's active `interface.artwork_file_limit_mb` (default 16 MiB, range
1–64 MiB). The manager captures it at startup; changing or drafting the setting
does not change admission until restart. Published artwork leases carry that
immutable limit through GUI reads, independently of decoded-image budgets. A
shared content path alone cannot authorize reuse under a different encoded policy;
both successful decodes and remembered failures are policy-keyed.
Directory discovery checks only the source's immediate directory and exact
`cover`, `folder`, or `front` stems; full candidate rules are documented in
link:04_playback.adoc#_mpris_and_artwork[MPRIS and artwork].
There is no automatic file-count or total-byte budget, startup directory inventory,
or automatic cleanup. No persistent track-to-image index is restored after restart:
the first source probe discovers the image hash, then reuses its file if present.

Static GUI covers generate lossless WebP tiers at 256, 512, or 1024 physical pixels
on demand, without enlarging small originals. Animated GIF/WebP keep original
frames. Same-source work coalesces and publishes complete files atomically; missing
or damaged thumbnails regenerate, and write failure does not prevent display.
Reuse neither rewrites files nor refreshes age.

Tier filenames have no processing-version suffix, so future processing changes
need explicit invalidation. Thumbnail reads have an independent 8 MiB cap and
still require original-source admission under the current encoded policy. These
files are disposable even with a resident source lookup: displayed pixels do not
depend on them. Three tiers per source are not a global disk-capacity limit.

The MPRIS default export uses the same content-hash directory and is protected
once exported; later sessions can clean it when it is no longer resident.

Maintenance scans managed originals and thumbnails only within one level of
two-character lowercase-hex buckets, using the filename forms described above.
Files at the cache root and unrecognized names are excluded from statistics and
cleanup. It does not follow symlinks or descend into nested directories.

Only explicit link:01_config.adoc#_artwork_cache_maintenance[Settings maintenance]
enumerates disposable files. Statistics and cleanup use modification age, not
last-access age; normal reuse does not touch timestamps. Cleanup skips every
file referenced by a resident lookup result, including idle cached results and
active old versions. Multiple track identities may protect the same file.
Released results merely become evictable; neither release nor eviction performs
filesystem work. Disk usage can grow until the user requests maintenance, and
age-based cleanup does not enforce a global capacity limit.

Acquisition holds shared maintenance exclusion through probing, publication, and
lookup registration. Cleanup takes exclusive exclusion before checking protection
and deleting, so a slow probe can delay it. Cache-only rendering/MPRIS reads do
not wait on that gate. Maintenance never follows symlinks or touches audio sources
and reports inspection/deletion failures.

=== Window-owned real-cover decoding

GUI previews keep decoded images separate from this session-wide lookup cache.
Within one window, metadata previews, album cards, and the large artwork panel
share one pending load or completed decode per immutable content path and active
encoded admission policy, even when different tracks reference the same bytes.
Background same-source sharing also keys the encoded policy and decoded budget;
neither admitted images nor remembered failures cross policy identities. Each
consumer retains its own lookup identity and source-file protection. Loading
starts only when a preview requests the image and runs the artwork-specific
bounded decoder on GPUI's background executor, not render-time file I/O.

Static previews select the smallest sufficient tier from actual display size,
scale, and cropping aspect ratio; demand above 1024 uses the original. Visible
consumers share their largest required tier. Upgrades retain the old image until
ready; smaller demand is debounced 300 ms. Old textures retire only after consumers
acknowledge scene replacement. Within-tier resizing does not decode again.

Thumbnail filtering uses row-sized workspace rather than a full intermediate
image, with premultiplied-alpha filtering to avoid fringes. Complete source/output
pixels, codecs, and encoded bytes still contribute independently to memory use.

Replaced or hidden consumers retire through a window-owned queue after scene
replacement; removed panels need not paint again. Releasing one consumer cannot
cancel or unload another's image. Only the last retired consumer cancels the
pending load or removes the completed image from the renderer. Hiding Track
details or the large artwork panel retires its display owner and queued lookup
demand; a late shared lookup may warm the session cache but cannot restore a
hidden owner or start another hidden acquisition. Track details keeps its editor
draft independently. Window hide, close, or reload releases
current and retired display owners without waiting for another frame. Another
window owns an independent decode.

Revisiting an image after its last consumer retires decodes it again; there is
no idle decoded-image cache across selections or windows. A still-live consumer
can supply the shared decode. Each real-cover decode uses
`interface.artwork_decode_budget_mb` (default `64`, range `1`–`1024` MiB),
including cumulative BGRA pixels and conservative frame/vector overhead. The
budget includes every composited GIF/WebP animation frame; even tiny frames
incur an overhead charge. It applies per immutable content path per window, not
across all active/retired images or windows. Settings operation is described in
link:01_config.adoc#_desktop_settings[Desktop settings].

A committed budget change invalidates shared cover loads and completed failures,
retires completed pixels at the existing scene boundary, and refreshes all cover
consumers. Unchanged budgets retain their decodes. Pending old items are cancelled;
already-running synchronous decode work may finish, but cannot publish its old
result. Hidden windows flush retirement without waiting for another frame.
Re-decoding and scene retirement can temporarily overlap allocations; lowering
the budget is not instantaneous RSS reclamation. Settings drafts do not change
the active policy.

Before pixel decoding, dimensions must be nonzero and at most 4096 per side.
A separate 64 MiB workspace admission estimate charges four RGBA canvases
(at most 16 MiB per canvas), with additional checks for native static-pixel
conversion costs. GIF receives decoder allocation limits; WebP canvas, frame
rectangle and embedded VP8/VP8L dimensions are checked before pixel decode.
This estimate is not a hard codec-scratch, process-RSS or GPU-resource cap:
encoded input, codec state, transient buffers and renderer textures have separate
costs. Simultaneously live/retired owners and other windows add their own costs.

An over-budget or corrupt cover is rejected as a whole, logged, and replaced
with the existing default cover in metadata previews, album cards and the artwork
panel. No partial animation or silent first-frame fallback is published. Accepted
GIF/WebP animations retain all frames and original delays. Stable element IDs
retain their playback cursors; multiple artwork panels share decoded pixels but
not cursor state. GPUI handles final display scaling of the selected image tier.
Trusted decorations and generated default artwork keep their separate policies.
Encoded-file maintenance does not measure or reclaim decoded images; the
encoded-file limit is not a pixel budget.

=== Generated defaults and decorations

Decorations decode lazily once per visible style/window. The last consumer retires
them at a frame boundary; hide/close flushes immediately. Cancelled synchronous
work may finish but cannot publish, and old scenes cannot restart it. Reopening
reuses only owners that have not retired.

Default SVG covers use a separate window-local memory cache keyed by physical
size and style. Background rasterization is serialized; consumers share immutable
images, and obsolete sizes cannot replace newer demand.

This memory-only cache admits at most 16 pending/completed size keys and 32 MiB
of final BGRA pixels. Least-recently-used eviction cancels pending assets and
retires GPU images at the next window-frame boundary; temporary retired images
are outside the resident budget. Raster sides are capped at 2048 physical pixels
(larger surfaces scale that image). Only one generation uses rasterizer workspace
at a time. The last shared owner releases its assets and GPU images on window
close or reload; other windows have independent caches. More active sizes than
these limits can regenerate evicted images. Generation failures are logged and
display `Artwork unavailable`.
Generated bitmaps remain in RAM/GPU memory and never create disk files; existing
media-cover/MPRIS disk paths and encoded-file maintenance are unchanged.


== Font and rendering resources

=== Native graphics preparation

Native window creation selects instance, surface and device together. Vulkan
hardware must configure the real surface successfully to avoid initializing GL.
If it cannot, GL hardware is tried before either backend's software adapters.
Each backend is initialized at most once per preparation; software fallback
reuses the prepared instance and surface. Device recovery rejects software
adapters, and additional windows reuse an existing healthy shared context's
originating instance rather than choosing a new backend.

=== Font data and glyphs

Font retention is independent of visualization caching and Still Mode. Primary
family resolution runs at startup or saved-setting changes, not painting. Linux
matching and missing-character lookup share one lazily initialized Fontconfig
owner for the text system's lifetime, including retained initialization failure.
Faces load in candidate order; individual failures are logged and skipped, with
native shaping fallback last. First-use lookup may block text preparation.

Successful candidate lookups, including no coverage, use a 64-entry FIFO bounded
by 64 KiB of request keys and 1 MiB of candidate storage. Oversized results remain
usable without caching or truncation; failed requests are not cached. Keys include
family, locale, weight/style, and unique missing Unicode scalars, so reordered or
repeated scalars reuse candidates, not shaping. Normalization retains at most
64 KiB of scratch. Text-size changes alone do not resolve families again.

These bounds exclude Fontconfig metadata, externally held candidates, loaded
fonts, and allocator overhead; they promise neither total RSS nor startup latency.
Font selection belongs to link:01_config.adoc[Configuration and layout].

Icon text uses a separate symbol family; `embed-nerd-font` embeds one discovered
font file and registers it before GUI creation, not a subset or fallback chain.
This removes the runtime file dependency at the cost of executable bytes and
backend font storage. A patched text font can be much larger than a symbols-only
font; shaping and glyph rendering still need their own allocations. Font choice
and build/startup requirements belong to link:01_config.adoc[Configuration] and
link:../readme.adoc[README].

The backend owns font, shaping, glyph, and atlas caches. It may retain multiple
faces or fonts considered during fallback, not only those that supplied visible
glyphs. Parsed fonts and FontId assignments are not evicted, so switching fonts
may leave earlier font data resident. Raster-bounds memoization is capped at
32768 entries and clears on a successful distinct miss at that budget; bounds
are recomputed without changing font identity.

The cosmic backend keeps only the latest nonempty bounds-to-rasterize bitmap,
with at most 256 KiB of pixel-buffer capacity (a 256-by-256 RGBA bitmap). This is
an opportunistic handoff, not atlas residency: an atlas hit may never consume it.
The next bounds request releases it, including empty or failed requests. Matching
rasterization takes the bitmap; interleaved requests recompute evicted content
without changing pixels. Larger glyphs remain supported but are not retained,
so their bounds-to-rasterize path renders twice. The limit excludes scaler scratch,
caller-owned output pixels, atlas uploads and textures, and total process memory.

Glyph atlas reclamation starts above 8192 glyph entries after 120 frames with
sprite demand at no more than one-quarter of that count. Once the old frame is
discarded, every texture page referenced by the current replayable Scene is
protected, including color glyphs and textured Paths. Only glyphs on unprotected
pages are evicted; image and SVG owners remain responsible for their own tiles.
Whole-page protection preserves cached paint ranges but can retain unused
glyphs alongside live ones, so this is a high-water policy, not a hard byte cap.

Atlas uploads own their pixel buffers through deferred frame preparation; retired
textures can discard pending uploads. Font-file mappings may share kernel pages,
but parsed fonts, shaping, glyphs, and unrelated renderer resources have separate
costs. Font discovery is not a measurement of retained memory.

=== Settings view reuse

Settings owns its draft, inputs, navigation, and save feedback in a separate
GPUI entity. Playback and analysis updates do not invalidate that entity's
cached element tree. Settings interactions and relevant runtime changes do;
GPUI also invalidates reuse when bounds or inherited text style change.
This cache retains no settings bitmap and does not freeze background
visualizations or eliminate window composition.

=== Renderer buffers, atlases, and display lifecycle

Cached Paths and replayed Scenes share immutable vertices while draw order and
masks remain independent; editing uses copy-on-write. The renderer reuses expanded
vertex and Path upload buffers. Above 4096 elements, 120 frames at no more than
one-quarter use shrink them toward twice observed demand with a 1024-element
floor. Surface unconfiguration releases them immediately.

Tessellation retains one idle scratch pair per calling thread, capped at 1 MiB;
larger paths work but discard oversized scratch afterward. Checked-out scratch
cannot affect submitted Paths. GPUI idle reclamation releases its calling thread's
idle scratch; other threads retain only their bound until exit.

Ordinary Paths and multisampled GPU materials, including rectangles and segments,
share one renderer-owned resolve/MSAA scratch pair. Current demand is the
componentwise maximum of clipped raster extents; retained attachment capacity
may exceed it. Bounded slack absorbs small changes, fitting demand reuses the
pair, and sustained low demand reclaims capacity rather than replacing it on
every size change. Capacity stays within the physical viewport/device limit;
growth or a lower limit replaces it immediately. A frame with no raster demand
drops renderer ownership. Capacity slack does not enlarge raster or composition
bounds. Submitted GPU work retains replaced resources until completion;
reclamation neither destroys in-flight textures nor waits for the GPU. These
attachment bytes are separate from the GPU-material buffer budget. Exact
capacity and reclamation policy is authoritative in
link:25_gpu_rendering.adoc#_shared_local_multisample_scratch[Shared local multisample scratch].
Instance storage above its initial capacity shrinks after
120 successful frames at no more than one-quarter utilization, retaining twice
the observed peak rounded up to a power of two and never below initial capacity.
Discarded CPU Frame, Scene, and line-layout buffers reclaim high-water capacity
after 120 small uses of each buffer (normally 240 draws for double buffering).
The live frame and replay ranges remain untouched. These policies use existing
draws, not timers, and do not promise reclamation while drawing is inactive.

Cached dispatch replay maps source parents into the destination ancestry stack,
without allocating a second traversal stack. Replay preserves node ancestry,
focus and listeners, then restores the enclosing dispatch and context stacks.

Atlas admission rejects invalid or over-device-limit dimensions before allocation.
Failed first-tile reservation leaves no empty page or consumed page slot.

After the window is destroyed, the application requests headless mode. A
successful transition releases the display connection and its shared GPU
context; a failed transition is logged, not treated as completed reclamation.
Reopening reconnects to the original display before creating a new window;
requests arriving during a connection switch are coalesced. A failed reconnect
leaves the application running so another open request can retry.

After successful headless transition, GPUI reclaims idle derived storage once the
current update's callbacks finish, unless a window reopened. Empty element/event
arenas retain one 1 MiB chunk each; live allocations remain valid. Layout scratch,
font metrics/glyph bounds, and idle text wrappers/runs are released, but registered
font identities remain. Reopening rebuilds these caches on demand. This adds no
timer and waits for neither GPU nor background work.

Playback, IPC, tray, MPRIS, and accepted business operations remain independent
of this transition. The GPUI event loop, executors, registered font system, and
business caches remain available; this is not full framework teardown. Allocator arenas,
thread-local state, and backend display bookkeeping can outlive a window or
display reconnect, so RSS is not a count of live rendering resources. No
allocator trim is performed, and closing the window does not promise
serve-level process memory.

GUI and tray share one startup Localizer, including parsed resources and fixed
messages, across window reopen. Language changes require restart; window strings
and tray protocol payloads retain their separate owners.
