= Visualization Cache

== Scope

Rivu exposes one `visualization_cache` setting under Visualizations / Common.
It defaults to `true` and controls reusable caches owned by visualization
controls. The setting changes rendering cost only; it does not change audio
analysis, waveform samples, spectrum levels, frequency interpolation, palette
mapping, or playback state.

The current scope is:

* Waveform: pooled display columns and four tessellated RMS/Peak paths per
  active panel.
* Spectrum: body and Peak paths per Spectrum panel.
* Spectrogram: one-pixel-wide `RenderImage` per retained history column, plus
  derived heat samples used to generate those images.
* Radial Spectrum: no cache is currently implemented, so the setting has no
  effect on that control.

== Expected cache hit behavior

=== Waveform

A cached Waveform geometry is reusable while the following remain unchanged:

* Waveform frame revision;
* panel plot origin;
* plot width and height;
* display mapping parameters that affect the pooled levels.

Playback cursor movement does not invalidate the waveform paths. Once a
waveform is stable, the first repaint builds the paths and subsequent repaints
normally hit the cache. During progressive decoding, each new frame revision
causes one rebuild; additional repaints for that revision can reuse it.

For an approximate UI rate of 60 FPS and a waveform revision rate of 10 FPS,
the upper-bound repaint hit ratio is approximately:

[source,text]
----
(60 - 10) / 60 = 83%
----

The actual ratio depends on layout, repaint scheduling, and progressive scan
activity.

=== Spectrum

Spectrum geometry is keyed by panel position and size, frequency range, style,
bar layout, interpolation, peak state, dB mapping, and analysis revision.
Every non-empty analysis frame advances the revision, so active playback
rebuilds once per analysis frame. Repaints between analysis frames can reuse
the paths.

With a 20 FPS analysis rate and a 60 FPS UI repaint rate, the idealized ratio
is approximately:

[source,text]
----
cache hits: 40 / 60 = 67%
path rebuilds: 20 / second instead of 60 / second
----

This is most useful when the UI repaints more often than analysis publishes,
and when Spectrum is paused. During a stable paused frame, the hit ratio is
close to 100% until a size, position, style, or display-range change occurs.

=== Spectrogram

Spectrogram history columns retain their own `RenderImage`. A column can be
reused while its levels, image height, stream generation, palette, dB range,
and interpolation inputs remain valid. During continuous playback, new or
max-pooled columns change while older history columns remain reusable.

For example, with 1200 retained columns and one changed column per update, the
stable-column ratio is approximately:

[source,text]
----
(1200 - 1) / 1200 = 99.9%
----

This does not remove the cost of submitting every visible image with
`paint_image`; it removes repeated RGBA image construction and image upload
work for unchanged columns.

Palette, dB-range, interpolation, source-frequency, image-height, and stream
changes invalidate affected images. These changes intentionally trade one
rebuild for correct colors, rows, and frequency placement.

== CPU impact

The caches avoid the most expensive repeated work in the affected controls:

[source,text]
----
Waveform:   columns -> PathBuilder -> tessellation
Spectrum:   bars/peaks -> PathBuilder -> tessellation
Spectrogram: levels -> heat samples -> RgbaImage -> RenderImage
----

They do not eliminate:

* palette-segment scene submissions;
* GPUI `Path` ownership copies required by the current `paint_path` API;
* per-frame Spectrum level evaluation when analysis data changes;
* per-column Spectrogram `paint_image` submissions;
* Radial Spectrum path construction.

`gpui::Path` owns a vertex `Vec`, so cloning a cached path still copies its
vertices. Eliminating that copy requires a GPUI shared-immutable-vertex paint
API; it is outside this application-level cache and is intentionally deferred.

A manual runtime comparison observed roughly half the CPU usage with the cache
enabled in the tested visualization workload. The exact result depends on
panel count, style, analysis rate, repaint frequency, and window dimensions;
that observation is not a universal benchmark.

== Memory cost

=== Waveform

A previous 1200-column geometry workload produced approximately 36,000 path
vertices. With the current GPUI vertex layout estimated at about 32 bytes per
vertex, the vertex payload is approximately:

[source,text]
----
36,000 * 32 bytes ~= 1.1 MiB
----

The practical retained amount is approximately 1--2 MiB per active Waveform
panel after accounting for vector capacity, Path metadata, scene objects, and
renderer resources. Multiple active panels scale approximately linearly.

=== Spectrum

Spectrum retains one body and one Peak path per Spectrum panel. Memory depends
strongly on style and bar count:

* Line and Solid usually produce smaller paths;
* Bars and Outline produce more vertices;
* LED grows with the number of visible segments and can approach the GPUI
  vertex limit at high slot counts.

=== Spectrogram

Raw RGBA payload is approximately:

[source,text]
----
retained columns * image height * 4 bytes
----

For 1200 columns at 300 rows:

[source,text]
----
1200 * 300 * 4 bytes ~= 1.37 MiB
----

Actual CPU/GPU usage is higher because it also includes `RenderImage`, Arc,
sprite-atlas, scene, and deferred-retirement overhead. Spectrogram therefore
has the highest retained image cost, but also the highest reuse potential for
stable history.

When cache settings or image inputs change, old atlas images are retired and
released through the Window image-drop path. A short-lived peak is expected
while old resources await the next paint lifecycle.

== Cache switch behavior

With `visualization_cache = true`:

* reusable geometry and images may be retained and reused;
* unchanged Spectrum/Waveform geometry is reused;
* unchanged Spectrogram columns are reused.

With `visualization_cache = false`:

* cached Spectrum and Waveform geometry is bypassed;
* Spectrogram columns are rebuilt instead of retained;
* temporary Spectrogram images are submitted and deferred for atlas release;
* audio data, history, peak hold, smoothing, and display calculations remain
  semantically unchanged.

Turning the cache off reduces retained memory but increases allocations,
Path construction, image construction, and CPU usage. Turning it back on
causes a one-time rebuild before normal reuse resumes.

== Reliability and invalidation rules

Cache keys and invalidation must include geometry-affecting state, not palette
or cache policy itself. Current important invalidation inputs include:

* panel origin and dimensions;
* source or analysis revision;
* frequency range and stream generation;
* style, bar layout, interpolation, peak state, and dB mapping;
* Spectrogram image height and heat-sample generation;
* palette, color-range, and interpolation changes for Spectrogram images.

The cache policy is a control-flow decision, not a geometry property. It should
not be added as another field to each geometry key. A policy transition should
clear the relevant retained cache and then choose the cached or uncached
ownership path.

Raw waveform data, spectrum history, and playback state are not cache entries.
They must not be discarded merely because the visualization cache is disabled.

== Design tradeoffs

The current application-level cache is intentionally bounded and local:

* Waveform geometry is owned by its panel entry;
* Spectrum geometry is owned by its panel ID;
* Spectrogram images are owned by bounded history columns;
* removed panel entries are pruned;
* GPUI image resources are released through the Window lifecycle.

The main remaining efficiency limit is GPUI's owned `Path` API: cached paths
still need ownership copies for gradient submissions. Changing that boundary
would affect the renderer and should be measured separately rather than
introducing a second application-level geometry representation.

The conservative optimization order is:

. Keep the current bounded caches and measure real workloads.
. Keep cache-toggle invalidation and image retirement simple and explicit.
. Avoid adding more geometry-key fields unless a real stale-render case is
  reproduced.
. Defer shared GPUI vertices or a single combined Spectrogram texture until
  profiling shows that image submission or Path copying dominates.
