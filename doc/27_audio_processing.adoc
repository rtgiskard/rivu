= Audio processing: usage, design and acceptance
:toc:
:toclevels: 2

== Scope and status

Rivu provides live Monitor EQ, source-preserving restoration and neural speech
enhancement/separation, and a node graph for combining them. Monitor EQ changes
playback; graph nodes and offline jobs use independent settings. Processing never
rewrites source media, and no model download occurs during playback or a build.
The practical workflow describes available behavior. <<_ownership_and_invariants,Ownership
and invariants>> is the implementation contract; <<_quality_acceptance,quality
acceptance>> defines evaluation requirements rather than claiming they all pass.
<<_recorded_local_evidence_and_remaining_limits,Recorded evidence>> distinguishes
measured observations from remaining acceptance gaps.

== Practical workflow

Add the Audio processing panel from the layout panel catalog. Processing graph,
Monitor EQ, Restoration, Speech enhancement, Separation, and Results are separate
single-line tabs. Tabs scroll horizontally when space is limited. Switching tabs
does not run a job, change the audition, or discard field drafts. Settings remain
core-owned and shared with the CLI. Monitor EQ changes live playback independently
of graph-node EQ. The footer identifies the source track, its sample rate and
channel count, the actual audition and transport state; Monitor EQ status stays
at the right. Processing never edits library media. Keep headroom when boosting
or remixing: there is no implicit loudness matching or limiter.

. Make the desired input track current in playback; it may remain paused while
  configuring or rendering. CLI processing commands accept an explicit track ID.
. For live tonal adjustment, use Monitor EQ. For restoration or neural processing,
  configure that operation; neural backends need explicit preparation below.
. For a combined chain, connect graph ports, apply field drafts, then Preview a
  node output or Run an Output node with the chosen execution mode.
. Follow the task summary to completion; use the selected-audio line to confirm
  what is actually being auditioned, then compare with Original at fixed levels.
. To keep a graph output, Export WAV to a new file. Retained audition results
  alone do not survive session retirement.

The selected-audio line is Core's admitted source, not a guess from the latest
task: it identifies the retained run, exact graph port and live/hybrid/cached path,
with Playing, Paused or Stopped reported separately. Explicit Offline runs do
not select their results. Auto, Realtime and Hybrid runs request audition when
ready, provided the playback generation has not changed in the meantime.
Return to original addresses the currently selected audition, even when the latest
task belongs to a different run. Invalid node/port requests leave the prior
selection unchanged; playback retirement clears it.

To return all playback effects to the original path, use the footer's bypass
button or `rivu processing bypass`. This disables Monitor EQ and restores original
audio from any live, hybrid or cached audition. EQ parameters, graph and restoration
settings, queue and retained results remain available; rendering and export jobs
continue. Pending automatic audition is revoked, so a late result cannot undo the
bypass. Re-enabling EQ or selecting a retained output is an explicit later action.

=== Node graph desktop workflow

Choose an execution mode for the current playback track. Preview executes the
selected node output's ancestors; Run targets the first Output node in the graph,
identified by node ID on its button. To execute another Output, select it and use
Preview, or specify its ID with the CLI. Algorithm and model settings belong to
each node, so separate nodes can use different prepared backends. A completed
task reports its frozen graph revision separately from later edits. Audition and
export operate on that retained snapshot.
The graph is acyclic: Source supplies the track, processing nodes transform it,
Mix combines explicit inputs, and Output marks a final destination. Separation
has two output ports: vocals (0) and accompaniment (1); other nodes have one
output (0). Connections carry all stream channels, not individual speaker
channels. Fan-out is allowed; every input needed by the selected chain must be
connected. A Mix has 2–16 inputs with independent gain, mute and solo; any solo
excludes non-solo inputs, while mute still silences a soloed input.
Requested execution mode and selected output are editing choices, not proof of
the current audio path. The persistent task summary reports captured settings,
actual execution mode, progress and cancellation independently of the editor.
The Results tab contains task details, retained outputs and graph export controls.
Running never applies field drafts implicitly; unapplied fields are reported at the execution bar.
The desktop Export WAV path must be absolute and name a new file in an existing
directory; relative destinations are supported by the CLI, not this field.

Choose Add node from the graph toolbar, then select a node to inspect its algorithm
and parameters. The toolbar groups history, viewport navigation and inspector
controls without group labels. Reset view is directly available with zoom, fit and locate; it restores
pan and zoom without changing graph nodes or settings. The adjacent info icon
shows editor and shortcut help on hover. Execution mode uses a dropdown. Wide panels
place the canvas and independently scrolling, collapsible inspector side by side.
Drag the separator or focus it and use Left/Right to resize the inspector. Narrow
panels switch between the canvas and parameters using the parameter toggle and
return control. Execution controls remain outside the scrolling working area.
Press and drag a node header or its non-port card surface to select and move it
in one gesture; no preliminary click is needed.
A click without movement selects without editing the graph and transfers keyboard
focus to the node, so Delete/Backspace and graph shortcuts work immediately after
leaving another control. Positions do not change execution order. Port labels and
dots are separate connection controls: they focus and select their node without
starting a drag. Click an output port, then an input port explicitly; Escape cancels
the pending connection without changing the selected preview output. Disconnecting
or deleting a node never guesses replacement connections. Undo/Redo applies graph
edits, not playback or completed results. Keyboard deletion, duplication and history
commands leave focus on the canvas: Undo/Redo remain available after a card disappears,
and the next edit targets the current selection rather than a previously focused node.

Middle-drag or wheel over the canvas pans its viewport. Ctrl+wheel zooms around
the pointer; the zoom slider supports clicking, dragging and keyboard adjustment
from 35% to 200%, with the current percentage shown on hover. Reset view provides
an alternative. Fit graph includes
all nodes, including those outside the current viewport; Locate selected centers
the selected node. The Connections toggle exposes explicit source/destination
pairs; selecting one locates its endpoints and highlights that wire. Disconnect
remains a separate action. Canvas space follows the available panel height; short
panels scroll the graph tools and canvas independently rather than letting them
overlap the execution bar. Working-area scrolling never moves the footer or
execution bar. Multiple processing panels share typed graph drafts and
acknowledged settings. EQ band editors retain panel-local drafts and reject
conflicting values when applying them together; valid overall-gain edits submit
directly. Each field has its own focus, cursor and hit-test geometry; each panel
retains its graph parameter view and scroll positions.
Node parameters use typed choices, toggles, precision numeric entry/steps and
explicit file selection. Backend paths and parameters unused by the current
algorithm are available in an expandable section, not discarded. Enter and
Apply this field commit one draft. Apply all node drafts validates and commits
the selected node atomically, including EQ drafts; Discard restores committed
values. Stale graph revisions and rejected values retain the draft and report
errors at the affected controls. Acknowledgements do not clear text edited after
submission. File selection changes only the path draft and never starts a run.
Deleting or duplicating a node requires its drafts to be applied or discarded;
undo and redo require all graph drafts to be resolved. These guards apply to
keyboard shortcuts as well as buttons. Keyboard viewport changes cancel active
pointer gestures before changing pan or zoom.

Accepted graph and processing-setting edits are saved to `config.toml`
immediately, independently of Settings Apply. Field drafts, the canvas viewport
and retained audio results are not configuration commits. See
link:01_config.adoc#_saving_configuration[Saving configuration] for all save triggers.


=== Equalizer

Monitor EQ and EQ nodes use the same curve, band and precision editor with
independent explicit targets; presets and playback A/B remain monitor-owned.
Monitor EQ uses recursive IIR filters. An EQ graph node can instead select
linear-phase FIR with an odd tap count from 3 to 16,385. FIR approximates the
same magnitude target with a finite, windowed impulse; more taps change its
resolution, preparation cost and latency. Graph execution aligns branches and
compensates published audio back to the source timeline. It is not a quality
label for IIR.
The EQ curve and precision editor share a row in wide editors and stack in narrow
ones; an empty bank does not reserve an empty property column. Input and Output
gain remain above that working area. Valid finite values within ±24 dB submit as
you type, without Enter or a separate Apply control. Empty text, a lone sign,
incomplete exponents and out-of-range values remain drafts and do not
change the committed gain. Acknowledgements preserve newer typed text.
IME preedit remains a draft even when it parses as a valid gain. Unmarking or
committing submits the completed value once; Escape cancels composition without
applying the preedit.
Band numeric step icons stage drafts; Enter or the check icon commits a band field.
The compact response-channel dropdown shares a wrapping row with input/output gain
controls. It is hidden for mono and follows the available stream channels;
changing it only changes the displayed response, never the channels a band
processes. The overall toolbar groups monitor presets, total band count and
reset/A-B/help actions. Groups wrap together in narrow panels.
The preset dropdown loads a preset; its management popover exposes naming, save,
delete, copy and file actions without expanding the toolbar.

The bottom-right bypass button bypasses all playback effects. When fully bypassed,
click it again to enable monitor EQ; it does not restore a previous graph audition.
The button uses the accent color while effects are active and the warning color
while fully bypassed. While EQ is off, its desktop
configuration controls are locked: input/output gain, band properties and curve
edits, band-count changes, reset, A/B and preset actions are unavailable. The curve
still supports band selection and overlap cycling, and the selected band's values
remain visible. Switching EQ off preserves existing field drafts and band
selection; switching it back on makes those drafts editable again without
committing them automatically.

With EQ enabled, enter the total band count (0–32) and press Enter. Hover the
count field for its range and commit behavior. Increasing the count appends new
enabled peak filters at 0 dB, with default Q and all channels selected; the first
new band becomes selected in the linked property editor. Decreasing the count
removes bands from the end, preserving all remaining band parameters. The change
is atomic and leaves preamp, output gain and the EQ enable state unchanged.
An empty bank uses logarithmically uniform
cell centers from 20 Hz to the lower of 20 kHz and 0.499 × the known current
track sample rate; an unknown rate uses 20 kHz. With existing bands, each new
band bisects the largest remaining logarithmic frequency gap, including the
range edges. Existing bands outside this range keep their original frequencies.
Invalid counts are rejected without changing the configuration. The count field
is unavailable while a processing command is awaiting acknowledgement.

Numbered nodes on the EQ curve select the band shown in the linked property
editor, whose heading identifies the band number and filter kind. Disabled bands
remain selectable as hollow numbered nodes, with their disabled state shown in
the editor. Input and output gain remain distinct overall-gain controls, not
properties of the selected band. An empty bank prompts you to add a band before
editing its properties.

Select a band node and drag horizontally for frequency and vertically for
peak/shelf gain. Overlapping nodes stay at their true Hz/dB positions and show
the stack count and current member. A press prefers the selected member;
clicking without dragging cycles through overlapping members, while dragging
keeps the chosen member. Pointer selection and overlap cycling transfer keyboard
focus to that member; Tab or accessibility focus also selects its corresponding
band. Selection alone does not edit the EQ configuration. Numerical fields provide
exact frequency, gain, Q, shelf slope, stages and channel selection. Focused nodes
support Left/Right in semitone steps and Up/Down in 0.5 dB steps for gain-bearing
filters. Enter/Space selects the node; Delete removes the focused band while EQ
is enabled. Delete in a parameter input edits text, not bands. Removing bands or replacing the bank retires
obsolete node focus; selecting a surviving node establishes the new keyboard target.
The curve shows the configured IIR magnitude at the current stream rate. For a
linear-phase graph node this is the design target, not a measurement of the
finite FIR's realized response or phase. An unavailable rate does not establish
a playback response.

Peak, low/high shelf, low/high pass, bandpass and notch filters are available.
Q controls resonance/bandwidth except for shelves, which use cookbook shelf
slope S (0.1–1). Pass/bandpass/notch filters cascade 1–4 identical sections;
this is a stage count, not an independently designed Butterworth order. Peak
and shelf filters have one stage. Gain, preamp and output gain are bounded to
±24 dB, Q to 0.1–20, and the bank to 32 bands. Active EQ supports 8–768 kHz
and up to 64 channels. Stored frequencies are 1 Hz–96 kHz; applied bands must
also stay at or below 0.499 × the stream sample rate. Unsupported active
frequencies or channel targets fail validation rather than being retuned or
dropped. Disabled bands and bands excluded by solo keep their stored values
without imposing those stream-specific constraints.

Channel targets are `all`, or selected channels numbered from 1 in GUI text fields
and from 0 in JSON (`{"selected":[0,1]}`). Solo is global: any enabled solo band excludes
enabled non-solo bands, even when their channel targets differ. Disable a band
to exclude it, or disable EQ for global bypass. Monitor EQ edits and bypass
transitions crossfade complete filter banks over 10 ms; settled bypass preserves
samples. Graph node edits affect future snapshots, not an already admitted run.
Save/load/delete named presets, or import/export an EqualizerConfig JSON file.
Imports require an ordinary file of at most 64 KiB; FIFOs and devices are rejected
without waiting for a writer, and a bounded descriptor read enforces the size limit
even if the source grows. A/B swaps the current configuration with the saved
alternate; the first swap uses a disabled empty alternate. Save a named preset
before experimenting if both alternatives must be retained.

[source,shell]
----
rivu processing show
rivu processing eq '{"Enabled":true}'
rivu processing eq '{"PreampDb":-4.0}'
rivu processing eq '{"AddBands":{"count":6}}'
rivu processing eq '{"AddBand":{"band":{"kind":"peak","frequency_hz":1200.0,"gain_db":3.0,"q":0.8}}}'
rivu processing eq '{"BandField":{"index":0,"field":{"Channels":{"selected":[0]}}}}'
rivu processing eq '{"SavePreset":{"name":"Voice presence"}}'
rivu processing eq '"SwapAb"'
rivu processing eq '{"LoadPreset":{"name":"Voice presence"}}'
rivu processing eq '{"ExportPreset":{"path":"/absolute/presence.json","name":"Voice presence"}}'
----

`AddBands` uses the same core-owned generation rules as desktop Add and appends
without replacing earlier edits. `AddBand` remains available for an explicit
band configuration, as shown above; use it when exact frequency, gain or filter
settings are already known. Both operations respect the 32-band bank limit.

CLI preset import/export paths are relative to the invoking client's working
directory, not the host's. Absolute paths are unchanged.

=== Restoration

Stationary mode derives fixed white-noise power from the declared RMS level
(`stationary_noise_dbfs`); it does not learn colored noise from the track.
Profile uses a selected noise-only source-relative time range; Adaptive tracks
changing noise. Choose a range without wanted content: a profile containing voice
or music can remove that content. Strength scales noise power, noise floor is
the minimum spectral gain (not an input gate), attack/release control gain timing,
smoothing spans frequency bins, and transient protection preserves positive flux.
FFT size trades time/frequency resolution (power of two, 256–8192). Spectral gains
are shared across channels, preserving their per-bin phase and level ratios rather
than gating each channel independently. Wet blends the entire restoration chain
against the original.

Hum removal applies harmonic notches at the chosen fundamental (for example
50 or 60 Hz); harmonic count includes the fundamental, and Q sets notch width.
Impulse repair interpolates only short detected damage (1–8 samples), not long
dropouts. Threshold, floor and transient protection trade missed clicks against
damaged musical attacks. Hum and repair remain independent of spectral mode,
including `off`. Classical restoration supports 8–384 kHz and 1–32 channels,
with validated allocation bounds; unsupported input fails instead of silently
downmixing.

The Restoration page exposes Off, Stationary, Profile and Adaptive as direct mode
choices. Off hides only spectral-noise parameters; hum removal and impulse repair
each have their own enable switch and reveal their parameters when enabled.
Noise-range fields appear only for Profile. Wet controls the complete chain.
Speech enhancement and Separation have separate pages with operation-specific
controls; environment/model paths and shared device/thread settings live under
advanced settings. Collapsing an advanced section preserves its drafts.

[source,shell]
----
rivu processing denoise '{"mode":"adaptive","strength":1.0,"noise_floor_db":-18.0,"wet":0.8}'
rivu processing denoise '{"hum_enabled":true,"hum_fundamental_hz":50.0,"hum_harmonics":6,"hum_q":30.0,"impulse_enabled":true,"impulse_max_width":3}'
rivu processing start 42 denoise --wait
rivu processing denoise '{"mode":"profile"}'
rivu processing start 42 denoise --noise-start 0.0 --noise-end 0.5 --wait
----

Here `42` is an existing library track ID, not a file path. Replace it with the
chosen track ID. Speech enhancement is a separate neural operation, not another
classical spectral preset.

=== Explicit neural installation and offline deployment

Speech backends include MossFormer2 SE48K, NSNet2 and DeepFilterNet3. Separation
backends include Kim MelBand RoFormer and HTDemucs; they are genuinely different
models, not quality labels for the same weights. Each graph node selects its own
prepared manifest, interpreter and worker. Install explicitly with `uv` already
available. From the repository root, create separate pinned environments
(do not combine their differing PyTorch requirements):

The installer requires at least 10 GiB free before each invocation. The original
two-environment estimate was approximately 5–8 GiB including checkpoints but
excluding corpora/results; additional backends and download caches need more space.
Preparation requires a new output directory with an existing parent and at least
2 GiB free. `--weights` selects local weights; preparation can still need network
access for pinned code/license evidence. Installation and preparation are explicit
network operations; neither playback, build nor worker inference downloads models.
CPU is the default; CUDA requires an explicitly compatible prepared environment,
not an automatic fallback. The pinned NSNet2 environment is CPU-only. Worker
thread settings accept 1–8; use at most four threads for the documented local
evaluation workflow.

[source,shell]
----
python3 tools/audio_processing/install.py moss
python3 tools/audio_processing/install.py separate
python3 tools/audio_processing/prepare.py moss --download --directory .cache/neural/moss --interpreter "$PWD/.cache/neural/moss-venv/bin/python"
python3 tools/audio_processing/prepare.py separate --download --directory .cache/neural/kim --interpreter "$PWD/.cache/neural/separate-venv/bin/python"
----

The primary example prepares MossFormer2 and Kim. Add only the optional
backends you intend to compare; HTDemucs shares the separation environment,
while DeepFilterNet3 needs its own pinned environment:

[source,shell]
----
python3 tools/audio_processing/prepare.py htdemucs --download --directory .cache/neural/htdemucs --interpreter "$PWD/.cache/neural/separate-venv/bin/python"
python3 tools/audio_processing/install.py df3
python3 tools/audio_processing/prepare.py df3 --download --directory .cache/neural/df3 --interpreter "$PWD/.cache/neural/df3-venv/bin/python"
----

For the optional NSNet2 baseline, use `install.py speech`, then
`prepare.py nsnet2` with `.cache/neural/speech-venv/bin/python`. Installation
names the environment by operation; preparation names the actual model. Run
only the backend setup steps you need; the example does not require all models.


In the GUI, model manifest paths are optional: applying an empty value clears
the selected model. Interpreter and worker paths are required; empty values do
not restore defaults. Their placeholders show path examples, not installed
resources. Hover the path controls for their requirements. These
hints apply to both standalone processing controls and each graph node's fields.


Preparation prints absolute `worker`, `interpreter` and `model_manifest` paths.
Configure *all three*, not only the manifest, and preserve the venv executable
symlink path rather than resolving it to base Python. The binary does not bundle
the worker, models or Python. Inference requires a provisioned manifest with
`runtime` and `dependencies` records. Runtime metadata binds the bundle paths and
interpreter hash; dependency records match the model pins and bind supplied
notices to hashed files. Keep the hashed worker sidecars/schema, resources and
license records with the manifest. Provisioning verifies construction artifacts
and validates the completed bundle before printing paths. To copy an already
verified bundle without a download:

[source,shell]
----
/absolute/moss-venv/bin/python /absolute/rivu/tools/audio_processing/provision.py --manifest /absolute/moss/manifest.json --directory /absolute/new-moss-bundle
----

The destination must be new; provisioning does not copy the interpreter environment.
Model assets are hard-linked on the same filesystem and copied otherwise: treat
both bundles' assets as immutable, not independently editable copies. Use the
emitted paths, and keep the separate environment installed. Absolute paths make
inference independent of the application's working directory or repository.

A bundle's runtime is a source snapshot. Updating the checkout does not update an
already copied worker. To receive worker fixes, run the provisioning command above
from the updated checkout into a new bundle and configure all three emitted paths;
do not edit the old bundle's hashed files in place.

The worker accepts request version 1 and emits event version 2. Completion is a
bounded summary: source format/length, model ID and manifest hash, and fixed WAV
basenames relative to that request's `output_dir`. Full provenance, absolute
output paths and per-block measurements remain in `output_dir/result.json`.
The worker writes that report before emitting completion; callers still require
a successful process exit and validate outputs before publication. Rust keeps
the 64 KiB event-line limit and does not load the full report. Benchmark and corpus
evaluation tools read the full report only after successful completion.

Provision runtime bundles from verified manifests with current tooling. Keep hashed
sidecars immutable; update the configured worker path to select a new bundle.

For a shared worker, select the emitted runtime worker compatible with both
prepared manifests; interpreters and manifests remain operation-specific:

[source,shell]
----
rivu processing neural '{"worker":"/absolute/new-moss-bundle/runtime/worker.py","speech_interpreter":"/absolute/moss-venv/bin/python","speech_manifest":"/absolute/new-moss-bundle/manifest.json","separation_interpreter":"/absolute/separate-venv/bin/python","separation_manifest":"/absolute/kim/manifest.json","device":"cpu","threads":4}'
rivu processing start 42 speech --wait
rivu processing start 43 separate --wait
----

MossFormer2's primary model card declares Apache-2.0; Kim's original trainer card
declares MIT. Preparation pins checkpoints and records primary weight evidence
separately from code permissions. HTDemucs and public DeepFilterNet3 preparation
retain their actual provenance and unresolved weight-permission facts rather than
synthesizing a grant or blocking model comparison. Review those notices before
redistribution; local provisioning grants no additional license. NSNet2 remains
an explicit baseline, not an alias for the quality-priority speech model.

Preparation accepts an explicit `--proxy` for network access. It is not a worker
inference option; inference remains offline. Never include proxy credentials in
shared evidence, manifests or logs.

Speech controls include wet mix and attenuation limit; the optional post-filter
is supported only by DeepFilterNet3. Enabling it for another speech model fails
rather than silently ignoring it. Separation overlap controls model overlap,
not a quality guarantee. Neural source rates are 8–192 kHz; speech accepts
mono/stereo, separation requires stereo. Speech channels are inferred
independently, so stereo image can change. Rate conversion to 48 kHz speech /
44.1 kHz separation is explicit; output is trimmed back to the original rate,
channel count and exact frame count. No implicit downmix or duplicated mono
separation is offered.

With speech Wet set to zero, the worker copies dry float PCM in bounded blocks
without loading the model, running inference, or resampling. Input, controls and
the provisioned manifest and artifact hashes are still validated. This path needs
NumPy and SoundFile for PCM I/O, but does not check or load model execution
dependencies. The result report explicitly identifies bypass and records that
the model was not executed.
Dry statistics reuse the validated source blocks and their energy sum; peak
statistics use scalar reductions without a full-block magnitude array.

=== Tasks, retention and audition

Only one processing task runs at a time. `queued`, `rendering` and `processing`
describe preparation/work; `complete`, `failed` and `cancelled` are terminal
task states. Not every task visits every work phase: realtime preparation need
not render a file. Start acceptance is not completion; `--wait` waits for that
task and fails on cancellation/error. Use `task status processing ID` and
`task cancel processing ID` for an asynchronous start. A cancellation acknowledgement
accepts the request, not proof that the worker has already retired. Cancellation
invalidates publication, terminates/reaps neural workers and retires partial
scratch; it does not publish a partial result. Source identity and job settings
are captured. Later configuration or graph edits do not change that snapshot;
changes to its registered source or media invalidate publication. Switching the
playback track is different: it suppresses a pending automatic graph-audition
handoff through the playback generation, but does not discard a valid completed
result. Use task IDs for completion and the selected-audio line for playback.

Scratch directory creation, path preparation and neural-backend filesystem checks
run on the processing worker. An accepted start can therefore fail asynchronously
during preparation; no terminal result is published until Core rechecks source
identity and cancellation. Queued can also mean waiting for retired cache files
to be deleted before preparation or final publication proceeds.

Processing and stem-mix workers are established before their retirement barrier
enters the bounded reclamation mailbox. A thread-spawn failure returns to Core
without leaving queued work, so repeated retries cannot consume retirement
capacity. An admitted worker waits off Core for earlier deletions; Core never
blocks on the reclamation mailbox. A deletion failure still rejects the waiting
task and keeps the unreclaimed bytes charged until shutdown.

Native source preparation checks cancellation between decoder calls; a backend
call or filesystem operation has no hard cancellation-time guarantee. A retained
audition or stem mix is rejected if the registered source's decoder hint changed,
as well as when its media identity no longer matches.
`task cancel processing ID` also returns a matching selected audition to Original after
its preparation task has completed. For realtime/hybrid graph runs it additionally
marks the task `cancelled`; stopping a cached offline audition leaves its completed
task status intact. Completion of preparation is not the lifetime of live audio.

Scratch lives in session-owned `processing-*` directories under the data
directory. Up to four retained results share 4 GiB; the selected audition stays
protected, so a result too large to coexist with it fails. Old task status does
not guarantee that its audio remains available. See
link:22_cache.adoc#_processing_output_retention[Processing output retention]
for eviction and status-history lifetimes. Export a graph output to keep a durable
WAV. Shutdown closes task admission and joins processing/reclamation workers while
preserving retained outputs until playback has retired; final service destruction
removes those temporary results, never original media or exported files.

Input files are bounded to 8 GiB; source rendering has the float WAV RIFF limit
(under 4 GiB). Admission opens the selected decoder once and validates its actual
format and source identity before creating PCM output. Known duration is checked
against the render allowance up front; unknown or understated duration is still
bounded while writing, and failure removes partial output.

Offline/hybrid graph execution limits its per-run cache to 2 GiB. Admission counts
unique PCM files, propagated causal guards, public crops and transient denoise
copies, plus each neural node's request (1 MiB), report (8 MiB) and retained stderr
(64 KiB) allowances. Disabled EQ and true denoise bypass share their input PCM and
timeline instead of writing another file. Off denoise with active hum/impulse
processing is not a bypass; wet-zero Profile mode still validates/captures its
selected noise range.

Neural jobs require nonempty input of at most four hours and total stem output at
most 8 GiB; the worker also checks free space for its predicted outputs plus
256 MiB. Its report is written within the 8 MiB allowance; overflow fails and
removes that task's outputs. These checks do not reserve disk space or supersede
the retained-cache limit. The limits apply at different stages and are not a
combined scratch or RAM budget. Leave room for rendered input, stems, graph
intermediates and an optional remix; an input within worker duration/size limits
can still exceed graph or retention capacity.
The neural worker chooses RIFF or RF64 independently for each output stem;
combined stem size does not force individually small files into RF64. Application
rendering and retained-cache limits still apply.

[source,shell]
----
rivu task status processing 1
rivu processing audition 1 denoised
rivu processing audition 1 original
rivu processing audition 2 vocals
rivu processing audition 2 accompaniment
rivu processing audition 2 mix --vocal-gain-db -3 --accompaniment-gain-db 0
----

Use IDs actually returned by Start. A speech result uses the `denoised` audition
mode. Audition starts the result's original queue source if necessary, then hands
off to aligned rendered audio; Original returns to source audio. Separation Mix
renders the retained stems with independent gains; it is not a second inference.
Do not mistake source-preserving audition/remix for a stem export feature. EQ
remains a playback setting when comparing results. Listen at matched levels and
compare quiet words, consonants, reverb, attacks and stereo ambience; neither
exact stem summation nor a screenshot constitutes listening approval.

=== Node graph CLI

`processing graph show` prints a readable graph summary, node IDs, connections,
and latest task. Add `--json` for the full `graph` object, including its `revision`,
nodes, positions and explicit port-to-port edges, plus `latest_task` (or null).
The latest task may belong to an older graph revision or a non-graph operation; it
is not the current graph's execution state. `processing show` summarizes playback
EQ, denoise, neural settings, graph and task; `--json` includes their complete
settings and presets. Node-local graph processing does not replace playback EQ.

Every `graph edit` takes one externally tagged `GraphEdit` JSON value and a
required `--expected-revision` matching the graph currently held by Core. Refresh after
each accepted edit or concurrent change; a stale revision is rejected rather
than overwriting another client's edits. Edits include `Add`, `Remove`, `Replace`,
`Move`, `Connect`, `Disconnect`, `Duplicate` and `ReplaceGraph`. Node kinds use
snake_case JSON names, and ports are zero-based. Quote the complete JSON argument
so negative gains and positions reach the parser unchanged.
The persisted graph is bounded to 64 nodes and 128 edges, including nodes outside
the selected ancestor closure.

For a fresh default graph (Source node 1, Output node 2, revision 0), this example
adds an explicit two-input mix, fans the source into both inputs, and connects the
mix to Output. Existing graphs may have different IDs or revisions: inspect them
first instead of replaying these edits blindly.

[source,shell]
----
rivu --json processing graph show
rivu processing graph edit --expected-revision 0 '{"Add":{"kind":{"mix":{"gains_db":[-6.0,-12.5],"muted":[false,false],"solo":[false,false]}},"position":[200.0,120.0]}}'
rivu processing graph edit --expected-revision 1 '{"Connect":{"from":{"node":1,"port":0},"to":{"node":3,"port":0}}}'
rivu processing graph edit --expected-revision 2 '{"Connect":{"from":{"node":1,"port":0},"to":{"node":3,"port":1}}}'
rivu processing graph edit --expected-revision 3 '{"Disconnect":{"to":{"node":2,"port":0}}}'
rivu processing graph edit --expected-revision 4 '{"Connect":{"from":{"node":3,"port":0},"to":{"node":2,"port":0}}}'
rivu --json processing graph run 42 2 --port 0 --mode offline --wait
----

`graph run TRACK_ID NODE_ID` snapshots the current graph and processes only the
selected output port's ancestor closure. `--port` defaults to 0; `--mode` accepts
`auto` (default), `offline`, `realtime` or `hybrid`. Auto first attempts an exact
native realtime plan, then a useful precomputed-prefix/live-suffix hybrid, then
offline rendering. It never changes algorithms. `settings.graph_mode` records
the actual selected mode; `settings.graph_boundary` identifies a hybrid boundary.
Explicit modes reject unsupported plans instead of silently changing modes.
Native realtime planning supports IIR/FIR EQ, non-Profile classical restoration,
Mix and Output; Profile capture and neural inference require an offline prefix
or fully offline execution. A native plan also has admission bounds: at most 32
channels, 64 MiB estimated state, two seconds of latency and a conservative
arithmetic-work budget. These are planning limits, not measured device-deadline
guarantees. An EQ configuration supported by the DSP crate alone can therefore
still be rejected by the realtime graph planner.

Admission charges IIR stages only for effective bands: disabled bands, bands
excluded by an enabled solo selection, and identity peak/shelf sections do not
consume filter-stage estimates. Disabled EQ and fully bypassed restoration use
pass-through nodes without DSP state or processing latency; node buffers and
input edges still count toward graph budgets. Configuration validation remains
required. Enabled flat FIR keeps its convolution latency and budget, and active
hum or impulse repair is not bypassed merely because spectral denoising is Off.

Hybrid uses a single cached output port as its boundary: every path into the
live target must cross that exact port. A separate uncached source branch or
another separation output cannot be substituted by the same cached stream.
Planning and FFT preparation run on the processing worker, not Core dispatch or
the device callback. `--wait` prints one terminal task result and returns failure
for failed or cancelled jobs; without it, an accepted acknowledgement is not proof
of completion. Use `task status processing RUN_ID` and
`task cancel processing RUN_ID` for the same task.

A realtime task reaching `complete` means its immutable live plan is prepared,
not that an offline file was rendered: `graph_outputs` is empty. Automatic
admission still depends on the captured playback generation; confirm the actual
selection in the selected-audio line. Offline and hybrid tasks can retain rendered
node outputs separately from later graph edits. Cached node/port audition is
immediate; uncached snapshot audition prepares a new run and returns its own task ID.
To render a selected output from any retained graph snapshot, including realtime,
use `graph export` with the actual run ID and node/port from that snapshot:

[source,shell]
----
rivu task status processing 7
rivu processing graph audition 7 3 --port 0
rivu processing graph export 7 3 'rendered outputs/mix -6 dB.wav' --port 0 --wait
----

Audition uses the retained snapshot, not subsequently edited settings.
The Results tab lists every output port in the retained graph, not only cached
ports or the original run's ancestor closure. Calculate-and-audition/export
actions can execute another valid closure from that snapshot. Both cached and
uncached requests recheck the registered source and media identity; keeping a
result does not make it independent of the original source.

Export starts a new task: it copies an already cached node output when available,
otherwise it renders the requested output offline from the retained graph and
source. Neither path uses the subsequently edited graph. The acknowledgement
supplies a new `processing_id`; `--wait` returns that export's terminal task result.
Without `--wait`, query the new task ID, not the
original run, to determine completion.
`settings.graph_export_path` records the requested destination;
`graph_exported_path` is populated only after the completed export is published.
Export accepts a real filesystem path, including spaces; relative destinations
are anchored to the invoking client's working directory, not the core's. Choose
a new file in an existing directory; existing destinations are never overwritten.
Retained temporary outputs remain session-owned; an exported file is the durable
result. Source files are not modified.

== Ownership and invariants

* Core commits configuration; UI submits edits, not stale replacement snapshots.
* The GUI processing owner retains drafts, selection and cancellable pointer intent.
  Its link:../src/gui/audio_processing/processing_graph_ui.rs[graph editor] owns
  inspector, workbench and result-view state; Core owns committed graph state and
  admits processing results. The equalizer editor is a sibling within the same
  GUI feature, not a second configuration owner.
* Prepared DSP owns its coefficients, history, rate and channel layout. The device
  callback performs no model loading, FFT planning, file I/O or unbounded work.
* Disabled processing preserves the original signal path. Protection, resampling,
  gain compensation and latency are explicit, not silent quality fallbacks.
* Non-finite graph input or intermediate PCM fails before downstream publication.
  Finite over-range samples are not clipped or replaced with silence.
  Numerical failure can advance a finite prefix of DSP history; reset the processor
  before reuse and discard the failed job's partial output. Failed noise-profile
  capture cannot publish a profile and also requires reset before reuse.
* Every task result is bound to source identity and captured processing settings,
  including model identity where applicable. Core alone admits worker results;
  cancellation or events from an inactive task cannot publish audio. Playback
  generation separately governs automatic audition handoff. Source files and
  existing export destinations are never overwritten.
* Seeking, changing a source and incompatible format changes reset history. Pause
  does not invent audio time. Tail flushing and trimming preserve source alignment.
* Allocation, channel count, block work, retained results and scratch storage have
  explicit finite bounds. Long processing stays outside the device callback.

=== Timeline and source identity

Graph execution retains full causal intermediate context: FIR ringing, denoiser
startup delay and branch-alignment delays are not trimmed before downstream nodes.
Only published node audio is compensated and restricted to the original source
timeline. A retained `graph_outputs[].context`, when present, names guarded PCM
and its signed source-relative `start_frame`; hybrid suffixes consume that context
rather than the trimmed audition/export file. At EOF each denoiser finishes at
its actual upstream end, before its output and FIR tails propagate downstream;
padding is never treated as new source input. Graph audition checks the opened
decoder descriptor against the admitted source identity (or guarded cache identity),
so replacing a pathname with same-format media cannot substitute another source.

=== DSP crate features

`rivu-dsp::equalizer` groups shared parameters and implementation selection in
`config`, the recursive processor in `iir::Equalizer`, and the linear-phase
processor in `fir::FirEqualizer`. Both implementations consume the same
`config::EqualizerConfig`; `config::EqImplementation` selects between them.

Configuration and validation remain available without execution support. The
default feature set is empty; the optional `execution` feature enables `iir`,
`fir`, response sampling, denoising implementations and the `rustfft` dependency.
Execution APIs are absent when disabled, not replaced by no-ops. Serialization,
defaults and validation semantics remain unchanged.

The desktop application and `rivu-audio` explicitly enable `execution` with
default features disabled. `rivu-format` uses only the resident contracts with
default features disabled and does not request execution. Cargo feature
unification can still enable execution when these crates share a dependency
graph with an execution consumer. The `equalizer_benchmark` and `denoise_render`
examples require `--features execution`.

Disabled FIR constructs no FFT plans or convolution storage.
Active FIR construction shares its frequency grid, inverse design FFT plan and
scratch, window and impulse workspace across channels of that construction.
Each channel still evaluates its own target response; the workspace is released
before streaming and is not a global kernel cache.

Classical restoration prepares only the required path: exact bypass for zero Wet or an entirely disabled
chain, time-domain state for hum/repair without spectral denoising, and FFT/STFT
storage only for spectral modes. Configuration and required noise profiles are
still validated on bypass. Hum-only processing has no lookahead or dry-alignment
queue; partial-wet delayed processing retains only the alignment it needs.

== Quality acceptance

=== Equalizer acceptance

The equalizer provides editable bands, peak/shelf/pass/bandpass/notch filters,
frequency/gain/Q controls, applicable slope choices, enable/solo, channel targets,
input/output gain, presets and response inspection. Graphical and numerical
editing operate on one authoritative filter configuration.

Numerical acceptance is based on independent transfer-function evaluation and
processed signals, not source-text or copied-value tests:

* Disabled processing is sample-exact and does not allocate in processing.
* At defined passband measurement points, steady-state measured response agrees
  with the declared transfer response within 0.1 dB. Nulls and startup transients
  are evaluated separately; dB comparisons at zero are undefined.
* Supported boundary rates, gains and Q values remain finite and stable under
  impulses, silence, tones and broadband input. No output sanitization hides
  unstable filter state.
* Reset eliminates old history; independent channels do not leak. Parameter
  changes are bounded continuous transitions, including bypass and solo changes.
* The displayed IIR response represents actual cascaded coefficients at the current
  sample rate. Frequencies beyond that rate's usable range are explicit. FIR
  acceptance measures the realized finite impulse separately from its displayed
  IIR magnitude target; target agreement alone is not realized-response evidence.

=== Denoising acceptance

Required modes cover stationary noise, a captured noise profile, adaptive noise,
speech-targeted enhancement, hum and impulse suppression. Controls must affect
real algorithm parameters, not relabel an identical preset. Suppression and
content preservation are evaluated separately.

Use clean references mixed with known noise at declared SNR, plus real noisy
recordings. Include speech consonants, quiet words, pauses, nonstationary noise,
music transients, sustained harmonics and stereo ambience. Record input/output
level, residual noise, reference distortion and speech intelligibility where a
valid reference exists. Stereo coherence and musical-noise artifacts require
additional listening; a high scalar score alone is not acceptance.

Ported neural inference must be compared against the selected upstream reference
using the same weights and parameters. An optimization may not silently replace
the model, alter rate handling or claim equal quality from throughput alone.

=== Separation acceptance

Evaluate both vocals and accompaniment against reference stems. Include backing
vocals, reverb, dense instrumentation, transients and stereo mixtures. Measure
source quality and leakage, absolute sample alignment, output length, stereo
coherence, block-boundary discontinuity and mixture reconstruction residual.
If accompaniment is defined as mixture minus vocals, exact reconstruction proves
that definition only; it does not prove separation quality.

Compare the integrated inference with its upstream algorithm under identical
weights, segment, overlap and seed settings before changing those settings for
speed. Synthetic independent components establish alignment/invariants, not
real-world vocal-separation quality. Multi-instrument stems and exporting stems
are not automatically added to the accepted scope.

=== Evidence and performance

An acceptance evidence bundle must record source revision, dirty changes,
executable/model hashes, configuration, corpus provenance/license, exact commands,
device and thread settings; a normal task status is not that evidence bundle.
Keep evaluation data and large outputs in task-owned `.cache/` paths. Never use
private library files without explicit permission.

Separate cold initialization, warm processing, file I/O and playback behavior.
Benchmark bypass, representative and worst supported configurations, and enabled
versus disabled feature branches. Report repeated measurements and variability:
wall/CPU time, real-time factor, block latency percentiles, peak resident memory,
allocations/capacity and underruns. End-to-end seek/cancel/shutdown behavior and
GUI controls require actual application smoke proof.

The Python benchmark and corpus evaluator report two distinct wall times.
`worker_subprocess_wall_seconds` covers only the worker subprocess call, including
startup and captured pipes. `evaluation_wall_seconds` starts before per-sample
reference/input reads and request creation and ends after output reads, artifact
writes, hashes, scoring and sample-record construction. It excludes record append,
progress printing, cross-sample summaries and final aggregate report serialization
or writing. `timing_summary` summarizes each field separately; compare only
measurements with matching timing boundaries.

Both tool families encode undefined scores/gains as JSON `null`. SNR requires
nonzero reference energy; SI-SDR requires nonzero mean-centered reference energy.
Exact reconstruction is `"infinity"` only when that condition holds. A constant
reference therefore has undefined SI-SDR/gain; a silent estimate has undefined
SI-SDR and zero gain for a nonconstant reference. Infinite-baseline gains can be
`"-infinity"`; infinity minus itself is undefined.

Summaries exclude undefined values, preserve infinity ordering, and report
defined/undefined and signed infinity counts. A median between opposite infinities
is undefined. These numerical cases do not establish quality.

Music corpus manifest schema 2 records each prepared directory relative to the
corpus root and explicitly binds `diagnostic_only` to source identity and SHA256.
Directory numbering is not a diagnostic rule. During preparation, mark any known
reference erratum with repeatable `--diagnostic-source` paths; the marker follows
identical source bytes even when renamed or reordered. Run the following from the
repository root after binding the variables to actual local source files. The
output directory must not already exist; keep prepared corpora under `.cache/`:

[source,shell]
----
python tools/audio_quality/prepare_music.py "$al_james_source" "$other_source" \
  --diagnostic-source "$al_james_source" \
  --output .cache/new-music-float --provenance 'actual source and license'
----

Prepare a new corpus if its manifest lacks these identity records. Keep recorded
measurements bound to their original corpus and timing definitions.

Automatic metrics and actual listening are distinct evidence. No automated
analysis is reported as human listening. Missing listening approval remains an
explicit acceptance gap, even when objective and integration checks pass.

cumulative requested bytes, not application RSS or callback-deadline claims.
Seven timing repetitions did not show a uniform speedup: some spectral modes
were slightly slower. Raw observations and workload/source identities are in
`.cache/experiments/audio/classical-audit/results.json`.

==== NSNet2 numerical processing

The first NSNet2 cost pass reused spectral-feature and overlap-add temporaries
without changing its window, hop, masks or gain floor. Comparisons covered 13 lengths and
mono/stereo under both NumPy 1.26.4 (the pinned runtime) and NumPy 2.5.4;
features and synthesized output matched each environment's baseline exactly.
The pinned runtime also explicitly verified in-place mask multiplication against
the previous expression. For a 12-second stereo synthetic workload, nine
alternating-order repetitions under 1.26.4 measured feature temporary peaks of
18,567,672 versus 13,875,816 bytes;
synthesis peaks were essentially unchanged (55,394,728 versus 55,394,788 bytes).
Under 2.5.4, synthesis temporary peaks were 36,919,120 versus 27,710,208 bytes,
and feature peaks were 9,251,860 versus 4,626,684 bytes. Timing distributions
overlapped; neither environment establishes an end-to-end model speedup.
Evidence is in `.cache/speech-optimize-20261023/`; `nsnet-numeric.json` identifies
the pinned runtime, and `nsnet-numeric-numpy-2.5.4.json` identifies the other run.

A subsequent pass bounds the synthesis inverse FFT to 64 frames at a time,
releasing each batch's frame views before allocating the next. Frame accumulation
order and transform dtype remain unchanged; output/weight arrays still scale
with the block duration. Against the previous all-frame synthesis, 44 length and
mono/stereo cases in each of NumPy 1.26.4 and 2.5.4 matched their respective
baseline exactly and left the input spectrum unchanged. These include partial
batches, hop boundaries and long nonuniform frequency masks.

At 48 kHz stereo, 576,037 samples (12 seconds plus 37 frames), traced synthesis
peaks fell from 55,394,788 to 18,485,420 bytes in the pinned NumPy 1.26.4 runtime,
and from 27,710,088 to 18,477,416 bytes under 2.5.4. Nine alternating-order timing
repetitions under 1.26.4 had medians 25.899/23.107 ms and ranges
25.125--31.046/22.243--24.647 ms (baseline/batched). The 2.5.4 distributions and
short-input distributions overlap; no universal or end-to-end speedup is claimed.
The real FFT/synthesis consumer and raw measurements with source identities are
retained under `.cache/audio-review-next/`. This does not measure model execution
or whole-process RSS.

==== Shared worker storage

The shared neural worker accumulates RMS energy in float64 without full-block
float64 conversion/square arrays and releases block views before the next
inference. On 24 seconds of 192 kHz stereo data, seven energy-reduction repetitions
measured temporary peaks of 147,456,192 versus 132,544 bytes; relative energy
difference was about 2.05e-15 due to reduction order, not a change to audio.
The ownership experiment demonstrates removal of previous-block references,
not immediate OS memory reclamation or a measured Torch/ORT peak-RSS reduction.
Kim/HTDemucs inference, overlap, context, resampling and source-minus-vocals
semantics remain unchanged, as does DF3 inference.

==== MossFormer2 numerical processing

The audited MossFormer2 change scales an owned padded waveform, clamps its private
CPU mask, multiplies the spectrum and rescales synthesized samples in place.
Kaldi/delta scratch ends before model inference; features end before synthesis,
and waveform and mask views end before the next channel. Padding still reaches the same full
frame, with the same per-channel dither seed. Across 99 length/layout/floor
combinations under pinned Torch/torchaudio 2.11.0 CPU and NumPy 2.2.6,
features and synthesis matched the previous expressions exactly
and read-only caller input was preserved. The real final-ReLU/two-speaker mask
view was checked; the source and other speaker remained unchanged.

For a 12-second 48 kHz stereo DSP workload, profiler operation counts confirmed
four fewer out-of-place multiplies and two fewer out-of-place floor operations.
Their output buffers plus NumPy output rescaling account for 43,719,744 bytes of
eliminated allocation per block, not a peak-memory reduction: on CPU the in-place
mask keeps both speakers' ReLU storage alive until synthesis ends. Integrated
seven-repetition alternating timings had medians 113.221/112.601 ms and ranges
109.746--117.522/111.389--114.702 ms; an earlier run's candidate median was slower.
No stable speedup is claimed. Integrated consumer evidence is
`.cache/audio-review-next/moss-numeric-integrated.json`; preparation and adoption
evidence is `.cache/speech-optimize-20261023/moss-adoption-evidence.json`.
These checks execute real Torch/Kaldi/DSP, not a model or its weights. CUDA
ownership was reviewed but not exercised.

This audit's neural numerical checks do not establish real-model equivalence,
listening quality or fixed-environment throughput. Real-weight regression tests
require explicitly prepared manifests and their matching interpreters; skipped
tests are not passes. Model-environment installation/download failures must be
reported separately from the numerical and classical-render checks above.
Worker evidence is under `.cache/experiments/audio/audio-implementation-audit/`.
