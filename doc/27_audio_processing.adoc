= Audio processing: usage, design and acceptance
:toc:
:toclevels: 2

== Scope and status

Rivu provides live Monitor EQ, source-preserving restoration and neural speech
enhancement/separation, and a node graph for combining them. Monitor EQ changes
playback; graph nodes and offline jobs use independent settings. Processing never
rewrites source media, and no model download occurs during playback or a build.
The practical workflow describes available behavior. <<ownership-and-invariants,Ownership
and invariants>> is the implementation contract; <<quality-acceptance,quality
acceptance>> defines evaluation requirements rather than claiming they all pass.
<<recorded-local-evidence-and-remaining-limits,Recorded evidence>> distinguishes
measured observations from remaining acceptance gaps.

== Practical workflow

Add the Audio processing panel from the layout catalog. Each named layout allows
one instance, providing Processing graph, Monitor EQ, Restoration, Speech
enhancement, Separation and Results. Switching tabs or layouts does not run a
job, change audition or discard drafts. Closing and readding the panel preserves
window-owned drafts for still-valid targets, but cancels focus and pointer
interaction. Core owns committed settings. Monitor EQ affects playback
independently of graph-node EQ. See link:24_layout.adoc#_panel_insertion[Panel insertion].

Keep headroom when boosting or remixing: there is no implicit loudness matching
or limiter.

. Make the desired input track current in playback; it may remain paused while
  configuring or rendering. CLI processing commands accept an explicit track ID.
. For live tonal adjustment, use Monitor EQ. For restoration or neural processing,
  configure that operation; neural backends need explicit preparation below.
. For a combined chain, connect graph ports, apply field drafts, then Preview a
  node output or Run an Output node with the chosen execution mode.
. Follow the task to completion; confirm the actual audition before comparing
  with Original at fixed levels.
. To keep a graph output, Export WAV to a new file. Retained audition results
  alone do not survive session retirement.

Core reports the actual audition independently of the latest task, identifying
the retained run, graph port and live/hybrid/cached path separately from transport
state. While bypassed, the actual route is Original and a separate selection
identifies the eligible resume target.
Explicit Offline runs do not select their results. Auto, Realtime and Hybrid runs
request audition when ready only if bypass is off, their pending selection has
not been revoked and the playback generation has not changed in the meantime.
Return to original addresses the currently selected audition, even when the latest
task belongs to a different run. Invalid node/port requests leave the prior
selection unchanged; playback retirement clears it.
Selecting an audition preserves Playing; paused or stopped playback loads it paused.
Preparing a mix leaves the current source unchanged until the result is ready.

[[playback-bypass]]
The footer's bypass icon temporarily routes playback to Original without changing
EQ enablement, effect parameters or the selected processing configuration.
Cancelling bypass restores the still-valid selected audition and the configured
Monitor EQ state. It never enables an independently disabled EQ. Track replacement
or source invalidation must not restore an old track's output.
If a retained target fails source validation, resume reports an error, clears that
selection and leaves bypass active. A subsequent explicit resume can enable the
current Monitor EQ state without the rejected audition. Failure to open a resumed
source stops playback conservatively and restores bypass rather than selecting a
different algorithm or source.

The persisted `playback.processing_bypassed` setting is independent of `equalizer.enabled`.
Parameter editing remains available while master bypass is active, subject to
each effect's own enablement. Rendering and export continue; entering bypass
revokes pending automatic audition, and late results cannot cancel bypass.
Explicit audition requires cancelling bypass first. Retained audition audio
remains session-owned rather than being persisted with the bypass preference.

The footer bypass button, Restoration hum/impulse checkboxes and Speech
post-filter checkbox send toggle intents. Core flips its current value when each
queued action executes, so repeated clicks accumulate even before the display
refreshes. Interleaved explicit settings are applied in the same execution order.

Use `rivu processing bypass on` to enter bypass and
`rivu processing bypass off` to resume processing. Both are explicit, idempotent
state requests rather than toggles, so multiple clients do not race a stale
display state.

=== Node graph desktop workflow

The graph is acyclic: Source supplies the track, processing nodes transform it,
Mix combines explicit inputs, and Output marks a destination. Connections carry
all stream channels, not individual speaker channels. Separation exposes vocals
(port 0) and accompaniment (port 1); other nodes expose output 0. Fan-out is
allowed, but every required input in the selected chain must be connected.
A Mix has 2–16 inputs with independent gain, mute and solo: any solo excludes
non-solo inputs, while mute still silences a soloed input.

Add nodes from the toolbar and select one to inspect its algorithm and parameters.
Each node has independent settings, including its prepared neural backend.
Click an output port, then an input port to connect them; Escape cancels the
pending connection. Disconnecting or deleting never guesses replacement edges.
Drag a node's header or non-port surface to select and move it; positions do not
change execution order. Undo/Redo affects graph edits, not playback or results.
Delete/Backspace acts on the selected node when the canvas has keyboard focus,
not while editing parameter text.

Middle-drag or wheel pans; Ctrl+wheel zooms around the pointer. The zoom slider
covers 35%–200%. Reset view restores pan/zoom without editing nodes; Fit graph
includes offscreen nodes, and Locate selected centers the selection. Connections
lists explicit endpoint pairs and locates/highlights a selected wire; disconnect
is a separate action. The toolbar's info icon provides shortcut help.
Fit may use a smaller zoom for very wide graphs; relative zoom preserves its
pointer anchor without jumping to the slider minimum. Viewport transforms use
rebased double-precision coordinates, preserving local card geometry even near
the finite limits of persisted single-precision positions. Nodes and connections
are culled or clipped in screen space before conversion to GUI pixels. Drag previews and
new-node placement use the same representable positions that an edit can commit.

Wide panels have a resizable, collapsible inspector beside the canvas; narrow
panels switch between canvas and parameters. A focused separator supports
Left/Right. Working areas scroll independently of execution controls and footer.
Removing a panel discards local interaction state and invalidates its previous
frame's input, including zoom/resize gestures.

Enter or Apply this field commits a parameter draft, except for the live EQ
numeric controls below. Apply all node drafts validates and commits that node
atomically. Discard removes unapplied text/errors without undoing accepted live
edits. Invalid values and stale revisions retain their drafts with errors;
acknowledgements do not erase text typed after submission. File selection only
changes a path draft. Unused backend settings remain available in an expandable
section. Delete/Duplicate requires that node's drafts to be resolved; Undo/Redo
requires all graph drafts to be applied or discarded.
The denoise node's FFT selector offers only 256, 512, 1024, 2048, 4096 and 8192
samples. Selecting a size changes the draft, not the committed node. It is
independent of the visualization analysis FFT setting.

Auto selects an execution path, not a quality level. Preview selected executes
the selected node output's ancestors; in Offline mode it computes without
selecting an audition. Process output targets the first Output node. To process
another Output, select it and use Preview selected, or use its ID in the CLI.
Neither action applies drafts implicitly.

Audition and export use the frozen run and captured settings, not the current
editor. Results retains outputs for audition and export. Desktop Export WAV
requires an absolute path naming a new file in an existing directory; the CLI
also accepts relative destinations.

Accepted graph and processing-setting edits save to `config.toml` immediately,
independently of Settings Apply. Drafts, viewport and retained audio are not
configuration commits. See link:01_config.adoc#saving-configuration[Saving configuration].

=== Equalizer

Monitor EQ and graph EQ share an editor but have independent settings. Presets
and playback A/B belong to Monitor EQ. Monitor EQ uses recursive IIR filters;
graph EQ can select linear-phase FIR with 3–16,385 odd taps. More taps change
resolution, preparation cost and latency, not an IIR quality label. The curve
shows the configured IIR magnitude at the current stream rate; for FIR it is the
design target, not the realized finite response or phase. Graph execution aligns
branches and compensates published audio to the source timeline.

Input/output gain and band frequency, gain, Q, shelf slope and stages submit
valid numeric edits as you type; step buttons and sliders apply immediately.
Channels requires Enter/Apply. Incomplete/out-of-range text and IME preedit stay
drafts. Committing composition submits once; Escape cancels it. Newer typed text
survives acknowledgements, and Enter on unchanged displayed text does not round
the stored value. Numeric controls retain the latest local intent while a command
is pending; unrelated graph revisions do not inherit it. Accepted edits are not
rolled back when a slider gesture is cancelled. Focused-node arrow steps edit the
same frequency/gain drafts, so held keys accumulate locally and coalesce behind
the pending command instead of queuing separate edits.

The band count precedes the grouped input/output gains, separated by a divider,
and remains visible with no bands. Enter 0–32 and press Enter. Increasing appends
enabled, 0 dB peak bands with default Q and all channels selected; decreasing
removes tail bands. Existing bands and overall gains are preserved. New bands fill
logarithmic gaps from 20 Hz to `min(20 kHz, 0.499 × track rate)`, or 20 kHz when
the rate is unknown. Apply all commits retained-band drafts and gains atomically
with the resize; shrinking discards removed bands and their drafts.
When a track rate is known, adding bands requires room for the 20 Hz lower
bound; otherwise the editor reports an error. Removing bands remains available.

Reset preserves the enabled state but clears bands and both gains; graph EQ also
returns to IIR. It discards that target's EQ drafts, including implementation/taps,
and retires queued local edit intent.
Band-count changes and Reset are unavailable while a processing acknowledgement is pending.

Hover/focus the curve to see numbered band nodes. Drag horizontally for frequency
and vertically for peak/shelf gain; release commits once, while Escape or lost
interaction cancels the preview. Clicking an overlapping stack cycles its members
without moving them. Disabled bands remain selectable. Focused nodes support
Left/Right semitone steps, Up/Down 0.5 dB gain steps, Enter/Space selection and
Delete removal. Parameter fields provide exact values; deleting text there never
deletes a band. The gain row keeps dB inside each numeric field and groups the
input/output controls; Curve channel sits at the right or wraps below when space
is limited. It changes only the displayed curve, not processing targets.
Band parameters stay below the curve at every panel width.
Bands outside the plotted frequency range remain valid. Their nodes show an
edge marker and retain the exact frequency in the selected-band hint and
tooltip; clamping the plotted position does not retune the band.

Monitor EQ can be enabled independently of master bypass. While EQ is off,
configuration, preset and reset controls are locked; curve selection and values
remain visible. A/B stays available to reverse a swap to a disabled configuration.
Disabling preserves drafts and selection without applying them on re-enable.
Master bypass does not lock an enabled EQ's editor; see <<playback-bypass,Playback bypass>>.

Peak, low/high shelf, low/high pass, bandpass and notch filters are available.
Q controls resonance/bandwidth except for shelves, which use shelf slope S
(0.1–1). Pass/bandpass/notch filters cascade 1–4 identical sections, not an
independently designed Butterworth order; peak/shelf filters have one stage.
Gain, preamp and output gain are bounded to ±24 dB, Q to 0.1–20, and the bank to
32 bands. Active EQ supports 8–768 kHz and up to 64 channels. Stored frequencies
are 1 Hz–96 kHz; effective bands must also be at or below 0.499 × the stream rate
and address existing channels. Unsupported active settings fail validation rather
than being retuned or dropped. Disabled/solo-excluded bands keep stored values
without imposing stream-specific constraints.
With no current track, frequency editing uses the stored 1 Hz–96 kHz range.
For a known track rate, the upper bound is `min(96 kHz, 0.499 × rate)`;
if it is below 1 Hz, frequency controls and curve retuning are unavailable
without changing stored band values. Other numeric parameters remain editable.

Channel targets are `all`, or selected channels numbered from 1 in GUI text and
from 0 in JSON (`{"selected":[0,1]}`). Any enabled solo band excludes enabled
non-solo bands globally, even across differing channel targets. Monitor edits
and bypass crossfade complete banks over 10 ms; settled bypass preserves samples.
Reapplying the already accepted monitor configuration preserves the current fade.
Accepted EQ changes affect subsequent PCM; the GUI preserves old waveform bins
until revisited intervals overwrite them. Graph edits affect future immutable
render snapshots, not an admitted run. Explicit Before/After preview semantics are
defined in link:23_visuals.adoc#waveform[Waveform].

Save/load/delete named presets or import/export EqualizerConfig JSON. Save new
preset is create-only. Overwrite, same-name import and deletion require desktop
confirmation identifying the target (and import source path); cancellation sends
no command. Changing the target or reopening the dialog invalidates old confirmation.
CLI SavePreset/ImportPreset omit `overwrite` or set it false to create only;
`overwrite: true` replaces only an existing preset, never creates a missing one.
Imports require an ordinary file of at most 64 KiB; devices/FIFOs are rejected
and reads remain bounded if the file grows. A/B swaps with the alternate; the
first swap saves the current configuration and selects the disabled, zero-gain,
empty-band default. Save a preset if both alternatives must be retained.


[source,shell]
----
rivu processing show
rivu processing eq '{"Enabled":true}'
rivu processing eq '{"PreampDb":-4.0}'
rivu processing eq '{"AddBands":{"count":6}}'
rivu processing eq '{"AddBand":{"band":{"kind":"peak","frequency_hz":1200.0,"gain_db":3.0,"q":0.8}}}'
rivu processing eq '{"BandField":{"index":0,"field":{"Channels":{"selected":[0]}}}}'
rivu processing eq '{"SavePreset":{"name":"Voice presence"}}'
rivu processing eq '{"SavePreset":{"name":"Voice presence","overwrite":true}}'
rivu processing eq '"SwapAb"'
rivu processing eq '{"LoadPreset":{"name":"Voice presence"}}'
rivu processing eq '{"ExportPreset":{"path":"/absolute/presence.json","name":"Voice presence"}}'
----

`AddBands` uses the same core-owned generation rules as increasing the desktop
band count and appends without replacing earlier edits. `AddBand` remains available for an explicit
band configuration, as shown above; use it when exact frequency, gain or filter
settings are already known. Both operations respect the 32-band bank limit.

CLI preset import/export paths are relative to the invoking client's working
directory, not the host's. Absolute paths are unchanged.
Preset export publishes atomically to a new destination. Failed writes do not
leave a partial preset at the requested final path; existing files are never replaced.

=== Restoration

Stationary mode derives fixed white-noise power from the declared RMS level
(`stationary_noise_dbfs`); it does not learn colored noise from the track.
Profile uses a selected noise-only source-relative time range; Adaptive tracks
changing noise. Choose a range without wanted content: a profile containing voice
or music can remove that content. Strength scales noise power.
`spectral_gain_floor_db` is the minimum spectral amplitude gain (−100…0 dB,
default −24 dB), not an input gate or an estimate of the source noise level.
Attack/release control gain timing, smoothing spans frequency bins, and transient
protection preserves positive flux.
FFT size trades time/frequency resolution (power of two, 256–8192). Spectral gains
are shared across channels, preserving their per-bin phase and level ratios rather
than gating each channel independently. Wet blends the entire restoration chain
against the original.

Hum removal applies harmonic notches at the chosen fundamental (for example
50 or 60 Hz); harmonic count includes the fundamental, and Q sets notch width.
Impulse repair interpolates only short detected damage (1–8 samples), not long
dropouts. Threshold, floor and transient protection trade missed clicks against
damaged musical attacks. Hum and repair remain independent of spectral mode,
including `off`. Classical restoration supports 8–384 kHz and 1–32 channels,
with validated allocation bounds; unsupported input fails instead of silently
downmixing.

The Restoration page exposes Off, Stationary, Profile and Adaptive as direct mode
choices. Off hides only spectral-noise parameters; hum removal and impulse repair
each have their own enable switch and reveal their parameters when enabled.
Noise-range fields appear only for Profile. Wet controls the complete chain.
Speech enhancement and Separation have separate pages. Sound parameters are
separate from Model configuration; advanced runtime options are nested under
the latter. The post-filter is explicitly labeled DeepFilterNet3-only: enabling
it with another speech model reports an error, not a fallback. Environment/model
paths and numeric fields still require Enter or Apply; toggles and device choices
submit directly, and choosing the current mode or device sends nothing. Worker
script, device and threads are shared by Speech and Separation. Collapsing an
advanced section preserves its drafts.
Applying a non-graph restoration or neural page parses all dirty fields before
submission, then sends one sparse patch. Core validates and saves the combined
candidate atomically: invalid fields cannot leave earlier fields applied or
persisted. Acknowledgements clear only the exact submitted drafts; edits made
while submission is pending remain drafts even when the text returns to its
submitted value. Enter still applies only its field. A draft generation already
owned by a pending command is not submitted again by repeated Enter or Apply.


[source,shell]
----
rivu processing denoise '{"mode":"adaptive","strength":1.0,"spectral_gain_floor_db":-18.0,"wet":0.8}'
rivu processing denoise '{"hum_enabled":true,"hum_fundamental_hz":50.0,"hum_harmonics":6,"hum_q":30.0,"impulse_enabled":true,"impulse_max_width":3}'
rivu processing start 42 denoise --wait
rivu processing denoise '{"mode":"profile"}'
rivu processing start 42 denoise --noise-start 0.0 --noise-end 0.5 --wait
----

Here `42` is an existing library track ID, not a file path. Replace it with the
chosen track ID. Speech enhancement is a separate neural operation, not another
classical spectral preset.

=== Explicit neural installation and offline deployment

Speech backends are UL-UNAS and GTCRN (Rust + ONNX Runtime, CPU only),
MossFormer2 SE48K and DeepFilterNet3 (Python). The separation backend is
Kim Mel-band RoFormer (`melband_roformer_kim`, Python). Standalone operations and
graph nodes select the backend from the prepared manifest; each graph node has
its own model configuration. Native speech does not use Python interpreter or
worker paths. It requires the `onnx` build feature (enabled by default); builds
without it reject native manifests rather than falling back to Python.
Model manifests must resolve to ordinary files; symlinks to ordinary files are
accepted. FIFOs and other non-regular inputs are rejected during preparation
without waiting for a writer.

Use `rivu processing setup MODEL` to prepare a model without starting Core.
Installed distributions include the preparation tools; Python 3 is required.
Choose exactly one of `--download` or local `--weights PATH`; even local weights
require network access for pinned source/license evidence. Preparation requires
a new destination directory and 2 GiB free. Playback, builds and inference never
download models. MossFormer2 loads its pinned publisher checkpoint as a strict
state dictionary with exact parameter names.

`make install` builds then installs; `make install-only` copies existing release
binaries and the preparation/runtime resources without building. Resources live
at `PREFIX/share/rivu/audio_processing` beside `PREFIX/bin/rivu`. Setup prefers
these installed resources; only a checkout-built executable in its build tree
falls back to that checkout's tools, never the caller's working directory.
Export, benchmark and corpus-evaluation tools are checkout tools, not installed
resources. See link:../Makefile[the installation recipe].

The default bundle is `DATA_DIR/neural/MODEL`; override the application directory
with `--data-dir` or the bundle with `--directory PATH`. Existing bundles are
never overwritten. Updates require a new bundle and its emitted paths. Results
are JSON (`--json` selects compact output); installer diagnostics go to stderr.
`--activate` submits the prepared paths through the running Core's neural-settings
interface. It does not edit configuration directly, add graph nodes or start
inference. Activation failure leaves the prepared bundle available.
Standalone speech and separation settings share one worker path. Activation rejects
replacing that path while another Python backend is selected, rather than silently
invalidating its bundle; clear that selection explicitly before switching workers.
Native ONNX speech does not consume the shared worker.

For native speech, install ONNX Runtime 1.23 or newer using the system package
manager (on Arch Linux: `sudo pacman -S --needed onnxruntime`). If it is not on the
dynamic-loader search path, set `ORT_DYLIB_PATH` to its absolute shared-library
path before starting Rivu. Preparation uses only Python's standard library;
there is no model-specific Python environment:

[source,shell]
----
rivu processing setup ul-unas --download
rivu processing setup gtcrn --download --activate
----

Configure the emitted `model_manifest` as the speech manifest. The bundle pins
the official streaming ONNX artifact and retains upstream source/license evidence.
Both models operate at 16 kHz internally; the native path preserves the source
sample rate, exact frame count and mono/stereo speaker layout. Channels have
independent recurrent state. CPU and 1–8 threads are supported; CUDA and the
DeepFilterNet-only post-filter report errors rather than selecting another model.
Wet mix and attenuation-limit controls remain available.
Short inputs and partial final frames retain the original length. Numerical
comparisons must use the same padding; see <<timeline-and-source-identity,Timeline
and source identity>>.

Native preparation validates the manifest contract and all pinned bundle hashes
before materializing source PCM. Execution consumes the prepared model bytes and
controls rather than reopening the manifest; changing bundle files affects a
later preparation, not an admitted run. Reads remain cancellable: the manifest
is bounded to 256 KiB and bundle artifacts to 16 MiB in total, independently of
the retained-PCM budget.
Dry runs still validate the bundle but do not load ONNX Runtime.

For Python models, install `uv` first (Arch Linux:
`sudo pacman -S --needed python uv`). Setup installs a CPU environment beneath
`BUNDLE.environment`: `.venv` for MossFormer2/Kim or `df3-venv` for DeepFilterNet3.
Default setup gives each bundle its own environment. Alternatively,
`--interpreter /absolute/venv/bin/python` skips package installation; preserve
that venv symlink and keep the shared environment unchanged while bundles use it.

The default installer resolves compatible dependency ranges; DF3 pins its older
stack. `installed.txt` or `df3-installed.txt` records the resolved environment,
and preparation binds the bundle to exact installed identities. Installation
requires 10 GiB free; model preparation separately requires 2 GiB. uv retains
its configured cache/managed-Python locations; setup puts extraction/build
temporaries under `DATA_DIR/.cache/neural`. Environments and bundles are not
caches. A failed installation/preparation can leave the environment for reuse;
failed preparation removes its newly created bundle.

BS-RoFormer 124-band (https://www.mvsep.com/quality_checker/entry/10197[MVSEP entry 10197], 2026-07-10) is not an installed backend:
its exact checkpoint and complete inference configuration have not been located
in the publisher's public artifacts. The open weights linked by the
https://github.com/lucidrains/BS-RoFormer[lucidrains homepage] include a different 62-band ViperX checkpoint; it is not a substitute
for the selected 124-band model or its reported scores.

Allow additional space for models, caches, corpora and results. CUDA requires an
explicitly compatible environment; inference has no automatic CPU fallback.
Threads accept 1–8.

[source,shell]
----
rivu processing setup moss --download
rivu processing setup separate --download
----

DeepFilterNet3 is optional and keeps its own pinned environment because its
NumPy dependency is below 2, whereas Kim requires NumPy 2 or later:

[source,shell]
----
rivu processing setup df3 --download
----

Python preparation emits absolute `worker`, `interpreter` and `model_manifest`
paths; configure all three unless using `--activate`. The application ships
preparation/runtime sources, not environments, ONNX Runtime or models. Clearing
the manifest field in the GUI, or sending JSON `null`, clears selection without
deleting files. Interpreter/worker values remain retained, nonempty settings;
native speech does not execute them.

Provisioned bundles execute their own `runtime/worker.py` snapshot. Application
inference validates artifact hashes and requires the manifest's worker and
interpreter paths to match the configured and actually executing runtime. The
interpreter identity preserves the venv path, not just its resolved base binary.
The checkout sources are under `tools/audio_processing/runtime/`; they are not
interchangeable with a prepared bundle's worker.

Keep the complete provisioned bundle together: hashed runtime sidecars/schema,
model assets and license/dependency records. Its manifest binds bundle paths,
interpreter hash and dependency pins. To provision verified assets offline using
the default installed tools and the bundle's prepared interpreter:

[source,shell]
----
/absolute/.venv/bin/python /usr/local/share/rivu/audio_processing/provision.py --manifest /absolute/moss/manifest.json --directory /absolute/new-moss-bundle
----

Adjust `/usr/local` for the installation prefix, or use the checkout's
`tools/audio_processing/provision.py`. The destination must be new and its parent
must exist. Provisioning retains the installed interpreter rather than copying
its environment. Assets are hard-linked on the same filesystem and copied
otherwise; treat both bundles as immutable. After runtime updates, reprovision
with the updated tools into a new bundle and configure its emitted paths. Do not
patch hashed bundle files in place or assume a directory move updates absolute
manifest paths.

Python application inference runs `worker.py --stream`; request and event protocol
version 4 is defined by `VERSION` and `EVENT_VERSION` in
link:../tools/audio_processing/runtime/worker.py[the worker contract]. Explicitly
reprovision or prepare older bundles with updated tools and configure the new
bundle's emitted paths. Earlier protocol versions are not accepted; inference
never rewrites an older bundle or falls back to another runtime.
Stdin/stdout carry JSON controls and interleaved float32-le PCM in
frames: one-byte kind, four-byte little-endian length, at most 64 KiB payload.
Requests declare rate, channels and exact frame count, not audio paths. Each
process handles one task: request, declared PCM, empty input-end marker, then
immediate stdin EOF. The producer must close stdin without waiting for completion;
trailing bytes fail the task. Diagnostics go to stderr. Completion identifies
model, format, frames and stems; Rust validates framing, finite/aligned PCM,
completion and successful exit before publication. Linux `poll` waits without a
timeout on nonblocking pipe readiness, pidfd child-exit notification and sticky
eventfd cancellation; there are no periodic wakeups. Bounded drain rounds preserve
duplex backpressure. Pipe EOF is distinct from process exit; cancellation or
failure terminates/reaps the child, including after early stdout EOF. This path
requires Linux `pidfd_open` support and permission, not generic Unix support.
Readiness/setup syscall failures report the OS error and retire the child rather
than falling back to timed polling.
Application streams collect no export-only PCM hashes, timing/energy statistics
or detailed report; completion still requires validated input-end and EOF.

For Python speech with `wet_mix=0`, the request still declares the retained input's
format and frame count, but sends only the empty input-end marker and EOF, without
PCM in either direction. The child validates the manifest, artifact hashes,
runtime identity and controls, then acknowledges `outputs={"speech":"input"}`.
Rust checks alignment, completion and successful child exit before reusing the
same retained PCM storage. No model dependencies, inference or context windows
are loaded for this application dry path.

Benchmark/corpus tools use the explicit
link:../tools/audio_processing/export.py[`export.py --request` adapter], separate
from application execution. File jobs require absolute `input_path` and
`output_dir`: input must be IEEE float32 WAV/WAVEX/RF64 and destination must be
new with an existing parent. The adapter writes stem WAVs and `result.json`,
with an 8 GiB total audio-output limit and 256 MiB additional free-space reserve.
Detailed hashes and timing/energy evidence are collected only for this explicit
export. The actual UTF-8 `result.json`, including its final newline, is limited
to 8 MiB. Completion follows closed and checked audio files and a successfully
written report; failure removes the new export directory.
Dry file export still reads and validates finite source PCM, writes bit-exact
float32 samples and collects the detailed report; its completion declares the
written speech output rather than requesting retained application storage.
These offline adapters record the implementation and interpreter actually used.
Their reports do not prove that a provisioned bundle's runtime snapshot executed
when the adapter used the checkout implementation instead.
Both Python entrypoints validate inference controls before constructing stream
input or creating export outputs. File export opens one source descriptor for
metadata, bounded hashing and PCM reads; replacement or in-place mutation rejects
the result. The independent reference loader captures PCM and its hash together,
so later pathname replacement cannot relabel the inference input. Model assets and
PCM/output protocol checks remain separate.


Standalone speech and separation share one worker setting, but each Python
manifest is bound to its own bundle's worker. Sharing an interpreter does not
make different bundle workers interchangeable. Select one Python operation at a
time, clearing the other manifest when switching; graph nodes instead carry
independent runtime settings. Replace all placeholder paths below with emitted
paths from the corresponding preparation:

[source,shell]
----
rivu processing neural '{"worker":"/absolute/new-moss-bundle/runtime/worker.py","speech_interpreter":"/absolute/.venv/bin/python","speech_manifest":"/absolute/new-moss-bundle/manifest.json","separation_manifest":null,"device":"cpu","threads":4,"speech_post_filter":false}'
rivu processing start 42 speech --wait
rivu processing neural '{"worker":"/absolute/kim/runtime/worker.py","separation_interpreter":"/absolute/.venv/bin/python","separation_manifest":"/absolute/kim/manifest.json","speech_manifest":null,"device":"cpu","threads":4}'
rivu processing start 43 separate --wait
----

MossFormer2's primary model card declares Apache-2.0; Kim's original trainer card
declares MIT. Preparation pins checkpoints and records weight evidence separately
from code permissions. DeepFilterNet3 retains actual provenance and unresolved
weight-permission facts, not synthesized grants. Review notices before
redistribution; provisioning grants no additional license.

`prepare.py --proxy` applies only to preparation, never inference. Do not put
proxy credentials in shared evidence, manifests or logs.

Speech controls include wet mix and attenuation limit; the optional post-filter
is supported only by DeepFilterNet3. Separation overlap controls model overlap,
not a quality guarantee. Python backends accept 8–192 kHz source rates; native
speech accepts 8–384 kHz. Speech accepts Front Center mono or Front Left/Front
Right stereo in that order, while separation requires that stereo layout. Other
speaker identities or permutations are rejected rather than guessed from channel
count. Speech channels are inferred independently, so stereo image can change.
Attenuation controls are backend-specific: MossFormer2 uses a spectral-mask floor,
DeepFilterNet3 uses its upstream dry/enhanced spectral blend, and native speech
uses its own time-domain dry/enhanced weighting. Equal control names do not imply
identical algorithms.
Inference rate conversion is explicit: 16 kHz for native speech, 48 kHz for Python
speech and 44.1 kHz for separation. Output preserves the original rate, layout
and exact frame count. No implicit downmix or duplicated mono separation is offered.

Speech Wet=0 copies dry PCM without executing a model or resampling. Input,
controls, manifest and artifact hashes are still validated. Native dry bypass
does not load ONNX Runtime. Python streaming still requires NumPy but skips
model-execution dependency checks; the Python file adapter also requires
SoundFile and records bypass/model-not-executed in `result.json`.

=== Tasks, retention and audition

Only one processing task runs at a time. `queued`, `rendering` and `processing`
are work phases; `complete`, `failed` and `cancelled` are terminal. A task need
not visit every phase. Start acceptance is not completion: `--wait` returns the
terminal result and fails on cancellation/error. Asynchronous callers use
`task status processing INSTANCE:ID` and `task cancel processing INSTANCE:ID`.
The returned nonzero decimal instance/task reference binds status, cancellation,
audition and export to the accepting service. Bare IDs are insufficient; a
restart cannot retarget an old reference to a new task.

Cancellation acknowledgement accepts the request, not worker retirement.
Cancellation invalidates publication and retires partial PCM; Python children
are terminated/reaped, while native ONNX checks between model frames and
resampling batches. Registered source/media changes invalidate publication, but
later configuration/graph edits cannot change the captured snapshot.
Starting another source, Stop or clearing the queue revokes pending automatic
audition even without physical playback. It does not cancel processing or erase
valid retained audio. Task status describes work; the selected-audio line
describes playback.

Numeric progress is coalesced at 100 ms and cannot accumulate behind a slow
consumer. Phase changes, graph-node stages and terminal results remain reliable.

Node-specific preparation errors identify that node. Failures or cancellations
during final graph compilation, rendering or output publication identify the
requested output node; an earlier node-specific error is not reported again.

Preparation/backend validation runs on workers, so accepted starts can fail
asynchronously; Queued may include waiting for retired audio's reservation.
Failure or unwinding produces a terminal result after neural child retirement.
Core rechecks cancellation/source identity before publication, commits terminal
state, then completes waits. Validation/admission failure does not revoke PCM;
later audition failure can mark an operation `failed` while leaving valid audio
available. Eviction changes availability, not the recorded outcome. Model nodes
retain independently known identity/hashes on failure; the operation remains a graph.

Manifest/decoder capabilities are checked before whole-source allocation or
native-prefix execution; runners still perform full artifact/runtime validation.
Native preparation checks cancellation between decoder calls, without a hard
deadline for decoder/filesystem operations. Retained audition rechecks the
registered decoder hint and media identity. Uncertain database/queue recovery
rejects it without replacing playback or committing a late stem-mix selection.

`task cancel processing INSTANCE:ID` also returns a matching selected audition to
Original after preparation has completed. For realtime/hybrid runs it marks the
task cancelled; stopping a cached offline audition leaves its completed status
intact. Current status, bounded task history and retained runs resolve the same
task record, including later audition or stem-mix failure.

Results are immutable shared in-memory PCM: node execution creates no processing
directory, intermediate WAV, request file or result report. A 512 MiB allocation
budget covers active, retained and retiring PCM, charging shared backing storage
once until its last owner releases it. Exhaustion fails explicitly without disk
spill. Decoder/DSP state, model weights, ONNX Runtime and Python workspace are
additional costs; the budget is not a process-RSS limit.
Outputs preserve the ordered speaker layout, sample rate and immutable frame
count through processing, mixing and audition; channel count alone is not a layout.
Graph model nodes retain only output ports needed by the selected target and
its remaining dependencies. Unneeded separation streams are still fully received
and validated, but do not accumulate retained PCM. Standalone separation retains
both stems for audition and mixing; graph fan-out retains both when required.

A successfully admitted non-export run releases unselected PCM/prepared runners
before worker allocation; selected audition audio remains pinned. Up to four
frozen run snapshots support recomputation after their PCM retires.
`graph_actions_available` describes snapshot addressability, separately from
cached output availability and task phase: failed/cancelled runs can remain
usable, and completed tasks can outlive both capabilities. GUI actions use that
capability. Exports preserve source handles but retain only a terminal receipt
and destination WAV, not another audition slot. Their `id` identifies the receipt;
`graph_run_id` identifies the frozen run for further actions. See
link:22_cache.adoc#processing-output-retention[Processing output retention].

Standalone restoration and native-only graphs share the native execution engine:
they decode blocks and retain only final PCM plus bounded DSP/delay state.
Uncached, entirely native exports instead stream to an
unpublished WAV without whole-output PCM; cached exports share existing PCM.
Model ancestors and Hybrid boundaries retain their PCM requirements. Export
checks the cached render's source stamp against the current source, never
relabeling old samples as a new source version.

Workers share full-graph validation and topology through an immutable graph borrow
for one run. Candidate planning still checks each boundary's dominance, format,
capabilities and budgets; only structural proof and execution-prefix order are
reused. Public planning validates all stored nodes, including controls outside the
selected output. Editing a graph requires a new proof, not revision-based cache reuse.

For fixed graph/format, native streaming export's output memory is independent
of duration; decoder, DSP/profile, delays and existing caches remain costs.
Synchronous native processing borrows format-checked decoder blocks until the
next mutable decoder operation, without caller staging copies. The boundary
also checks cancellation and opened-source identity at EOF; retained PCM and
DSP-owned buffers keep their own lifetimes.

Profile capture reads the required prefix, including upstream context/latency.
The initially opened decoder serves the first capture; each consumed decoder
retires before the next capture or output pass opens another, with the same
source-stamp and format checks. No unused output decoder spans capture passes.
An early stop validates cancellation/opened source without pretending it is EOF
or flushing tails. Actual decoded frames determine EOF even for unknown-duration
streams; real EOF flushes DSP context. File output discards causal preroll and
crops all tails to decoded source length, including FIR tails longer than latency.
Out-of-source profiles fail. Cancellation or source/destination validation failure
discards temporary exports; only Core publishes completed WAVs.

Neural graphs retain budgeted PCM at model boundaries. Before inference output
allocation, unreachable boundaries retire; aliases, source forks and remaining
branches retain the backing storage they need. Source format/frame metadata
outlives its retired PCM. Source media files are limited to 8 GiB; neural input
must be nonempty and at most four hours. Each Python source context window is
bounded to 128 MiB, excluding model weights/workspace.

Shutdown joins processing/reclamation workers; existing live PCM handles remain
valid until released. Original media and explicit exports are never reclaimed
as results.

[source,shell]
----
rivu task status processing INSTANCE:1
rivu processing audition INSTANCE:1 denoised
rivu processing audition INSTANCE:1 original
rivu processing audition INSTANCE:2 vocals
rivu processing audition INSTANCE:2 accompaniment
rivu processing audition INSTANCE:2 mix --vocal-gain-db -3 --accompaniment-gain-db 0
----

`INSTANCE` is a placeholder for the returned service identity. Speech uses the
`denoised` audition mode. Audition starts the original queue source if necessary
and hands off to aligned PCM; Original returns to source audio. Separation Mix
remixes retained stems, not a second inference or a stem export. Monitor EQ
remains active in both comparison paths. At matched levels, compare quiet words,
consonants, reverb, attacks and stereo ambience; stem summation or screenshots
do not establish listening approval.

Configuration tables and IPC integration are described in

=== Node graph CLI

`processing graph show` prints a readable graph summary, node IDs, connections,
and latest task. Add `--json` for the full `graph` object, including its `revision`,
nodes, positions and explicit port-to-port edges, plus `latest_task` (or null).
The latest task may belong to an older graph revision or a non-graph operation; it
is not the current graph's execution state. `processing show` summarizes playback
EQ, denoise, neural settings, graph and task; `--json` includes their complete
settings and presets. Node-local graph processing does not replace playback EQ.

Every `graph edit` takes one externally tagged `GraphEdit` JSON value and a
required `--expected-revision` matching the graph currently held by Core. Refresh after
each accepted edit or concurrent change; a stale revision is rejected rather
than overwriting another client's edits. Edits include `Add`, `Remove`, `Replace`,
`Move`, `Connect`, `Disconnect`, `Duplicate` and `ReplaceGraph`. Node kinds use
snake_case JSON names, and ports are zero-based. Quote the complete JSON argument
so negative gains and positions reach the parser unchanged.
The persisted graph is bounded to 64 nodes and 128 edges, including nodes outside
the selected ancestor closure.

For a fresh default graph (Source node 1, Output node 2, revision 0), this example
adds an explicit two-input mix, fans the source into both inputs, and connects the
mix to Output. Existing graphs may have different IDs or revisions: inspect them
first instead of replaying these edits blindly.

[source,shell]
----
rivu --json processing graph show
rivu processing graph edit --expected-revision 0 '{"Add":{"kind":{"mix":{"gains_db":[-6.0,-12.5],"muted":[false,false],"solo":[false,false]}},"position":[200.0,120.0]}}'
rivu processing graph edit --expected-revision 1 '{"Connect":{"from":{"node":1,"port":0},"to":{"node":3,"port":0}}}'
rivu processing graph edit --expected-revision 2 '{"Connect":{"from":{"node":1,"port":0},"to":{"node":3,"port":1}}}'
rivu processing graph edit --expected-revision 3 '{"Disconnect":{"to":{"node":2,"port":0}}}'
rivu processing graph edit --expected-revision 4 '{"Connect":{"from":{"node":3,"port":0},"to":{"node":2,"port":0}}}'
rivu --json processing graph run 42 2 --port 0 --mode offline --wait
----

`graph run TRACK_ID NODE_ID` snapshots the current graph and processes only the
selected output port's ancestor closure. `--port` defaults to 0; `--mode` accepts
`auto` (default), `offline`, `realtime` or `hybrid`. Auto first attempts an exact
native realtime plan, then a useful precomputed-prefix/live-suffix hybrid, then
offline rendering. It never changes algorithms. `settings.graph_mode` records
the actual selected mode; `settings.graph_boundary` identifies a hybrid boundary.
Explicit modes reject unsupported plans instead of silently changing modes.
Native realtime planning supports IIR/FIR EQ, non-Profile classical restoration,
Mix and Output; Profile capture and neural inference require an offline prefix
or fully offline execution. A native plan also has admission bounds: at most 32
channels, 64 MiB estimated state, two seconds of latency and 300,000,000
arithmetic-work units/second. These are planning limits, not measured device-deadline
guarantees. Heavier graphs can require Hybrid/Offline execution even when their
state fits in memory; an EQ configuration supported by the DSP crate alone can
still be rejected by the realtime graph planner. See
<<graph-resource-admission,Graph resource admission>> for effective-work accounting,
bypass rules and the scope of the state estimate.

Admission checks capability and budgets before allocating DSP state. A selected
plan can still fail numerical construction, in which case automatic selection
continues with the next candidate.

Hybrid has one cached boundary port, which every path into the live target must
cross. An uncached source branch or another separation port cannot use that
same stream. Planning/FFT preparation runs on the processing worker, not Core
dispatch or the device callback. Task references and `--wait` follow
<<tasks-retention-and-audition,the common task contract>>.

Realtime `complete` means an immutable live plan is prepared, not a rendered file:
`graph_outputs` is empty. Automatic audition still requires pending intent and
the captured playback generation. Offline/Hybrid may retain rendered outputs.
Cached node/port audition is immediate with no new task ID; uncached audition
starts a new run with its own ID. To export any retained snapshot, including
Realtime, use its instance-qualified reference and node/port:

[source,shell]
----
rivu task status processing INSTANCE:7
rivu processing graph audition INSTANCE:7 3 --port 0
rivu processing graph export INSTANCE:7 3 'rendered outputs/mix -6 dB.wav' --port 0 --wait
----

Results lists every output port in the frozen graph, not just cached ports or
the original ancestor closure. Calculate-and-audition/export can execute another
valid closure. Both cached and uncached actions recheck the registered source
and media identity; retained audio is not independent of the source.

Export starts a new task, copying cached output or rendering the requested
snapshot closure offline. Later editor changes affect neither path. Use the
acknowledgement's new `processing_id` (or `--wait`) for export completion, not the
original run ID.
`settings.graph_export_path` records the admitted destination with its parent resolved;
`graph_exported_path` is populated only after the completed export is published.
Export accepts a real filesystem path, including spaces; relative destinations
are anchored to the invoking client's working directory, not the core's. Choose
a new file in an existing directory; existing destinations are never overwritten.
The parent is resolved at admission so retargeting a directory alias cannot redirect
the export. The worker writes a temporary sibling only for this explicit export,
then commits without overwriting an existing destination after cancellation and
source checks. These checks do not guarantee safety against arbitrary concurrent
directory replacement. The output is float32 RIFF/WAVE with the actual speaker
mask and samples in ascending WAVE-speaker-bit order. RIFF size overflow fails
rather than switching to RF64; evaluation exports choose RIFF/RF64 per stem.
Publication requests no file or directory storage sync and does not guarantee
survival of power or operating-system failure; see
link:91_design_decisions.adoc#DEC-018[file publication policy].
In-memory results remain session-owned; source files are not modified.

== Ownership and invariants

Core owns committed configuration and result admission. Editors retain drafts
and interaction state, submitting typed, validated edits; graph commits require
the expected revision. Failed validation leaves committed settings unchanged.
JSON is a command-line/import representation, not a second configuration owner.

Page edits submit sparse patches; graph edits replace a node at its expected
revision. Draft acknowledgements and file-choice completions belong to the
window feature owner, target and edit generation. Hiding node parameters or retiring
a panel host invalidates native input frames and dismisses preedit, but preserves
drafts and submitted edit acknowledgements. Stale completions
cannot clear newer drafts, busy state or errors; programmatic synchronization is
not a user edit.

The processing service owns task records, retained outputs, audition selection
and physical worker retirement. Current selection, terminal history and retained
runs reference one status record per ID; published snapshots remain immutable.
Record retention is bounded by the current task, 32 terminal history entries and
four retained runs. Frozen run metadata survives PCM release, while resource
eviction updates availability without changing the recorded outcome.

Core owns cross-domain playback intent, cancellation/source admission and export
commit. Cancellation invalidates publication
without transferring worker ownership. Model runners return audio and provenance;
they do not own task status.

Prepared DSP owns its coefficients, history and stream format. Device callbacks
do no model loading, FFT planning or file I/O. Allocation, block work and retained
storage are bounded; long-running preparation stays on workers. Bypass, gain,
resampling and latency compensation are explicit, not silent quality fallbacks.

Realtime and offline graphs share bounded denoiser staging and EOF handling.
Padding drains delay rather than extending the source; short reads and ended
branches are zero-extended while downstream tails drain. Reset clears DSP history
and staging. Native/offline Mix uses `f64` gains and accumulation, rounding once
per node to finite `f32` without clipping or normalization. Realtime admission
includes reusable wide-sum scratch; processing allocates no mixing scratch.

Non-finite input or intermediate PCM fails without publishing partial audio;
finite over-range samples are preserved. A failed DSP/profile operation requires
reset before reuse because a finite prefix may have advanced history. Seeking,
source changes and incompatible formats reset history; pause does not advance it.
Source identity/settings bind results; playback generation and pending intent
independently govern automatic audition, as described in the workflow.

[[graph-resource-admission]]
=== Graph resource admission

Admission uses a lightweight plan before preparing DSP, delay lines or PCM blocks;
Auto/Hybrid candidates rejected for capability or budget allocate no DSP state.
The work estimate counts effective DSP: disabled/solo-excluded IIR bands and
identity peak/shelf sections consume no stage estimates. Disabled EQ and fully
bypassed restoration have no DSP latency/state, but edges and node buffers still
count. Restoration bypass means Wet=0, or spectral Off with both hum and repair
disabled. DSP construction, realtime/offline planning and status share this
configuration predicate. Validation and Profile requirements still apply; enabled
flat FIR retains convolution latency, and spectral Off does not bypass active
hum/repair.

Active restoration adds work independently of spectral mode: each enabled hum
harmonic adds 12 units per channel/frame. For impulse-repair width `W`, radius
`R=W+2` and `K=W+3` median differences, repair adds
`4*R + K*K + 24*W + 32` units per channel/frame for context, sorting and worst-case
search/interpolation, in addition to common restoration work. These are
conservative planning allowances, not instruction counts or measured CPU time.

The state estimate covers DSP objects/buffers, graph PCM blocks, wide summation
scratch and edge delay lines. Logical node PCM blocks are charged conservatively
even when pass-through outputs alias an upstream block. This is not total retained
process memory or RSS: graph topology/configuration containers, allocator metadata
and decoder/device state are outside the budget.

Restoration obtains its estimate from the DSP implementation without constructing
a processor or FFT plan. For block size `B`, channel count `C` and lookahead `L`
in frames, processor/staging charges are:

* Adapter: `(L+B)*C` output samples and `(2*L+B)*C` queue samples, totaling
  `(3*L+2*B)*C*4` bytes, plus the boxed adapter object (which already contains the
  denoiser and inline repair object).
* Active hum: one notch object and `C*2*8` state bytes per harmonic.
* Repair radius `R`: `(2*R+2)*C*4` context/frame bytes.
* Delayed partial-wet blend: `(L+1)*C*4` dry bytes; full Wet and zero-lookahead
  hum retain no dry queue.
* Spectral paths: channel/STFT and mode-specific PSD/gain arrays, plus a separate
  RustFFT power-of-two allowance of `2*N` complex scratch entries and `64*N` bytes
  for the two retained plan trees, where `N` is FFT size. This backend-specific
  allowance is not a multiplier over unrelated storage; changes to RustFFT or
  supported FFT sizes require reevaluating it.

Spectral modes retain one noise spectrum. Stationary and Profile reset preserve
that fixed spectrum; Adaptive reset fills its existing estimate from the configured
floor without allocating a recovery copy.

Bypassed graph nodes construct no adapter and incur none of these processor/staging
charges.

=== Timeline and source identity

Graph intermediates preserve causal context, including FIR ringing, denoiser
startup and branch delays. Only published audio is compensated/cropped to the
source timeline. Optional `graph_outputs[].context` describes guarded PCM with a
signed source-relative `start_frame`; hybrid suffixes consume it rather than the
trimmed audition slice. At EOF, each denoiser finishes at its actual upstream end
before tails propagate downstream; padding is not new source input.

Native ONNX speech completes FFT512/hop256 analysis frames by reflecting the
original signal at the endpoint, then crops synthesis to the source length.
References must match this padding, including short inputs and partial final hops.
Streaming resampling preserves length and independent channel state without
retaining a full model-rate intermediate.

Original audition validates the opened source descriptor; processed audition
uses immutable PCM handles. Waveform reuse follows exact PCM identity and slice
interval, not just matching path/format. Node failures identify the denoise node
for profile capture or the requested output for final compilation/decode/allocation.

=== DSP crate features

`rivu-dsp` defaults to configuration/validation only. Its optional `execution`
feature enables IIR/FIR, response sampling, denoising and `rustfft`; disabled APIs
are absent, not no-ops. The application and `rivu-audio` enable execution;
`rivu-format` does not request it, though Cargo feature unification can enable it
in a shared dependency graph. Examples `equalizer_benchmark` and `denoise_render`
require `--features execution`.

Disabled FIR allocates no convolution/FFT state. Restoration prepares only the
needed path: exact bypass for zero Wet or a disabled chain, time-domain state for
hum/repair, and STFT state for spectral modes. Configuration and required profiles
are validated even on bypass; delayed partial-wet processing retains dry alignment.

== Quality acceptance

=== Equalizer acceptance

Equalizer controls operate on one authoritative filter configuration. Their
presence alone does not establish numerical quality.

Numerical acceptance is based on independent transfer-function evaluation and
processed signals, not source-text or copied-value tests:

* Disabled processing is sample-exact and does not allocate in processing.
* At defined passband measurement points, steady-state measured response agrees
  with the declared transfer response within 0.1 dB. Nulls and startup transients
  are evaluated separately; dB comparisons at zero are undefined.
* Supported boundary rates, gains and Q values remain finite and stable under
  impulses, silence, tones and broadband input. No output sanitization hides
  unstable filter state.
* Reset eliminates old history; independent channels do not leak. Parameter
  changes are bounded continuous transitions, including bypass and solo changes.
* The displayed IIR response represents actual cascaded coefficients at the current
  sample rate. Frequencies beyond that rate's usable range are explicit. FIR
  acceptance measures the realized finite impulse separately from its displayed
  IIR magnitude target; target agreement alone is not realized-response evidence.

=== Denoising acceptance

Required modes cover stationary noise, a captured noise profile, adaptive noise,
speech-targeted enhancement, hum and impulse suppression. Controls must affect
real algorithm parameters, not relabel an identical preset. Suppression and
content preservation are evaluated separately.

Use clean references mixed with known noise at declared SNR, plus real noisy
recordings. Include speech consonants, quiet words, pauses, nonstationary noise,
music transients, sustained harmonics and stereo ambience. Record input/output
level, residual noise, reference distortion and speech intelligibility where a
valid reference exists. Stereo coherence and musical-noise artifacts require
additional listening; a high scalar score alone is not acceptance.

Ported neural inference must be compared against the selected upstream reference
using the same weights and parameters. An optimization may not silently replace
the model, alter rate handling or claim equal quality from throughput alone.

=== Separation acceptance

Evaluate both vocals and accompaniment against reference stems. Include backing
vocals, reverb, dense instrumentation, transients and stereo mixtures. Measure
source quality and leakage, absolute sample alignment, output length, stereo
coherence, block-boundary discontinuity and mixture reconstruction residual.
If accompaniment is defined as mixture minus vocals, exact reconstruction proves
that definition only; it does not prove separation quality.

Compare the integrated inference with its upstream algorithm under identical
weights, segment, overlap and seed settings before changing those settings for
speed. Synthetic independent components establish alignment/invariants, not
real-world vocal-separation quality. Multi-instrument stems and exporting stems
are not automatically added to the accepted scope.

=== Evidence and performance

An acceptance evidence bundle must record source revision, dirty changes,
executable/model hashes, configuration, corpus provenance/license, exact commands,
device and thread settings; a normal task status is not that evidence bundle.
Keep evaluation data and large outputs in task-owned `.cache/` paths. Never use
private library files without explicit permission.

Separate cold initialization, warm processing, file I/O and playback behavior.
Benchmark bypass, representative and worst supported configurations, and enabled
versus disabled feature branches. Report repeated measurements and variability:
wall/CPU time, real-time factor, block latency percentiles, peak resident memory,
allocations/capacity and underruns. End-to-end seek/cancel/shutdown behavior and
GUI controls require actual application smoke proof.

The Python benchmark and corpus evaluator report two distinct wall times.
`worker_subprocess_wall_seconds` covers only the worker subprocess call, including
startup and captured pipes. `evaluation_wall_seconds` ends after output reads,
artifact writes, scoring and record construction. In the repeated benchmark it
starts before each run's request creation; fixed reference/input/backing reads,
hashes, reference metric preparation and input scoring happen once outside the runs.
Each worker result must
identify that same input. In the corpus evaluator it starts before each sample's
reference/input/backing reads and request creation, including those reads and hashes.
Both exclude record append, progress printing, aggregate summaries and final report
serialization or writing. `timing_summary` summarizes each field separately;
compare only measurements with matching timing boundaries.

Evaluation hashes bracket each loaded PCM snapshot; changed identities and worker
input hashes that differ from the scored baseline fail the run rather than
retrying or mixing evidence. Reports identify the loaded reference, input, backing
and output snapshots, not later versions of those paths. Classical corpus runs
retain one reference per corpus and one noisy baseline per case across Stationary,
Profile and Adaptive. Each mode scores its final repeat independently; timing
repeats and their reports retain the existing boundaries. Profile capture uses
that same loaded noisy-clean pair.
The processing benchmark and corpus evaluator retain the worker's input-duration
contract; sharing identity capture does not impose the standalone quality tool's
12,000,000-frame admission bound.
Each processing benchmark retains prepared reference statistics across repeats.
Quality evaluation prepares each channel's projection, raw energy and DC once
per reference, sharing them across baseline and all candidate outputs, including
separation comparisons. Output-dependent errors and projections are not cached.
Preparation owns only summaries and weak-frame indices, borrowing unchanged PCM;
it does not cache by path. Per-output boundary checks still use that run's core
duration. Reduced scoring work is not model-inference speedup.
Scoring accumulates float64 conversion and residual scratch in bounded blocks.
Loaded full-track PCM, model workspace and outputs remain separate costs: bounded
metric scratch does not make the evaluation parent process duration-independent
or place it under the worker's PCM budget. Both tool families define stereo side
as `(L-R)/2`; historical processing-benchmark side RMS used `L-R` and is twice the
current amplitude definition.

Both tool families encode undefined scores/gains as JSON `null`. SNR requires
nonzero reference energy; SI-SDR requires nonzero mean-centered reference energy.
Exact reconstruction is `"infinity"` only when that condition holds. A constant
reference therefore has undefined SI-SDR/gain; a silent estimate has undefined
SI-SDR and zero gain for a nonconstant reference. Infinite-baseline gains can be
`"-infinity"`; infinity minus itself is undefined.

Summaries exclude undefined values, preserve infinity ordering, and report
defined/undefined and signed infinity counts. A median between opposite infinities
is undefined. These numerical cases do not establish quality.

The link:../tools/audio_quality/music_manifest.py[music corpus manifest contract]
records each prepared directory relative to the corpus root, explicitly binds
`diagnostic_only` to source identity and SHA256, and requires a `float` identity
(`path`, SHA256 and byte count) for each generated mixture, vocals and accompaniment
WAV. The evaluator checks the loaded PCM file snapshots against those prepared
identities before launching a model. Paired VoiceBank evaluation likewise consumes
the recorded clean/noisy `float` identities and requires complete manifest membership.
Recorded paths are provenance, not admission locations: a corpus can move without
its original containers or archives, but replacing prepared WAV content is rejected.
Directory numbering is not a diagnostic rule. During preparation, mark any known
reference erratum with repeatable `--diagnostic-source` paths; the marker follows
identical source bytes even when renamed or reordered. Run the following from the
repository root after binding the variables to actual local source files. The
output directory must not already exist; keep prepared corpora under `.cache/`:

[source,shell]
----
python tools/audio_quality/prepare_music.py "$al_james_source" "$other_source" \
  --diagnostic-source "$al_james_source" \
  --output .cache/new-music-float --provenance 'actual source and license'
----

Prepare a new corpus if its manifest lacks the required prepared-file identities;
incomplete legacy manifests are rejected. Keep recorded measurements bound to
their original corpus and timing definitions.

`tools/audio_quality/run_classical.py` requires a new output root and isolates each
corpus occurrence and case in its own numbered subdirectory, so repeated corpus
names and source stems do not share configurations, noise profiles or rendered
WAVs. Numbering is only an output namespace, not source identity. Consumers should
read the root `report.json` and follow each row's `estimate.path`; `reference` and
`noisy_baseline` retain the actual source paths and content identities.

Automatic metrics and actual listening are distinct evidence. No automated
analysis is reported as human listening. Missing listening approval remains an
explicit acceptance gap, even when objective and integration checks pass.

=== Native ONNX speech integration checks

Recorded synthetic comparisons used ONNX Runtime 1.23.2 CPU with the pinned
GTCRN and UL-UNAS graphs and an independent Torch STFT/ISTFT reference using
the same complete-hop reflection. Short inputs and partial final hops were
included. UL-UNAS's log-magnitude features amplify FFT roundoff near zero:
its constant one-sample extension differed by 6.39e-4, while feeding the exact
Rust spectrum to the Python runtime reduced the difference to 7.4e-11. This

=== Node graph measurements

`audio-graph-evidence/graph-baseline.json` and `graph-optimized.json` recorded
nine repetitions for each of 18 native graph workloads, excluding preparation,
copying, file I/O and device output. Untimed output comparisons were sample-exact
and processing allocated no additional storage. Timings did not show a uniform
speedup or establish physical-device deadlines.

`neural/graph-backend-evidence/comparison.json` covered three seconds of a MUSDB
AAC excerpt with Kim. Its mixture reconstruction checks the accompaniment
definition; one timing run is not a repeated performance estimate, quality ranking
or fullband/listening acceptance.

=== Implementation cost audit

Earlier records in `experiments/audio/classical-audit/`,
`experiments/audio/audio-implementation-audit/`, `audio-review-next/` and
`speech-optimize-20261023/` isolate native allocation, shared worker storage and
MossFormer2 numerical-processing costs. They do not measure whole-process RSS,
model-weight equivalence or device deadlines. Paired numerical checks preserved
outputs within their stated precision; timing did not establish a stable speedup.
Torch/Kaldi/DSP checks did not execute model weights or CUDA. Real-model regression
checks still require prepared manifests and matching interpreters; skipped tests
and environment-installation failures are not passes.
