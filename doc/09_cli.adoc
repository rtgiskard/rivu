= CLI
:toc:
:toclevels: 2

Start a shared instance with `rivu serve`, or open the GUI or TUI, before
issuing commands that control the shared player. Use `rivu play-file` to play a
local file independently. See link:00_getting_started.adoc[Getting started] for
installation, instance selection and data directories.

== Command conventions

anchor:cli-command-conventions[]
Control commands require a running core. `play-file`, `library probe`,
`library tags`, `playback devices`, and `processing setup` also work without
Core (`processing setup` contacts it only with `--activate`). Use `rivu -h` for
concise help, `rivu --help` for startup details, or a subcommand's `--help` for
arguments.

[cols="1,2",options="header"]
|===
|Option |Purpose
|`--data-dir DIRECTORY`
|Select the instance
|`--config FILE`
|Select startup/probe configuration
|`--log-level LEVEL`
|Override this process's stderr and enabled file logging: `debug`, `info`, `warning`, `error`
|`--json`
|Write results to stdout and Rivu runtime diagnostics as JSON to stderr; unavailable for GUI, serve and TUI. The external installer used by `processing setup` keeps its own stderr format.
|`-v`, `--verbose`
|Include additional text details, such as command revisions and audio diagnostics; does not change JSON results or logging
|===

[source,sh]
----
# Scan after configuring library roots
rivu library scan ~/Music --wait
rivu library list --query "artist"

# Control the current playback
rivu playback toggle
rivu playback volume 50
----

* *Success output:* Routine control commands are silent in text mode unless
  `-v` is set. Background task starts still print a task reference. Commands
  with a result, such as database optimization or a waited audio export, retain
  their result summaries.
* *Tasks:* `rivu task status KIND INSTANCE:ID` retrieves a task result, not
  proof that the task succeeded; inspect its phase and error. `rivu task cancel
  KIND INSTANCE:ID` requests cancellation (`KIND`: `scan`, `relocation`, or
  `processing`). Use the instance-qualified reference supplied by the command,
  not a bare numeric ID. Closing a waiting client does not cancel the task.
* *Completion:* Acceptance is not completion. For commands that support
  `--wait`, a received terminal result is written to stdout without separate
  acceptance or progress output, even if the task failed or was cancelled.
  A rejected start can return a failed acknowledgement instead; a timeout or
  connection failure while waiting may leave no terminal result. Inspect the
  task or saved state before retrying an uncertain outcome. Even an authoritative
  failure can report changes that were already committed.
* *JSON:* `--json` writes a command-specific result to stdout, including
  authoritative failure acknowledgements when available. Runtime diagnostics go
  to stderr as objects with `error` and, for transport command failures, `status`;
  an uncertain transport result does not invent a revision or task ID.
  Listings may stream an array (`playlist list`) or an object containing rows
  (`playlist show`, which also identifies the playlist and revision). Discard
  incomplete listing output on failure; check the exit status before using it.
* *Text output:* Control characters in metadata, paths, and diagnostics are
  escaped for display (for example, `\n`, `\t`, or `\x1b`); this does not change
  stored values or JSON data.
* *Exit status:* Success is 0, runtime failure is 1, and argument or usage
  errors retain Clap diagnostics and exit 2. A stdout write or final flush
  failure, including a closed pipe, exits 1 even if an operation took effect.
* *Paths:* Relative command-line filesystem paths use the invoking client's
  working directory, not the Core's; absolute paths are accepted. Rivu does
  not expand `~` or shell variables: let the shell expand `~/Music` or use
  `"$HOME/Music"`, not `"~/Music"`. Paths inside a playlist document have
  link:03_playlist.adoc#m3u-document-paths[their own base directory].

See also link:02_library.adoc#cli-output[Library result shapes],
link:21_ipc.adoc#request-failures-and-completion[IPC request outcomes], and
link:01_config.adoc#logging-and-diagnostics[logging and diagnostics].

[[play-file]]
== Play a local file once

[source,sh]
----
rivu play-file "$HOME/Music/example.flac"
rivu play-file --device 'PipeWire: your-device-name' "$HOME/Music/example.flac"
rivu play-file --speed 1.25 "$HOME/Music/example.flac"
----

The foreground process plays one local audio file once and exits with status 0
when playback finishes. `--speed` sets the initial multiplier from 0.5× to 2×.
In a foreground terminal, `{` and `}` lower and raise the speed by 0.05× and
print the new multiplier to stderr. Press Ctrl+C to stop early. File, decoder,
and output errors go to stderr and exit with status 1.

The command follows the system's default PipeWire sink unless `--device` selects
an exact name from `rivu playback devices` for this invocation. An unavailable
device causes playback to fail. The command reads the selected configuration for
volume, channel mixing, media read buffer, and FFmpeg access.
It starts its own PipeWire stream and leaves Rivu's library, queue, listening
history, and application files untouched. A running `rivu serve` continues to
manage its own playback. PipeWire can mix the two streams when they use the same sink.
