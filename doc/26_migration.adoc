= Database and configuration migration
:toc:
:toclevels: 2

== Scope and decisions

This document describes current-format validation, startup invocation, and the
offline migration execution boundary. The <<_future_historical_conversion>>
section defines requirements for additional conversions, not supported inputs.
Operational commands belong in
link:02_library.adoc#_sqlite_maintenance[SQLite maintenance] and
link:01_config.adoc#_saving_configuration[Saving configuration].

=== Current implementation

The database format is `4`; the independent configuration schema is `1`.

* `rivu-migrate check` validates current resources and reports supported database
  upgrades without changing them.
* `rivu-migrate apply` upgrades a validated format `2` database directly to `4` under
  offline ownership, retaining a durable SQLite backup. Current resources are left
  unchanged and do not create a backup.
* Format `4` stores playlist catalog order in `playlists.position`. Upgrading from
  format `2` initializes this order from playlist IDs and retains all playlist
  contents, playback statistics, indexes, and the playback queue.
* Missing default resources are reported without creating them; an explicitly
  selected missing database is an error. Unknown or malformed formats are rejected.
* A valid configuration without an explicit version is current and left untouched.

To inspect or upgrade an existing format `2` database before application
startup, stop Rivu and run the tool with the intended data directory and configuration:

[source,sh]
----
rivu-migrate --data-dir /path/to/data --config /path/to/config.toml check
rivu-migrate --data-dir /path/to/data --config /path/to/config.toml apply
----



=== Integration scope

The application operates on current formats. Before configuration-dependent
services or writable business operations, startup detects a database version
mismatch and invokes the independent tool as described in <<_application_invocation>>.
Normal database opening still initializes an empty database or requires the
current format; all historical recognition and conversion stay in the tool.

Non-goals are automatic downgrade, a migration plugin framework, distributed or
cross-file transactions, a recovery-state database, automatic paired restore,
changes to layout/cache formats, and invented conversions for undocumented history.

== Dependency and ownership boundaries

`rivu-format` owns the current database schema, configuration representation,
defaults, and validation, with no application or migration dependency. Its
optional `database` feature enables SQLite; configuration-only consumers such as
`rivu-audio` leave it disabled. Cargo feature unification can enable it in a
combined build. The application and migration tool both use this current contract.

The application owns runtime connections, caches, configuration I/O, Settings,
and Core/UI state. `rivu-migrate` independently owns offline preflight, backups,
and maintenance. Historical recognizers and conversions belong only in that tool,
not in `rivu-format` or normal application decoding and SQL.

`rivu-utils` shares logging and terminal diagnostics between the executables,
without depending on application configuration or database formats. The
application supplies logging options at startup and when settings change.

Migration progress uses `info` events and failures use `error`, following the
link:01_config.adoc#_logging_and_diagnostics[normal logging rules]. The tool's
result and backup summaries remain on stdout; it does not create log files.

For contract tests, use `cargo test -p rivu-format --no-default-features`;
add `--features database` for schema and trigger behavior.

== Version authority

=== Database schema

The singleton `rivu_meta` row stores `format_version` and
`current_queue_entry_id`. The version describes persistent structure and
interpretation, not the application release or a count of writes. The current
queue occurrence references unified `playlist_entries.id` with `ON DELETE SET NULL`;
runtime storage accepts only occurrences belonging to the system queue.
New databases create format `4` directly, without historical migrations.


Offline preflight checks required tables and readable columns, primary and unique
keys, index properties and usability, the queue singleton, and required trigger
names. Before a migration transaction commits, its complete user-defined schema
is also compared with a fresh database created by the current schema authority.
Tables, indexes, views, and triggers must have the same identities and definition
tokens, including columns, defaults, constraints, and expressions. Whitespace and
unquoted token case are ignored; quoted identifiers and literal contents remain
exact. Equivalent hand-written schema rewrites can therefore be conservatively
rejected. Unexpected objects or definitions fail with the object name and roll
back the migration; unknown objects are not silently deleted. Current-format
resources use this same strict check without rewriting or creating a backup.
SQLite-owned internal objects are excluded, and file bytes and size need not match.
This is not a full integrity check or validation of stored derived-summary data.
Normal application opening uses the cheaper format guard rather than repeating
offline structural preflight.

A missing version is not evidence of a known oldest schema. Unknown, future, or
malformed formats are rejected; changing a marker does not make them current.

Empty-database detection ignores only SQLite's literal `sqlite_` table prefix.
Other user tables without a supported Rivu marker cause rejection, not initialization.

=== Configuration schema

The current configuration schema is `1`. A top-level integer `schema_version` is
optional: omission means the current schema, not an inferred historical version.
Missing files retain the normal application defaults. New serialization writes
an explicit current version; format-preserving saves retain an omitted version.
Loading never rewrites a file to add one.
Database and configuration versions evolve independently of each other and of
the software release number.

The application and tool strictly validate current configuration without decoder
guessing or historical aliases (`format_version` is not an alias). Explicit
noncurrent versions are rejected before current-field decoding; malformed TOML
and file I/O retain their distinct causes. The tool never rewrites configuration,
creates its backup, or takes a configuration writer lock. See
link:01_config.adoc#_saving_configuration[Saving configuration] for persistence.

== Persistent summaries and runtime authority

`albums` and `album_artists` are persistent derived summaries maintained by four
SQLite triggers. They belong to the database format, not an independently revised
cache; future changes must handle both existing summaries and subsequent writes.

Queue and playlists share `playlist_entries`. The protected system playlist
`(id = 0, name = '')` is hidden or rejected by ordinary playlist APIs. Each entry
has a globally unique occurrence ID and a contiguous collection-local position;
repeated track IDs are valid. Copies preserve order and multiplicity without
linking later collection edits. Indexed position and track-reference lookups
support this model; there is no separate queue table or persisted queue-ID array.

Core owns queue and album revisions, playlist content/lifetime tokens and their
issuing sequence in memory. They are reconstructed at startup and never persisted.
Normal queries and state publication do not synchronize tokens from SQLite.

Runtime business writes must be coordinated by Core. Background saves use their
own connections under the existing save gate; external writes while Rivu runs
are unsupported. Stop Rivu before modifying its database with another tool.
Confirmed commits advance affected tokens before fallible projection refreshes;
rollbacks and no-ops do not advance them. Unknown worker outcomes close database
business operations until restart, including shutdown database saves, rather than
replaying writes or guessing the result.

== Target selection and exclusion

The tool accepts data-directory and configuration-file overrides using the same
selection rules as the application. A configuration path alone does not determine
the library path. The chosen database and resolved configuration destination remain
fixed throughout one operation; conversion must not redirect the operation midway.
An explicitly selected missing library is an error, not permission to create an
empty replacement database.

`check` opens SQLite read-only and does not create application directories, writer
lock files, backups, or perform maintenance or format conversion. SQLite may still
create or update WAL shared-memory sidecars for reader coordination; read-only does
not mean zero filesystem activity. Its result is advisory, not a reservation.
`apply` rechecks under ownership before changing formal resources.

Apply takes the application's device/inode-based data-directory ownership,
independent of path spelling and protocol version, so aliases share one exclusion
domain. The migration process does not serve or acknowledge IPC commands.

Directory ownership does not protect configuration shared by different data
directories, and external SQLite writers are outside advisory exclusion. Stop
external database writers during maintenance. The tool only reads configuration,
preserving existing bytes and symlinks, and cannot overwrite an application writer.
Normal save destinations, symlink handling and last-writer-wins behavior belong to
link:01_config.adoc[Configuration and layout]. A check reserves neither database
ownership nor configuration against later edits.

Configuration admission uses the application's ordinary-file rules and 4 MiB
UTF-8 TOML limit; symlinks are accepted and FIFOs rejected without waiting.
Reports escape control characters without changing literal paths. Argument errors
preserve clap's usage layout, output stream, and exit status.

== Apply protocol

The supported `apply` command upgrades validated format `2` databases
directly to `4`. The independent tool admits the source format before applying
its conversion. Current-format resources return unchanged. Configuration remains
read-only. Every database change follows this protocol:

. Acquire data-directory ownership and fix the selected targets.
. Recheck database structure and readability and strictly validate configuration.
. Create a unique SQLite backup, sync its contents, publish its final `.bak` name
  without replacement, and sync its parent directory before permitting a write.
. Apply the change, its validation, and authoritative markers in one transaction.
. Report the outcome and actual backup paths. Do not start the application,
  rewrite configuration, or delete backups.

SQLite's backup API includes committed WAL contents; copying a live database file
alone is not a consistent backup. Publication proceeds from `.bak.partial` to
`.bak`, with these reported durability states:

* `unpublished; may be incomplete`: the retained partial file is not a restore point.
* `published; directory sync uncertain`: the final name exists, but its directory
  durability is unconfirmed.
* `complete; file and directory synced`: database maintenance may start.

Failures retain evidence, including any partial alias left by no-overwrite
publication, and never trigger automatic restoration. The transaction has its own
durability boundary; this is not a cross-resource commit protocol.

Backup and transaction/WAL growth consume disk space. Preflight checks an advisory
capacity estimate on the database filesystem; later storage errors still fail.
Large data transformations stay in SQLite rather than whole-library Rust buffers.
No media scanning, network access, decoder probing, or inferred user intent belongs
in migration unless a specific released conversion requires it.

== Failure and reentry

The database transaction is the only formal mutation boundary in the current tool;
configuration remains unchanged on both success and failure.

* Preflight or backup failure does not authorize modifying a formal resource.
* Database transaction failure rolls back that transaction.
* When a commit outcome is uncertain, inspect the actual persisted version and
  structure rather than blindly replaying a mutation.
* Current resources are no-ops: no rewrite, repeated transformation, or backup.

Persisted versions and actual resource state determine reentry; there is no step
journal or automatic rollback engine. Backups never overwrite earlier ones and
are not an automatic paired restore point. Manual restoration requires choosing
the appropriate backup with all writers stopped.

Errors report targets, retained backups, and known completed changes; failure is
not a guarantee that nothing changed. Never recover by resetting data, substituting
defaults, or blindly replaying an uncertain commit.

== Acceptance boundaries

Acceptance must cover unversioned current configuration without rewriting values,
comments, or symlinks; strict rejection of noncurrent explicit versions and invalid
inputs with useful causes; missing-resource behavior; database user-state preservation;
transaction failures and reentry; current-resource no-ops; backups retained across
retries; directory aliases; and data-directory ownership exclusion. These are
acceptance requirements, not a record of executable checks performed by this document.

Actual executable proof runs the migration command and then uses its output with
the application to load settings and query/write the database. Unit tests and
compilation alone do not prove that integration. The application dependency graph
must contain no migration package or historical decoder.

== Future historical conversion

The supported source format `2` upgrades directly to the current format `4`;
format `3` is not a supported historical format. Version numbers need not be
consecutive. Additional conversions require evidence
of the source structure and interpretation; missing or invalid versions do not
authorize guessing. Database changes need a deliberate schema-version decision
and must validate the source and target structure and user data before updating
the marker in the same transaction. An incompatible database cannot be made
current by merely changing its marker.

Each conversion must explicitly remove known obsolete tables, indexes, and columns
inside the migration transaction and verify their absence before committing.
Unknown objects are not garbage to delete. The current `2` to `4` conversion adds
playlist catalog positions; it does not retire any format `2` table, index, or
column, so no removal is needed for this conversion.

Configuration conversion additionally needs a source contract for omitted settings
so current defaults cannot redefine historical intent. It must define its own
mutation and recovery boundaries; the database protocol does not make both files
atomic. All historical rules remain in the independent tool.

== Application invocation

On a database version mismatch, GUI and headless host startup automatically run
`rivu-migrate --data-dir DATA --config CONFIG apply` with the resolved host paths.
The executable is selected beside the running `rivu` binary when present,
otherwise from `PATH`. Current or empty databases do not invoke it.

Startup first acquires data-directory ownership and inspects the database through
a short-lived read-only connection. It closes that connection and releases ownership
before invoking the tool, which acquires its own exclusive ownership. After the
child exits successfully, startup reacquires ownership and verifies the current
format through a fresh connection. If another instance acquires ownership during
this handoff, startup fails rather than proceeding without ownership or retrying.
No skip-lock option or historical decoder is added to the application.

Missing executables, failed conversion, or a noncurrent result stop startup before
configuration, database business connections, and audio initialization. Failure
never triggers data reset, automatic restoration, or blind retry.
