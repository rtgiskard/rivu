= Database and configuration migration
:toc:
:toclevels: 2

== Scope and decisions

This chapter defines format authority, startup handoff and offline conversion.
<<_future_historical_conversion,Future conversions>> are requirements, not supported
inputs. See link:02_library.adoc#_sqlite_maintenance[SQLite maintenance] for database
operations and link:01_config.adoc#_saving_configuration[configuration saving].

=== Current implementation

The database format is `4`; the independent configuration schema is `1`.

`rivu-migrate check` validates without conversion; `apply` upgrades validated
database format `2` directly to `4`, retaining a durable SQLite backup. The upgrade
adds `playlists.position` in playlist-ID order and preserves contents, playback
statistics, indexes and queue state. Current resources remain unchanged without
a backup; configuration is always read-only.

Missing default resources are reported without creation; an explicitly selected
missing database is an error. Unknown or malformed formats are rejected. Valid
unversioned configuration is current and remains untouched.

To inspect or upgrade an existing format `2` database before application
startup, stop Rivu and run the tool with the intended data directory and configuration:

[source,sh]
----
rivu-migrate --data-dir /path/to/data --config /path/to/config.toml check
rivu-migrate --data-dir /path/to/data --config /path/to/config.toml apply
----

`check` exits `0` when no conversion is needed, `1` for a supported upgrade, or `2`
on failure. `apply` exits `0` on success or a no-op, otherwise `2`. Reports and backup
paths go to stdout, diagnostics to stderr. Check reserves nothing; Apply revalidates.

=== Integration scope

Normal application opening initializes empty databases or requires the current
format. Historical recognition and conversion belong only to the independent tool.
Downgrade, cross-file transactions, paired restore, layout/cache conversion and
undocumented historical conversions are outside this contract.

== Application invocation

On a database version mismatch, GUI and headless startup run
`rivu-migrate --data-dir DATA --config CONFIG apply` with resolved host paths,
selecting the executable beside `rivu` or otherwise from `PATH`. Current and empty
databases skip this step.

Startup acquires data-directory ownership for read-only inspection, closes the
connection and releases ownership before invoking the tool. After child success,
it reacquires ownership and checks the format through a fresh connection. Losing
ownership during this handoff, a missing tool, failed conversion or a noncurrent
result stops startup before configuration, business connections or audio initialize.
There is no blind retry, data reset or automatic restoration.

== Dependency and ownership boundaries

`rivu-format` owns current schemas, defaults and validation without application or
migration dependencies. Its optional `database` feature enables SQLite;
configuration-only consumers leave it disabled, subject to Cargo feature unification.
Both executables use this authority.

The application owns runtime connections, caches, configuration I/O and Core/UI
state. The tool owns offline preflight, backups and historical conversions; these
do not enter normal decoding or SQL. `rivu-utils` shares logging and terminal
diagnostics without depending on configuration or database formats.

Run `cargo test -p rivu-format --no-default-features` for configuration contracts;
add `--features database` for schema and trigger behavior.

== Version authority

=== Database schema

`rivu_meta.format_version` identifies structure and interpretation, independently
of releases or write counts. Its singleton also stores `current_queue_entry_id`,
referencing system-queue `playlist_entries.id` with `ON DELETE SET NULL`.
New databases create format `4` directly.


Offline preflight checks tables, readable columns, primary/unique keys, usable
indexes, the queue singleton and required triggers. Before migration commits,
all user-defined schema objects must also match a fresh current database by
identity and definition tokens. Whitespace and unquoted token case are ignored;
quoted identifiers and literals remain exact. Equivalent hand-written schemas
can be conservatively rejected. Unexpected objects fail with their names and roll
back conversion rather than being deleted. Current resources undergo the same
strict target check without rewriting or backups.

SQLite-owned objects and file-byte equality are excluded. This is not a full
integrity or derived-data check; normal application opening uses the cheaper
format guard. Empty detection ignores only the literal `sqlite_` table prefix.
Other unversioned tables, unknown or future formats are rejected: changing a marker
cannot establish compatibility.

=== Configuration schema

Configuration schema `1` permits an omitted `schema_version`, meaning current,
not historical. Missing files use defaults. New serialization includes the version;
format-preserving saves retain its omission, and loading never adds it. Database,
configuration and application versions evolve independently.

Explicit noncurrent versions are rejected before field decoding; malformed TOML
and I/O retain distinct causes. There are no historical aliases. The tool neither
rewrites nor backs up configuration and takes no configuration writer lock; see
link:01_config.adoc#_saving_configuration[Saving configuration].

== Persistent summaries and runtime authority

`albums` and `album_artists` are trigger-maintained persistent summaries, part of
the database format rather than independently versioned caches. Conversion must
handle existing data and subsequent trigger behavior.

Queue and playlists share ordered `playlist_entries`; the protected system
playlist is `(id = 0, name = '')`. Occurrence identity, multiplicity, runtime
revision tokens and coordinated writes follow
link:21_ipc.adoc#_business_ownership_and_transactions[Core/Store transaction ownership].
Runtime tokens are not persisted. External writes require stopping Rivu first.

== Target selection and exclusion

Target selection follows the application's
link:../readme.adoc#_files_and_data_directories[path rules]; `--config` alone does
not select a database. Targets remain fixed for one operation, and an explicitly
selected missing database is an error.

Check opens SQLite read-only without creating application directories, writer
locks or backups. SQLite may still update WAL shared-memory sidecars. Its result
is advisory. Apply revalidates under the same device/inode-based data-directory
ownership as the host, so directory aliases share exclusion independently of path
spelling or protocol version. The tool does not serve IPC.

This advisory exclusion does not cover external database writers or configuration
shared by different data directories. Stop external writers for maintenance;
configuration remains read-only, preserving bytes and symlinks. Its ordinary-file
admission and 4 MiB UTF-8 TOML limit follow
link:01_config.adoc#_file_access_and_external_editors[Configuration file access].

Reports escape control characters without changing paths; argument errors retain
clap's layout, streams and status. Progress uses `info`, failures `error`, under
link:01_config.adoc#_logging_and_diagnostics[normal logging rules]. The tool creates
no log files.

== Apply protocol

Current databases are no-ops and configuration stays read-only. A supported
database conversion follows this protocol:

. Acquire data-directory ownership and fix the selected targets.
. Recheck database structure and readability and strictly validate configuration.
. Create a unique SQLite backup, sync its contents, publish its final `.bak` name
  without replacement, and sync its parent directory before permitting a write.
. Apply the change, its validation, and authoritative markers in one transaction.
. Report the outcome and actual backup paths. Do not start the application,
  rewrite configuration, or delete backups.

SQLite's backup API includes committed WAL contents; copying a live database file
alone is not a consistent backup. Publication proceeds from `.bak.partial` to
`.bak`, with these reported durability states:

* `unpublished; may be incomplete`: the retained partial file is not a restore point.
* `published; directory sync uncertain`: the final name exists, but its directory
  durability is unconfirmed.
* `complete; file and directory synced`: database maintenance may start.

Failures retain partial evidence and never trigger restoration. Backup durability
and the migration transaction are separate boundaries, not a cross-resource commit.
Backup and transaction/WAL growth need disk space; preflight's capacity estimate
is advisory and later storage errors still fail. Transformations remain in SQLite,
without whole-library buffers, scanning, network access or decoder probing.

== Failure and reentry

Only the database transaction mutates formal resources; configuration stays
unchanged. Preflight or backup failure permits no mutation, and transaction failure
rolls back. For an uncertain commit, inspect persisted version and structure before
retrying. Current resources need no rewrite, transformation or backup.

Persisted state determines reentry; there is no step journal or rollback engine.
Backups never replace earlier ones. Manual restoration requires selecting the
appropriate backup with all writers stopped. Errors report targets, backups and
known completed changes: failure does not imply nothing changed. Never recover by
resetting data, substituting defaults or replaying an uncertain mutation.

== Acceptance boundaries

Acceptance covers unchanged unversioned configuration (including comments and
symlinks), strict version/input rejection, missing resources, preserved user data,
transaction failure/reentry, no-ops, retained backups, directory aliases and ownership
exclusion. These are requirements, not a record of checks run by this document.

Integration proof must run the tool, then load settings and query/write its database
with the application. Unit tests or compilation alone are insufficient. The
application dependency graph must contain no migration package or historical decoder.

== Future historical conversion

Only source format `2` upgrades to `4`; `3` is not a supported historical format.
Additional conversions require evidence of source structure and interpretation,
a deliberate version decision, and validation of source, target and user data.
The marker advances within the conversion transaction, not as a compatibility fix.

Known obsolete schema objects must be removed transactionally and their absence
verified; unknown objects must not be deleted. The current conversion only adds
catalog positions and retires no format `2` object.

Configuration conversion needs a source contract for omitted settings so new
defaults cannot redefine historical intent. It must define separate mutation and
recovery boundaries; database atomicity does not cover both files. Historical
rules stay in the independent tool.
