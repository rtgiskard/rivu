= Database and configuration migration
:toc:
:toclevels: 2

== Scope and decisions

This document describes current-format validation and the offline migration
execution boundary. The separate <<_future_historical_conversion>> and
<<_future_application_invocation>> sections define design requirements, not
additional supported inputs or startup behavior.
Operational commands belong in
link:02_library.adoc#_sqlite_maintenance[SQLite maintenance] and
link:01_config.adoc#_configuration_upgrades[Configuration upgrades].

=== Current implementation

The database format is `2`; the independent configuration schema is `1`.

* `rivu-migrate check` validates existing current configuration and database formats.
* `rivu-migrate apply` repeats validation under offline ownership. The current
  release baseline has no migration steps, so current resources are left unchanged
  and no backup is created.
* Populated databases with missing or noncurrent format metadata are rejected,
  not upgraded or reset. No historical conversion is implemented.
  A valid configuration without an explicit version is current and left untouched.


=== Integration scope

The application operates on current formats only. Historical recognition and
conversion belong to an independent migration executable. Isolation is a dependency
and responsibility boundary, not a prohibition on invoking another process.

The application does not invoke the tool during startup. Normal database opening
creates current structures only for an empty database and otherwise requires the
current format. A later startup integration may invoke the
executable before business initialization without moving historical rules into
the application.

Non-goals are automatic downgrade, a migration plugin framework, distributed or
cross-file transactions, a recovery-state database, automatic paired restore,
changes to layout/cache formats, and invented conversions for undocumented history.

== Dependency and ownership boundaries

`rivu-format` owns the current disk contracts: database version and current schema,
configuration representation, necessary value types, defaults, and validation.
It has no dependency on the application, UI, audio engine, or migration package.
Current defaults and validation share this implementation rather than a second
configuration model with different rules.

The package has no default features. Its `database` feature enables the database
module and SQLite dependency; the application and `rivu-migrate` explicitly enable
it. `rivu-audio` leaves it disabled, so its standalone dependency graph uses the
configuration and file-admission contracts without pulling in SQLite. Cargo may
unify `database` when these consumers are built together; the application still
requires SQLite.

Run `cargo test -p rivu-format --no-default-features` for the non-database contracts,
and add `--features database` to include schema and trigger behavior tests.

The application depends on that current contract. Runtime owners, connection caches,
Settings patches, Core, and UI remain application responsibilities. Application
configuration I/O is distinct from the shared configuration representation.

`rivu-migrate` depends on the current contract, not the application. It owns offline
preflight, backups and maintenance filesystem operations, validating results against
the same current contract as the application. Future historical recognizers and
conversion steps must stay within this boundary. Neither the application nor
`rivu-format` depends on migration code.

No historical aliases, version-specific decoders, or old-schema SQL may leak into
normal business operations. Generic resource exclusion and current-format validation
are not historical compatibility logic.

== Version authority

=== Database schema

The singleton `rivu_meta` row stores `format_version` and
`current_queue_entry_id`. The version describes persistent structure and
interpretation, not the application release or a count of writes. The current
queue occurrence retains its foreign key with `ON DELETE SET NULL`.
New databases create the current format directly, without historical migrations.


Offline preflight checks required tables and readable columns, primary and unique
keys, index properties and usability, the queue singleton, and required trigger
names. It does not rely on a version stamp alone or compare SQL text for exact
spelling. A failed structural check is rejected, not repaired by installing
current triggers. This is not a full integrity check or proof of trigger semantics
and derived-summary correctness. Normal application opening uses the cheaper
format guard rather than repeating offline structural preflight.

A missing version is not evidence of a known oldest schema. Unknown, future, or
malformed formats are rejected; changing a marker does not make them current.

Empty-database detection excludes only tables whose names begin with the literal
`sqlite_` internal prefix. Names such as `sqlitex_data` are user tables, not SQLite
internals: without a supported Rivu version marker, such a populated database is
rejected and preserved rather than initialized as an empty library. This rule is
shared by application opening and offline inspection.

=== Configuration schema

The current configuration schema is `1`. A top-level integer `schema_version` is
optional: omission means the current schema, not an inferred historical version.
Missing files retain the normal application defaults. New serialization writes
an explicit current version; format-preserving saves retain an omitted version.
Loading never rewrites a file to add one.
Database and configuration versions evolve independently of each other and of
the software release number.

The application decodes only the current configuration schema. A valid unversioned
document is current and requires no migration. Parsing and validation remain strict.
Parsing and validation failures retain their specific causes. Malformed TOML
cannot establish a version and must be corrected first. File I/O failures are not
version failures. Explicit noncurrent versions are rejected before decoding
current fields; no decoder guessing or historical aliases are allowed.

The current migration tool validates configuration without conversion, backups,
writer locks, or replacement. `format_version` is not an alias. User-facing loading,
saving and upgrade guidance is authoritative in
link:01_config.adoc#_configuration_upgrades[Configuration upgrades].

== Persistent summaries and runtime authority

`albums` and `album_artists` remain derived summaries maintained by their existing
four SQLite triggers and indexes. Their definitions belong to the database format;
there is no independent trigger-maintenance revision. A future persistent trigger
change must account for both future writes and already stored summaries.

The seven application tables are `tracks`, `playlists`, `playlist_entries`,
`queue_entries`, `rivu_meta`, `albums`, and `album_artists`.
Core owns queue and album revisions, playlist content/lifetime tokens and their
issuing sequence in memory. They are reconstructed at startup and never persisted.
Normal queries and state publication do not synchronize tokens from SQLite.

Runtime business writes must be coordinated by Core. Background saves use their
own connections under the existing save gate; external writes while Rivu runs
are unsupported. Stop Rivu before modifying its database with another tool.
Confirmed commits advance affected tokens before fallible projection refreshes;
rollbacks and no-ops do not advance them. Unknown worker outcomes close database
business operations until restart, including shutdown database saves, rather than
replaying writes or guessing the result.

== Target selection and exclusion

The tool accepts data-directory and configuration-file overrides using the same
selection rules as the application. A configuration path alone does not determine
the library path. The chosen database and resolved configuration destination remain
fixed throughout one operation; conversion must not redirect the operation midway.
An explicitly selected missing library is an error, not permission to create an
empty replacement database.

`check` opens SQLite read-only and does not create application directories, writer
lock files, backups, or perform maintenance or format conversion. SQLite may still
create or update WAL shared-memory sidecars for reader coordination; read-only does
not mean zero filesystem activity. Its result is advisory, not a reservation.
`apply` rechecks under ownership before changing formal resources.

Apply excludes an application instance through the existing data-directory identity
ownership mechanism. Device/inode identity, rather than path spelling or a new
protocol-version-dependent name, keeps directory aliases and existing application
binaries in the same exclusion domain. The migration process is not a normal IPC
service and must not pretend to acknowledge application commands.

Directory ownership does not protect configuration shared by different data
directories, and external SQLite writers are outside advisory exclusion. Stop
external database writers during maintenance. The tool only reads configuration,
preserving existing bytes and symlinks, and cannot overwrite an application writer.
Normal save destinations, symlink handling and last-writer-wins behavior belong to
link:01_config.adoc[Configuration and layout]. A check reserves neither database
ownership nor configuration against later edits.

Configuration preflight uses the same ordinary-file admission and 4 MiB UTF-8
TOML limit as the application, including symlinks, and rejects FIFOs without
waiting for a writer. Human-readable reports escape control characters in paths
and error chains, and argument errors escape untrusted command-line values while
preserving clap's usage layout, styling, output stream and exit status. These
escapes do not change literal filesystem paths; help and version output retain
their normal formatting.

== Apply protocol

. Acquire data-directory ownership and select the fixed targets.
. Reinspect versions, database structure, and readability; strictly validate existing
  configuration before mutating the database.
. Before changing the database, copy it into a unique `.bak.partial` file, close
  SQLite and sync the file, publish the final `.bak` name without overwriting an
  existing file, then sync its parent directory. Report the actual location and
  completion state. Do not back up a resource that will not be changed.
. Execute the selected migration and update its authoritative markers in one
  SQLite transaction. The current baseline supplies no conversion steps.
. Return success only when the selected existing resources meet current contracts.
  Do not start the application, rewrite configuration, or delete backups as a side effect.

A SQLite backup uses SQLite's backup API so committed WAL contents are included.
Copying only a live database file is not a consistent backup. Backup completion
and database transaction durability require their own handling; no configuration
write or cross-resource commit protocol is involved.
An `unpublished; may be incomplete` report identifies the retained partial file;
it is not a completed restore point. `published; directory sync uncertain` means
the final name was published but its directory durability is not established.
Only `complete; file and directory synced` permits database maintenance to start.
Failures preserve the actual artifact path, including a complete-content partial
alias if a no-overwrite publication fallback leaves one. They do not delete
evidence or trigger automatic rollback.


Migration execution must not scan the music library, access the network, probe
decoders or infer missing user intent unless a specific released conversion
requires it. Its costs include the database backup and SQLite transaction/WAL
growth. Large database work stays in SQLite rather than copying the library into
Rust collections. Before backup, preflight checks available capacity on the
database destination filesystem, including backup and transaction overhead.
Capacity estimates are advisory: other writers can consume space, so runtime
storage errors remain errors rather than an excuse to drop data. No speedup is
implied by this separation.

== Failure and reentry

The database transaction is the only formal mutation boundary in the current tool;
configuration remains unchanged on both success and failure.

* Preflight or backup failure does not authorize modifying a formal resource.
* Database transaction failure rolls back that transaction.
* When a commit outcome is uncertain, inspect the actual persisted version and
  structure rather than blindly replaying a mutation.
* Current resources are no-ops: no rewrite, repeated transformation, or backup.

Versions and actual resource state determine remaining work. There is no separate
step journal, backup manifest, upgrade-group registry, or automatic rollback engine.
Backups never overwrite earlier backups, including across retries. They are database
execution backups, not a promise of automatic restoration to one software-upgrade
boundary. Manual restoration must select an appropriate original backup with all
writers stopped.

Errors identify the failed operation, affected targets, available backups, and any
known already-completed changes. A failure must not be presented as a guarantee that
nothing changed. The tool must not suppress an error by resetting data or falling
back to application defaults.

== Acceptance boundaries

Acceptance must cover unversioned current configuration without rewriting values,
comments, or symlinks; strict rejection of noncurrent explicit versions and invalid
inputs with useful causes; missing-resource behavior; database user-state preservation;
transaction failures and reentry; current-resource no-ops; backups retained across
retries; directory aliases; and data-directory ownership exclusion. These are
acceptance requirements, not a record of executable checks performed by this document.

Actual executable proof runs the migration command and then uses its output with
the application to load settings and query/write the database. Unit tests and
compilation alone do not prove that integration. The application dependency graph
must contain no migration package or historical decoder.

== Future historical conversion

No historical database or configuration conversion is implemented. A future
supported format needs evidence of its actual source structure and interpretation;
an absent or invalid version is not permission to guess. Recognition and conversion
rules belong in the independent tool, never in normal application decoding or SQL.

Changes to persistent tables or their interpretation require a deliberate database
schema-version decision. A supported conversion must transform actual structure
and data, validate constraints and update the authoritative version in the same
transaction. Merely stamping a version number is not migration. Deterministic local
conversion must not scan media, use the network or invent missing user intent.

Configuration conversion needs its own source contract, including the meaning of
omitted settings; today's defaults must not silently redefine historical intent.
It would add mutation and failure boundaries absent from the current read-only
configuration path and must define those before implementation. The current
database backup/transaction protocol is not a cross-resource commit guarantee.

== Future application invocation

The application may detect a noncurrent format and invoke the independent tool
before configuration-dependent services or writable database business operations
start. It does not need historical version tables or conversion rules to do so.
User confirmation policy is separate from the migration mechanism.

There must be one explicit resource owner during invocation and startup handoff.
A parent holding ownership cannot ask a child to reacquire the same exclusive
resource. Any future delegation must define the ownership transfer or inherited
capability; a caller-controlled skip-lock switch is not an ownership protocol.

Successful process completion means the selected existing resources are current and
validated. The application then rereads configuration and opens fresh database
connections. It must not reuse preconversion objects. Failure prevents normal
business initialization and presents the tool's error; it does not trigger an
unrelated fallback or blind automatic retry.
