= Library

CLI scan and playlist import/export paths are relative to the invoking client's
working directory. Playlists deduplicate track IDs while queues may repeat tracks.
Exported playlist paths are relative to the destination directory.

Scanning requires configured `library_roots`. Add a directory with the GUI Library
`+` button or set absolute directory paths in `config.toml` before scanning.
GUI, CLI, and IPC scans normalize `.` and `..` without resolving symlinks. Every
requested logical path must lie within a configured root; a mixed inside/outside
request is rejected before scanning begins. File and directory symlinks are
followed even when their targets are outside the configured roots. Stored paths
and directory views retain the logical aliases; distinct aliases remain distinct
library identities. Directory symlink cycles are reported as scan errors.
CUE audio sources may use any configured logical root, but paths outside all roots
are rejected. An unavailable root does not prevent scanning another configured
root. `library probe` remains an independent metadata inspection.

== Library metadata and favorites

`library probe PATH` reads audio metadata without starting a core. Library rows and
Track details show codec, sample rate, channels, bitrate, track/disc numbers,
release date, path, missing status, CUE boundaries, play count, and favorite state.
Unknown metadata is reported as `—` or JSON `null`.
Track details defaults to the current playback track when no Library track is
selected. An explicit selection takes precedence; clearing it restores playback
details, or the empty state when there is no current track.

Editing titles, artists, albums, and favorites changes only Rivu's library data;
media tags and audio files are never rewritten. Track identity uses the stored
path and fingerprint. Rescans preserve identity, overrides, counts, and history.

Refreshing the same track updates favorites, statistics, and technical details
without replacing unsaved title, artist, or album edits. Selecting another track
loads that track's editable metadata.

[source,sh]
----
# Force metadata reprobe while retaining library identity and user data
./target/release/rivu library scan ~/Music --force --wait

# Filter by favorites or missing status (both flags select their intersection)
./target/release/rivu library list --favorites
./target/release/rivu library list --missing
./target/release/rivu library favorite 12 34 --set on
./target/release/rivu library favorite 12 34 --set off

# Remove missing records and their queue/playlist references, not media files
./target/release/rivu library clean-missing
----

The GUI Library toolbar switches between a flat track list and an expandable
directory tree. Search and favorite/missing filters use the flat list. Compact
icon buttons browse earlier or more items without exposing page numbers or
batch ranges; list controls are hidden when all results fit. Tree rows keep
their ancestors visible and load children only on expansion; each directory
has independent browsing controls.
Buttons provide tooltips and use plain-symbol fallbacks when Nerd symbols are
disabled.
In the flat list, Up/Down crosses page boundaries and keeps the selected row in
view, including the last row when returning to an earlier page.
Click, Enter, or Space toggles a selected folder. Up/Down move through visible
rows; Right expands a folder or enters its first child; Left collapses it or
selects its parent. Enter on a track plays it. These tree keys take precedence
over playback shortcuts while the tree has focus. The TUI directory browser
continues to open directories with Enter and return to the parent with Left.
The rescan icon appears only on selected directory rows. Ctrl/platform-click
toggles selection without expanding folders. Dragging files or directories to
Queue or a Playlist adds their matching tracks.

Interactive text search uses a 150 ms quiet interval to coalesce rapid edits.
GUI responses for superseded queries are discarded; the TUI also waits for the
last edit's deadline before submitting a search. Typing and playback controls
remain responsive while the database query runs.

== Database-backed views and queue limits

The complete library and playlists stay in SQLite, not in published playback
snapshots. Snapshots contain library counts and revisions, recent history,
current-track details, and ID-sorted lightweight display rows for distinct queued
tracks. Queue membership keeps only entry IDs and Track IDs; display rows omit
paths, fingerprints, CUE segments and audio-format metadata. The current track
holds complete details independently of the LRU. Read queries do not change
playback revisions or wake state subscribers.

Library search, directory children, playlist summaries, and playlist entries are
queried in pages configured by `page_size` (default 64, range 20–256).
Each GUI list retains its current page; the directory tree retains one page per
open branch and discards descendants on collapse or branch-page changes.
TUI lists retain at most three pages and fetch another page when selection
crosses a boundary.
Pages carry only the fields needed for display and selection, rather than full
Track objects. This keeps rendering independent of individual detail queries
and prevents simultaneously visible panels from churning the detail LRU.


Track detail lookups retain at most `2 * page_size` distinct tracks in an
in-memory LRU cache (128 by default). Hits refresh recency; overflow evicts
the least recently read detail. Reducing the page size immediately trims the
cache. Track edits, favorites, playback statistics and deletion invalidate
affected details; scans and missing-track cleanup clear it. Failed writes may
also discard cached details, but never publish uncommitted values. The cache
does not add database tables or writes and does not truncate queue entries.

CLI library and playlist listings and playlist export stream all pages, so their
output is complete rather than limited to the first page.

The playback queue defaults to a maximum of 4096 entries, configured by
`queue_limit`. Duplicate occurrences count toward that limit but share display
metadata. Oversized enqueue operations, directory expansion, and playlist-to-queue
loads are rejected without truncating the requested selection or changing the
existing queue. Playlists themselves are not capped by the queue limit.
Saved queues restore the first `queue_limit` valid occurrences in their original
order, skipping removed records before applying the limit. Duplicate occurrences
remain distinct and share one display row; restoration queries stay bounded.

Rust/IPC consumers use `Command::LibraryPage`, `Command::DirectoryPage`,
`Command::PlaylistSummaries`, and `Command::PlaylistEntries` for list views, and
`Command::Track` for full details of any library track. Whole-library and
whole-playlist collections are no longer part of status snapshots.

== Play counts and recent tracks

A playback increments its track's play count once, only when confirmed heard time
*strictly exceeds* `play_count_threshold_percent` of the track duration (20% by
default). Reaching exactly the threshold does not count. Pause/resume and seeks
do not reset the playback's count state or create additional counts; skipped time
does not count as heard. When duration is unknown, counting waits until a natural
EOF can supply a duration from the final position; without one, no play is counted.

Recent history contains one entry per track, ordered by its last-played timestamp.
A successful backend start registers the track immediately. Natural completion,
track changes, stops, and shutdown persist the latest confirmed playback activity
into that same entry. Progress updates only in-memory session state, not the
database every second. Paused time never advances activity timestamps; late audio
confirmations still contribute their full heard time to play-count decisions.
Pause/resume and seeks do not create separate recent entries, and seeking does
not itself count as playback activity. Failed loads do not create recent entries.
A recent entry is not a claim that a play reached the counting threshold. Rivu
stores only aggregate play counts and last-played timestamps, not per-play records
or per-play/cumulative heard durations; heard time exists only in memory for
playback and count decisions.
The GUI Recent tracks and Track details panels show the confirmed current playback
as `0s ago (playing)`. Paused playback shows its frozen last activity time with
`(paused)`; other tracks and stopped playback show stored local
`YYYY-MM-DD HH:MM:SS` times. Stored and JSON timestamps remain Unix seconds;
unavailable or unrepresentable dates display `—`. Existing timestamps are not
rewritten retroactively.

Track identity uses path and fingerprint. Rescanning or updating tags preserves
that identity, user metadata overrides, counts, and last-played timestamps.

== Database initialization and maintenance

Rivu creates the database structure directly. Stop the instance before removing
`library.db` and its `-wal`/`-shm` sidecars, then rescan the music files. This
resets playlists, queue, favorites, metadata overrides, and playback statistics;
source audio files, `config.toml`, and `workspace.json` are independent.

To optimize the database, stop playback, wait for scans to finish, and run:

[source,sh]
----
./target/release/rivu library optimize
----

Optimization is rejected while playback or scanning is active. It reclaims
database/WAL space and refreshes query statistics; failures are reported as errors.
