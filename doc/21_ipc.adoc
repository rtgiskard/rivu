= IPC
:toc:
:toclevels: 2

This chapter follows the boundary from application ownership through socket
sessions and consistency to the business operations behind them. External clients
need <<_transport_and_frame_format,framing>>, <<_session_handshake,Hello>>,
<<_revisions_and_watching,revisions>>, and
<<_request_failures_and_completion,completion semantics>> before issuing commands.
Query and task results belong to the running instance; neither a timeout nor a
disconnected client rolls back an accepted operation.

== Core and client boundary

One Core owns library storage, queue mutations, configuration, and playback
coordination for a data directory. Frontends submit commands and query projections
rather than maintaining independent authoritative library or playback state.
Audio output and analysis have their own workers; transport and rendering stay
outside the audio callback.

The root Rust crate is an application library for its own executable, not a
stable embedding SDK. Storage transactions, mutable analysis publication, and
frontend implementation modules are crate-internal capabilities. External
clients use the protocol rather than bypassing Core validation through storage.

`rivu-protocol` defines commands, queries, snapshots, positional wire schemas, and
bounded transport. `rivu-client` provides synchronous sessions, instance binding,
cancellation, typed task waiting, command-failure evidence, and one-shot helpers.
External Rust clients use these crates rather than the root application crate.
Their standalone dependency graph requires no GPUI, audio execution, PipeWire,
SQLite, or FFT execution, although Cargo feature unification can enable database
or DSP execution in a combined build.

The client drives I/O on its calling thread, so async callers must move it off
their executor thread. Retained sessions reuse sockets and bounded framing storage.
The GUI calls Core directly and owns only its view and audition state.

Protocol codec and transport contracts are tested in `rivu-protocol`; client
session, cancellation, and task-wait contracts are tested in `rivu-client`.
Run these independently with `cargo test --locked -p rivu-protocol -p rivu-client`.
Socket interactions involving App and Core remain in the root application's IPC
integration tests rather than making the standalone crates depend on the host.

=== Consumer and application lifetimes

The GUI, tray, and MPRIS service use `CoreHandle` for business commands and
purpose-specific projections. Opening a window and quitting use a separate
App-owned control endpoint. CLI and TUI clients use the local IPC socket, whose
dispatcher separates application requests from Core operations without changing
the wire format. Shared analysis and waveform data are in-process resources,
not IPC state sections.

The graphical host has three lifetime boundaries within one process:

* `App` owns `TaskRuntime`, the Core runtime, IPC listener and instance ownership,
  shutdown signals, shared artwork, logging session, optional tray, MPRIS manager,
  and open/focus/quit coordination. Its GPUI host remains available without a
  window. The headless `serve` host uses the same application ownership.
* Core owns accepted business operations and authoritative state. Closing a
  window does not cancel playback, scans, saves, or accepted commands. Dismissing
  a relocation review explicitly requests cancellation of its verification task,
  without undoing a commit.
* `UiSession` owns window creation, focus, reload, and close; `WindowView` owns view
  state, subscriptions, and render resources. Reopening builds a new view from
  current Core state; repeated open requests focus the existing window. Late
  background results use weak references and need not reach a closed view.

Window-open requests coalesce at App until the graphical host is ready. Core
completion notifies App independently of GUI registration, including on panic.
Shutdown has a bounded lifecycle signal independent of the business queue;
accepted IPC shutdown acknowledgements drain before transport retirement.
Service joins run outside GPUI quit callbacks. Window/display resource release
is described in link:22_cache.adoc#_renderer_buffers_atlases_and_display_lifecycle[Resource lifecycles];
closing a window is not framework teardown or a promise of headless-equivalent memory.

=== Owner execution and retirement

Core applies state transitions on one persistent dedicated thread. Bounded
channels carry requests and worker facts; replies and revision subscriptions
wake consumers without polling. Notifications coalesce, so consumers read the
current authoritative projection after a wakeup rather than replaying events.

Command execution returns an explicit outcome: immediate acknowledgement, an
allocated task ID, or a deferred export/maintenance reply. Dispatch publishes the
state transition and applies that outcome; it does not infer task identity from
the current active-task slots. The task owner retains any deferred reply through
completion or shutdown.

SQLite writes and their state transitions stay atomic on Core. A separate bounded
query owner reuses a read connection and pins a SQLite snapshot per request,
validating it against captured Core revisions. A publication fence prevents reads
from pairing a committed database change with preceding state. Count reuse follows
data-domain revisions; maintenance waits for physical snapshot retirement.

IPC disconnection or shutdown drops a pending query's reply receiver. Obsolete
queued reads are skipped before database admission, but SQL already executing
keeps its snapshot lease until completion. This does not cancel accepted commands.

App explicitly supplies execution capabilities to Core and services, independently
of the business `CoreHandle`. It retains `TaskRuntime` through Core, service, and
GUI resource retirement. File, probe, and background transaction stages share at
most four blocking slots; waiting for Core admission or replies holds none.
`BlockingExecutor` bounds physical closures, not a private pool of threads. A
closure keeps its slot after async cancellation. Shutdown joins started work
before retiring execution: cancelling a waiter is neither worker retirement nor
rollback.

=== Projection and view costs

State reads contain summaries, compact queue state, playback, runtime System state,
and independently requested Configuration state; library rows are queried separately.
In-process consumers can share immutable
projections, whereas socket responses serialize them. Queue displays resolve
metadata from bounded queue queries and their content revision, not unrelated
library pages. TUI rendering visits visible queue rows while retaining global
occurrence selection and scroll position. GUI page, selection-index, and worker
retention are described in link:22_cache.adoc#_window_local_query_retention[Resource lifecycles].
This avoids both a second control implementation and a universal whole-library
snapshot on every playback update.

Startup and single-instance operation are documented in
link:../readme.adoc[README]. Socket clients and Core must use compatible builds.


== Sessions and protocol

=== Transport and frame format

IPC uses a Unix domain socket. Each frame contains:

[source,text]
----
u32 body_length       # little-endian
u8  protocol_version
u8  message_type
body
----

The frame header is six bytes. `body_length` excludes the four-byte length field
and includes the version, message type, and serialized body.

Bodies use Postcard serialization without COBS framing. The current protocol
version is `12`. Both peers must use matching protocol versions and positional
wire schemas. The four-byte frame length remains little-endian; body integers
follow Postcard's encoding.
Version mismatches are rejected before decoding the body. There is no schema
negotiation. See <<_wire_schemas,Wire schemas>> for positional fields and adapters.
Monitor EQ `SavePreset` and `ImportPreset` carry an explicit positional `overwrite`
boolean: false creates only, true replaces only an existing named preset.
JSON commands may omit it for create-only behavior; positional wire encoding
always carries it.


Frame content is limited to 4 MiB for requests and 16 MiB for responses, including
version/type but excluding the length prefix. The server admits 16 clients;
additional connections receive `IPC server is busy` and close.

Before Hello, each incoming frame has a one-second completion limit. Once bound,
an incomplete request must finish within five seconds of its first byte, including
during a Query wait. Further bytes, revision updates, and socket backpressure do
not renew or suspend the deadline. Expiry closes the connection and releases its
slot. Idle sessions, Watch, and Query waits without an incomplete following frame
do not expire under this rule.

An oversized prefix closes immediately, before consuming its body. Invalid headers,
types, versions, malformed Postcard, and trailing payload bytes within the limit
receive Error and close that session. Other sessions remain usable.

Query read-ahead is bounded to one maximum request frame plus its prefix. Complete
frames wait untimed and in order behind earlier replies; incomplete tails retain
their deadline even when the buffer is full. A framing failure drops the pending
reply receiver, without interrupting or replaying SQL.

Frame limits bound encoded bytes, not decoded heap usage. Current nonrecursive
schemas and decoder length checks make allocation and iteration scale with actual
input, rather than arbitrary declared collection lengths. Decoded messages can
still be larger; recursive types, zero-byte elements, or custom deserializers
would require reviewing that bound.

IPC uses one Linux abstract Unix stream socket for both communication and
exclusive data-directory ownership. No `rivu.sock` or `rivu.sock.lock` file is
created. The abstract name is the five bytes `rivu.` followed by the directory's
device number and inode number, each encoded as an eight-byte big-endian integer.
The leading abstract-namespace NUL is not part of that name. Following directory
symlinks and using filesystem identity makes relative paths, symlinks, and bind
mount aliases reach the same instance; distinct directories have independent
addresses. The data directory must remain in place for the instance lifetime.

Abstract sockets have no filesystem permissions. Both endpoints read kernel
`SO_PEERCRED` credentials and reject a peer whose UID differs from their effective
UID, before exchanging protocol frames. The server checks credentials before
admitting a client to its bounded session set. This protects commands and state,
not availability: another user can occupy the public abstract name and prevent
startup, but cannot impersonate the server to a client.

Startup binds the listener before database, configuration-write, or audio work;
only successful binding grants ownership. App retains it through teardown and
partial startup failures. The kernel releases the address when the last listening
descriptor closes, including on process death; there is no stale-file cleanup.

Ownership is scoped to a Linux network namespace. Instances in different network
namespaces must not share a data directory.

Sessions process requests serially, without request IDs or multiplexing. Partial
input survives cancelled reads. Framing enforces the direction's size limit while
encoding and decodes complete frames directly into owned messages.

Send buffers above 256 KiB are released after write/flush; receive buffers above
that capacity are released once pending bytes drain. Smaller buffers are reused.
Pipelined tails and cancelled partial reads keep their bytes until consumed or
disconnected. These are framing-storage bounds, not decoded-message or RSS limits;
bulk transfers can allocate again and allocator pages may remain resident.

=== Session handshake

A client session starts unbound and must send Hello before State, Query, Command,
or Watch. Hello can request initial state sections, including none. A non-Hello
request before binding or a second Hello receives Error, but does not close the
session. The first successful Hello binds it.

The Hello response contains a random nonzero `u32` instance ID encoded as four
little-endian bytes. The ID is generated once per server start. Zero is reserved
as the invalid instance ID. IDs are equality tokens for detecting server
identity changes; they are not ordered identifiers, authentication credentials,
or globally unique identifiers.

The TUI uses independent retained command, query, and Watch sessions. The Watch
Hello supplies initial state and pins the instance; the loading screen still
accepts `q`. Other sessions must bind to that instance. Command/query reconnection
cannot target a replacement instance, and Watch never automatically reconnects.
A fatal connection, handshake, or identity error restores the terminal and exits,
without replaying queued commands.

Query replacement drains the active exchange before sending only the latest
pending query. TUI exit closes in-flight waits, including command and Hello waits.

=== Message types

Request types:

* `Hello` (`0`) — initialize a session and optionally read selected state sections
* `State` (`1`) — read selected state sections
* `Query` (`2`) — execute a read-only query
* `Command` (`3`) — execute a state-changing command
* `Watch` (`4`) — wait for a revision change
* `WaitTask` (`5`) — wait for a specific scan, relocation, or processing task's terminal result

Response types:

* `Hello` (`0`) — returns the server instance ID and selected state
* `State` (`1`) — returns selected state sections
* `Query` (`2`) — returns query revisions and the query result
* `Ack` (`3`) — returns command outcome, error, publication revision, optional
  `scan_id`, `relocation_id`, or `processing_id`, and the completed operation's
  optional database-optimization report
* `Watch` (`4`) — returns changed state revisions
* `Task` (`5`) — returns the task-specific terminal status or a task-wait error
* `Error` (`255`) — returns a protocol or request error

These numbers are the frame's `message_type` byte, represented by `wire::RequestTag`
and `wire::ResponseTag`, not Postcard enum ordinals inside a body. Wire enum variant
and field order are part of the binary schema.

=== Wire schemas

Configuration state carries the effective `Config` and `config_path`; its Config
uses the explicit positional `WireConfig` adapter. Runtime `SystemState` contains
no configuration payload. Both section schemas are versioned positional contracts;
collection lengths and optional fields are encoded in the message body.
Library information-column selection is encoded in WireConfig as five booleans
in Artist, Album, Duration, Codec, and Bitrate order; all false means no columns.
Protocol version `9` removes the visualization-cache field from `WireConfig`;
there is no compatibility schema for its former positional layout.

Library, Queue, album-member, and playlist-entry rows carry source paths, CUE
track numbers, and cached audio specifications, including bitrate certainty.
These fields let frontends format complete hover information without a separate
track lookup. Query revisions cover labels and other query-dependent metadata;
bitrate-bearing payload queries also depend on the committed bitrate revision.

The codec and positional payload schema are not negotiated. Changes require
coordinated client and server updates, preserving configuration semantics such
as omitted overrides inheriting their common setting. The IPC protocol version
is independent of on-disk configuration and database schema versions:
`WireConfig` transports runtime settings, not a versioned TOML document. Disk
version authority and maintenance belong to
link:26_migration.adoc#_version_authority[Database and configuration migration].

Processing task status distinguishes the task `id` from `graph_run_id`, the retained
graph snapshot accepted by audition and export commands. Export receipts carry
the source run ID rather than becoming retained audition results or command aliases.

`EditTrack` carries optional title, artist, and album fields. `None` leaves a
field untouched; `Some("")` explicitly overrides it with empty text. The core
merges these field intents into the current track rather than replacing it
with a client snapshot.

Exact positional schemas and adapters are defined in
link:../crates/rivu-protocol/src/wire.rs[wire.rs];
link:../crates/rivu-protocol/src/transport.rs[transport.rs] owns framing and deadlines.

=== Request failures and completion

Well-formed requests with invalid values, handshake-order errors, and server-side
dispatch failures receive Error without ending the session. Core query failures
instead appear in the Query result, and core command failures in an unsuccessful
Ack. Transport failure or an oversized response can end the connection without
a usable response.

Core request capacity is bounded to 64 queued operations. Requests waiting for
capacity or a result can fail as unavailable; UI fire-and-forget sends report
`Rivu is busy or stopped` rather than blocking. Core allows two seconds for queue
admission and twelve seconds for a reply, or 120 seconds for database optimization.
The operation interface owns that total waiting budget; IPC adds one second for
the server bridge rather than classifying commands again. Local ShowWindow and
Shutdown operations have a twelve-second budget without queue admission.
Each server response write, including Hello, Error, busy replies, and shutdown
acknowledgements, has a five-second completion deadline covering write and flush.
Client request writes use the same five-second write-and-flush deadline, including
Hello, Watch, and WaitTask requests. Serialization precedes that deadline; the client response
read deadline starts only after the request write and flush complete. A stalled
write discards that connection; server writes cannot block teardown indefinitely.
Accepted operations still finish their replies during shutdown rather than
cancelling acknowledgements when shutdown starts.
Client response reads cover the operation budget, bridge allowance, response-write
deadline and one additional second for transport: 21 seconds for queries, state
reads (including Hello) and ordinary commands, 129 seconds for database optimization,
and 19 seconds for ShowWindow or Shutdown. Persistent and one-shot sessions use
the same policy. Watch and WaitTask have no response deadline. These are waiting
limits, not guarantees on operation execution time or system scheduling.

`Ack.status` is `Succeeded`, `Failed`, `NotAdmitted`, or `Unknown`. `Succeeded`
means the owner returned success; scan/import/relocation startup still requires
its task's terminal result. `Failed` means the owner returned an error, not that
all effects were rolled back. `NotAdmitted` means no business request was admitted.
Once admitted, a missing response is `Unknown`: the operation may still execute.
Do not automatically repeat a mutation; inspect authoritative state or the output.
If startup timed out before its task ID arrived and reconciliation is unavailable,
keep the result unknown rather than guessing that no task started.

An acknowledgement's `processing_id` identifies processing work admitted by that
command, not another active task. Cached graph audition and synchronous audition
omit it; callers must not infer task creation from the command type alone.

Client command failures before handshake or encoding completes are `NotAdmitted`.
Once a socket write is attempted, write, flush, response, and cancellation failures
are conservatively `Unknown`, even without evidence that bytes reached the peer.
The client's `CommandFailure` carries no invented Core revision or task ID.
`Shutdown` is an App lifecycle request and bypasses GUI draft confirmation;
interactive GUI/tray quit uses the separate user-shutdown path. Shutdown
acknowledgement means accepted shutdown, not final persistence or worker
retirement. Blocking I/O and cooperative cancellation provide no hard exit deadline.
The host attempts each final persistence domain even if another fails, retires
its workers and services, then exits with failure if final persistence failed.
The earlier successful shutdown acknowledgement is not changed by that result.
If read-worker startup fails, the host still attempts final persistence and retains
both the startup cause and any finalization failure in its returned error.

Failed exchanges, including an unexpected response type, discard the client
connection and its bound instance identity. A later explicit request can reconnect
and perform a fresh Hello, but clients never automatically replay a failed command.

`rivu_client::SessionCancellation` permanently cancels a client session and wakes
current and future waits. It does not cancel accepted work; replacing a query only
revokes its result.

== Consistency

=== Revisions and watching

State revisions are tracked independently for Playback, Queue, Library, System,
and Configuration sections, in that positional order. Section selection uses the
same order. Tokens are compared for equality, not ordered as clocks. A Watch
request waits until the current revisions differ from the expected revisions;
its response contains the latest revisions rather than an event log.

The `system` token in `StateRevisions` invalidates the System section. It is
distinct from `SystemState.revision` and acknowledgement `revision`, which are
the Core publication/wakeup sequence used to detect a newer assembled snapshot;
neither token is a query-data freshness clock.

Clients initialize from a state read, watch for revision changes, then read only
the invalidated sections. State reads capture selected sections and all revision
tokens under one shared-state lock. Omitted sections preserve the client's
previous values; the client advances tokens only for sections actually read,
otherwise it could acknowledge an unseen change. Notifications coalesce to the
latest state. A server restart requires a fresh Hello and state read.

Configuration changes advance their own token and wake Watch even when runtime
System fields are unchanged. Runtime progress does not materialize or transmit
the unchanged configuration. Request Configuration on initial/full state reads
and after its token changes; a runtime-only response cannot clear a retained
configuration or acknowledge an unread configuration revision. Selected sections,
including simultaneous runtime/configuration changes, come from one publication.

Each in-flight Watch owns its revision subscription. Reply, disconnection or
cancellation releases that registration without waiting for another publication.

The Queue state section is constant-size: `{total, current_id, current_position,
revision}`. It never embeds all occurrence IDs or track metadata. Queue content
and queued display-metadata edits advance its content revision; changing only the
current occurrence updates the Queue state-section token without invalidating
content pages. Unrelated track edits advance Library only. Last-played activity
does not invalidate Queue unless a displayed field, such as play count, changes.
Reapplying identical metadata or favorites, including a forced scan that keeps
the same displayed values, does not advance the queue content revision.
Raw title, artist, or album changes hidden by overrides also leave queue content
valid when their effective display values are unchanged.
Scan publication distinguishes effective display changes, structure, duplicate
groups, and duplicate-member verification facts. Size/mtime-only changes and raw
metadata hidden by overrides need not invalidate display pages. Recording an
override equal to the displayed raw value changes override ownership and member
facts, not display content; reapplying that override is a no-op. Playlist reference
changes affect duplicate-member facts only when membership changes, not on empty
collection lifecycles, rename, or reorder.

The Library section carries the summary catalog token `playlist_revision` and
`playlist_entry_revisions`, a playlist-ID-keyed map containing exactly the extant
playlists. Each value is a content/lifetime equality token issued independently
of the catalog. Creation registers a fresh token; deletion removes it. A missing
key means the playlist is unavailable, never a fallback to the catalog token.
Actual membership changes and reorders advance only the owning content token;
membership also changes summary counts. Rename changes only the summary token.
Core issues content/lifetime tokens from one in-memory sequence after confirmed
commits. Deleting and recreating a playlist, even with the same ID, cannot revive
an old token within that Core instance. Retention is bounded by extant playlists;
no durable versions, additional per-track version table or mutation event log is
needed. Restart reconstructs tokens; the existing instance identity isolates old
results from the new process.

Queries take their revision stamps from Core memory. Publishing state performs
no database version reads and queries do not reconcile an independent SQLite
version authority. Runtime writes must pass through Core; background connections
are admitted under the existing save gate. Direct external database writes while
Rivu runs are unsupported.

Confirmed commits advance affected tokens before any fallible count or view
refresh; rollback and no-op operations advance none. A refresh or worker-retirement
failure cannot discard confirmed commit facts. Unknown outcomes keep database
operations and final saves blocked until restart; they authorize neither prepared
views nor automatic mutation replay.

Playback-statistics writes return count and activity time directly to the Core.
The bounded track cache and current/recent snapshots receive these scalar changes
without reloading complete metadata. Count threshold and activity timing remain
independent.

Watch has no fixed expiry. A complete new request on that connection supersedes
a pending Watch without a Watch response. The preserved input then becomes the
next request; disconnect or server shutdown terminates the wait.

=== Query results and pagination

Query responses contain the requested projection and its data revisions, not a
full client state or queue snapshot. Core captures collection tokens with each
serialized query; the save gate prevents reads before background commit facts
have been applied. Publication sequence, four state-section tokens, query-data
tokens, and consumer request generations have distinct responsibilities.

`Query::stamp` selects query-dependent freshness for scheduling, projection
identity, result acceptance, and batch validation. Library pages use library
content; directory/location projections also use structure. Album projections use
the Core-owned `album` collection token rather than the global library token.
A single Track query uses `track = {track_id, revision}`. Bitrate-bearing payloads
also select the bitrate revision described below.
Root counts use structure only. Root size/count statistics use library content,
including changes to cached source-file sizes.
Playlist summaries use the summary catalog only; full entry rows use
`playlist_metadata = {playlist_id, revision}` plus their scoped content/lifetime
token. Unfiltered compact entry locations use only their content token; filtered
locations also use scoped metadata, with the same library fallback as full rows.
Queue queries use queue content and, while filtered, library content. Duplicate
groups use `duplicate_groups`; members use library, `duplicate_members`, and queue
content. Playlist reference changes advance member facts, while playlist names
and order do not.

Task-status queries select no query-data revision domains. Their empty stamp does
not make status immutable: query the exact task again to observe progress or
completion, or use System state updates to drive presentation. Status retention
and task IDs are scoped to the running instance, not a persistent job database.

Track and playlist metadata scopes share an index of at most 256 entries. Commits
identify affected display metadata transactionally; decoder hints and playback
statistics can update Track details without invalidating playlist rows. Unknown
bulk effects, overflow, or unavailable/currently mismatched scope information fall
back conservatively to the global library token. There is no whole-library reverse
cache, and retained metadata cannot recreate a deleted playlist's scope.

`LibrarySnapshot.bitrate_revision` advances only after a source-conditional
commit actually changes the `bitrate_bps`/`bitrate_exact` pair.
`QueryRevisions.bitrate` participates in stamps for payloads containing bitrate:
Track, library/directory rows, album representatives and members, Queue rows,
playlist entries, and duplicate members. Counts, statistics, summaries without
Track payloads, and ID/location-only queries do not depend on this revision.
Bitrate-only publication does not advance structure, collection membership, or
count revisions, and does not query Queue, album, or playlist membership.

Consumers discard old-stamp payloads and reload on demand; hidden views wait for
reveal. Selection, counts, navigation geometry, and metadata drafts survive
bitrate-only invalidation. The global bitrate revision may conservatively invalidate
unrelated track payloads, but needs no event history. Hover uses retained rows,
not another Track request. Range anchors ignore bitrate-only changes, while range
responses still require their full stamp.

Freshness never substitutes for physical completion: rejected reads hold their
reader slot until retirement. Current transport failures are displayed without
automatic retry; stale work or revision changes can drive fresh demand. Playback
statistics use scoped metadata revisions, not bitrate, and publish with EOF facts.

Whole-collection transfers carry an album key plus its `album` revision, or a
playlist ID plus its content/lifetime revision. Destination playlists carry their
own content/lifetime token; positional Queue insertion carries its in-memory
queue revision. Core validates these tokens before Store starts the transaction
that resolves members and inserts them. Serialized ownership and the save gate
prevent another runtime writer from changing the validated state. Album lookup
uses exact parent/title and album order; both Queue and Playlist destinations
preserve source occurrences and their order, including repeated track IDs.

Entry pages/batches and scoped `PlaylistEntryLocations` (including empty results)
attach `revisions.playlist_entries = {playlist_id, revision}` when the collection
exists. Missing scoped collections attach no token and fail the query. Successful
standalone single-entry lookups attach the discovered scope; missing lookups have
none, so selection relocation uses the explicitly scoped locations query.
Consumer generations independently reject abandoned identity/intent submissions;
fresh data cannot authorize an obsolete operation. Acknowledgements carry outcome
and diagnostic information plus publication revision, never replacement state.

Interactive pages return an exact filtered total and at most 256 rows; larger
limits are clamped, and `limit = 0` returns the count without rows. Offset pages
do not reserve a snapshot across requests. Cursor batches avoid the total-count
query and return a continuation only when more rows exist. They require a limit
from 1 through 256 and reject zero or larger values.

To traverse consistently, capture the first batch's query revisions and supply
them as `expected` on later requests. The same query-owned stamp validates
track batches (library), playlist-summary batches (catalog only), queue batches
(queue, plus library while filtered), and playlist-entry batches (scoped metadata
plus scoped content/lifetime, with the library fallback described above).
Queue and playlist-entry batches return `BatchContinuation` values. Pass the
complete previous `next` unchanged as `after`; do not construct one from a page's
filtered rank or substitute rank for its original position/id. A continuation's
scope is checked against the current normalized query, collection and selected
revisions even when `expected` is omitted. Stale or foreign continuations return
typed `QueryError::RevisionChanged`; restart with `after = None` and discard
partial traversal state. Changing only the batch limit does not change scope.
Renaming or changing another playlist cannot interrupt an entry traversal. A
catalog baseline without an entry token may start an entry traversal
(`after = None`) with unchanged library content, but cannot continue one. The CLI
retains its summary baseline while capturing each playlist's entry baseline
separately. Clients match the error variant, not diagnostic text. Other failures
return `QueryError::Message`. In-process demand cancellation can instead return
`QueryError::Cancelled` before dispatch; it does not interrupt SQL already running
or act as an IPC cancellation request. Without `expected`, track and summary
batches do not reserve consistency between requests; occurrence continuations
still enforce their embedded scope. All use bounded results and explicit restart,
not a database snapshot retained for an arbitrarily slow client.

Playlist-only edits leave library and structure tokens unchanged. Imports can
still invalidate track queries when their scan changes effective library facts.
If creation fails after a successful scan, those committed changes remain visible.

==== Query projections

`QueuePage {query, offset, limit}` returns `Page<QueueRow>` in queue order. Each row
is `{id, track_id, position, offset, track}`: `position` identifies its original
zero-based occurrence order, while `offset` is its rank among query matches.
`QueueBatch {query, after, limit, expected}` uses a
`{cursor: {position,id}, offset, scope}` continuation. Its `offset` is the next
matching rank, never the SQL keyset position. Queue content validates unfiltered
batches; filtered batches additionally use library content per `Query::stamp`.
Playback-only selection changes do not interrupt traversal.
`QueueEntries {query, queue_ids}` resolves at most 256 occurrence IDs,
omits removed IDs, deduplicates repeated IDs, and returns rows in queue order.
The query response's `revisions.queue` is captured with the rows; clients discard
late results if the active queue-content revision no longer matches.

`PlaylistEntryLocations {playlist_id, query, entry_ids}` resolves at most 256 stable
entry IDs to compact `{id, playlist_id, track_id, position, offset, total}` records
in current playlist order, without projecting full track metadata. Repeated IDs are deduplicated;
missing IDs and IDs belonging to other playlists are omitted. Empty requests
return no rows, while a nonexistent playlist or oversized input returns a query
error. Split larger selections into bounded requests and discard completions when
the playlist, request generation, or captured revision baseline changes.

`DirectoryPage {path, query, favorite, missing, offset, limit}` returns immediate
directory children and tracks as `Page<DirectoryRow>`. Search, favorite, and missing
predicates compose and filter tracks before directory grouping, counting, and
paging; a descendant match keeps its ancestor directories visible. `favorite` and
`missing` are optional booleans: omitted means unrestricted, `true` selects set
rows, and `false` selects unset rows. GUI configured-root entries remain visible
independently of these filters. Directory page and range-selection consumers
discard results when the captured filters, view, request generation, or library
and structure revisions no longer match. Filtering display rows does not restrict
directory source expansion: dragging a directory still adds its complete contents.

`OtherTracksPage {query, favorite, missing, sort, offset, limit}` returns a flat
`Page<LibraryRow>` for registered tracks outside current configured roots;
`OtherTracksCount` returns its unfiltered total. With no roots, both include the
whole library. `OtherTracksLocate {track_id, query, favorite, missing, sort}`
returns the matching rank or a filtered/unavailable result. These queries depend
on library content and root configuration; discard stale results when either
changes. `DirectoryRow::OtherTracks` identifies the collection, not a filesystem path.
Display track rows include their logical source `path`.

`QueuePage`, `QueueBatch`, `QueueEntries`, `PlaylistSummaries`,
`PlaylistSummaryBatch`, `PlaylistEntries`, `PlaylistEntryBatch`,
`PlaylistEntryLocations`, and `AlbumTracks` accept an optional `query`.
Summary searches match playlist names; track searches match effective title,
artist, album, and file name. Filtering precedes count and pagination; an empty
query does not restrict membership. Query identity includes the filter so a
response from an older search cannot satisfy a different projection.
Queue and playlist entry rows retain their original absolute `position`; their
`offset` is the matching row's zero-based ordinal in the filtered view. Location
results likewise distinguish original position from filtered offset, and their
`total` counts matching entries. Commands continue to target stable occurrence
or entry identities, not filtered offsets.

`Albums {query, sort, offset, limit}` returns `Page<AlbumSummary>`;
`AlbumTracks {key, query, offset, limit}` returns `Page<LibraryRow>`. Both use the
interactive page limit and the Core-owned `album` token, with the bitrate token
for their track payloads. An album key is the exact effective title plus its
immediate parent directory (no trailing slash, except `/`).
Blank/Unicode-whitespace-only titles are ineligible; explicit empty
overrides remain authoritative, and nonblank keys are not normalized. Artist
differences do not split an album and child directories never merge. Blank/stale
keys return empty member pages with total zero.

Browsing uses case-insensitive SQLite substring matching on effective album
titles and member artists. Artist matches include the whole album. Null/empty
queries match all; sort is `title` (default: title, directory) or `artist` (summary
artist, title, directory), with binary ordering. Members and representatives use
disc number, track number (nulls last), effective title, then ID. Summary artist
is the sole nonempty effective artist, `Various artists` for multiple, or an empty
string for none; artist sorting uses `Unknown artist` for that missing value.
Count/page filters are identical but do not constrain
whole-album actions. Indexed membership and persistent summary costs are covered
under <<_transactional_inputs_and_bounded_storage_queries,storage ownership>>;
browsing behavior is in link:02_library.adoc[Library].

`DuplicateGroups` pages ordinary-file groups by cached fingerprint and reports
present/missing counts. `DuplicateMembers {fingerprint, offset, limit}` returns
full track, size/mtime verification, override/independent, and playlist/queue
reference facts. `DuplicateMemberSelection {fingerprint, track_ids}` resolves at
most 256 selected member IDs to the same facts, omitting deleted, foreign-group,
and CUE identities and deduplicating repeats. This bounded lookup validates
off-page choices without scanning a group or treating cache eviction as deletion.
Fresh cached fingerprints are not a substitute for relocation's final source
and target identity/content verification.

`LibraryRootPage` returns the same display projection and filtered total as
`LibraryPage`, scoped recursively to one root. It preserves the library's search,
favorite/missing filters, and sort order. Root paths use the existing lexical
directory normalization and component boundary: `/home/a` never includes
`/home/ab`; `/` includes the whole absolute-path library.

`LibraryRootCounts` accepts up to 256 root paths and returns one `{path, total}`
per input, in input order, using a single batched query. Larger input batches
return a query error. Counts include all scanned tracks, including missing ones,
regardless of view filters; a root without scanned tracks returns zero. An empty
path requests the entire library. Overlapping query paths each count their own
subtree independently, even though configured roots must not overlap. Clients keep unavailable counts
distinct from zero, split larger root sets into bounded requests, and discard
results when their roots, request generation, or structure revision have changed.
Library-content-only changes do not invalidate these unfiltered root totals.
These requests use the bounded query owner and Core's revision boundary;
frontends must not query storage from rendering.

`LibraryRootStats` accepts the same bounded root list and returns one
`{path, total, file_size}` per input, in order. `total` counts catalog tracks;
`file_size` sums cached bytes grouped by source path, so CUE segments sharing a
source count bytes once while identical content at separate paths counts
separately. Missing tracks retain their scanned sizes; this query performs no
filesystem inventory. It uses the library-content stamp rather than the
count-only structure stamp. Settings batches requests and rejects obsolete
results when its session, draft roots, or library revision changes.

== Business ownership and transactions

The wire interface does not transfer ownership to the caller. Core validates
commands against current state, Store owns transaction-local invariants, and
background tasks return commit facts before Core publishes new validity.
The following sections explain those boundaries and their costs; user workflows
remain in link:02_library.adoc[Library], link:03_playlist.adoc[Playlists], and
link:04_playback.adoc[Playback].

=== Ordered collections and transaction ownership

Queue and ordinary playlists use the same `playlist_entries` occurrence table.
The protected system playlist has `id = 0` and `name = ''`; ordinary playlist IDs
are positive. Catalogs, playlist queries, playlist commands and Playlist transfer
scopes exclude or reject `0`; clients keep using the queue-specific commands,
rows and revisions for the queue. Entry IDs are globally unique occurrence
identities, not track identities, and remain stable across moves. Shared storage
does not transfer playback ownership or merge collection validity tokens.

Queue and playlist positions are contiguous and zero-based. Deletions close gaps
inside the same transaction; moves preserve occurrence identities and the current
selection. Storage work is scoped to affected collections and position ranges,
but widely scattered moves can touch a list-length span. Business owners retain
validation, playback effects, and revision publication.

After a confirmed structural queue commit, Core advances its in-memory content
revision once, before refreshing projections. Store transactions do not persist
or issue that token; rollback and no-op mutations leave it unchanged. Metadata
invalidation remains field-sensitive.

`RemovePlaylistEntries {playlist_id, entry_ids, expected_revision}` removes a
selection atomically and closes its position gaps. `MovePlaylistEntries
{playlist_id, entry_ids, before_entry_id, after, expected_revision}` moves the selected
entries together, preserving their original playlist order regardless of submitted
ID order. With `after = false`, the group goes before the target; `after = true`
places it after the target. `before_entry_id = None` appends in either case.
The target is a stable entry identity in the same playlist, not a row index.
Moving onto a selected target or requesting an already-current order is a no-op.

Both commands compare `expected_revision` with that playlist's current scalar
entry token at core dispatch, before storage mutation. A nonexistent playlist,
missing/foreign selected ID, missing/foreign move target, or stale token fails
without changing membership or positions. Duplicate selected IDs are applied
once. Empty selections still validate the playlist, revision, and move target;
valid empty selections and other no-ops do not advance revisions. Mutations are
SQL transactions retaining only selected identities and positions, not complete
playlist metadata or an all-entry vector. Actual group moves advance only their
playlist's scoped token; removal advances that token and summary counts, without
invalidating other collections.

Bulk favorites use atomic `SetFavorite {track_ids, favorite}` or
`ToggleFavorite {track_ids}`. Toggle reverses current values transactionally;
repeated IDs toggle once, and any unknown ID rejects the whole request.

`DeduplicatePlaylist {playlist_id, expected_revision}` keeps the first occurrence
of each track in playlist order, preserving each retained entry's ID and closing
position gaps. It rejects the protected system playlist and unknown playlists.
Core requires `expected_revision` to match the current content token before
mutation; the desktop supplies the displayed playlist's token. Removing
duplicates advances only the affected playlist's content token and summary
counts. An already-unique playlist is a no-op and advances no revision. Queue
deduplication remains a separate queue command with Core-owned playback effects.

`EnqueueSources` expands inputs directly in SQL with no total queue cap.
Source commands with only explicit track IDs preserve input order and repetitions.
When directories or Other are included, expansion selects a stable track-ID set
union, so overlapping sources contribute each track once.
`CreatePlaylistFromQueue {name}` atomically
saves every queue occurrence as a new playlist in queue order, including duplicates.
Explicit ID selections remain bounded by request-frame bytes, not total queue size.

The source commands `EnqueueSources`, `InsertQueueSources`, `AddPlaylistSources`,
and `InsertPlaylistSources` also accept `other_tracks`. When set, they include
the complete Other collection using current roots at execution time, independently
of display filters, with the same union ordering and deduplication as other sources.

`QueueExternalPaths {paths, index, expected_revision}` admits ordinary local audio
and inserts occurrences in input order, preserving duplicates. An absent `index`
appends; insertion requires `expected_revision`. Registration and queue insertion
commit atomically; stale revisions reject the whole commit without an append fallback.
The accepted command returns `Ack.scan_id`; completion and cancellation use the
shared media-task lifecycle below. User-visible file admission rules are in
link:04_playback.adoc#_adding_local_files[Adding local files].

`InsertQueue {track_ids, index, expected_revision}` and
`InsertPlaylist {playlist_id, track_ids, index, expected_revision}` insert directly
at an original-list boundary in `0..=total`. The corresponding
`InsertQueueSources` and `InsertPlaylistSources` also accept `directories` and
use stable track-ID union order for source expansion. Core checks the destination's
order revision even for empty requests; stale revisions, invalid boundaries, or
unknown tracks fail without partial writes. Explicit occurrences preserve input
order and duplicates without changing existing entries or the playing occurrence.
Gap creation and insertion commit in one transaction. Explicit `Enqueue` and
`AddPlaylist` additions have the same multiplicity-preserving behavior.

SQLite owns the complete occurrence order. Core retains only its scalar queue
projection and bounded navigation history; client state frames remain constant-size.
Normal navigation and Shuffle resolve occurrence positions through the queue-order
index, without a whole-queue ID cache or random-offset traversal. Shuffle samples
positions uniformly, so each occurrence remains equally likely, including the
current one. Whole-queue randomization uses an operation-local ID permutation.

Shuffle navigation retains at most 4096 successful occurrence starts for
Previous; it does not maintain a nonrepeating shuffle cycle.
Playlist entry page and batch rows include effective duration, codec, and favorite
state alongside display metadata. Duration is optional and describes the CUE
segment for CUE tracks, not the entire source. Favorite changes advance library
content and the affected track/playlist metadata scopes, not playlist entry order.

`PlayAlbum { key }` validates nonempty membership before stopping playback,
replaces the whole queue in member order, and starts its first track.
`EnqueueAlbum { key }` appends the entire album in that order, preserving current
playback. Blank or stale keys fail without changing the queue or playback. Both commands
resolve all current members in the backend independently of page limits; clients
must not collect paged track IDs to perform album actions.

`TransferCollection {source, destination}` copies a version-pinned Album or Playlist
without client-side page collection. Album sources carry their key and `album`
revision; Playlist sources carry ID and content/lifetime token. Queue destinations
carry insertion index and queue revision; Playlist destinations carry ID, entry
token, and optional index (omitted means append). Core validates both sides before
the transaction resolves and inserts members. Staleness rejects the whole operation.
Every occurrence and its order survive, including repeated tracks; later edits to
either collection are independent.

=== Library root identity and configuration

Configured roots are logical paths: relative paths resolve against the host's
working directory, and normalization removes `.` and collapses `..` lexically,
without resolving symlinks or requiring existence. Distinct logical aliases can
therefore identify the same physical directory. Loading, saving, and command
changes reject equal roots or component-wise ancestor/descendant pairs after
normalization; rejection replaces neither persisted nor published configuration.
Adding an existing root through the desktop is an idempotent no-op.

The configuration file owns roots, not a database membership table. Removing a
root does not delete tracks, metadata, references, or files; track deletion is a
separate operation. Overlapping low-level query ranges do not relax this
configuration invariant. Root operations and admission settings are described in
link:01_config.adoc[Configuration] and link:02_library.adoc[Library].

=== Scanning and metadata ownership

Core owns task admission and retirement; library workers prepare filesystem facts,
and Store commits database facts. Scans and external queue admission share source
identity checks, metadata reuse, probing, and hashing. Directory traversal, CUE
expansion, and coverage detection apply only to scans.

Scan-backed metadata and user overrides skip unchanged stored values. An override
equal to the raw value still records editing intent; an omitted field continues
to follow rescans. No-op edits succeed for existing tracks and reject unknown IDs.
The new-track minimum-duration policy is captured when a scan/import starts and
applied after exact-identity and relocation matching, never to previously stored
identities. Successfully validated CUE sheets exempt their subtracks and referenced
whole-file identities; failed sheets grant no exemption. See
link:02_library.adoc#_minimum_duration_for_new_tracks[Library].

Metadata reuse requires the current probe version, independently of schema or
protocol versions; mismatch reprobes without invalidating fingerprints. Preparation
is bounded to 32 sources or CUE sheets per batch. Ordinary identities can reuse
full-source metadata; CUE identities can reuse fingerprints and preparation across
shared sources within configured roots. Force bypasses reuse. Cancellation and
task identity are checked before each batch, so stale tasks cannot commit for a
replacement. Waiting for Core holds no blocking slot.

Relocation matching uses fingerprint and CUE segment identity. Exact identity wins;
multiple compatible candidates remain ambiguous, and only a confirmed missing
source permits relocation. Incomplete scans disable relocation and missing
detection. Fingerprints are validated before commit.

`CheckOtherTracks {force}` checks only registered sources outside current roots,
or all registered sources with no roots. It does not discover, relocate, or delete
tracks; commit rechecks current scope. `force` bypasses metadata reuse. File checks
and external queue admission share the scan task slot, saving boundary, cancellation,
and shutdown joining contract.
External-file preparation owns path normalization and occurrence indexing. Its
prepared records and indices are read-only outside that owner; Saving consumes
them without repeating normalization or an index-validation pass. Queue insertion
positions and database identities are still checked against the saving transaction.

Accepted scan, playlist-import, file-check, and external-admission commands return
`Ack.scan_id` with their `u64` task ID. Acceptance is not completion. The CLI sends
`WaitTask` on the same session and receives that exact task's terminal result:
only `Completed` succeeds; `Failed` and `Cancelled` report the task's error or
message. Global scanning state and `last_error` are presentation fields, not
evidence that a particular task finished.
JSON completion output contains the task status rather than a global state snapshot.
Startup and waiting share one connection; disconnection fails the wait rather
than binding the same numeric task ID to a newly started instance.
The CLI represents saved task references as `INSTANCE:ID`, paired with the task
kind. It obtains INSTANCE from the same Hello session that starts the task;
independent task status and cancellation bind to that instance before sending a
business request. References from an earlier instance are rejected after restart.
The reference does not extend task retention or persist tasks across restarts.

Task completion waiting belongs to Core, not to a socket-side revision observer.
The owner atomically checks retained terminal results or registers a completion
waiter, then continues processing business operations. At most 256 waits may be
reserved, including requests still queued for owner admission; dropping the wait
releases its reservation immediately. Ordinary progress does not inspect waiting
clients or clone their result payloads. Completion
returns the task-specific final object directly, without an intermediate
notification or a follow-up query. `task status` remains an immediate query.
Disconnecting or cancelling a wait releases its registration without cancelling
the task; task cancellation remains an explicit command. A waiting connection
cannot pipeline another request. Unknown or expired tasks fail rather than wait
for a future task with the same numeric ID.

`ViewResponse::ScanTask` contains `{id, progress, message, library_committed,
playlist_id, error}`. The phases are `Discovering`, `ReadingMetadata`, `Saving`,
`Completed`, `Failed`, and `Cancelled`; the last three are terminal. The core
retains the active task and latest 32 terminal results. Unknown/evicted IDs fail.
`library_committed=true` confirms a library commit (and the atomic queue insertion
for external admission); `playlist_id` confirms a subsequent playlist commit even
if refresh failed. A failed task is not evidence of zero side effects; after an
uncertain worker failure, absent confirmation is not proof that no commit happened.
An uncertain worker outcome disables database business operations until restart;
after reopening, inspect committed data before submitting any missing operation.
`CancelScan` requests cancellation before Saving and is rejected during Saving;
its Ack never proves worker retirement. Only the task terminal result resolves it.
A failed wait never automatically replays startup.

Shutdown cancels and joins scan preparation, but drains accepted Saving completion
so committed facts cannot be reported as cancellation.

=== Transactional inputs and bounded storage queries

Library deletion validates its selected identities before playback effects, then
deletes references and compacts positions transactionally. Stop returns final
position and heard time independently of lifecycle-event backpressure; later
events cannot count that time twice.

A confirmed deletion advances affected revisions before fallible projection reads.
Catalog/history and scalar Queue recovery proceed independently; a failed refresh
reports the committed deletion, not rollback, and leaves that domain pending.

Queue consumers recover stale control projections before using occurrence order,
insertion boundaries, or navigation history. Recovery does not materialize the
complete queue. A pending runtime selection is persisted before accepting database
current; a committed removal owns the disappearance of its occurrence.
The queue becomes ready only when all required refreshes succeed; a later consumer
retries an incomplete recovery. Existing playback Pause and Stop do not require
queue recovery. External admission repeats the readiness and insertion-baseline
check before authorizing Saving, since preparation can outlive queue changes.

Count-only pages omit row projection; queue/playlist totals do not join metadata.
Unfiltered entry pages seek contiguous positions, and playlist totals use the
indexed maximum position. Filtered random-access pages count and skip matches in
SQL before projecting rows. Sequential filtered batches instead retain matching
rank plus the original occurrence keyset and a fixed-size query/revision scope.
Core supplies the stamp in serialized dispatch and Store rejects foreign scopes
before reading, even without `expected`. One matching lookahead decides whether
to continue. A stable traversal searches each interval at most twice plus indexed
keyset seeks, rather than recounting every preceding prefix. No retained SQLite
snapshot, per-client map, or full-list cache is introduced.

Directory/root queries use indexed, case-sensitive component ranges, preserving
literal path characters and Unicode. Storage enforces one ordinary whole-file
identity per path while allowing CUE segments to share their source. Equivalent
root ranges are counted once and expanded to the requested order, bounded by
256 roots.

Directory pages count and select children before projecting track payloads.
Temporary work scales with matching children; count-only requests omit it, and
empty/out-of-range pages still report exact totals. OFFSET traversal retains its
preceding-match cost. Count retention is described under
link:22_cache.adoc#_core_owned_lookup_retention[Core lookup retention].

Album summaries and artist counts are persistent SQLite projections maintained
in the same transaction as track changes. Unchanged effective metadata does no
summary work. Indexed membership avoids rescanning an album per changed member;
substring search and OFFSET still scale with matching summaries. Reverse-reference
indexes keep sparse library deletion scoped to affected queue/playlist entries.
These indexes trade storage and write maintenance for scoped lookup work.
Database format validation is described in
link:26_migration.adoc#_version_authority[Database and configuration migration].

=== Background commits and maintenance

Playlist export owns one physical worker and read-only SQLite snapshot. Keyset
reads retain at most 256 export rows; missing references and invalid CUE runs fail.
The target is atomically replaced only after complete output and a final
cancellation check. Timeout does not cancel export or free its slot. Shutdown
cancels cooperatively and joins it. Its snapshot retains WAL pages, excluding
concurrent optimization.

Scan preparation is cancellable. Core authorizes Saving after relocation retires;
Saving persists queue selection, merges library facts, creates any playlist, and
prepares projections on a worker connection. This is the cancellation cutoff,
not commit confirmation. Core installs confirmed facts and projections, invalidates
caches, and publishes revisions before database reads resume. Shutdown drains
Saving rather than falsely reporting cancellation.

Optimization likewise has one physical worker and retains its original reply
until completion. During Saving or optimization, database requests are rejected
promptly, not queued behind maintenance. Published state/task status and existing
playback volume, seek, pause/resume, stop, and cancellation remain serviceable.
Playback accounting coalesces in one active or retired record; EOF navigation
waits for maintenance and retains later pause/stop intent. Failed retired-record
persistence does not gate independent controls. Deferred writes must settle
before replacement playback, deletion, relocation, or Saving can retire its
track identity. User mutations are never replayed automatically.

Relocation verification is Core-owned and single-flight. Acceptance returns
`Ack.relocation_id`; exact task queries and System status expose completion, with
32 terminal results retained. Hashing is cancellable in at most 4 MiB stages with
one 128 KiB buffer; started stages retire before admission is released. The verified
descriptor survives to commit, where source absence, path/descriptor identity,
playback, and destination conflicts are rechecked. Shutdown joins the worker.

=== Playback and audio admission

Interactive playback changes use execution-time intent commands:
`AdjustVolume { delta }` adds a finite signed delta to the core's current volume
and clamps the result to 0..1; `CycleRepeat` cycles Off → All → One → Off;
`ToggleShuffle` flips the core's current setting. Queued commands are applied in
order rather than deriving absolute targets from a frontend's earlier snapshot.
`SeekRelative { queue_id, delta }` adds finite signed seconds to the core's current
position, bounded below by zero and by an explicit CUE end, not estimated metadata
duration. A different current occurrence or stopped playback makes it a no-op.
`SeekQueue { queue_id, seconds }` retains an absolute target bound to one occurrence;
interactive start/end seeks use it, with the end captured from that occurrence's
known duration. Neither command can seek a replacement occurrence of the same track.
CLI `Seek` and `Volume`, and MPRIS absolute properties, retain their absolute semantics.
Audio admission has a separate 64-command queue and 128 worker-event slots.
Ordinary audio admission never waits for capacity: a full queue returns an
unsuccessful acknowledgement explicitly stating that the command was not queued.
There is no automatic replay. Core can therefore keep draining critical lifecycle
events, whose worker-thread delivery retains backpressure; progress remains
best-effort. Configure checks capacity for its complete audio batch, and Still
Mode for its single command, before persisting or publishing the change. Device
request identity advances only after admission. A worker disconnect after settings
are saved retains the committed desired configuration and reports audio-application
failure. Ordered stop acknowledgement keeps draining events while waiting;
shutdown independently cancels blocked event delivery.

First-frame opening and playback refill share finite decode-work scheduling:
each opening round retains its decoder and packet progress and performs at most
64 work steps before returning to command handling. Stop, replacement Load and
shutdown retire the unfinished opening; other controls update its pending target.
An abandoned opening cannot publish Started or Failed for a later generation.
Container setup, seeking and individual decoder, file or device calls can still
block; these work bounds are not wall-clock deadlines.

Queue mutations commit their own transactions; playback selection persists the
current occurrence, while unrelated controls do not rewrite queue metadata. Stop
drains lifecycle facts while waiting under one deadline, without a second receiver
or automatic replay. Shutdown acknowledges acceptance before final stop/persistence;
later failures remain published errors, not rejection of the accepted exit.

Core awaits the process-wide completion of the first explicit FFmpeg load,
including loads initiated by waveform work. Success or failure publishes runtime
availability without starting a load or periodically polling. Disabled and
native-only builds have no FFmpeg status polling wakeups.

=== Application services

App owns and joins MPRIS, tray, and logging services independently of windows.
MPRIS registration is asynchronous and cancellable; failures wait for a later
off/on transition, not a retry timer. Teardown removes interfaces, allows up to
one second for active replies and a separate second for connection close, then
joins the publisher. Synchronous artwork work still has to finish. Metadata
signals reflect exposed-value changes, not ordinary clock or unrelated queue updates.

Tray registration reconciles current publication state independently of bus setup.
Unchanged menus retain their revision; shutdown cancels bus work and closes under
a bounded deadline rather than waiting indefinitely for peers.

App installs the process logger and owns writer lifetime; Core controls settings.
A new writer is prepared before configuration persistence and activated only on
save success. Producers retire before file output is flushed, outside GUI callbacks.
Standalone Core runtimes install no process subscriber. Processing shutdown closes
event admission, joins workers, and drains unpublished outputs; retained auditions
last until service retirement. See
link:22_cache.adoc#_processing_output_retention[Processing output retention].

=== Audio processing commands

`EqualizerEdit { edit }` carries a field edit, preset operation or A/B swap;
`DenoiseEdit { patch }` and `NeuralEdit { patch }` merge specified fields into
current core configuration. In human-readable serde form, boxed Rust patch
storage does not add a wrapper: a patch remains an ordinary object. For example,
command values are `{"DenoiseEdit":{"patch":{"mode":"adaptive","wet":0.8}}}` and
`{"NeuralEdit":{"patch":{"threads":4}}}`. Equalizer edits use externally tagged
variants, for example `{"EqualizerEdit":{"edit":{"Enabled":true}}}`.
These examples describe command shape, not socket input: IPC sends the corresponding
WireCommand as a Postcard body in the ordinary Command frame after Hello, never
raw JSON. Unknown patch fields and invalid settings fail; omitted patch fields
remain unchanged. For neural manifests, explicit JSON `null` clears the selected
manifest, whereas an omitted manifest leaves it unchanged; the binary adapter
preserves the same three-way intent.

`ProcessingBypass` disables Monitor EQ, restores original playback and revokes
pending automatic audition without cancelling render/export jobs or deleting their
results. Parameters and queue remain intact. See
link:27_audio_processing.adoc#_practical_workflow[Playback bypass] for desktop/CLI use.

`StartProcessing { track_id, operation, profile }` accepts `denoise`, `speech` or
`separate`; profile is null or `{start_seconds,end_seconds}` in source-relative
seconds. Acceptance returns `Ack.processing_id`, not completed output.
`Query::ProcessingTask { id }` returns an optional task status: unknown or no-longer
retained IDs return `None`, unlike unknown scan and relocation task queries.
`CancelProcessing { id }` requests cooperative cancellation of the matching active
task; its acknowledgement does not prove worker retirement. `AuditionProcessing
{ id, mode, vocal_gain_db, accompaniment_gain_db }` selects
original/denoised/vocals/accompaniment/mix. System state exposes the latest
`processing` status. Use the exact task query for completion rather than an
unrelated latest-task field, and keep task IDs bound to the Hello instance.
Settings and source identity are captured with the job; output status reports
the models actually used. Retained output availability is session-bounded.
`ProcessingOutputs` exposes boolean stem availability, not paths. Graph outputs
identify their ports and optional causal `start_frame` context; PCM remains owned
by the service and is never serialized into status. Only an explicit export
receipt carries a durable output path. See
link:27_audio_processing.adoc#_tasks_retention_and_audition[Audio processing] for
CLI equivalents, terminal states, provisioning, PCM ownership and audition lifetime.

==== Immutable audio graph runs

`ProcessingGraphEdit { expected_revision, edit }` compares `expected_revision` with
the authoritative graph revision before applying one typed edit. A stale revision
rejects the entire edit. Node removal disconnects its edges; it never guesses
replacement routing. Positions do not affect audio. Graphs allow at most 64 nodes
and 128 typed, acyclic edges, with
one connection per input and explicit mix nodes for fan-in.
Generic `Configure` requests cannot replace this graph, including from a stale
settings snapshot; graph changes use the revision-checked edit command.

`ProcessingGraphRun {track_id, target: {node,port}, mode}` freezes source and graph
revision. Default `auto` chooses supported realtime, hybrid, or offline execution;
explicit modes reject unsupported plans. `settings.graph_mode` reports the actual
mode, `graph_boundary` the actual hybrid prefix, and `graph_plan` native-rate
latency/tail frames and admission/work estimates, not a deadline guarantee.
Preparation runs on the processing worker, not Core or the device callback.
Realtime tasks are `complete` when live-ready, without retained PCM; a nonplaying
source opens paused/live-ready and cannot replace newer playback intent. Planning
and execution algorithms belong to link:27_audio_processing.adoc[Audio processing].

`ProcessingGraphAudition { id, node: {node,port} }` takes the retained `graph_run_id`,
not an export task ID. It selects retained PCM directly, or queues a new preparation
task using the frozen snapshot when that output has
no cache. `ProcessingGraphExport { id, node: {node,port}, path }` starts a distinct,
cancellable offline task using that same graph and original source. Existing
cached PCM is copied without re-decoding or running DSP again; an unrendered port
executes only its ancestor closure. Queued operations acknowledge the new task ID.
Destinations are
absolute paths to new WAV files; existing files are never overwritten. Only a
successful terminal task sets `graph_exported_path`: an accepted request is not
an exported file. Cancelled or stale-source tasks publish neither partial PCM nor
partial export files. `CancelProcessing` also stops the selected live audition,
but only while its run and playback generation still match.

`settings.graph`, `graph_target`, `graph_mode`, and `graph_revision` distinguish
captured run state from later edits. `graph_outputs` lists only real cached output
ports and optional causal `start_frame` context (separation ports 0/1 are
vocals/accompaniment), not PCM or file paths. Only `graph_exported_path` records a
successful export's durable path. `graph_nodes` reports per-node execution state
and actual neural model IDs/SHA256 hashes.
Output availability and status retention are separate; a terminal task alone
does not authorize audition. Shared processing budgets and pinned-audition
publication failure are specified in
link:22_cache.adoc#_processing_output_retention[Processing output retention].
