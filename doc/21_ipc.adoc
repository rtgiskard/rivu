= IPC

== Core and client boundary

One core owns library storage, queue mutations, configuration, and playback
coordination for a data directory. Commands and queries are dispatched through
that core; frontends do not maintain independent authoritative playback or
library state. Audio output and analysis have their own workers, so client
transport and rendering are outside the audio callback.

Queue and playlist positions remain contiguous and zero-based. Deletion captures
only removed positions before changing rows, then closes gaps in ascending,
disjoint original-position intervals within the same transaction. Gap compaction
updates each affected survivor at most once and leaves the preceding prefix alone;
tail deletion requires no position updates. Library deletion applies this to its
queue references and separately to each affected playlist. Temporary position
storage scales with removed references, not the full surviving collections.
Compaction executes one SQL update per contiguous run of deleted positions; the
final suffix update may affect zero rows. Bounded-interval updates reuse a prepared
statement, and these local executions do not add client IPC round trips.

Single-entry moves update only the positions between the old and new locations.
Bulk queue moves rewrite the affected interval rather than the full queue;
reorders skip rows whose position is already correct. Entry identities and the
current occurrence remain stable, and no-op moves leave queue content valid.

Scan-backed metadata and user overrides skip writes when their stored values are
unchanged. Setting an override equal to its raw value still records that editing
intent; an omitted field continues to follow rescanned metadata. No-op edits
succeed for existing tracks and still reject unknown IDs. Queue-content validity
is described in <<_revisions_and_watching,Revisions and watching>>.

Track-ID mutations serialize each input list once. Library deletion validates
before playback-side effects, then consumes the prepared input in the same
serialized core dispatch. Stopping playback can update statistics, not catalog
identities; reference deletion and gap compaction remain transactional.
The audio stop acknowledgement supplies its final position and confirmed heard
time independently of lifecycle-event delivery. Event-channel backpressure does
not delay that snapshot, and later events cannot account for the same heard time twice.
Count-only pages omit row projection; queue and playlist totals do not join
track metadata. Equivalent normalized root prefixes are counted once per request,
then expanded to the original paths and order. Root aggregation state is
request-local and bounded by the 256-root query limit.

Directory and root queries use BINARY path ranges: a normalized nonempty prefix
ends in `/`, and replacing that delimiter with `0` gives its exclusive upper
bound. These ranges preserve literal characters, case, Unicode, and component
boundaries. A full path index includes ordinary files and CUE segments alongside
the separate identity constraints. It avoids full table scans per distinct root,
at the cost of index storage and maintenance during library writes.

Playlist deletion-reference lookup has an additional index on
`(track_id,playlist_id)`. It avoids scanning unrelated playlist entries for sparse
library deletions. Position is deliberately excluded: capturing removed positions
needs table lookups, but moving or compacting entries does not rewrite the reverse
index in addition to the ordering index. Dense capture alone can be slower; the
choice reduces storage and favors complete deletion/compaction and movement.

The GUI, tray, and MPRIS service use `CoreHandle` for business commands and
purpose-specific projections. Opening a window and quitting the application use
the separate App-owned control endpoint. CLI and TUI clients use the local IPC
socket; its dispatcher separates application requests from core commands and
queries while preserving the wire format. Shared analysis and waveform data
are in-process resources, not IPC state sections.

The graphical host has three lifetime boundaries within one process:

* `App` in `app.rs` owns the core runtime, IPC server and socket acquisition,
  shutdown signals, MPRIS, shared artwork, logging session, optional tray, and
  open/focus/quit coordination. Its GPUI event loop remains available when no
  window exists.
* The core owns accepted business operations and authoritative state. Closing a
  window does not cancel playback, scans, saves, or other accepted commands.
* `UiSession` owns window creation, focus, reload, and close. `GuiApp` owns the
  window's view state, subscriptions, and render resources. Reopening creates a
  new view from current core state; repeated open requests focus the existing
  window. Closing releases window demand and subscriptions, not application
  services. Background results use weak UI references and may finish without
  delivering to a closed view.

Window-opening requests coalesce at the App endpoint and remain pending until
the graphical host is ready. Core completion explicitly notifies App, including
completion before GUI registration and core panic; it does not reuse a window
opener callback. Shutdown uses a bounded lifecycle signal independent of the
business queue. IPC shutdown acknowledgements are drained before transport and
socket retirement, and service joins occur outside GPUI quit callbacks.

The same App owns the headless `serve` instance. The process logging subscriber
is installed once; file-writer lifetime belongs to App, while Core receives only
a configuration control handle. Logging prepares a candidate writer before
configuration persistence and commits its route only after a successful save.
App retires core, media, IPC, and signal producers before flushing file output,
outside GPUI callbacks and writer locks. Standalone Core runtimes do not install
a process subscriber. A TUI is a separate IPC client, not another host runtime.

These boundaries do not introduce internal IPC or require destroying and
reinitializing GPUI. Framework-global resources remain resident; no headless
memory equivalence is promised. Desktop controls and window operations are
described in link:04_playback.adoc#_desktop_tray_and_window_lifecycle[Playback].

Projections expose what a consumer needs without copying the whole library on
each playback update. Library rows are queried separately; state reads contain
summary information, compact queue state, playback, and system state. In-process
projections can share immutable data, whereas socket responses serialize it.
This avoids a second control implementation without making every consumer pay
for a universal snapshot.

Queue displays resolve metadata from bounded queue queries captured with their
content revision; unrelated library pages cannot substitute stale values. GUI history retains one
sorting index for the current immutable history and sort choice, rebuilding it
on source or sort changes rather than during painting. Tree selection locations
are updated when selection or accepted pages change, not on each viewport demand.
The TUI builds queue widgets only for visible rows, retaining global occurrence
selection and scroll position; position-only updates do not rescan the queue.
Configured TUI roots reuse their immutable storage until the paths change.

The tray subscribes after establishing its published baseline and reconciles
the latest state before reporting startup readiness. Menu layout and revision
are read together from that publication; unchanged menus retain their revision.

Startup and single-instance operation are documented in
link:../readme.adoc[README]. Socket clients and the core must use compatible builds.

== Transport and frame format

IPC uses a Unix domain socket. Each frame contains:

[source,text]
----
u32 body_length       # little-endian
u8  protocol_version
u8  message_type
body
----

The frame header is six bytes. `body_length` excludes the four-byte length field
and includes the version, message type, and serialized body.

Bodies use Postcard serialization without COBS framing. The current protocol
version is `11`; clients and servers must use matching wire schemas. The four-byte
frame length remains little-endian; body integers follow Postcard's encoding.

Request frame content is limited to 4 MiB
and response frame content to 16 MiB, including the version and message type but
excluding the length prefix. The server accepts at most 16 concurrent clients;
additional connections receive `IPC server is busy` and close. An unbound client
has one second to complete each incoming frame while waiting for Hello.

Frame limits bound encoded bytes, not decoded heap usage. Decoding must reject
malicious lengths without disproportionate allocation or work; changes to the
Wire schema must preserve that resource bound.

An oversized frame prefix closes the connection before its body is consumed.
Invalid headers, unknown message types, incompatible versions, malformed
Postcard payloads, and trailing payload bytes within the frame limit receive an
Error response and close that connection; other client sessions remain usable.

The socket has owner-only permissions (`0600`) before it starts listening.
The server also checks kernel-provided peer credentials and accepts only peers
with the same effective UID, even if filesystem permissions would allow another
user to connect; no application-level credential exchange is required.
Before opening the data database, saving configuration, or
starting audio workers, startup acquires a nonblocking advisory lock on the
stable `rivu.sock.lock` file and binds a real listener. The lock file is retained
after shutdown: unlinking it while Rivu is running would break the shared-inode
locking boundary. Concurrent Rivu starters therefore cannot both recover a
stale socket or initialize the same data directory.

Startup refuses to replace a non-socket path or an accepting socket, and
recovers a stale socket only after connection refusal, under that lock. Only a
successful bind grants ownership of the socket pathname. The application keeps
that owner until runtime shutdown, including all IPC worker startup failures;
the serving worker owns only a cloned listening descriptor, not that owner.
Failures and shutdown use the same retirement path. It unlinks only a pathname
whose device/inode still matches the bound socket. Failed bind or failed
competing startup cannot unlink another listener, and an externally replaced
pathname is left untouched.

The transport retains partial input across cancelled reads and keeps frames
independent. Sessions process requests serially; frames have no request IDs or
multiplexed response matching.

== Session handshake

A client session starts unbound and must send Hello before State, Query, Command,
or Watch. Hello can request initial state sections, including none. A non-Hello
request before binding or a second Hello receives Error, but does not close the
session. The first successful Hello binds it.

The Hello response contains a random nonzero `u32` instance ID encoded as four
little-endian bytes. The ID is generated once per server start. Zero is reserved
as the invalid instance ID. IDs are equality tokens for detecting server
identity changes; they are not ordered identifiers, authentication credentials,
or globally unique identifiers.

The TUI keeps separate command, query, and Watch sessions on its existing
workers. Each worker reuses its runtime, connection, and framing buffers;
Watch never blocks command or query traffic. Replacing a query discards its
result but drains the active exchange before sending only the latest pending
query. Exiting the TUI closes an in-flight socket wait, including command and
handshake waits, without waiting for a response.
The Watch worker's first Hello requests all state sections and supplies the
initial TUI snapshot and instance identity. Command and query sessions must bind
to that same Hello instance before issuing requests. Until the snapshot arrives,
the screen stays in a loading state that accepts `q`; no separate foreground
state request is made. Command and query sessions can reconnect only to the
same pinned instance; the Watch worker does not automatically reconnect. A
changed instance is fatal, without replaying queued commands against a
replacement server. Fatal connection, handshake, and instance-identity failures
restore the terminal before returning the error.

== Message types

Request types:

* `Hello` — initialize a session and optionally read selected state sections
* `State` — read selected state sections
* `Query` — execute a read-only query
* `Command` — execute a state-changing command
* `Watch` — wait for a revision change

Response types:

* `Hello` — returns the server instance ID and selected state
* `State` — returns selected state sections
* `Query` — returns query revisions and the query result
* `Ack` — returns command success, error, revision, and optional scan task ID
* `Watch` — returns changed state revisions
* `Error` — returns a protocol or request error

Wire enum variant order is part of the binary protocol. Existing variants must
not be reordered; new variants may only be appended.

== Revisions and watching

State revisions are tracked independently for Playback, Queue, Library, and
System sections. They are equality tokens, not ordered clocks. A Watch request
waits until the current revisions differ from the expected revisions. The
response contains the latest revisions rather than an event log.

Clients initialize from a state read, watch for revision changes, then read only
the invalidated sections. State reads capture selected sections and all revision
tokens under one shared-state lock. Omitted sections preserve the client's
previous values; the client advances tokens only for sections actually read,
otherwise it could acknowledge an unseen change. Notifications coalesce to the
latest state. A server restart requires a fresh Hello and state read.

The Queue state section is constant-size: `{total, current_id, current_position,
revision}`. It never embeds all occurrence IDs or track metadata. Queue content
and queued display-metadata edits advance its content revision; changing only the
current occurrence updates the Queue state-section token without invalidating
content pages. Unrelated track edits advance Library only. Last-played activity
does not invalidate Queue unless a displayed field, such as play count, changes.
Reapplying identical metadata or favorites, including a forced scan that keeps
the same displayed values, does not advance the queue content revision.
Raw title, artist, or album changes hidden by overrides also leave queue content
valid when their effective display values are unchanged.

Watch has no fixed expiry. A complete new request on that connection supersedes
a pending Watch without a Watch response. The preserved input then becomes the
next request; disconnect or server shutdown terminates the wait.

== Query results and pagination

Query responses contain the requested projection and its data revisions, not a
full client state or queue snapshot. Rows and query revisions come from the same
core dispatch. Library-content, directory-structure, playlist, and queue-content
revisions are separate from the four state-section tokens. Command acknowledgements contain
success or an error and the core's publication revision, not replacement state.

Interactive pages return an exact filtered total and at most 256 rows; larger
limits are clamped, and `limit = 0` returns the count without rows. Offset pages
do not reserve a snapshot across requests. Cursor batches avoid the total-count
query and return a continuation only when more rows exist. They require a limit
from 1 through 256 and reject zero or larger values.

`QueuePage {offset, limit}` returns `Page<QueueRow>` in queue order. Each row is
`{id, track_id, position, track}` with absolute zero-based position and `LibraryRow`
display metadata. `QueueBatch {after, limit, expected}` uses a `{position,id}`
cursor and validates only `expected.queue`; playback-only selection changes do not
interrupt traversal. `QueueEntries {queue_ids}` resolves at most 256 occurrence IDs,
omits removed IDs, deduplicates repeated IDs, and returns rows in queue order.
The query response's `revisions.queue` is captured with the rows; clients discard
late results if the active queue-content revision no longer matches.

`EnqueueSources` expands directories and explicit track IDs directly in SQL with
no total queue cap. `CreatePlaylistFromQueue {name}` atomically saves the complete
queue as a playlist on the server, keeping each track's first occurrence order.
Explicit ID selections remain bounded by request-frame bytes, not total queue size.
The core retains only one private compact occurrence-ID vector (8 bytes per row,
about 1.53 MiB for 200,000 occurrences); client state frames remain constant-size.

Shuffle navigation retains at most 4096 successful occurrence starts for
Previous; it does not maintain a nonrepeating shuffle cycle.

`LibraryRootPage` returns the same display projection and filtered total as
`LibraryPage`, scoped recursively to one root. It preserves the library's search,
favorite/missing filters, and sort order. Root paths use the existing lexical
directory normalization and component boundary: `/home/a` never includes
`/home/ab`; `/` includes the whole absolute-path library.

`LibraryRootCounts` accepts up to 256 root paths and returns one `{path, total}`
per input, in input order, using a single batched query. Larger input batches
return a query error. Counts include all scanned tracks, including missing ones,
regardless of view filters; a root without scanned tracks returns zero. An empty
path requests the entire library. Overlapping roots
each count their own subtree independently. Clients keep unavailable counts
distinct from zero, split larger root sets into bounded requests, and discard
results when their roots, request generation, or library revision have changed.
These requests run on the same core owner and revision boundary as other queries;
frontends must not query storage from rendering.

To traverse consistently, the caller captures the first batch's query revisions
and supplies them as `expected` on later requests. Track batches check library
content; playlist batches check both library and playlist revisions. A mismatch
returns the typed `QueryError::RevisionChanged`; clients must match that variant,
not parse diagnostic text. Other query failures return `QueryError::Message`.
Without `expected`, the server does not enforce traversal consistency. This uses
bounded results and explicit restart rather than retaining a database snapshot
for an arbitrarily slow client.

Playlist-only edits advance the playlist revision without changing library-content
or directory-structure revisions, so an existing track traversal remains valid.
Importing a playlist can still invalidate track queries because its scan updates
the library before the playlist is created. If playlist creation fails after a
successful scan, the committed library changes remain visible.

== Request failures and completion

Well-formed requests with invalid values, handshake-order errors, and server-side
dispatch failures receive Error without ending the session. Core query failures
instead appear in the Query result, and core command failures in an unsuccessful
Ack. Transport failure or an oversized response can end the connection without
a usable response.

Core request capacity is bounded to 64 queued operations. Requests waiting for
capacity or a result can fail as unavailable; UI fire-and-forget sends report
`Rivu is busy or stopped` rather than blocking. The server bounds query and
ordinary command dispatch waits to 15 seconds, with 120 seconds for database
optimization. Clients allow 120 seconds for each non-Watch response read,
including Hello; persistent sessions keep the same limit as one-shot requests.

A timeout or client disconnect is not command cancellation: an operation
already queued at the core may still execute. An unsuccessful acknowledgement
caused by a response timeout therefore does not prove the requested mutation
was absent. Clients must consult current state before deciding whether to repeat
a non-idempotent operation.

Failed exchanges discard the client connection. A later explicit request can
reconnect and perform a fresh Hello, but clients never automatically replay a
failed command.

Accepted scan and playlist-import commands return `Ack.scan_id` with their `u64`
task ID. Acceptance is not completion. The CLI polls `Query::ScanTask { id }`
and waits for that exact task's result: only `Completed` succeeds; `Failed` and
`Cancelled` report the task's error or message. Global scanning state and
`last_error` are presentation fields, not evidence that a particular task finished.
JSON completion output contains the task status rather than a global state snapshot.
Startup and waiting share one connection; disconnection fails the wait rather
than binding the same numeric task ID to a newly started instance.

`ViewResponse::ScanTask` contains `{id, progress, message, error}`. The progress
phases are `Discovering`, `ReadingMetadata`, `Saving`, `Completed`, `Failed`, and
`Cancelled`; the last three are terminal. The core retains the active task and
the latest 32 terminal task results. Unknown or evicted IDs return a query error.
`Command::CancelScan { id }` requests cancellation of that task; cancellation
does not merge partial scan results. A failed wait never automatically replays
the startup command.

== Wire schemas

Runtime `Config` and `SystemState` use explicit positional Wire schemas. They are
not serialized directly because their in-process serde representation is not a
stable binary contract. Collection lengths and optional fields are encoded in
the message body.

The codec and positional payload schema are not negotiated. Changes require
coordinated client and server updates, preserving configuration semantics such
as omitted overrides inheriting their common setting.

`EditTrack` carries optional title, artist, and album fields. `None` leaves a
field untouched; `Some("")` explicitly overrides it with empty text. The core
merges these field intents into the current track rather than replacing it
with a client snapshot.

The source of truth for exact schemas and adapters is
link:../src/ipc/protocol.rs[protocol.rs];
link:../src/ipc/tests.rs[protocol tests] cover compatibility and transport bounds.
