= IPC

== Core and client boundary

One core owns library storage, queue mutations, configuration, and playback
coordination for a data directory. Commands and queries are dispatched through
that core; frontends do not maintain independent authoritative playback or
library state. Audio output and analysis have their own workers, so client
transport and rendering are outside the audio callback.

The root Rust crate is an application library for its own executable, not a
stable embedding SDK. Storage transactions, mutable analysis publication, and
frontend implementation modules are crate-internal capabilities. External
clients use the command/query protocol rather than bypassing Core's validation
through direct storage commits.

=== Ordered collections and transaction ownership

Queue and playlist positions remain contiguous and zero-based. Deletion captures
only removed positions before changing rows, then closes gaps in ascending,
disjoint original-position intervals within the same transaction. Gap compaction
updates each affected survivor at most once and leaves the preceding prefix alone;
tail deletion requires no position updates. Library deletion applies this to its
queue references and separately to each affected playlist. Temporary position
storage scales with removed references, not the full surviving collections.
Compaction executes one SQL update per contiguous run of deleted positions; the
final suffix update may affect zero rows. Bounded-interval updates reuse a prepared
statement, and these local executions do not add client IPC round trips.

Queue and playlist moves share one interval displacement algorithm for single
entries and selections. Only the span covering the selection and its destination
is updated, and each entry whose position changes is written once. Selected IDs
and original positions are captured before mutation; queue moves use the core's
existing ID order rather than loading it again. Explicit arbitrary reorders, such
as shuffle, retain a separate order-writing operation that skips unchanged rows.
Entry identities and the current occurrence remain stable, and no-op moves leave
queue content valid.

Deletion compaction, selection movement, and arbitrary order replacement remain
distinct operations. They share position ownership and scoped storage primitives,
not a generic list controller: business operations retain validation, transaction
ownership, playback state, and revision publication. Selection movement favors
ordinary small selections over uncommon dense scattered selections: interval SQL
avoids materializing survivor mappings and requires no size/density thresholds or
single-entry strategy branch. Its accepted cost is more local SQL executions for
many scattered selected runs; necessary position writes still scale with the
affected span. Arbitrary permutations keep a separate order writer rather than
being decomposed into repeated moves.
Structural queue mutations advance the content revision once inside their changing
Store transaction, including reference deletion and gap compaction. Metadata
invalidation remains field-sensitive; failures roll back structural revision and
content together. Already-unique deduplication leaves content and projections valid.

=== Library root identity and configuration

Configured library roots are logical paths, not filesystem object identities.
Relative paths are resolved against the host's working directory; normalization
removes `.` and collapses `..` lexically without resolving symlinks or requiring
the path to exist. Distinct logical aliases may therefore refer to the same
physical directory and still identify different library paths.

Configuration validation rejects equal roots and ancestor/descendant pairs after
normalization, using path-component boundaries rather than string prefixes.
`/Music` and `/Music/Jazz` conflict; `/Music` and `/Music2` do not. This invariant
applies to loading, saving, and command-driven configuration changes. A rejected
change does not replace the persisted or published root list; overlapping
configurations require correction rather than automatic merging or deletion.
Adding an already-configured root through the desktop remains an idempotent no-op.

Root configuration remains owned by the configuration file, not by a database
membership table. Removing a root changes only configuration: it does not delete
tracks, user metadata, playlist or queue entries, or files. Track deletion is a
separate library operation. Low-level path queries may accept overlapping ranges;
that query capability does not permit overlapping configured roots.

=== Scanning and metadata ownership

Scan-backed metadata and user overrides skip writes when their stored values are
unchanged. Setting an override equal to its raw value still records that editing
intent; an omitted field continues to follow rescanned metadata. No-op edits
succeed for existing tracks and still reject unknown IDs. Queue-content validity
is described in <<_revisions_and_watching,Revisions and watching>>.
The new-track minimum-duration policy is captured from configuration when a scan
or playlist import starts. Merge applies it only after exact-identity and
relocation matching; it does not filter previously stored identities. See
link:02_library.adoc#_minimum_duration_for_new_tracks[Library] for admission rules.

Raw metadata reuse also requires the stored probe version to match the current
probe version (`1`). This cache-validity marker is independent of the database
schema and IPC protocol. A mismatch requires a fresh probe during scanning but
does not invalidate the cached file fingerprint.

Scanning requests cached raw source metadata on demand through task-ID-tagged
Core events carrying at most 32 admitted source paths; it does not copy a
whole-library known-file snapshot at startup. Each indexed exact-path query decodes
at most one matching identity, preferring an ordinary file over CUE segments.
Core checks task identity and cancellation before servicing the bounded batch.
Only unchanged ordinary identities authorize full-source probe reuse; unchanged
CUE identities may still supply fingerprints. New or retargeted CUE sheets can
request sources outside the scanned subtree, within configured roots. Up to 32
sheets are prepared together, and shared sources reuse one result or error per scan.
Force scans bypass these lookups. The owner round trip and short-lived reply
channel are per batch, while indexed database reads remain per distinct encountered
source, never per unrelated library row. For an audio-only request with 64 admitted
sources, this is two owner round trips/reply channels instead of 64; partially
filled batches and CUE groups retain their own bounded requests. No blocking-pool
slot waits for Core, and at most 32 source descriptors are retained across a lookup.
This trades bounded descriptor/batch storage for fewer owner transfers, not a
second database owner or a stale state snapshot. Cancellation wakes async lookup
submission and reply waits without polling. Stale task IDs cannot obtain metadata
or commit results for a replacement scan.

Scan merging checks each eligible old CUE sheet's absence once per merge and
indexes relocation candidates by fingerprint, segment number and frame bounds.
Multiple compatible old identities remain ambiguous; exact identities still take
precedence. These indexes are merge-local, not persistent source-probe caches;
only `NotFound` permits relocation, and scan uncertainty protection is unchanged.
Incomplete scans skip global fingerprint candidates because both relocation and
missing detection are disabled; exact input identities remain covered by the
requested scopes and record paths. Fingerprint validation still runs before
commit, and complete scans retain scope-external missing-source discovery.

=== Transactional inputs and bounded storage queries

Track-ID mutations serialize each input list once. Library deletion validates
before playback-side effects, then consumes the prepared input in the same
serialized core dispatch. Stopping playback can update statistics, not catalog
identities; reference deletion and gap compaction remain transactional.
The audio stop acknowledgement supplies its final position and confirmed heard
time independently of lifecycle-event delivery. Event-channel backpressure does
not delay that snapshot, and later events cannot account for the same heard time twice.
Count-only pages omit row projection; queue and playlist totals do not join
track metadata. Equivalent normalized root prefixes are counted once per request,
then expanded to the original paths and order. Root aggregation state is
request-local and bounded by the 256-root query limit.
Library track/display pages retain only the latest exact filtered total, keyed
by normalized query, favorite/missing predicates and optional root prefix. Local
SQLite change counts and external-commit data versions invalidate that slot;
explicit transactions neither use nor populate it, preventing rollback leakage.
No row payloads or multi-query map are retained. Unfiltered root counts use the
covering path index. Directory child aggregation remains request-local; offset
pages still pay the traversal cost of skipping preceding matches.
Unfiltered queue and playlist entry pages seek by their contiguous position rather
than skipping an OFFSET prefix. Unfiltered playlist entry totals use the indexed
maximum position; this relies on the Store-owned contiguous-order invariant.
Filtered pages count and skip matching rows in the database before projecting the
requested page; title, artist, album, and file-name filters require track metadata.
Sequential filtered queue and playlist batches instead carry the next matching
offset alongside the original occurrence keyset and a fixed-size scope digest.
The scope binds normalized search text, queue/playlist identity and the current
query-owned revision stamp. Core supplies that stamp in its serialized dispatch;
Store rejects mismatched scopes before reading rows, including continuations
submitted without `expected`. Each batch seeks after the original position/id
and advances rank by returned row count; it never recounts the matching prefix.
One extra matching row decides whether to return a continuation. A lookahead can
read the intervening nonmatching gap again on the next batch, but a stable full
traversal visits each searched interval at most twice rather than recounting all
preceding prefixes. Each batch also pays an indexed keyset seek. No full-list
cache, per-client map or retained SQLite snapshot is introduced. Random-access
filtered pages keep their independent exact count/OFFSET path.

Playlist export runs as one Core-owned background worker with its own read-only
SQLite connection and one consistent snapshot, established by validating the
playlist once before output I/O. It reads only export fields in playlist order
with bounded keyset batches, without per-track queries or the interactive track
cache. Each batch retains at most 256 decoded rows. Concurrent edits do not mix
versions in the output; missing references fail rather than disappear.
The writer validates CUE runs across batches and atomically replaces the target
only after complete output and a final cancellation check. Shutdown requests
cooperative cancellation and joins the actual worker. A response timeout neither
cancels export nor frees its single-flight slot. The snapshot can retain WAL pages
until the worker exits; database optimization cannot run concurrently with it.

Scan preparation remains independently cancellable. Core authorizes Saving only
after any accepted relocation has retired; Saving runs queue-position persistence,
the atomic scan merge, playlist creation and expensive count/history projections
on a worker-owned connection. Saving is the cancellation cutoff, not a claim that a commit has
already succeeded. For playlist imports, Core reserves a content revision and
shares the latest revision-map snapshot when Saving begins; the worker copies
and extends that map only after playlist creation succeeds. Completion returns
confirmed commit facts and prepared projections, including the revision map;
Core installs it, invalidates its caches and publishes revisions before reads resume.
Shutdown drains a Saving completion rather than falsely recording cancellation.

Database optimization also has one physical worker and keeps the original reply
until completion. During Saving or optimization, database commands and queries
are rejected promptly instead of waiting on the maintenance connection. Task
status and published state remain readable; volume, seek, pause/resume of existing
playback, stop and cancellation requests remain serviceable. Playback accounting
coalesces in one active or retired record; EOF navigation waits for maintenance
and retains later pause/stop intent. Failed retired-record persistence does not
gate independent controls. Deferred writes must settle before a new playback
can replace a retired record, or deletion, relocation or scan saving can remove
its track identity. There is no automatic replay of user mutations.

Queue mutations persist their own transactions. Playback selection persists the
current occurrence; unrelated controls do not rewrite queue metadata, and Toggle
dispatches its selected pause/resume operation only once.
Shutdown acknowledges acceptance before stopping playback; stop or final-save
failures remain published errors rather than rejecting an already accepted exit.

Directory and root queries use BINARY path ranges: a normalized nonempty prefix
ends in `/`, and replacing that delimiter with `0` gives its exclusive upper
bound. These ranges preserve literal characters, case, Unicode, and component
boundaries. A full path index includes ordinary files and CUE segments alongside
the separate identity constraints. It avoids full table scans per distinct root,
at the cost of index storage and maintenance during library writes.
Directory pages derive narrow child identities once within a single SQL statement,
materializing them for both the exact total and ordered page selection. Full track
payload is joined only for selected track children, not directory representatives
or rows preceding the page. This trades a request-local temporary child relation
for avoiding repeated source derivation; its size follows the matching children,
not the requested page limit. Count-only requests instead use a direct count
without materializing children or building the page. Empty and out-of-range pages
still return the exact total.

Album pages read persistent SQLite summaries keyed by directory and exact effective
album title, rather than regrouping tracks for every count and page. Only effective
titles containing a non-whitespace character participate (Rust `str::trim`
semantics); an explicit override wins even when empty. Unicode whitespace is used
only to test eligibility, never to normalize keys. Member artist reference counts
preserve search across compilation artists. SQLite triggers maintain both summaries
in the same transaction as track changes, including rollback and writes from another
connection; unchanged effective grouping and artist values require no summary update.
When only the effective artist changes within the same eligible album, triggers
transfer artist reference counts and refresh the final summary artist once; the
album row and its member count remain intact. Directory or album-title changes
still remove the old membership and add the new one.
Each changed member uses indexed counter operations, not a scan of the album.
An ordered member index selects representatives by disc, track number, effective
title, then ID. This trades summary and index storage plus write maintenance for
cheaper reads. Only schema version 1 is supported; other versions and unversioned
databases are rejected without migration, reset, or deletion. A fresh database
creates the album summaries and triggers directly.
Exact substring searches and OFFSET traversal still scale with matching album
and artist summaries, not merely the requested page size.

Playlist deletion-reference lookup has an additional index on
`(track_id,playlist_id)`. It avoids scanning unrelated playlist entries for sparse
library deletions. Position is deliberately excluded: capturing removed positions
needs table lookups, but moving or compacting entries does not rewrite the reverse
index in addition to the ordering index. Dense capture alone can be slower; the
choice reduces storage and favors complete deletion/compaction and movement.

=== Consumer and application lifetimes

The GUI, tray, and MPRIS service use `CoreHandle` for business commands and
purpose-specific projections. Opening a window and quitting the application use
the separate App-owned control endpoint. CLI and TUI clients use the local IPC
socket; its dispatcher separates application requests from core commands and
queries while preserving the wire format. Shared analysis and waveform data
are in-process resources, not IPC state sections.

Ordinary-file relocation uses a Core-owned single-flight verification worker.
Acceptance carries `Ack.relocation_id`; final completion or failure is reported
by `RelocationTask` and system task status. Core retains 32 results and joins the
worker on shutdown. A verified open descriptor survives to the commit boundary;
file identity, source absence and affected playback are checked again before
Store atomically revalidates identities and destination conflicts. UI request
epochs discard results belonging to closed or superseded reviews.

The graphical host has three lifetime boundaries within one process:

* `App` in `app.rs` owns the core runtime, IPC server and socket acquisition,
  shutdown signals, shared artwork, logging session, optional tray, and
  open/focus/quit coordination. It holds the MPRIS manager; the MPRIS module owns
  enable transitions, registration cancellation, publisher startup, and service
  teardown. Its GPUI event loop remains available when no window exists.
* The core owns accepted business operations and authoritative state. Closing a
  window does not cancel playback, scans, saves, or other accepted commands.
  Explicit relocation review is an exception: dismissing its dialog requests
  cancellation of that dialog's verification task, without undoing a commit.
* `UiSession` owns window creation, focus, reload, and close. `GuiApp` owns the
  window's view state, subscriptions, and render resources. Reopening creates a
  new view from current core state; repeated open requests focus the existing
  window. Closing releases window demand and subscriptions, not application
  services. Background results use weak UI references and may finish without
  delivering to a closed view.

Window-opening requests coalesce at the App endpoint and remain pending until
the graphical host is ready. Core completion explicitly notifies App, including
completion before GUI registration and core panic; it does not reuse a window
opener callback. Shutdown uses a bounded lifecycle signal independent of the
business queue. IPC shutdown acknowledgements are drained before transport and
socket retirement, and service joins occur outside GPUI quit callbacks.

Core waits for events and applies state transitions on one persistent dedicated
thread. Bounded Tokio channels carry requests, audio facts, processing, scan and
relocation events; one-shot channels carry export and optimization completion.
The owner polls one `select!` event per turn with randomized selection, using the
shared Tokio reactor for I/O and timers. IPC directly awaits Core's bounded
request/reply path; revision watching observes authoritative publication.

Synchronous SQLite access and its corresponding business-state transition stay
atomic on that owner. This keeps database work off the shared I/O driver and out
of the file/probe blocking pool; it does not make SQLite natively asynchronous.
Independent async tasks coordinate bounded synchronous file stages, probes and
database transactions on a shared four-thread blocking pool. Waiting for Core
does not retain a file-work pool slot. App retains the shared runtime until Core
and IPC connections have retired; shutdown joins run outside GUI callbacks.
Core unwinds and retires its resources on its dedicated thread before publishing
lifecycle completion. Started background work is joined before resource
retirement; cancelling a waiter is not completion or rollback.

Processing shutdown signals cancellation and closes bounded event admission before
joining its worker. Closing admission wakes blocked progress/result senders; after
the join, draining buffered events destroys unpublished outputs. Retained audition
results remain owned by the processing service until its own final retirement.

Manual relocation verification admits its regular-file descriptor and metadata
together, then hashes in at most 4 MiB blocking stages using one reusable
128 KiB buffer. Cancellation is checked between reads; every started stage is
awaited before releasing admission. The descriptor and path are revalidated
before accepting the hash and again at the existing commit boundary.

Audio's real-time callback and dedicated decoding/output worker remain
synchronous. Their non-real-time event boundary uses a bounded Tokio channel.
Stop/snapshot temporarily owns that channel's sole receiver, drains facts while
awaiting command capacity and the one-shot reply, and retains one absolute
deadline. No second receiver or automatic stop replay is introduced.

Core owns a 100 ms FFmpeg status poll only while the enabled decoder status is
`not loaded`. It observes the nonblocking one-time load result, including loads
initiated by GUI waveform work outside the audio engine; status checks never
start or wait for a load. Unrelated requests retain the same pending timer.
Disabling FFmpeg or publishing its success/failure result drops the timer;
configuration changes re-evaluate demand before Core waits again. Disabled,
resolved, and native-only builds retain no FFmpeg status polling wakeups.

The MPRIS module's media manager owns registration and the resulting publisher;
App retains and joins the manager. Each enable attempt uses one temporary
registration worker; the manager remains responsive to core changes and shutdown.
Disabling or stopping cancels the asynchronous bus build and joins that worker
before retiring the attempt. A completed connection starts publishing only if
MPRIS is still enabled and the core is not shutting down. Failed attempts wait
for a later off/on transition, not a retry timer; registration never blocks the
first window. Initially disabled controls publish the disabled status too.

Publisher status is ordered by the publisher itself, so an immediate failure
cannot be overwritten by the manager's startup success. Retirement cancels
pending signal writes and joins the publisher. It removes the Root and Player
interfaces to stop new MPRIS calls, waits up to one second for their active reply
guards (including an accepted Quit acknowledgement), then explicitly closes the
connection with a separate one-second deadline. A peer cannot retain the manager
indefinitely by keeping a method call or connection reference alive. Cold artwork
loads remain synchronous on the publisher and must finish before that join.

MPRIS metadata follows the selected track's immutable snapshot as well as its
queue occurrence, selection validity and playback duration. A scan that changes
only its path or content identity can invalidate metadata without changing the
queue's row revision. The publisher compares exposed metadata values before
sending a change signal; ordinary audio-clock updates and unrelated queue
revisions do not rebuild it.

The same App owns the headless `serve` instance. The process logging subscriber
is installed once; file-writer lifetime belongs to App, while Core receives only
a configuration control handle. Logging prepares a candidate writer before
configuration persistence and commits its route only after a successful save.
App retires core, media, IPC, and signal producers before flushing file output,
outside GPUI callbacks and writer locks. Standalone Core runtimes do not install
a process subscriber. A TUI is a separate IPC client, not another host runtime.

These boundaries do not introduce internal IPC or require destroying and
reinitializing GPUI. Framework-global resources remain resident; no headless
memory equivalence is promised. Desktop controls and window operations are
described in link:04_playback.adoc#_desktop_tray_and_window_lifecycle[Playback].

=== Projection and view costs

Projections expose what a consumer needs without copying the whole library on
each playback update. Library rows are queried separately; state reads contain
summary information, compact queue state, playback, and system state. In-process
projections can share immutable data, whereas socket responses serialize it.
This avoids a second control implementation without making every consumer pay
for a universal snapshot.

Queue displays resolve metadata from bounded queue queries captured with their
content revision; unrelated library pages cannot substitute stale values. GUI history retains one
sorting index for the current immutable history and sort choice, rebuilding it
on source or sort changes rather than during painting. Tree selection locations
are updated when selection or accepted pages change, not on each viewport demand.
Page acceptance indexes borrowed row identities once, then revalidates retained
selection locations with keyed lookups rather than rescanning the page per
selection. Expected work is linear in page rows plus retained selections; the
temporary index is bounded by the accepted page and copies no directory paths.
Viewport page demand locates its first intersecting preorder segment by binary
search, then visits only intersecting segments and any stale ancestors that need
revalidation; offscreen retained expansions do not require a full segment scan.
The TUI builds queue widgets only for visible rows, retaining global occurrence
selection and scroll position; position-only updates do not rescan the queue.
Configured TUI roots reuse their immutable storage until the paths change.

The tray starts a background owner without waiting for session-bus setup or
watcher registration. Its worker subscribes after establishing the published
baseline, before bus setup, then reconciles the latest state independently of
registration replies. Menu layout and revision are read together from that
publication; unchanged menus retain their revision. Shutdown cancels bus setup,
signal publication, and pending watcher registration. Connection close has a
bounded deadline rather than waiting for bus replies or outstanding peer calls.

Startup and single-instance operation are documented in
link:../readme.adoc[README]. Socket clients and the core must use compatible builds.

== Transport and frame format

IPC uses a Unix domain socket. Each frame contains:

[source,text]
----
u32 body_length       # little-endian
u8  protocol_version
u8  message_type
body
----

The frame header is six bytes. `body_length` excludes the four-byte length field
and includes the version, message type, and serialized body.

Bodies use Postcard serialization without COBS framing. The current protocol
version is `6`; clients and servers must use matching wire schemas. The four-byte
frame length remains little-endian; body integers follow Postcard's encoding.
Restart clients and hosts together after upgrading: incompatible versions are
rejected before decoding the body. There is no compatibility alias or schema
negotiation. See <<_wire_schemas,Wire schemas>> for positional fields and adapters.

Request frame content is limited to 4 MiB
and response frame content to 16 MiB, including the version and message type but
excluding the length prefix. The server accepts at most 16 concurrent clients;
additional connections receive `IPC server is busy` and close. An unbound client
has one second to complete each incoming frame while waiting for Hello. After
binding, each request frame must complete within five seconds of its first byte;
additional bytes and revision updates do not restart that deadline. Incomplete
frames close the connection and release its session slot. Normal idle sessions
and Watch waits have no inactivity expiry.

Frame limits bound encoded bytes, not decoded heap usage. Decoding must reject
malicious lengths without disproportionate allocation or work; changes to the
Wire schema must preserve that resource bound.

An oversized frame prefix closes the connection before its body is consumed.
Invalid headers, unknown message types, incompatible versions, malformed
Postcard payloads, and trailing payload bytes within the frame limit receive an
Error response and close that connection; other client sessions remain usable.

IPC uses one Linux abstract Unix stream socket for both communication and
exclusive data-directory ownership. No `rivu.sock` or `rivu.sock.lock` file is
created. The abstract name is the five bytes `rivu.` followed by the directory's
device number and inode number, each encoded as an eight-byte big-endian integer.
The leading abstract-namespace NUL is not part of that name. Following directory
symlinks and using filesystem identity makes relative paths, symlinks, and bind
mount aliases reach the same instance; distinct directories have independent
addresses. The data directory must remain in place for the instance lifetime.

Abstract sockets have no filesystem permissions. Both endpoints read kernel
`SO_PEERCRED` credentials and reject a peer whose UID differs from their effective
UID, before exchanging protocol frames. The server checks credentials before
admitting a client to its bounded session set. This protects commands and state,
not availability: another user can occupy the public abstract name and prevent
startup, but cannot impersonate the server to a client.

Before opening the database, saving configuration, or starting audio workers,
startup creates the data directory if necessary and binds the real listener.
Only a successful bind grants instance ownership. App retains its listening
descriptor through runtime and IPC teardown, including partial startup failures;
the serving worker holds a clone. The kernel releases the address after the last
listening descriptor closes, including on process death. No stale-file recovery
or pathname cleanup is needed.

Ownership is scoped to a Linux network namespace. Instances in different network
namespaces must not share a data directory.

The transport retains partial input across cancelled reads and keeps frames
independent. Sessions process requests serially; frames have no request IDs or
multiplexed response matching.

Sessions reuse encoding buffers up to 256 KiB capacity. Larger send buffers are
released after the write and flush, before an idle request or Watch wait; repeated
bulk transfers therefore allocate again. Large encodings grow with at most 64 KiB
requested spare capacity rather than doubling, capped at the frame boundary.
Client responses decode directly from the receive buffer without splitting or
copying the payload. Once decoding finishes and no pending frame bytes remain,
backing allocations above 256 KiB are released, including growth caused by several
individually smaller frames. Disconnects discard partial input and release
oversized client buffers. These bounds concern framing
storage, not decoded response objects or allocator-resident pages; releasing a
buffer does not guarantee an immediate RSS decrease.

== Session handshake

A client session starts unbound and must send Hello before State, Query, Command,
or Watch. Hello can request initial state sections, including none. A non-Hello
request before binding or a second Hello receives Error, but does not close the
session. The first successful Hello binds it.

The Hello response contains a random nonzero `u32` instance ID encoded as four
little-endian bytes. The ID is generated once per server start. Zero is reserved
as the invalid instance ID. IDs are equality tokens for detecting server
identity changes; they are not ordered identifiers, authentication credentials,
or globally unique identifiers.

The TUI keeps separate command, query, and Watch sessions on its existing
workers. Each worker reuses its runtime, connection, and framing buffers;
Watch never blocks command or query traffic. Replacing a query discards its
result but drains the active exchange before sending only the latest pending
query. Exiting the TUI closes an in-flight socket wait, including command and
handshake waits, without waiting for a response.
The Watch worker's first Hello requests all state sections and supplies the
initial TUI snapshot and instance identity. Command and query sessions must bind
to that same Hello instance before issuing requests. Until the snapshot arrives,
the screen stays in a loading state that accepts `q`; no separate foreground
state request is made. Command and query sessions can reconnect only to the
same pinned instance; the Watch worker does not automatically reconnect. A
changed instance is fatal, without replaying queued commands against a
replacement server. Fatal connection, handshake, and instance-identity failures
restore the terminal before returning the error.

== Message types

Request types:

* `Hello` — initialize a session and optionally read selected state sections
* `State` — read selected state sections
* `Query` — execute a read-only query
* `Command` — execute a state-changing command
* `Watch` — wait for a revision change

Response types:

* `Hello` — returns the server instance ID and selected state
* `State` — returns selected state sections
* `Query` — returns query revisions and the query result
* `Ack` — returns command outcome, error, publication revision, and optional scan or relocation task ID
* `Watch` — returns changed state revisions
* `Error` — returns a protocol or request error



Wire enum variant and field order are part of the binary schema. Incompatible
schema changes require a new protocol version and coordinated client and host
updates; there is no obligation to preserve earlier schemas.
The current protocol version is `6`; hosts and clients must both use this version.

== Revisions and watching

State revisions are tracked independently for Playback, Queue, Library, and
System sections. They are equality tokens, not ordered clocks. A Watch request
waits until the current revisions differ from the expected revisions. The
response contains the latest revisions rather than an event log.

Clients initialize from a state read, watch for revision changes, then read only
the invalidated sections. State reads capture selected sections and all revision
tokens under one shared-state lock. Omitted sections preserve the client's
previous values; the client advances tokens only for sections actually read,
otherwise it could acknowledge an unseen change. Notifications coalesce to the
latest state. A server restart requires a fresh Hello and state read.

The Queue state section is constant-size: `{total, current_id, current_position,
revision}`. It never embeds all occurrence IDs or track metadata. Queue content
and queued display-metadata edits advance its content revision; changing only the
current occurrence updates the Queue state-section token without invalidating
content pages. Unrelated track edits advance Library only. Last-played activity
does not invalidate Queue unless a displayed field, such as play count, changes.
Reapplying identical metadata or favorites, including a forced scan that keeps
the same displayed values, does not advance the queue content revision.
Raw title, artist, or album changes hidden by overrides also leave queue content
valid when their effective display values are unchanged.
Scans reduce committed changes into effective-track, structure, duplicate-group,
and duplicate-member verification impacts. A size/mtime-only change to a
fingerprinted ordinary file advances member facts, not library, structure, or
playlist tokens. Raw metadata hidden by overrides and probe bookkeeping do not
invalidate effective-track pages. Scan status and requested playlist imports
still complete. Empty or existing-only playlist additions and same-position
moves preserve playlist query validity; missing identities still fail validation.
An explicit override equal to the displayed raw value can still change override
presence, which advances duplicate member facts without invalidating display rows.
Reapplying that stored override is a true no-op. This distinction preserves user
override ownership without treating bookkeeping as changed metadata.
Playlist creation and deletion advance duplicate member facts only when the created
or deleted collection has members. Empty collection lifecycles, rename, and reorder
do not advance those facts. Lifecycle publication uses the committed write's effect
or validated creation input, without an additional membership count read.

The Library section carries the summary catalog token `playlist_revision` and
`playlist_entry_revisions`, a playlist-ID-keyed map containing exactly the extant
playlists. Each value is a content/lifetime equality token issued independently
of the catalog. Creation registers a fresh token; deletion removes it. A missing
key means the playlist is unavailable, never a fallback to the catalog token.
Actual membership changes and reorders advance only the owning content token;
membership also changes summary counts. Rename changes only the summary token.
The issuer survives deletion, so an old scalar mutation token cannot become valid
again after another collection is created. Retention is bounded by extant
playlists, with no per-track version table or mutation event log.
Every scoped change advances the Library state-section token, so coalesced
watches receive current scoped validity, not just a GUI-local command hint.
Committed lifecycle and content tokens advance before the fallible summary
refresh, so a refresh error cannot make an obsolete mutation valid again.

Playback-statistics writes return count and activity time directly to the Core.
The bounded track cache and current/recent snapshots receive these scalar changes
without reloading complete metadata. Count threshold and activity timing remain
independent.

Watch has no fixed expiry. A complete new request on that connection supersedes
a pending Watch without a Watch response. The preserved input then becomes the
next request; disconnect or server shutdown terminates the wait.

== Query results and pagination

Query responses contain the requested projection and its data revisions, not a
full client state or queue snapshot. Rows and revisions are captured in the same
core dispatch. Publication sequence, four state-section tokens, query-data
tokens, and consumer request generations have distinct responsibilities.

`Query::stamp` is the sole query dependency contract for scheduling, projection
identity, result acceptance, and batch validation. Library pages use library
content; directory/album/location projections also use structure. A single
Track query uses `track = {track_id, revision}`. Root counts use structure only.
Playlist summaries use the summary catalog only; full entry rows use
`playlist_metadata = {playlist_id, revision}` plus their scoped content/lifetime
token. Unfiltered compact entry locations use only their content token; filtered
locations also use scoped metadata, with the same library fallback as full rows.
Queue queries use queue content and, while filtered, library content. Duplicate
groups use `duplicate_groups`; members use library, `duplicate_members`, and queue
content. Playlist reference changes advance member facts, while playlist names
and order do not.

Track and playlist metadata scopes share a bounded index of at most 256 entries.
Committed title/artist/album/favorite changes identify affected tracks and playlist
rows inside the write transaction. Decoder hints, playback statistics, and bitrate
changes affect Track details without invalidating playlist display rows. Unknown
bulk effects or index overflow conservatively invalidate all metadata scopes;
there is no whole-library track-to-playlist reverse cache. Missing targeted
metadata scopes use the global library token conservatively. A non-scoped
baseline can bootstrap an entry traversal only while its library token is current.
Core and GUI/TUI snapshots use one pure response-layer policy to select these
scopes. Playlist presence is authoritative: retained metadata cannot resurrect a
deleted collection's scope. If the retained metadata index does not match the
current library token, selection falls back to that library token rather than
reusing an unrelated scoped revision.

Entry pages/batches and scoped `PlaylistEntryLocations` (including empty results)
attach `revisions.playlist_entries = {playlist_id, revision}` when the collection
exists. Missing scoped collections attach no token and fail the query. Successful
standalone single-entry lookups attach the discovered scope; missing lookups have
none, so selection relocation uses the explicitly scoped locations query.
Consumer generations independently reject abandoned identity/intent submissions;
fresh data cannot authorize an obsolete operation. Acknowledgements carry outcome
and diagnostic information plus publication revision, never replacement state.

Playlist entry page and batch rows include effective duration, codec, and favorite
state alongside display metadata. Duration is optional and describes the CUE
segment for CUE tracks, not the entire source. Favorite changes advance library
content and the affected track/playlist metadata scopes, not playlist entry order.

Interactive pages return an exact filtered total and at most 256 rows; larger
limits are clamped, and `limit = 0` returns the count without rows. Offset pages
do not reserve a snapshot across requests. Cursor batches avoid the total-count
query and return a continuation only when more rows exist. They require a limit
from 1 through 256 and reject zero or larger values.

`QueuePage {query, offset, limit}` returns `Page<QueueRow>` in queue order. Each row
is `{id, track_id, position, offset, track}`: `position` identifies its original
zero-based occurrence order, while `offset` is its rank among query matches.
`QueueBatch {query, after, limit, expected}` uses a
`{cursor: {position,id}, offset, scope}` continuation. Its `offset` is the next
matching rank, never the SQL keyset position. Queue content validates unfiltered
batches; filtered batches additionally use library content per `Query::stamp`.
Playback-only selection changes do not interrupt traversal.
`QueueEntries {query, queue_ids}` resolves at most 256 occurrence IDs,
omits removed IDs, deduplicates repeated IDs, and returns rows in queue order.
The query response's `revisions.queue` is captured with the rows; clients discard
late results if the active queue-content revision no longer matches.

`PlaylistEntryLocations {playlist_id, query, entry_ids}` resolves at most 256 stable
entry IDs to compact `{id, playlist_id, track_id, position, offset, total}` records
in current playlist order, without projecting full track metadata. Repeated IDs are deduplicated;
missing IDs and IDs belonging to other playlists are omitted. Empty requests
return no rows, while a nonexistent playlist or oversized input returns a query
error. Split larger selections into bounded requests and discard completions when
the playlist, request generation, or captured revision baseline changes.

`RemovePlaylistEntries {playlist_id, entry_ids, expected_revision}` removes a
selection atomically and closes its position gaps. `MovePlaylistEntries
{playlist_id, entry_ids, before_entry_id, expected_revision}` moves the selected
entries together, preserving their original playlist order regardless of submitted
ID order; `before_entry_id = None` appends the group. The target is a stable entry
identity in the same playlist, not a row index. Moving onto a selected target or
requesting an already-current order is a no-op.

Playlist moves use the shared queue/playlist interval algorithm described above.
Only selected identities and positions are retained, without building a mapping
for surviving entries. Left shifts run in ascending original-position order and
right shifts in descending order; selected entries are then placed by identity.
Dense, scattered selections require many interval SQL updates; widely separated
selections can still require work proportional to the playlist length. No track
metadata is loaded for movement.

Both commands compare `expected_revision` with that playlist's current scalar
entry token at core dispatch, before storage mutation. A nonexistent playlist,
missing/foreign selected ID, missing/foreign move target, or stale token fails
without changing membership or positions. Duplicate selected IDs are applied
once. Empty selections still validate the playlist, revision, and move target;
valid empty selections and other no-ops do not advance revisions. Mutations are
SQL transactions retaining only selected identities and positions, not complete
playlist metadata or an all-entry vector. Actual group moves advance only their
playlist's scoped token; removal advances that token and summary counts, without
invalidating other collections. Existing single-entry commands retain their CLI
contracts. Bulk favorites use the atomic `SetFavorite {track_ids, favorite}` or `ToggleFavorite {track_ids}`
commands. Toggle reads and reverses each track's current favorite state in one
transaction; repeated track IDs toggle once, and any unknown ID rejects the
whole request without changes.

`EnqueueSources` expands directories and explicit track IDs directly in SQL with
no total queue cap. `CreatePlaylistFromQueue {name}` atomically saves the complete
queue as a playlist on the server, keeping each track's first occurrence order.
Explicit ID selections remain bounded by request-frame bytes, not total queue size.
The core retains only one private compact occurrence-ID vector (8 bytes per row,
about 1.53 MiB for 200,000 occurrences); client state frames remain constant-size.

Shuffle navigation retains at most 4096 successful occurrence starts for
Previous; it does not maintain a nonrepeating shuffle cycle.

Interactive playback changes use execution-time intent commands:
`AdjustVolume { delta }` adds a finite signed delta to the core's current volume
and clamps the result to 0..1; `CycleRepeat` cycles Off → All → One → Off;
`ToggleShuffle` flips the core's current setting. Queued commands are applied in
order rather than deriving absolute targets from a frontend's earlier snapshot.
`SeekRelative { queue_id, delta }` adds finite signed seconds to the core's current
position, bounded below by zero and by an explicit CUE end, not estimated metadata
duration. A different current occurrence or stopped playback makes it a no-op.
`SeekQueue { queue_id, seconds }` retains an absolute target bound to one occurrence;
interactive start/end seeks use it, with the end captured from that occurrence's
known duration. Neither command can seek a replacement occurrence of the same track.
CLI `Seek` and `Volume`, and MPRIS absolute properties, retain their absolute semantics.
Protocol version 4 changes acknowledgement and scan-result schemas and requires
coordinated host and client updates; there is no older-protocol compatibility path.

`DirectoryPage {path, query, favorite, missing, offset, limit}` returns immediate
directory children and tracks as `Page<DirectoryRow>`. Search, favorite, and missing
predicates compose and filter tracks before directory grouping, counting, and
paging; a descendant match keeps its ancestor directories visible. `favorite` and
`missing` are optional booleans: omitted means unrestricted, `true` selects set
rows, and `false` selects unset rows. GUI configured-root entries remain visible
independently of these filters. Directory page and range-selection consumers
discard results when the captured filters, view, request generation, or library
and structure revisions no longer match. Filtering display rows does not restrict
directory source expansion: dragging a directory still adds its complete contents.

`QueuePage`, `QueueBatch`, `QueueEntries`, `PlaylistSummaries`,
`PlaylistSummaryBatch`, `PlaylistEntries`, `PlaylistEntryBatch`,
`PlaylistEntryLocations`, and `AlbumTracks` accept an optional `query`.
Summary searches match playlist names; track searches match effective title,
artist, album, and file name. Filtering precedes count and pagination; an empty
query does not restrict membership. Query identity includes the filter so a
response from an older search cannot satisfy a different projection.
Queue and playlist entry rows retain their original absolute `position`; their
`offset` is the matching row's zero-based ordinal in the filtered view. Location
results likewise distinguish original position from filtered offset, and their
`total` counts matching entries. Commands continue to target stable occurrence
or entry identities, not filtered offsets.

`Albums { query, sort, offset, limit }` returns `Page<AlbumSummary>`;
`AlbumTracks { key, query, offset, limit }` returns `Page<LibraryRow>`. Both cap returned rows at 256 and
carry library-content revisions. Album identity is the exact effective album
title plus the immediate parent directory, without a trailing slash except `/`.
Empty or entirely Unicode-whitespace effective titles do not form albums, and
neither directory names nor placeholder titles are substituted. An explicit album
override takes precedence even when empty; nonblank titles remain byte-for-byte
unchanged. Missing artists do not prevent membership. Artist differences do not
split compilations; directories never merge, including disc subdirectories.
Blank or stale keys return empty member pages with total zero, following the
existing unavailable-album detail behavior. Tracks without an album remain
available through library, directory, queue, and playlist queries and track actions.

Album browsing searches effective album titles and effective member artists using
case-insensitive SQLite substring matching. An artist match includes the complete
album, including its nonmatching members. `query: null` and an empty query match
all albums. `sort` is `title` (default) or `artist`: title order uses title then
directory; artist order uses summary artist, title, then directory (binary ordering). Count and page
rows use the identical album-level filter. Browsing filters never restrict
whole-album playback or queue command membership.

Representative-track lookups, member pages and whole-album queue operations use
the ordered `tracks_album_members` index. Exact direct-parent directory and
effective album title select the member range, without scanning descendant paths.
Member-page totals and rows use separate count and ordered-selection queries;
album-summary counts do not regroup tracks. Resource and retention details are
documented in link:22_cache.adoc#_query_projection_retention[Query projection retention].

Members and the representative track use disc number, track number (each null
last), effective title, then track ID. Summary artist is the sole nonempty
effective artist, `Various artists` for multiple, or `Unknown artist` for none.

`PlayAlbum { key }` validates nonempty membership before stopping playback,
replaces the whole queue in member order, and starts its first track.
`EnqueueAlbum { key }` appends the entire album in that order, preserving current
playback. Blank or stale keys fail without changing the queue or playback. Both commands
resolve all current members in the backend independently of page limits; clients
must not collect paged track IDs to perform album actions.

`DuplicateGroups` pages ordinary-file groups by cached fingerprint and reports
present/missing counts. `DuplicateMembers {fingerprint, offset, limit}` returns
full track, size/mtime verification, override/independent, and playlist/queue
reference facts. `DuplicateMemberSelection {fingerprint, track_ids}` resolves at
most 256 selected member IDs to the same facts, omitting deleted, foreign-group,
and CUE identities and deduplicating repeats. This bounded lookup validates
off-page choices without scanning a group or treating cache eviction as deletion.
Fresh cached fingerprints are not a substitute for relocation's final source
and target identity/content verification.

`LibraryRootPage` returns the same display projection and filtered total as
`LibraryPage`, scoped recursively to one root. It preserves the library's search,
favorite/missing filters, and sort order. Root paths use the existing lexical
directory normalization and component boundary: `/home/a` never includes
`/home/ab`; `/` includes the whole absolute-path library.

`LibraryRootCounts` accepts up to 256 root paths and returns one `{path, total}`
per input, in input order, using a single batched query. Larger input batches
return a query error. Counts include all scanned tracks, including missing ones,
regardless of view filters; a root without scanned tracks returns zero. An empty
path requests the entire library. Overlapping query paths each count their own
subtree independently, even though configured roots must not overlap. Clients keep unavailable counts
distinct from zero, split larger root sets into bounded requests, and discard
results when their roots, request generation, or structure revision have changed.
Library-content-only changes do not invalidate these unfiltered root totals.
These requests run on the same core owner and revision boundary as other queries;
frontends must not query storage from rendering.

To traverse consistently, capture the first batch's query revisions and supply
them as `expected` on later requests. The same query-owned stamp validates
track batches (library), playlist-summary batches (catalog only), queue batches
(queue, plus library while filtered), and playlist-entry batches (scoped metadata
plus scoped content/lifetime, with the library fallback described above).
Queue and playlist-entry batches return `BatchContinuation` values. Pass the
complete previous `next` unchanged as `after`; do not construct one from a page's
filtered rank or substitute rank for its original position/id. A continuation's
scope is checked against the current normalized query, collection and selected
revisions even when `expected` is omitted. Stale or foreign continuations return
typed `QueryError::RevisionChanged`; restart with `after = None` and discard
partial traversal state. Changing only the batch limit does not change scope.
Renaming or changing another playlist cannot interrupt an entry traversal. A
catalog baseline without an entry token may start an entry traversal
(`after = None`) with unchanged library content, but cannot continue one. The CLI
retains its summary baseline while capturing each playlist's entry baseline
separately. Clients match the error variant, not diagnostic text. Other failures
return `QueryError::Message`. In-process demand cancellation can instead return
`QueryError::Cancelled` before dispatch; it does not interrupt SQL already running
or act as an IPC cancellation request. Without `expected`, track and summary
batches do not reserve consistency between requests; occurrence continuations
still enforce their embedded scope. All use bounded results and explicit restart,
not a database snapshot retained for an arbitrarily slow client.

Playlist-only edits leave library and structure tokens unchanged. Imports can
still invalidate track queries when their scan changes effective library facts.
If creation fails after a successful scan, those committed changes remain visible.

== Request failures and completion

Well-formed requests with invalid values, handshake-order errors, and server-side
dispatch failures receive Error without ending the session. Core query failures
instead appear in the Query result, and core command failures in an unsuccessful
Ack. Transport failure or an oversized response can end the connection without
a usable response.

Core request capacity is bounded to 64 queued operations. Requests waiting for
capacity or a result can fail as unavailable; UI fire-and-forget sends report
`Rivu is busy or stopped` rather than blocking. Core allows two seconds for queue
admission and twelve seconds for a reply, or 120 seconds for database optimization.
The operation interface owns that total waiting budget; IPC adds one second for
the server bridge rather than classifying commands again. Local ShowWindow and
Shutdown operations have a twelve-second budget without queue admission.
Each server response write, including Hello, Error, busy replies, and shutdown
acknowledgements, has a five-second completion deadline covering write and flush.
A stalled write closes that connection; it does not block teardown indefinitely.
Accepted operations still finish their replies during shutdown rather than
cancelling acknowledgements when shutdown starts.
Client response reads cover the operation budget, bridge allowance, response-write
deadline and one additional second for transport: 21 seconds for queries, state
reads (including Hello) and ordinary commands, 129 seconds for database optimization,
and 19 seconds for ShowWindow or Shutdown. Persistent and one-shot sessions use
the same policy. Watch still has no response deadline. These are waiting limits,
not guarantees on operation execution time or system scheduling.

Audio admission has a separate 64-command queue and 128 worker-event slots.
Ordinary audio admission never waits for capacity: a full queue returns an
unsuccessful acknowledgement explicitly stating that the command was not queued.
There is no automatic replay. Core can therefore keep draining critical lifecycle
events, whose worker-thread delivery retains backpressure; progress remains
best-effort. Configure checks capacity for its complete audio batch, and Still
Mode for its single command, before persisting or publishing the change. Device
request identity advances only after admission. A worker disconnect after settings
are saved retains the committed desired configuration and reports audio-application
failure. Ordered stop acknowledgement keeps draining events while waiting;
shutdown independently cancels blocked event delivery.

First-frame opening and playback refill share finite decode-work scheduling:
each opening round retains its decoder and packet progress and performs at most
64 work steps before returning to command handling. Stop, replacement Load and
shutdown retire the unfinished opening; other controls update its pending target.
An abandoned opening cannot publish Started or Failed for a later generation.
Container setup, seeking and individual decoder, file or device calls can still
block; these work bounds are not wall-clock deadlines.

`Ack.status` is `Succeeded`, `Failed`, `NotAdmitted`, or `Unknown`. `Succeeded`
means the owner returned success; scan/import/relocation startup still requires
its task's terminal result. `Failed` means the owner returned an error, not that
all effects were rolled back. `NotAdmitted` means no business request was admitted.
Once admitted, a missing response is `Unknown`: the operation may still execute.
Do not automatically repeat a mutation; inspect authoritative state or the output.
If startup timed out before its task ID arrived and reconciliation is unavailable,
keep the result unknown rather than guessing that no task started.

IPC command failures before handshake/encoding completes are `NotAdmitted`;
once writing the command has begun, exchange failures are conservatively `Unknown`.
The client exposes `CommandFailure` without inventing a Core revision or task ID.
Shutdown acknowledgement means accepted shutdown, not final persistence or worker
retirement. Blocking I/O and cooperative cancellation provide no hard exit deadline.

Failed exchanges discard the client connection. A later explicit request can
reconnect and perform a fresh Hello, but clients never automatically replay a
failed command.

Client session stopping shares one handle for the stop state and waiter wakeup.
Stopping is permanent and wakes all registered waits; a later wait also observes
the stopped state. TUI worker shutdown stops the session and discards its socket.
Replacing a query only invalidates its result: the active exchange still drains
before the latest queued query is sent.

Accepted scan and playlist-import commands return `Ack.scan_id` with their `u64`
task ID. Acceptance is not completion. The CLI polls `Query::ScanTask { id }`
and waits for that exact task's result: only `Completed` succeeds; `Failed` and
`Cancelled` report the task's error or message. Global scanning state and
`last_error` are presentation fields, not evidence that a particular task finished.
JSON completion output contains the task status rather than a global state snapshot.
Startup and waiting share one connection; disconnection fails the wait rather
than binding the same numeric task ID to a newly started instance.

`ViewResponse::ScanTask` contains `{id, progress, message, library_committed,
playlist_id, error}`. The phases are `Discovering`, `ReadingMetadata`, `Saving`,
`Completed`, `Failed`, and `Cancelled`; the last three are terminal. The core
retains the active task and latest 32 terminal results. Unknown/evicted IDs fail.
`library_committed=true` confirms the scan merge; `playlist_id` confirms the
subsequent playlist commit even if refresh failed. A failed task is not evidence
of zero side effects; after an uncertain worker failure, absent confirmation is
not proof that no commit happened. Retry only the missing step after inspection.
`CancelScan` requests cancellation before Saving and is rejected during Saving;
its Ack never proves worker retirement. Only the task terminal result resolves it.
A failed wait never automatically replays startup.

== Wire schemas

Runtime `Config` and `SystemState` use explicit positional Wire schemas. They are
not serialized directly because their in-process serde representation is not a
stable binary contract. Collection lengths and optional fields are encoded in
the message body.
Library information-column selection is encoded in WireConfig as five booleans
in Artist, Album, Duration, Codec, and Bitrate order; all false means no columns.

The codec and positional payload schema are not negotiated. Changes require
coordinated client and server updates, preserving configuration semantics such
as omitted overrides inheriting their common setting.

`EditTrack` carries optional title, artist, and album fields. `None` leaves a
field untouched; `Some("")` explicitly overrides it with empty text. The core
merges these field intents into the current track rather than replacing it
with a client snapshot.

The source of truth for exact schemas and adapters is
link:../src/ipc/protocol.rs[protocol.rs];
link:../src/ipc/tests.rs[protocol tests] cover compatibility and transport bounds.

== Audio processing commands

`EqualizerEdit { edit }` carries a field edit, preset operation or A/B swap;
`DenoiseEdit { patch }` and `NeuralEdit { patch }` merge specified fields into
current core configuration. Their boxed Rust patch storage does not add a JSON
wrapper: a patch remains an ordinary JSON object. For example, command values are
`{"DenoiseEdit":{"patch":{"mode":"adaptive","wet":0.8}}}` and
`{"NeuralEdit":{"patch":{"threads":4}}}`. Equalizer edits use externally tagged
variants, for example `{"EqualizerEdit":{"edit":{"Enabled":true}}}`. Send
these inside the ordinary Command request after Hello, not as a new protocol.
Unknown fields and invalid settings fail; omitted patch fields remain unchanged.
For neural manifests, explicit JSON `null` clears the selected manifest, whereas
an omitted manifest leaves it unchanged.

`StartProcessing { track_id, operation, profile }` accepts `denoise`, `speech` or
`separate`; profile is null or `{start_seconds,end_seconds}` in source-relative
seconds. Acceptance returns a processing task ID, not completed output.
`Query::ProcessingTask { id }` retrieves status; `CancelProcessing { id }`
invalidates the active task. `AuditionProcessing { id, mode, vocal_gain_db,
accompaniment_gain_db }` selects original/denoised/vocals/accompaniment/mix.
System state exposes the latest `processing` status. Use the exact task query
for completion rather than an unrelated latest-task field. Settings and model/
source identity are captured with the job; retained output availability is
session-bounded. See link:27_audio_processing.adoc[Audio processing] for CLI
equivalents, terminal states, provisioning, scratch and audition lifetime.

=== Immutable audio graph runs

`ProcessingGraphEdit { revision, edit }` compares the authoritative graph revision
before applying one typed edit. A stale revision rejects the entire edit. Node
removal disconnects its edges; it never guesses replacement routing. Positions do
not affect audio. Graphs allow at most 64 nodes and 128 typed, acyclic edges, with
one connection per input and explicit mix nodes for fan-in.
Generic `Configure` requests cannot replace this graph, including from a stale
settings snapshot; graph changes use the revision-checked edit command.

`ProcessingGraphRun { track_id, target: {node,port}, mode }` freezes the source and
graph revision. `auto` is the default: worker admission chooses the exact realtime
graph when supported, a useful hybrid suffix otherwise, and offline execution
when no useful supported suffix remains. Explicit modes reject unsupported plans
instead of changing algorithms. `settings.graph_mode` reports the actual selected
mode. All source probing, FIR design and FFT planning occur on the processing
worker, never Core dispatch or the device callback. Offline runs evaluate only
the target's ancestors and share fan-out PCM. Realtime runs become `complete`
when live-ready, without inventing cached files. A nonplaying selected source
opens paused/live-ready; a prepared result cannot replace newer playback intent.
Hybrid runs expose the actual offline prefix in `settings.graph_boundary`, then
play its exact realtime suffix; parallel heavy branches may move the boundary
through their downstream merge. `graph_plan` reports actual native-rate latency
and tail frames, plus admission state/work estimates, not a deadline guarantee.

`ProcessingGraphAudition { id, node: {node,port} }` selects retained PCM directly,
or queues a new preparation task using the frozen snapshot when that output has
no cache. `ProcessingGraphExport { id, node: {node,port}, path }` starts a distinct,
cancellable offline task using that same graph and original source. Existing
cached PCM is copied without re-decoding or running DSP again; an unrendered port
executes only its ancestor closure. Queued operations acknowledge the new task ID.
Destinations are
absolute paths to new WAV files; existing files are never overwritten. Only a
successful terminal task sets `graph_exported_path`: an accepted request is not
an exported file. Cancelled or stale-source tasks publish neither partial PCM nor
partial export files. `CancelProcessing` also stops the selected live audition,
but only while its run and playback generation still match.

`settings.graph`, `graph_target`, `graph_mode`, and `graph_revision` distinguish
captured run state from later edits. `graph_outputs` lists only real cached output
ports and paths (separation ports 0/1 are vocals/accompaniment). `graph_nodes`
reports per-node execution state and actual neural model IDs/SHA256 hashes.
Graph PCM caches are capped at 2 GiB per run and 4 GiB retained, with at most four
retained runs; native source rendering additionally has the RIFF 4 GiB scratch
limit. The selected audition stays pinned. Older status history is bounded to
32 tasks. Layout positions, revision counters and node-ID allocation history do
not affect `ProcessingGraph::audio_eq` or invalidate a frozen result.
