= GPU Measurement Archive (2026-10-18–2026-10-30)
:toc:
:toclevels: 2

These are historical experiments, not current performance guarantees. The dates
belong to the stated experiments; undated consumer and preparation comparisons
retain their original evidence limits rather than acquiring an inferred date.
Where no source commit is stated, the baseline is identified only by its described
implementation or compiled libraries, not a reproducible source revision.
Tables are not a cumulative speedup or a common benchmark series. No benchmark
or GUI rerun is implied by this archival move. Current contracts and the decision
index remain in link:25_gpu_rendering.adoc[GPU Rendering Design].

== Historical measurements

[[historical-vendor-measurement-method]]
=== Shared method for the 2026-10-18 vendor comparisons

The rectangle-only and unified field/path comparisons used Radeon 780M / RADV
Vulkan, Rust 1.99.0 and optimized release builds with thin LTO. Both used five
runs alternating baseline/candidate order, each retaining 20 frames after four
warmups. Steady-state times are microseconds: median of run medians, with the
minimum and maximum run median in brackets. Shared input generation is excluded
from CPU update; static replay requires no update. Workloads and baseline
identities remain specific to each experiment.

In those comparisons and the demand-specific preparation/batching probe,
render/readback includes CPU renderer preparation, submission, GPU completion,
copy-back and image assembly; it is not isolated GPU execution time. First-use
boundaries differ: the rectangle supplement includes construction and initial CPU
preparation, whereas renderer-first-draw observations and the demand-specific
probe exclude them. Their process/cache conditions are stated locally. These
conventions do not apply to the shared-MSAA encode/submit or application process
counter measurements.

[[capacity-neutral-regrouping-comparison-2026-10-30]]
=== Capacity-neutral regrouping comparison (2026-10-30)

Capacity-neutral regrouping was rejected. On Radeon 780M it benefited specific
sparse layouts but added a small measured cost to the ordinary mixed layout;
the gains did not justify the additional planning and composite bookkeeping.

[[shared-local-msaa-comparison-2026-10-23]]

Compared separate release binaries against commit `9b49886b60ce8955c243440b5ca0992118556605`
on Radeon 780M / RADV, Mesa 26.2.5. The baseline already has local Waveform
attachments; this comparison measures unifying the other multisampled materials
and ordinary GPUI Paths, not the earlier full-window-to-local Waveform change.

the following nominal attachment bytes. These describe renderer-owned capacity
in those runs, not physical VRAM or in-flight retired allocations. The later
capacity-slack and sustained-reclamation policy in

and image comparisons below.

Each warm/reference/measured submission completes before the next submission.
Measured frames match nonzero completed-reference attachment/pass counters for
their viewport. Completion waits are accumulated separately and are not GPU
execution timestamps. Earlier queued-submission profile results were invalid
because admission pressure omitted drawings; they are excluded.
Resize samples alternate viewport multipliers 1, 1.5, 0.625 and 1 and use the
same per-frame admission checks. No universal CPU speedup is claimed.

Real Rivu measurements used a 1280x800 nested niri window on Weston headless GL,
one minute of stereo 48kHz PCM16 media, muted output, and alternating baseline
and candidate order. Each version has three six-second samples per layout.
The table reports process-scoped DRM GFX engine busy percentage: median and
range across the three runs, not per-widget duration or GPU timestamps.

Mixed-layout engine occupancy improves in these workloads; Waveform-only
controls do not show a stable gain. CPU usage remains broadly similar and
process PSS does not show a consistent reduction. Paused samples record zero
process CPU and GFX counter deltas. The first run of each version/layout also
exercises compositor resize, surface close and CLI reopen; actual captures
were inspected. These checks do not cover host tray/IME integration or establish
cross-version pixel parity for unsynchronized live scenes.

The deterministic cross-binary capture matrix covers Unorm/sRGB,
integer/fractional origins, scales 1/1.5/2, opaque/transparent surfaces,
mixed/interleaved/overlapping content, replay, resize, hide/show, in-flight use
and alpha-pipeline rebuild. Every pixel passes the unchanged per-channel tolerance
of three. Exact native packed-alpha baseline probes also establish expected
sprite multiplicity. These results apply to that revision.

[[initial-comparative-measurements]]
=== Initial comparative measurements

This subsection describes the historical rectangle-only predecessor, not the
subsequently unified field/path renderer.

Measured on 2026-10-18 with the <<historical-vendor-measurement-method,shared vendor method>>.
The baseline was the then-current LED drawing kernel: append each cell to a
NonZero `PathBuilder`, tessellate, then render the textured path. Both paths ran
in the same executable with identical input and palette samples. This was not
an end-to-end player benchmark or a consumer cutover.

The workload uses 96 columns, a 1,024-sample Tokyo Night cubic palette and
3-pixel filled / 2-pixel empty segments. Single panels are 768 by 320 pixels;
four panels are each 768 by 160. Resize alternates heights 320 and 240.

[cols="2,2,2,2,2",options="header"]
|===
|Workload |Path CPU update |Instances CPU update |Path render + readback |Instances render + readback
|Static replay |No update |No update |640.51 [637.91–650.39] |227.82 [224.93–231.81]
|Continuous update |3,257.33 [3,245.21–3,266.90] |6.66 [6.65–6.68] |706.18 [699.49–721.07] |235.92 [233.15–241.96]
|Four panels, shared signal |6,698.95 [6,674.07–6,737.30] |6.70 [6.64–6.94] |1,356.77 [1,330.06–1,432.29] |309.53 [307.39–380.15]
|Resize |3,158.91 [3,142.97–3,173.37] |0.27 [0.25–0.31] |678.69 [664.00–682.63] |229.54 [229.45–235.06]
|===

The original renderer-first-draw observations exclude renderer construction and
initial CPU preparation, so they must not be read as complete first-use latency.

A supplemental run measures the full boundary symmetrically: five fresh processes
per path, alternating path order, with one renderer and one first image in each
process. It includes device/renderer construction, initial palette and geometry
preparation, scene recording, and first render/readback (including the candidate's
deferred pipeline creation). Common signal input and palette-sample generation are
excluded from both. Milliseconds below are median [minimum–maximum]:

[cols="2,2,2",options="header"]
|===
|First-use phase |Baseline LED Path |Instances
|Device/renderer construction |38.372 [37.241–39.534] |38.703 [37.206–38.924]
|Initial CPU preparation |4.002 [3.963–5.410] |0.0092 [0.0088–0.0109]
|First render and readback |4.473 [4.237–4.634] |2.741 [2.713–2.862]
|Complete first image |47.285 [45.966–47.987] |41.446 [39.956–41.714]
|===

Phase medians need not sum to the directly measured total. Fresh processes prevent
headless-device reuse, but the driver shader cache was not cleared: these are not
cold-driver-cache timings. The supplement does not replace the original
steady-state samples.

At the initial single-panel state, the baseline expands 3,308 cells into 19,848
CPU vertices. Tested record strides imply 2,858,128 bytes of path vertices and
sprites submitted per redraw, versus 19,536 bytes for a new rectangle publication
plus its placement, or 80 placement bytes for a static replay. The old palette's
4,096-byte initial atlas upload and common globals are separate. These are derived
payload counts, not measured bus traffic or physical allocation sizes.

Three independent processes per path, each running all four workloads, reported
peak process RSS medians of 86.48 MiB [86.05–87.43] for Path and
72.20 MiB [72.15–72.44] for instances (`wait4` maximum RSS). This is not isolated
VRAM accounting. The matched 768-by-320 output had maximum channel difference
1/255 and mean absolute channel difference 0.046/255. At that rectangle-only
stage, application animation, other visualizers, isolated GPU execution time and
GPU memory were not measured. The later consumer measurements below have their
own workloads and identities; neither set establishes total player CPU usage or
frame rate for the current revision.

[[unified-field-and-path-measurements]]
=== Unified field and path measurements

Measured on 2026-10-18 with the <<historical-vendor-measurement-method,shared vendor method>>.
Fields compare retained BGRA8 coloring/image drawing against fixed color-first
numerical drawing. The source is 256 by 256 with a 256-sample
palette and 70 dB logarithmic mapping. Outputs are 256 pixels square for native
replay, 1,024 for static enlargement, 768 for continuous updates, and four 512-pixel
panels sharing one publication. Resize alternates 768 and 576 pixels. Paths compare
the same 1,024-point, 2-pixel stroke at 768 by 320 through the existing textured
path and the new palette material; geometry generation is excluded from both.


[cols="2,2,2,2,2",options="header"]
|===
|Workload |Baseline CPU update |Material CPU update |Baseline render + readback |Material render + readback
|Field, native static |No update |No update |146.89 [142.82–151.21] |157.33 [154.28–190.41]
|Field, 4x static enlargement |No update |No update |565.78 [558.97–571.86] |670.89 [670.71–681.19]
|Field, continuous update |528.88 [528.03–532.66] |4.77 [4.67–4.90] |444.81 [438.90–479.38] |505.01 [500.14–549.93]
|Field, four shared-data panels |528.40 [527.29–538.30] |5.13 [5.11–5.32] |636.29 [601.46–653.52] |738.41 [719.01–772.00]
|Field, resize |0.29 [0.27–0.29] |0.34 [0.32–0.41] |321.38 [316.67–364.96] |379.46 [369.89–421.48]
|Path, static replay |No update |No update |378.39 [373.86–389.33] |310.60 [301.90–317.39]
|Path, changing geometry |3.79 [3.76–4.18] |4.35 [4.34–4.37] |405.66 [400.07–577.22] |355.90 [355.18–356.74]
|===

CPU field recoloring was removed, but static enlargement and resize render/readback
were slower. These costs informed the later consumer migrations; the measurements
do not justify a second sampling mode or an unmeasured color cache.
Both field representations upload 262,144 bytes per changed source. The new
256-sample palette adds 4,096 shared bytes, and each placement encodes 112 bytes.
These are payload counts at that revision, not bus traffic, current record strides
or physical VRAM measurements. Path intermediate/MSAA textures were outside the
extension's buffer-only budget, as shared scratch attachments remain today.

Matched field outputs differ by at most 1/255 per channel. The path comparison
has maximum difference 7/255, mean absolute difference 0.00338/255, with 58 of
245,760 pixels exceeding 3/255. That continuous palette material was not
bit-identical to BGRA texture sampling, so the vendor-only comparison did not
establish acceptance for subsequently migrated application palettes. No
application visualizer changed in this historical vendor slice.

In-process first-use observations do not reset device or driver caches and are
not cold-start results.


[[demand-specific-preparation-and-path-batching]]
=== Demand-specific preparation and path batching

A separate comparison uses the pre-review compiled libraries as its baseline and
identical probe source/compiler flags against the corrected libraries. It covers
rectangle-first, field-first and path-first rendering, plus 32 disjoint 56-pixel
path placements on a 512-by-256 target. Five fresh processes per workload/revision
alternate baseline/candidate order. The driver cache is not cleared. Replay records
20 frames after four warmups. Milliseconds below are median [minimum–maximum] of
first-render samples or per-process replay medians:

[cols="2,2,2",options="header"]
|===
|Workload |Before |Demand-local pipelines / safe path batches
|Rectangle first render |3.023 [2.938–3.894] |2.852 [2.797–3.425]
|Field first render |3.191 [3.096–3.615] |2.957 [2.920–3.256]
|Path first render |3.194 [3.146–3.356] |3.081 [2.918–3.814]
|32 disjoint paths, replay |2.652 [2.517–2.807] |0.570 [0.563–0.589]
|===

These render/readback values exclude device/renderer construction and initial CPU
preparation. Timing ranges overlap for individual first draws; removing an
unused pipeline does not establish a universal complete-startup speedup. The
multi-path replay improvement applies to the stated integer-aligned, disjoint
workload. Conservative union checks may split additional batches; fractional and
overlapping placements retain the individual route.

All four probe outputs match the pre-review images byte-for-byte. Regression
comparisons against individually resolved paths also require exact raw-image
equality, including clipping, fractional placement, MSAA overlap and interleaving.
A separate allocation smoke rejected a 262,144-byte field update with a largest
allocation of 72 bytes during rejection, retaining the previous publication;
validation-error allocation is not field payload copying. Probe-only headless
entry points and font fixtures do not become production rendering dependencies.

=== Density/Spatial consumer measurements

[[density-spatial-consumer-evidence]]
The actual application comparison uses two differently sized panels per style on
an isolated 1280-by-800 Wayland surface, identical PCM input, config and library
seed. Baseline/candidate process order was B–C–C–B–B–C.
Each fresh process warmed up for four seconds, then recorded three two-second live
intervals and three paused intervals. CPU is percent of one CPU from process ticks;
the table reports mean and range of the three process means, not GPU timestamps.

[cols="2,2,2",options="header"]
|===
|Observation |Before migration |GPU fields
|Live CPU |9.17% [9.00–9.33%] |8.00% [7.83–8.17%]
|Live RSS range |119.12–120.41 MiB |118.73–120.38 MiB
|Paused CPU mean |0% |0.17%
|===

Live CPU was lower in this short isolated workload; RSS overlaps. The paused
candidate samples total one 10-ms CPU tick per six-second run, insufficient to
infer recurring redraw. Process measurements neither isolate GPU cost nor prove
internal resource release. Cross-binary screenshots were not audio-frame
synchronized, so they do not establish exact pixel equivalence. Broader whole-app
performance and physical VRAM claims require separate evidence.

[[spectrum-barsled-consumer-measurements]]
=== Spectrum Bars/LED consumer measurements

The final comparison uses four unequal Spectrum panels, LED with 512 slots,
labels and Peaks enabled, caching enabled, 30 Hz analysis and an 8192-point
Blackman-Harris FFT. Three fresh processes per binary alternate baseline/candidate;
each CPU window lasts five seconds following the same seek
and playback-position gate. The isolated Weston GL/niri surface uses AMD 780M
with Mesa 26.2.4. CPU is a percentage of one core.

[cols="2,1,1",options="header"]
|===
|Observation |Textured Path baseline |Final MSAA instances
|CPU median [range] |9.194% [8.995–9.393%] |7.395% [7.394–7.595%]
|RSS range |118.43–121.21 MiB |119.00–121.06 MiB
|===

CPU was lower in this bounded workload; RSS/PSS ranges overlap. These observations
do not isolate GPU time or demonstrate physical VRAM savings. The final candidate
uses MSAA coverage: rejected direct/alpha-edge variants and their measurements
are not mixed into these results. Real-app frames were not synchronized, so
cross-binary screenshots do not establish pixel equality.
