= Parameter-Driven GPU Rendering Design
:toc:
:toclevels: 2

== Status and decision boundaries

Design baseline, 2026-10-18. The vendor-only fixed-schema rectangle slice described
under <<_internal_led_vertical_slice>> is implemented. The general `Program`,
generated-schema interfaces and consumer migrations below remain proposals, not
available APIs. Implementation details may change as subsequent consumers expose
different requirements; the agreed safety and platform boundaries remain binding.

The application supplies compact parameters and meaningful numerical data. The
GPU generates geometry and pixels. GPUI owns the common drawing, upload, storage,
composition, and retirement mechanisms.

Three kinds of decisions have different stability:

* *Design constraints:* the platform boundary, application/rendering ownership,
  coherent state publication, safe GPU resource use, bounded work and storage,
  and preservation of signal meaning.
* *Proposed mechanisms:* API names and type boundaries, shader generation,
  transaction implementation, data partitioning, pipeline preparation, and
  upload paths. Refine these against real consumers rather than preserving a
  sketch at the expense of simplicity or performance.
* *Measurement decisions:* pool depth, block size, reclamation thresholds,
  precision choices, and window resource budgets. No universal three-slot rule
  or fixed 128 MiB CPU/GPU budget is adopted.

Small visual differences, skipped intermediate display updates, and bounded
latency are acceptable when they buy demonstrated efficiency without degrading
perceived quality. This is not permission for invalid memory access, stale source
identity, unbounded retention, or graphics work that blocks audio output.

link:23_visuals.adoc[Visualization Rendering Design] and
link:22_cache.adoc[Caching and Resource Lifecycles] describe the current
implementation and its behavioral baseline. Existing internal ownership and
cache choices can change through this design. Update their authoritative sections
when a consumer actually migrates; do not describe a proposal as shipped behavior.

== Scope

Allowed changes are confined to:

* `vendor/gpui`: drawing descriptions, state and resource handles, scene
  integration, replay, and window-local logical resource management.
* `vendor/gpui_wgpu`: shaders, pipeline preparation/cache, uploads, GPU allocation,
  execution, device-generation handling, and reclamation.
* Application visualization consumers, palette construction, and obsolete CPU
  rendering intermediates.
* Necessary ABI tooling, build integration, tests, and documentation.

Keep `gpui_linux` on its existing pinned dependency: do not modify or vendor it.
Do not add `PlatformWindow` methods. Preserve the existing transport:

[source,text]
----
Rivu parameters and data
  -> GPUI Scene
  -> PlatformWindow::draw(&Scene)
  -> WgpuRenderer
----

The pinned Wayland and X11 implementations forward the complete scene to the
renderer; they do not decode each primitive. New drawing records therefore do
not inherently require a Linux platform extension.

Do not change native surfaces, presentation, platform frame callbacks, or window
event mechanisms. Do not expose device, queue, or renderer handles to application
consumers. Do not change audio playback, FFT, analysis publication, or the fractal
simulation. Do not import gpui-fast retention, replace text/layout machinery, or
introduce a second rendering engine as part of this work.

A concrete requirement that cannot fit this boundary needs evidence and separate
authorization before expanding the patch surface. In particular, do not invent a
window-to-renderer asynchronous preparation API and then treat it as justification
for a new platform method.

== Ownership and data model

[cols="1,2,2",options="header"]
|===
|Owner |Owns |Decides
|Application model/panel owner
|Signal history, envelopes, trajectories, coverage, source identity; logical render handles
|What data means, what remains useful, which consumers share it, and when to update or release it
|GPUI window resource manager
|Published drawing state, scene references, encoded drawing data and retirement bookkeeping
|How drawing data is captured, shared within the window, retained for replay, and released logically
|WGPU renderer
|Pipelines, physical buffers/textures, staging, execution references and reusable storage
|How to allocate, upload, execute, reuse and reclaim physical storage
|===

Do not move every application `Vec` into a common pool. Retain algorithm state in
the application, centralize drawing transport/storage, and eliminate intermediates
that the GPU can derive from parameters.

For example, replace LED rectangle meshes with bar parameters, and colored
Density images with scalar fields. Moving those same meshes or pixel loops into
a GPUI allocator would preserve the avoidable work.

Logical resources are window-scoped. Immutable CPU definitions may be shared more
widely, but GPU sharing must respect the actual device and lifetime. A global pool
must not keep a removed panel's data alive merely because another window exists.

== Application-facing interface

The proposed public model uses:

* `Program<Schema>`: a validated program description, not a promise that a device
  pipeline already exists.
* `RenderState<Schema>`: one complete published display state, including
  parameters, resource bindings, and draw ranges.
* `DrawRequest`: a temporary placement of a state in the scene.
* `RenderData<T>` and `Field2D<T>`: bounded linear records and two-dimensional
  numerical data. Their update/sampling contracts differ; neither is an
  untyped byte buffer with loosely related flags.
* `ColorRamp`: an immutable color definition with explicit sampled views.

Illustrative usage, not a compilable interface commitment:

[source,rust]
----
let mut state = RenderState::new(spectrum::SCHEMA, capacities)?;

state.update(|edit| {
    edit.replace(spectrum::BARS, &bars)?;
    edit.set_params(params)?;
    edit.bind(spectrum::PALETTE, palette_view)?;
    edit.set_instances(0..bars.len() as u32)?;
    Ok(())
})?;
cx.notify();

window.paint_gpu(
    spectrum::PROGRAM.draw(&state).bounds(plot),
)?;
----

Binding identifiers and parameter types come from the schema rather than string
lookups. The update publishes data, parameters, bindings and draw ranges together.
In particular, the instance count must not be read from an unrelated mutable
variable during painting.

Bounds, current placement, clip and inherited opacity belong to drawing placement.
Axes, source-dependent mappings, palette selection and data ranges belong to the
published content state. Update does not implicitly schedule animation or refresh
an unrelated business root. The application continues to invalidate the affected
views through the existing notification paths.

A window owns resources once attached to its rendering context. Cross-window use
of an attached state must be rejected or explicitly imported, never silently
borrow another renderer's allocation.

== Fixed and dynamic scene state

Use one drawing API with an explicit state policy, not independently mutable
bindings that happen to be sampled at different times.

=== Fixed content

For palettes, fixed geometry and stable cached content, record immutable content
revisions. Internally, `RecordedDraw` contains parameters, ranges and frozen
bindings, not `RenderData<T>` handles that resolve to the latest version later.

`Scene::replay` clones the recorded references. Recording A, publishing B, and
replaying the old draw must still produce A. Revisions identify stable content and
its backing, not merely a generation number followed by a lookup of current data.

=== Dynamic content

Real-time bars, segments and fields may use an explicit dynamic state slot.
Resolve each slot *once per prepared frame*, and use that complete publication for
parameters, instance ranges, axes and all resources. Multiple draws referencing
the same slot in that frame share the resolution.

A dynamic recorded draw retains the slot and content-independent placement/visible
bounds. It does not retain stale content-dependent parameters alongside bindings
that individually resolve to newer data. Intermediate publications that were never
sampled may be skipped; they are not an upload backlog.

The slot's schema, declared maximum resource/range envelope, and visible bounds
remain stable. Changing those requires scene rerecording. Actual counts may vary
inside the envelope as part of the atomic publication. Dynamic changes still need
an existing frame request/notification; latest-wins does not create a polling clock.

Once a dynamic slot has been resolved for execution, that resolved packet has the
same immutability and GPU safety requirements as fixed content. Latest-wins relaxes
which publication is selected, not whether submitted resources can be overwritten.

== Shader composition and ABI

=== Geometry and material

A program combines geometry, a material, typed parameters/bindings, and a bounded
set of pipeline properties. Support rectangular coverage, procedural instances,
and adapters for existing paths/meshes through the same drawing model.

Geometry produces local positions and declared interpolated values. Material
functions evaluate color from those inputs, parameters and resources. Framework
entry points apply window transforms, clip, inherited opacity, geometry coverage
and the output color convention. Existing path adapters retain path coverage;
reusing a material does not automatically remove CPU path tessellation.

Custom varyings require producer/consumer layout agreement. Do not claim that
arbitrary shader fragments compose without an ABI. Use explicit standard WGSL
modules and validation; do not build a new shader language, runtime node editor,
or arbitrary render-pass callback API.

The same material should work with both a procedural bar and a compatible path.
Styles such as LED, Spectrum or Fractal Flow remain application programs and
parameters, not GPUI business enums.

Shader code is trusted application content. Do not expose unrestricted user shader
loading as part of this feature. Read-only drawing resources and framework-owned
entry points keep graphics submission and composition under renderer control.

=== Host/shader encoding

WGSL declarations plus the program description form the authoritative schema.
Use a Naga version matched to the repository's wgpu baseline to validate and
produce Rust value types, binding identifiers, layout descriptions and encoders.

The encoding contract includes:

* scalar kind/width, field offset/alignment, and total structure size;
* array and matrix stride, nested layout and runtime-array placement;
* uniform versus storage address-space rules;
* binding access/type and minimum size;
* initialized padding and checked output bounds.

`Copy`, `repr(C)`, or `Pod` alone does not establish WGSL compatibility. Encode
fields into managed storage; direct byte copying is an optimization only for
layouts proven identical. Compare actual shader layouts structurally with the
schema; a type ID, hash or matching total size alone is insufficient.

Do not upload native Rust references, pointers, `usize`/`isize`, container memory
representations, or default bool/enum representations. Use explicit fixed-width
encodings and validity masks. Zero-sized record types are not upload elements;
an empty collection is still a legitimate value. Nonfinite floating-point policy
belongs to the consumer's signal contract rather than a blanket ABI prohibition.

The first vertical implementation may use a private fixed schema and encoder with
layout checks. Generalize the tool only after different consumers exercise its
requirements. This delays tooling, not encoding safety.

=== Program preparation

Build-time checks catch source and layout errors. The renderer creates and caches
device pipelines through the existing scene transport. Pipeline keys include the
program, binding layout, geometry adapter, relevant blend/sample/target state, and
device generation; not changing per-frame uniform values.

First-use preparation is a possible implementation, not a claim of zero startup
cost. Measure its visible latency. Evaluate renderer initialization or preparation
within the existing execution path before considering any platform-boundary change.
Do not parse source or recreate pipelines on every repaint.

Build-time shader generation does not eliminate driver compilation. No public API
may imply successful device preparation merely because a CPU description validated.

== Publication, storage and upload

=== Update transaction

Collect edits, validate their schema/ranges, reserve finite storage, encode the
candidate, then publish one complete state. Failure or abandonment leaves the old
publication unchanged. Do not mutate backing held by a published state as part of
an operation that can still fail.

The transaction performs no I/O, asynchronous wait, business notification or
reentrant publication. Sharing and copy-on-write are internal choices, not a
public historical snapshot service. Keep only content reachable from current
owners, scene records, upload work or execution.

For drawing-only instances, a managed writer can avoid an extra application
scratch vector. Existing algorithm output may be copied or explicitly transferred.
Do not pin analysis publication slots indefinitely in pursuit of zero-copy.

=== Resource-specific storage

Small parameters can be captured and packed centrally. Frequently replaced
instance batches benefit from contiguous reusable preparation/upload regions.
Static immutable content can reuse a device copy. Large locally changing fields
may use chunked revisions or region updates with preserved old backing.

Chunking introduces metadata and GPU addressing costs. A contiguous GPU replica
may require copying unchanged regions when an old revision remains live. Account
for that work explicitly; `write_region` must not conceal unmeasured whole-field
copies. Choose the mechanism and granularity using actual update patterns.

Deduplicate uploads by resource content revision and device generation, not panel
identity or a whole-payload hash on every repaint. Different transforms of the same
shared data should not upload the payload again.

=== Upload side effects and failure isolation

Do not require every panel to update in the same frame or make one visualizer's
preparation failure cancel unrelated menus and controls. The isolation unit is a
complete resolved drawing state, which can span several draws.

Queue writes and explicit staging/copy commands are both candidates. Select by
measured upload shape and cost, not a universal transaction requirement. Before
writing, targets must be safe: a changed payload cannot overwrite storage still
needed by an existing scene or execution.

`Queue::write_buffer` and `write_texture` are not rollback operations. A scheduled
write can execute on a later submission, including one from another window using
the queue. If subsequent preparation fails, a candidate may incur wasted work,
but cannot corrupt published content. Keep its storage/staging alive until the
actual upload lifetime permits reuse. Explicit copy commands avoid this particular
queued-write side effect when an unsubmitted command buffer is discarded.

Do not advertise a state as executable until all of its required resources and
bindings are ready. A recording success is not GPU execution success. Temporary
pressure may defer that visualizer's update without queuing every missed update.
The application can retain the newest valid model and a refresh-needed marker.
A previous display may be reused only while its source and mapping remain valid;
otherwise omit the invalid content or expose its failure instead of relabeling it.

== Scene integration and lifecycle

New records participate in GPUI's ordinary scene ordering, clipping, composition
and replay. They are not an unconditional topmost overlay. Visible bounds must
include stroke width, glow and procedural displacement. Compatible bindings and
pipelines alone do not permit reordering overlapping translucent content.

Keep scene/replay references separate from execution references. GPU completion
alone does not make a resource safe to overwrite if a scene can submit it again.
Likewise, releasing the last scene reference does not permit reusing staging that
is still being read by an upload.

The GPUI window manager owns logical retirement. The renderer reclaims physical
storage when execution and reference conditions permit. This intentionally
replaces application-specific retirement queues for migrated resources; it does
not require retaining the old implementation's frame-count heuristics forever.
Unmigrated image consumers retain their existing retirement mechanism until their
complete call chains migrate.

=== Hidden windows and shutdown

There is no new platform service or guaranteed draw after hiding. Adopt deferred
GPU reclamation rather than forcing a cleanup scene solely for reclamation.

[cols="1,2,2",options="header"]
|===
|Event |Application/GPUI |Renderer
|Hide
|Stop display demand; release content that the consumer's policy discards; invalidate and detach corresponding cached scene references
|May retain bounded GPU storage until its next execution opportunity or destruction
|Show
|Rebuild invalidated records from current valid state, without restoring discarded signal history
|Reconcile live resources and reclaim/reuse obsolete storage during draw
|Close
|Revoke window ownership and scene references
|Drop renderer-held resources; in-flight work remains subject to backend execution lifetime
|===

Dropping the model alone does not release CPU content still held by a cached scene.
The hide path must remove those references for resources it promises to discard.
This does not require discarding all static caches. Outstanding uploads may still
retain necessary data, so do not promise immediate release of every CPU byte.

Do not promise immediate VRAM reduction while no renderer callback runs. Idle GPU
capacity remains charged. Hiding stops new display preparation/uploads; it does
not launch a retry or cleanup-render loop. Reclamation on resume must account for
resources omitted from the new scene, including an empty visualizer set.

=== Device and surface changes

Use the existing renderer lifecycle. An unconfigured surface is not necessarily
a lost device. Device recovery invalidates device-local pipelines and allocations
by generation. Rebuild only from still-owned valid CPU content; discarded hidden
history must not reappear. Late preparation/errors from an old generation cannot
install a new device's resources or overwrite its status.

Keep frame scheduling, presentation and native recovery integration unchanged.
If safe event-driven progress cannot be achieved with existing callbacks, report
that concrete limitation rather than silently adding platform methods or polling.

== Palette and image semantics

`ColorRamp` represents color and alpha as a function of a normalized coordinate.
Separate its definition (stops, curve, interpolation space) from sampled views
(domain, resolution, filtering, clamping). Application-defined dB mapping,
nonlinear compression and spatial mapping remain outside the ramp itself.

CPU and GPU consumers use the same explicit definition/sampling rules. A domain
view can share data where equivalent; preserving an existing discretized result
may require a distinct bounded sampled representation. Do not assert that a
coordinate remap always reproduces a separately sampled subdomain exactly.

Numerical fields must not undergo color-space conversion. Color images and ramps
have explicit color/alpha conventions; backend BGRA/RGBA handling belongs below
the application API. Do not silently change interpolation to another color space
or add/remove premultiplication during optimization.

Preserve these distinct visual models:

* Spectrum: the authored cubic ramp and its visible domain, mapped spatially
  across the plot; Peak markers remain discrete.
* Waveform: a separate endpoint color for each RMS column, dim/desaturated center,
  color compression, and thin Peak markers. No replacement with one global gradient.
* Spectrogram: the complete palette including its black floor, and blank missing
  time rather than invented continuous history.
* Density/Spatial: their own hue progression, fixed signal references and alpha
  curves, including transparent empty cells.

Interpolating scalar values before color mapping is not equivalent to interpolating
already mapped colors. Programs must express the intended order. A scalar-field
replacement for an existing enlarged image may need to map neighboring source
samples separately and then interpolate colors. Preserve source resolution,
endpoint sampling and meaningful rounding unless an evaluated visual tradeoff
explicitly changes them.

|Special palette-image plumbing, not necessarily path tessellation

|Repeated CPU path construction for light layers

|Bounded history, time-bucket max pooling, axis identity and discontinuities

|Per-column colored images and repeated CPU coloring
|Density/Spatial
|Statistics, decay and field semantics
|Fixed-resolution values, ranges and color curves

Paint and resize never advance simulations. Differently sized panels share common
signal/segment data, not independent analysis. Spectrogram intervals cannot become
an equal-width scroll that fills gaps. Glow must not silently become blur or
additive overexposure. Verify segment intersection/cap behavior against the current
path composition rather than assuming instancing is visually equivalent.

A GPU Waveform may reduce image storage but increase fragment work during stable
repaints. Compare against current tile reuse before selecting its retention policy.
Keep the playback cursor independent so cursor movement does not upload unchanged
waveform data.

== Limits, pressure and acceptable approximation

Every logical resource has a finite maximum extent/record count. Physical active,
candidate, retired and pooled capacity, plus upload staging, all count toward
finite limits. Admission happens before allocation; do not evict scene-live content
to satisfy it. Device format/binding/texture limits are checked independently.

Existing consumer bounds are inputs, not a universal allocation algorithm. The
analysis-side Density three-slot publication pool remains its own contract; it
does not prescribe GPU ring depth. Do not introduce an arbitrary frequency-row cap
or shorten a supported history merely to simplify a shader.

Prototype with explicit finite experimental limits and report when they bind.
Measure live-version/region counts, payload versus allocated bytes, staging,
execution delay and idle high water. Then choose per-resource policies and product
budgets; experimental limits are not automatically shipping defaults. Measured
peaks alone are not safety bounds: exercise delayed GPU work and rapid changes.

Potentially worthwhile compromises include latest-wins updates, independent panel
refreshes, modest sampling/antialiasing differences and lower display precision.
Validate each against actual workload and perceived quality. Do not silently lower
precision, truncate data, or switch effects to make a failed allocation succeed.

Errors distinguish invalid schema/data, unsupported capability, temporary pressure,
resource limit, window closure and device failure. Temporary pressure coalesces
pending display work; it does not create an unlimited retry queue. No graphics
failure blocks or issues commands to the audio callback.

== Implementation slices

=== Internal LED vertical slice

Start with a private fixed program/schema through the existing Scene-to-renderer
path. Validate real ordering, clip, inherited opacity, palette use, uploads,
resource lifetime, multiple panels and resize. Do not place FFT or application
style state into GPUI. Do not add a general generator or platform service merely
to run this slice. Measure first-use pipeline latency as well as steady state.

This is a vertical implementation, not the final public API. Its private special
entry point must not become a permanent parallel convention.

The current vendor implementation exposes the deliberately experimental
`GpuRectangleFrame`, `GpuRectangleState`, `GpuRectangleSource` and
`Window::paint_gpu_rectangles` for integration work. It records normalized
rectangles, bottom-to-top palette coordinates and solid or bottom-aligned segmented
fill. Palette samples are straight-alpha sRGB values; their interpolation is in
sRGB numerical space. Bounds, clip, scale and inherited opacity belong to each
scene placement, independently of the shared content. No application visualizer
has migrated to this entry point, and it does not replace the existing textured
path interface.

Frame construction validates geometry, palette, parameters and explicit caller
capacities before copying payloads. A process-unique, checked monotonic frame ID
keys device-local uploads; allocator addresses are not content identities.
Fixed sources retain their publication. Dynamic sources retain a revocable slot;
the renderer captures each slot once per frame, including an empty/revoked result.
`publish` and `clear` require one synchronous owner to serialize mutations;
concurrent snapshot readers are supported. `clear` is not cancellation of a
concurrently preparing publication. Neither operation schedules a frame.
Placement and clip bounds are validated after scaling before a paint is recorded;
non-finite coordinates, negative dimensions and overflowing extents are rejected.

The fixed WGSL layout has explicit little-endian scalar encoders and zeroed
padding, checked structurally with the matching Naga version. This is not the
general ABI generator. The WGPU program is created on first nonempty use, not
when an unrelated window opens. Immutable content uploads are reused by all
placements of that frame and by static replay. Per-placement uniforms are currently
allocated for each prepared draw, and each newly published frame encodes its full
rectangle and palette payload; this prototype does not yet provide independent
palette revisions, reusable upload pages or partial-field updates.

GPU buffers are initialized through WGPU's write-only mapped view, never by
reinterpreting the Rust model or overwriting an older revision. Completion
watermarks retain charges for both active and retired buffers. The owner of frame
preparation also finalizes failed pre-submit recordings through the renderer's
existing queue-flush path, so a failed later path draw cannot strand a provisional
submission. Unsupported capabilities and rectangle capacity pressure are reported
and omit the affected drawing without preventing unrelated controls from rendering.
Capability failure is reported once per device-local program attempt. Other skipped
records are coalesced into one summary when the failure categories change; a
successful or empty frame resets that episode. Persistent failures do not log once
per drawing record or once per repaint.

Experimental limits per rectangle renderer are 32 MiB of charged buffer capacity,
8,192 allocation charges, 4,096 drawing records per frame and eight outstanding
completion callbacks. Buffer bytes and allocation counts conservatively charge two
initialization copies, including after completion; these are admission accounting
limits, not measured VRAM or a budget for the entire GPUI window. CPU payload
capacities are supplied separately by the caller. Keep these limits adjustable
until real consumers establish appropriate product budgets.

The GPU cache retains only weak CPU ownership. Clearing a dynamic slot releases
its CPU content once existing snapshots finish; fixed scene records deliberately
remain replayable until invalidated. No cleanup frame or background polling is
introduced. Completed storage omitted from a later scene is reclaimed on draw,
including an empty scene; window/device destruction drops the renderer's ownership.
Ordinary scenes with no rectangle resources do not perform extension-specific
device polling. Native Metal remains explicitly unsupported.

==== Initial comparative measurements

Measured on 2026-10-18 using Radeon 780M / RADV Vulkan, Rust 1.99.0 and an
optimized release build with thin LTO. The baseline is the current LED drawing
kernel: append each cell to a NonZero `PathBuilder`, tessellate, then render the
textured path. Both paths ran in the same executable with identical input and
palette samples. This is not an end-to-end player benchmark or a consumer cutover.
link:25_gpu_rendering_benchmark.json[Raw samples, workload, hashes and limitations]
record the complete comparison.

The workload uses 96 columns, a 1,024-sample Tokyo Night cubic palette and
3-pixel filled / 2-pixel empty segments. Single panels are 768 by 320 pixels;
four panels are each 768 by 160. Resize alternates heights 320 and 240. Five
runs alternate baseline/candidate order; each records 20 frames after four warmup
frames. Values below are microseconds: median of run medians, with the minimum
and maximum run median in brackets. Shared input generation is excluded.

|Continuous update |3,257.33 [3,245.21–3,266.90] |6.66 [6.65–6.68] |706.18 [699.49–721.07] |235.92 [233.15–241.96]

A supplemental run measures the full boundary symmetrically: five fresh processes
per path, alternating path order, with one renderer and one first image in each
process. It includes device/renderer construction, initial palette and geometry
preparation, scene recording, and first render/readback (including the candidate's
deferred pipeline creation). Common signal input and palette-sample generation are
excluded from both. Milliseconds below are median [minimum–maximum]:

The total is measured directly; phase medians need not sum to its median. Fresh
processes eliminate reuse of the headless device between paths, but the driver
shader cache was not cleared, so these are not cold-driver-cache timings. Original
steady-state samples remain associated with their recorded source hashes; the raw
record appends this first-use supplement rather than replacing historical samples.

At the initial single-panel state, the baseline expands 3,308 cells into 19,848
CPU vertices. Tested record strides imply 2,858,128 bytes of path vertices and
sprites submitted per redraw, versus 19,536 bytes for a new rectangle publication
plus its placement, or 80 placement bytes for a static replay. The old palette's
4,096-byte initial atlas upload and common globals are separate. These are derived
payload counts, not measured bus traffic or physical allocation sizes.

Three independent processes per path, each running all four workloads, reported
peak process RSS medians of 86.48 MiB [86.05–87.43] for Path and
72.20 MiB [72.15–72.44] for instances (`wait4` maximum RSS). This is not isolated
VRAM accounting. The matched 768-by-320 output had maximum channel difference
1/255 and mean absolute channel difference 0.046/255. Actual application animation,
other visualizers, isolated GPU execution time and GPU memory still need their
own measurements during consumer migration; do not extrapolate these kernel
results to total player CPU usage or frame rate.

=== Different consumers and interface extraction

Add Density to exercise numerical fields and existing path coloring to exercise
geometry/material reuse. Extract the common program/state/resource contracts and
schema tooling from these actual requirements. Migrate the initial slice and remove
its superseded entry point rather than retaining compatibility aliases.

=== Remaining consumers and integrated delivery

Migrate fractals, Spectrogram and Waveform with their distinct reuse patterns.
Remove only intermediates and retirement paths made obsolete by the cutover.
Retain algorithm state and unrelated artwork behavior. If the unified path
material fully replaces `paint_path_with_texture`, migrate all callers and remove
the obsolete specialized path.

The slices divide integration risk, not final scope. Generic supporting modules
belong with GPUI/WGPU; application programs and palette definitions belong near the
visualization consumers. Do not move audio visualization business code into
`rivu-ui` simply because it draws UI. Build-time tooling can be a separate small
crate to avoid linking the runtime renderer into a build script. Generated output
belongs in Cargo's `OUT_DIR`, with build artifacts under repository `.cache/`.

== Verification and decision gates

No performance outcome is established by this proposal. Verify the actual changed
path, not merely compilation or reduced submission counts.

[cols="1,3",options="header"]
|===
|Area |Required evidence
|ABI
|Offsets/strides for vectors, matrices, arrays and nested structures; uniform/storage distinction; invalid schemas rejected; padding initialized
|Fixed replay
|Record A, publish B, replay A; draw A and B in one frame without aliasing their content
|Dynamic consistency
|Publish during frame preparation; each slot resolves one complete publication for every consumer in that frame; count/axis/resource mismatches cannot occur
|Update failure
|Fail allocation or encoding between related edits; no partially published state
|Upload failure
|Inject failure after a candidate write or copy encoding; published backing remains unchanged, another window's submit cannot corrupt it, and failed candidates eventually release their charge
|Lifecycle
|Multi-panel sharing, last-consumer removal, resize, hide with no further draw, resume, close and device generation change; bounded retention and no invalid reuse
|Scene integration
|Clipping, scaling, overlap, inherited opacity, menus/tooltips over custom content, cached replay and ordinary unaffected primitives
|Visual quality
|Palette transitions, dark detail, thin lines, glow intersections, transparency, missing data and history gaps at real sizes/scales in motion
|Efficiency
|CPU construction, allocation/copy counts, upload bytes, GPU time, peak/steady memory, startup and recovery costs for equivalent workloads
|===

Use repeated measurements with variability for timing comparisons. Include static
repaints, changing data, dense LED scenes, multiple panels, resize and artificial
GPU delay. Pixel differences help locate errors but are not the sole visual
acceptance criterion. An imperceptible difference can be accepted for meaningful
performance gains; reduced draw calls or fewer source lines alone prove neither.

Follow repository checks for implemented changes: Rust changes require `make lint`
and relevant behavior tests; build/tooling/link changes require `make build`.
Exercise actual GUI behavior and affected feature branches. Keep permanent tests
for consumer-visible invariants and errors, not incidental API spelling or code
layout. Keep throwaway profiling/prototype artifacts separate from product code.

== References and rationale

* https://docs.rs/wgpu/29.0.4/wgpu/struct.RenderPipelineDescriptor.html[wgpu render pipelines]: explicit layouts and cached pipeline state.
* https://docs.rs/wgpu/29.0.4/wgpu/struct.Queue.html[wgpu queue]: staging, queued writes and submission lifetimes.
* https://skia.org/docs/user/sksl/[Skia Runtime Effects]: custom functions composed into framework coverage, clip and color processing; raw data differs from color images.
* https://doc.qt.io/qt-6/qsgmaterial.html[Qt Quick materials] and https://doc.qt.io/qt-6/qml-qtquick-shadereffect.html[ShaderEffect]: geometry/material separation, shared programs and build-time shader metadata.
* https://github.com/linebender/vello/blob/main/ARCHITECTURE.md[Vello architecture]: compact scene data and explicit CPU/GPU tradeoffs, not a requirement to adopt compute for all work.

These references inform the design, not a dependency replacement plan. Bindless
resources, indirect drawing, general render graphs, shader editors and GPU FFT
are not prerequisites. Add a mechanism only when a real consumer and measurements
justify its lifetime and maintenance cost.
