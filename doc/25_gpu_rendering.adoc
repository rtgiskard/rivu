= Parameter-Driven GPU Rendering Design
:toc:
:toclevels: 2

== Status and decision boundaries

The design baseline dates to 2026-10-18. The fixed-schema rectangle,
numerical-field, existing-path, independent-segment and numerical-waveform slices
under <<_implemented_fixed_schema_slices>> are implemented and used by Rivu.
The general `Program`, `RenderState<Schema>`, `RenderData<T>`, `Field2D<T>` and
`ColorRamp` APIs, generated schemas, and general update transactions are proposals,
not available interfaces. The agreed safety and platform boundaries remain binding.

Read the current implementation first, then the design and evidence:

* <<_implemented_fixed_schema_slices>> defines the available closed-schema API,
  consumer cutover, uploads, MSAA scratch and resource limits.
* <<_proposed_general_rendering_model>> separates the target public API and its
  constraints from shipped behavior; imperative wording there describes a design.
* <<_verification_and_decision_gates>> states acceptance requirements, while
  <<_recorded_measurements>> retains dated source/binary comparisons rather than
  a benchmark of every subsequent revision.

Current signal semantics and consumer ownership are authoritative in
link:23_visuals.adoc[Visualization Rendering Design]; cache invalidation and
retention are authoritative in
link:22_cache.adoc[Caching and Resource Lifecycles].

The application supplies compact parameters and meaningful numerical data. The
GPU materials expand instances and shade fields and existing paths. GPUI owns
the common drawing, upload, storage, composition, and retirement mechanisms.

Platform isolation, coherent publication, bounded storage, GPU safety and signal
meaning are constraints. Public API shapes, generated schemas and upload mechanisms
remain design choices; pool depth, precision and budgets require workload evidence.
No universal three-slot rule or fixed 128 MiB CPU/GPU budget is adopted. Bounded
display latency or small visual differences may be accepted for demonstrated gains,
not invalid memory access, stale source identity, unbounded retention or audio stalls.

== Implemented fixed-schema slices

[[_internal_led_vertical_slice]]
=== Publication and drawing API

Rivu uses a private fixed-schema model through the existing Scene-to-renderer path.
FFT, analysis and simulation remain application-owned; no platform service, arbitrary
shader composition or ABI generator is introduced. The original rectangle-only
LED experiment is retained under <<_initial_comparative_measurements>>.

The current vendor implementation exposes the deliberately experimental
`GpuPalette`, `GpuFrame`, schema-stable `GpuState`, `GpuSource` and
`Window::paint_gpu` for integration work. One recording entry accepts normalized
rectangle instances, row-major numerical fields, independent line segments,
numerical stereo waveform columns or an immutable existing tessellated path.
Rectangle segmentation and bottom-to-top palette coordinates
retain their initial behavior. Palette samples are straight-alpha sRGB values;
their interpolation is in sRGB numerical space. Bounds, clip, scale and inherited
opacity belong to each scene placement, independently of shared content.
Density/Spatial use fields; Spectrum bodies use rectangles or Paths; Fractal
Beams/Flow use segments; Spectrogram uses fields with independent column intervals;
Waveform uses stereo numerical columns. Spectrum Peaks remain ordinary GPUI
quads, and radial styles and artwork retain their independent rendering paths.

The definitions live in link:../vendor/gpui/src/gpu.rs[`gpui::gpu`]; the
device-local implementation is
link:../vendor/gpui_wgpu/src/gpu_material.rs[`gpu_material`]. These publication
handles contain CPU content, not device allocations or an attached-window
identity. They can be recorded in different windows; each renderer independently
uploads and budgets the content it uses. Attached-window state and explicit import
belong to the <<_application_facing_interface,proposed public model>>, not these handles.

==== Waveform columns

`GpuFrame::waveform` takes ownership of a vector of four normalized f32 levels per
column in left RMS, left Peak, right RMS, right Peak order. NaN denotes missing;
infinities and finite values outside `0..=1` are rejected.
`GpuWaveformParams::palette_start` selects the visible domain in a paired endpoint
palette. The lazy waveform pipeline expands four instances per column and selects
their continuously sampled endpoint colors in the vertex stage; bounds, logical
height and scale remain placement data.
Columns use existing publication budgets, weak upload ownership, coherent dynamic
snapshots, scene replay and completion-aware retirement. Application aggregation
and cache invalidation are authoritative in
link:22_cache.adoc#_waveform[Waveform caching].

==== Independent segments

Segments use butt caps and ordinary source-over blending in the shared MSAA
intermediate. Each immutable frame's endpoint array is uploaded once and reused
across that frame's ordered layers, with logical-pixel widths and palette-index
offsets. Layers retain their individual source-over order; shared scratch grouping
does not union overlapping geometry or introduce feedback. Zero-length segments draw nothing.
Fractal simulation and accepted audio time remain application-owned. Publications
change only with accepted geometry or display parameters, not repaint or resize;
hiding releases application display storage. The application retains the original
three light layers, intensity/color buckets and drawing order. Fine antialiasing
differences are accepted rather than reproducing CPU tessellation pixel for pixel.

Segment placement bounds map endpoint coordinates; they are not a clipping box.
Scene culling, overlap ordering and MSAA composition use a separate conservative
footprint covering endpoint extents and stroke expansion at the current scale,
intersected with the content mask. Endpoints outside the unit square and strokes
crossing placement edges remain visible wherever that mask permits.
All finite normalized endpoints remain admissible, including values near the
`f32` limit. Ordinary segments retain direct direction normalization. Distant
endpoints take a shader-only power-of-two scaling and viewport-rebasing path,
before stroke extrusion, to avoid overflow and loss of physical stroke width.
This arithmetic-path threshold does not restrict publication coordinates or add
CPU geometry copies, allocations, uploads or draws; masks, butt caps and layer
composition keep the same semantics.


==== Spectrogram column fields

Spectrogram packs at most 32 numerical columns and their independent x intervals
into each immutable field tile. Intervals are relative to the tile's own earliest
start and latest sample time, not the moving history window. Scrolling updates
only placement; a changed bucket resamples its tile directly from the retained
frequency levels. No per-column sampled frame is retained. The reusable packing
scratch holds at most 32 columns of f32 rows, plus eight bytes per interval;
unchanged tiles retain their immutable publication and GPU upload.
At 3600 history columns this is 113 draws per panel rather than 3600. Existing
renderer byte and in-flight resource budgets still apply; this is not a memory or
performance guarantee for arbitrary panel counts and sampling heights.
Below-floor and missing cells are opaque black independently of all 1024 palette
samples, so weak positive Tokyo Night values retain its first color. Real gaps,
startup window expansion, pooling and frequency sampling keep their existing meaning.
For logarithmic columns, the floor is palette coordinate zero at
`10 * log10(value) = -db_range`, not scalar zero. Floor detection shares the
mapping calculation with palette selection; values above it retain the first
palette color even when nearest-sample quantization still selects index zero.
Ordinary non-column fields keep palette-zero behavior at and below the floor.

Column intervals retain a one-logical-pixel minimum width, which can extend past
the placement's right edge. The inherited content mask, not the placement bounds,
clips that extension. Scene culling and overlap ordering use a conservative
footprint that includes it, independently of the unchanged mapping bounds.

==== Publication and scene recording

Frame construction validates geometry, palette, parameters and explicit caller
capacities before copying payloads. A process-unique, checked monotonic frame ID
keys device-local uploads; allocator addresses are not content identities.
For frequent raw updates, `GpuState::publish_rectangles` and `publish_field` check
the slot's fixed schema and capacities before allocating/copying a new snapshot.
Construction stays outside the publication lock, and failure preserves the old
publication or cleared state. `publish(frame)` instead attaches an already built
immutable snapshot for sharing with other slots or fixed scenes; its caller has
already paid construction costs under that frame's limits. It does not promise
admission under a narrower slot's limits before the caller constructs the frame.
Fixed sources retain their publication. Dynamic sources retain a revocable slot;
the renderer captures each slot once per frame, including an empty/revoked result.
Publication and `clear` require one synchronous owner to serialize mutations;
concurrent snapshot readers are supported. `clear` is not cancellation of a
concurrently preparing publication. These operations do not schedule frames.
Placement and clip bounds are validated after scaling before a paint is recorded;
non-finite coordinates, negative dimensions and overflowing extents are rejected.

==== Encoding and uploads

The fixed WGSL layout has explicit little-endian scalar encoders and zeroed
padding, checked structurally with the matching Naga version. This is not the
general ABI generator. Shared shader/layout preparation is lazy. The field pipeline
and the separate MSAA rectangle and path pipelines are created only after valid
draws pass upload/placement admission; replay reuses them.
An unused geometry pipeline is not compiled merely because another geometry is
drawn. Immutable content uploads are reused by all placements of that frame and
by static replay. Independently identified immutable palettes are shared across
geometry kinds and publications. Each preparation with admitted draws packs their
placement uniforms into one exact-size immutable buffer and bind group, selected
by device-aligned dynamic offsets. Alignment padding and initialization copies
remain charged until completion; this is not a retained high-water pool. A new
field publication still copies/uploads the complete numeric payload. There are
no reusable upload pages or partial-field updates.
Placement capacity for N admitted draws is
`(N - 1) * aligned_stride + 128` bytes; the stride rounds 128 bytes up to
the device's uniform-offset alignment. The final 16 bytes hold the raster
target's window-physical origin and eight bytes of zeroed alignment padding,
not a relocated mask or a second viewport scale.
Admission reserves the complete slab together with any new immutable data and palette.

=== Different consumers and interface extraction

The vendor interface covers numerical fields, existing path coloring and
rectangles without introducing application analysis or style state.
Fields use explicit linear or logarithmic scalar-to-palette mapping. Coordinates
use `uv * extent - 0.5` and clamp neighboring indices; empty extents emit no draw,
and one-cell dimensions repeat their only sample. Ordinary fields map nonfinite
values to the first palette sample; logarithmic mapping treats nonpositive values
likewise. Column fields instead use the opaque-black missing/floor rule described
under <<_internal_led_vertical_slice>>.
Each neighbor selects `floor(coordinate * (palette_length - 1) + 0.5)` before
straight RGBA interpolation. Moving coloring into the shader does not eliminate
its cost: enlarged or static draws still evaluate four mappings per output fragment.
Field upload uses four bytes per source cell. Shader coloring avoids CPU
recoloring; it does not by itself reduce upload size or fragment work.

Paths reuse existing tessellated vertices and coverage coordinates, not a filled
bounding rectangle. Their original bounds map into the recorded placement bounds;
the palette spans those full bounds, independently of clipping. Embedded path
color, texture, order and content mask do not override the material or scene
placement. Palette ownership is shared; path geometry remains immutable.
These Paths share the local multisample scratch described below rather than
owning a separate offscreen attachment. Numerical consumers use the renderer's
publication lifecycle; artwork keeps its independent image lifecycle.

=== Shared local multisample scratch

Waveform, rectangles, procedural segments, palette Paths and ordinary GPUI Paths
share one renderer-owned offscreen attachment/resolve pair. The existing adapter
sample count remains unchanged (4x when supported, single-sample fallback);
Field remains directly single-sampled. Adjacent rectangle instances retain
per-sample coverage rather than overlapping alpha ramps. There is no per-panel
texture cache, atlas, tiling or adaptive quality mode.

Within a scene GPU batch, only consecutive integer-aligned, disjoint multisampled
draws may share a resolve. Their union must occupy no more than twice the sum of
their visible areas: this explicit heuristic trades a bounded amount of empty
raster area for fewer passes, rather than merging distant small panels across
the window. It is not a universal performance optimum. Fractional edges,
overlap, single-sampled materials and intervening primitives terminate a group;
no primitive is reordered and overlapping draws resolve separately.

Native GPUI Path batches have different semantics: all batch vertices already
form a packed intermediate. Same-order batches composite each original path
bounds; mixed-order batches composite the original union once. Localization
preserves that whole batch and sprite multiplicity, even when its required union
is sparse. Splitting or treating these as independent material draws would change
alpha and ordering. Native batches and material groups reuse the same pair in
command order, never a separate fullscreen Path allocation.

Each raster footprint is clipped to the physical viewport and rounded outwards
only for attachment storage. Geometry retains its original window-to-clip
arithmetic, fractional window origin and DPI mapping. The raster pass keeps the
window-sized viewport and translates its origin by the negative integer
attachment origin; renormalizing vertices to the smaller texture could change
edge coverage. Scissors are attachment-local. Fragment masks, rectangle LED
periods and Path gradients use translated window-physical coordinates. Native
Path gradient evaluation receives that same translation; interpolated clip
distances are unchanged. Composition preserves original fractional bounds and
blend state and loads the corresponding resolved physical pixel, without
reapplying opacity or clipping. Both native instance transports use this ABI.

Planning includes only admitted material demand and native batches containing
actual vertices. Before allocating attachments, the renderer preflights every
native vertex upload and native/material composite record in scene order, starting
at the actual existing instance offset. Admission and the writer share transport
alignment, WebGL texel rounding, capacity growth and rollover arithmetic; the
original maximum upload budget remains authoritative. Rejected recordings release
scratch ownership and frame-plan storage without destroying in-flight resources.
Current raster demand is the componentwise maximum of clipped raster extents;
retained attachment capacity can be larger. Capacity adds `ceil(dimension / 8)`
pixels of slack per axis, capped at 64 pixels and at the physical viewport/device
limit. Demand that fits reuses the pair; growth or a viewport limit below retained
capacity replaces it immediately.

A padded demand at least 25% smaller in area starts a low-demand interval.
After 120 consecutive low-demand frames, capacity shrinks to the padded
componentwise peak of that interval, without growing either axis. Reclamation
accelerates to eight frames only when the interval's unpadded peak is below both
half the retained size and the retained size minus 64 pixels on at least one
axis. A frame above the low-demand threshold resets the interval, so alternating
large/small frames do not evict useful capacity. Orthogonal wide/short and
narrow/tall footprints can still require a large shared pair; this is a bounded
one-pair ownership tradeoff, not a claim of optimal packing.

A planned frame with no raster demand releases the pair immediately. Renderer
destruction, surface invalidation and device replacement also release renderer
ownership. Hiding does not guarantee another frame, and the low-demand policy is
frame-driven, not an idle timer. Resize recomputes footprints and viewport data;
fitting demand may reuse the pair. Capacity slack changes neither raster
viewport/scissor nor composition bounds; composition uses integer local pixels,
not normalized capacity-relative coordinates. Submitted commands retain replaced
textures until completion: explicit early `destroy()` is forbidden.
Changing only surface alpha mode rebuilds ordinary/composite pipelines without
invalidating same-size scratch attachments. Reattachment has a separate lifetime
boundary described under <<_surface_reattachment>>.

Reusable material-range and native-raster plan vectors follow the Path expansion
scratch policy: capacity above 4096 elements shrinks after 120 consecutive
successful frames at no more than one-quarter utilization, retaining twice the
interval peak with a 1024-element floor. They do not use the attachment's
eight-frame shortcut. Native plans are consumed in sorted scene order with
linear cursors rather than a retained hash map. Surface unconfiguration releases
both plan vectors immediately.

Attachment bytes are separate from the material buffer budget. Four-byte targets
with 4x sampling retain `width * height * (4 + 1) * 4` nominal bytes; single-sample
fallback retains only the resolved texture. Backend allocation overhead and
retired queue-owned attachments are not included. Test/bench-support headless
hooks report current extent, cumulative pair allocations, nominal retained bytes
and offscreen raster pass count, plus the actual adapter sample count. They also
support no-readback submission and explicit completion waits. Baseline image and
mixed-scene performance comparisons use separate binaries built from the fixed
baseline and new source; there is no shipping environment switch or legacy route.
Image comparisons must cover clipping, translucent overlap, fractional coverage,
native packed batches, nonzero raster origins, resize and resource recovery.


=== Admission and retirement

GPU buffers are initialized through WGPU's write-only mapped view, never by
reinterpreting the Rust model or overwriting an older revision. Completion
watermarks retain charges for both active and retired buffers. The owner of frame
preparation also finalizes failed pre-submit recordings through the renderer's
existing queue-flush path, so a failed later path draw cannot strand a provisional
submission. Unsupported capabilities and material capacity pressure are reported
and omit the affected drawing without preventing unrelated controls from rendering.
Capability failure is reported once per device-local program attempt. Other skipped
records are coalesced into one summary when the failure categories change; a
successful or empty frame resets that episode. Persistent failures do not log once
per drawing record or once per repaint.

Material admission checks the adapter's multisampled-shading capability as well
as storage limits before creating the shared shader module. The module contains
sample-interpolated rectangle coordinates even when a draw uses another schema.
Unsupported adapters omit these materials through the ordinary capability-error
path; unrelated GPUI controls do not require the material program.

The unified renderer defaults to 64 MiB of shared charged buffer capacity,
8,192 allocation charges, 4,096 drawing records per frame and eight outstanding
completion callbacks. Buffer bytes and allocation counts conservatively charge two
initialization copies, including after completion; these are admission accounting
limits, not measured VRAM or a budget for the entire GPUI window. CPU payload
capacities are supplied separately by the caller. A host sets the per-window limit
with `Window::set_gpu_material_budget` before drawing; the window's two scenes
retain it across clear and replay. Rivu applies `interface.gpu_material_budget_mb`
when creating its GUI, and retains that value for Spectrogram sampling until restart.
Spectrogram targets at most one eighth of that budget for one numerical payload
including column intervals: two history generations, each charged for two copies,
then consume at most half the shared limit. The remainder is headroom, not a hard
reservation. Additional unfinished generations can still encounter ordinary
per-upload admission pressure; existing uploaded tiles remain drawable.

The GPU cache retains only weak CPU ownership. Clearing a dynamic slot releases
its CPU content once existing snapshots finish; fixed scene records deliberately
remain replayable until invalidated. No cleanup frame or background polling is
introduced. Completed storage omitted from a later scene is reclaimed on draw,
including an empty scene; window/device destruction drops the renderer's ownership.
Ordinary scenes with no extension resources do not perform extension-specific
device polling. Native Metal remains explicitly unsupported.

=== Surface reattachment

Reattaching a native surface to an existing renderer preserves its device, queue,
atlas and immutable material uploads. It uses the originating WGPU instance;
this operation does not recreate a renderer whose GPU resources were released.
The replacement extent is clamped to at least one physical pixel per axis and
at most the renderer's device texture limit. Surface creation and handle errors
return through the existing failure path without introducing retries.

If the replacement changes alpha mode, ordinary drawing and Path-composite
pipelines rebuild for that mode, as they do for a transparency update. Material
and resolve composition use the current frame's alpha convention. Reattachment
releases size-bound MSAA scratch ownership; the next admitted frame recreates
it under the same bounded-capacity policy. In-flight commands retain prior
resources until completion. Headless alpha/pixel checks do not establish native
surface reattachment or compositor behavior; those require platform evidence.

=== Consumer integration boundary

The migrated consumers retain their algorithm state, content identity and bounded
immutable-publication caches. GPUI/WGPU own upload reuse and completion-aware
physical retirement; applications still decide when content changes or becomes
invalid. Artwork retains its independent image lifecycle.

Transport/storage belongs with GPUI/WGPU; consumer mappings and palette definitions
remain near visualization consumers, not in `rivu-ui` merely because they draw UI.

=== Consumer cutover contracts

The following contracts guided the completed fixed-schema migrations. They are
not a list of consumers still waiting for the proposed generic API.

[cols="1,2,2,2",options="header"]
|===
|Consumer |Application retains |GPU receives/does |Removed intermediate work
|Spectrum Bars/Outline/LED
|Frequency aggregation, envelope and Peak state
|Compact body rectangles, spacing and style parameters; procedural geometry and palette sampling (Peaks remain separate ordinary quads)
|Per-LED rectangles and their tessellation
|Spectrum Line/Solid
|Curve/geometry generation and CPU path tessellation
|Path geometry adapter with the shared material
|Special palette-image plumbing, not path tessellation
|Fractal Beams/Flow
|Simulation, trajectories and accepted-audio-time advancement
|Shared segment endpoints, intensity/color groups and layer parameters; instanced expansion
|Repeated CPU path construction for light layers
|Spectrogram
|Bounded history, time-bucket max pooling, axis identity and discontinuities
|Values, actual time intervals and sampling parameters; geometry and coloring
|Per-column colored images and repeated CPU coloring
|Density/Spatial
|Statistics, decay and field semantics
|Fixed-resolution values, ranges and color curves
|Whole-field BGRA generation on changes
|Waveform
|Coverage, source identity and RMS/Peak aggregation
|Numerical columns, validity and display mapping; per-column fills/markers
|Derived rectangle/image tiles and CPU gradient rasterization
|===

Paint and resize never advance simulations. Differently sized panels share common
signal/segment data, not independent analysis. Spectrogram intervals cannot become
an equal-width scroll that fills gaps. Glow must not silently become blur or
additive overexposure. Verify segment intersection/cap behavior against the current
path composition rather than assuming instancing is visually equivalent.

A GPU Waveform removes derived image tiles but still incurs fragment work during
stable repaints; the cutover alone does not establish a timing gain. Its playback
cursor remains independent, so cursor movement does not upload unchanged waveform
data.

== Proposed general rendering model

The following API and lifecycle design is not the closed-schema interface above.
It records requirements and candidate mechanisms for future generalization;
the fixed encoders and publication constructors remain the available path.

=== Scope

Allowed changes are confined to:

* `vendor/gpui`: drawing descriptions, state and resource handles, scene
  integration, replay, and window-local logical resource management.
* `vendor/gpui_wgpu`: shaders, pipeline preparation/cache, uploads, GPU allocation,
  execution, device-generation handling, and reclamation.
* Application visualization consumers, palette construction, and obsolete CPU
  rendering intermediates.
* Necessary ABI tooling, build integration, tests, and documentation.

Keep `gpui_linux` on its existing pinned dependency: do not modify or vendor it.
Do not add `PlatformWindow` methods. Preserve the existing transport:

[source,text]
----
Rivu parameters and data
  -> GPUI Scene
  -> PlatformWindow::draw(&Scene)
  -> WgpuRenderer
----

The pinned Wayland and X11 implementations forward the complete scene to the
renderer; they do not decode each primitive. New drawing records therefore do
not inherently require a Linux platform extension.

Do not change native surfaces, presentation, platform frame callbacks, or window
event mechanisms. Do not expose device, queue, or renderer handles to application
consumers. Do not change audio playback, FFT, analysis publication, or the fractal
simulation. Do not import gpui-fast retention, replace text/layout machinery, or
introduce a second rendering engine as part of this work.

A concrete requirement that cannot fit this boundary needs evidence and separate
authorization before expanding the patch surface. In particular, do not invent a
window-to-renderer asynchronous preparation API and then treat it as justification
for a new platform method.

=== Ownership and data model

[cols="1,2,2",options="header"]
|===
|Owner |Owns |Decides
|Application model/panel owner
|Signal history, envelopes, trajectories, coverage, source identity; logical render handles
|What data means, what remains useful, which consumers share it, and when to update or release it
|GPUI window resource manager
|Published drawing state, scene references, encoded drawing data and retirement bookkeeping
|How drawing data is captured, shared within the window, retained for replay, and released logically
|WGPU renderer
|Pipelines, physical buffers/textures, staging, execution references and reusable storage
|How to allocate, upload, execute, reuse and reclaim physical storage
|===

Do not move every application `Vec` into a common pool. Retain algorithm state in
the application, centralize drawing transport/storage, and eliminate intermediates
that the GPU can derive from parameters.

For example, replace LED rectangle meshes with bar parameters, and colored
Density images with scalar fields. Moving those same meshes or pixel loops into
a GPUI allocator would preserve the avoidable work.

Logical resources are window-scoped. Immutable CPU definitions may be shared more
widely, but GPU sharing must respect the actual device and lifetime. A global pool
must not keep a removed panel's data alive merely because another window exists.

=== Application-facing interface

The proposed public model uses:

* `Program<Schema>`: a validated program description, not a promise that a device
  pipeline already exists.
* `RenderState<Schema>`: one complete published display state, including
  parameters, resource bindings, and draw ranges.
* `DrawRequest`: a temporary placement of a state in the scene.
* `RenderData<T>` and `Field2D<T>`: bounded linear records and two-dimensional
  numerical data. Their update/sampling contracts differ; neither is an
  untyped byte buffer with loosely related flags.
* `ColorRamp`: an immutable color definition with explicit sampled views.

Illustrative usage, not a compilable interface commitment:

[source,rust]
----
let mut state = RenderState::new(spectrum::SCHEMA, capacities)?;

state.update(|edit| {
    edit.replace(spectrum::BARS, &bars)?;
    edit.set_params(params)?;
    edit.bind(spectrum::PALETTE, palette_view)?;
    edit.set_instances(0..bars.len() as u32)?;
    Ok(())
})?;
cx.notify();

window.paint_gpu(
    spectrum::PROGRAM.draw(&state).bounds(plot),
)?;
----

Binding identifiers and parameter types come from the schema rather than string
lookups. The update publishes data, parameters, bindings and draw ranges together.
In particular, the instance count must not be read from an unrelated mutable
variable during painting.

Bounds, current placement, clip and inherited opacity belong to drawing placement.
Axes, source-dependent mappings, palette selection and data ranges belong to the
published content state. Update does not implicitly schedule animation or refresh
an unrelated business root. The application continues to invalidate the affected
views through the existing notification paths.

A window owns resources once attached to its rendering context. Cross-window use
of an attached state must be rejected or explicitly imported, never silently
borrow another renderer's allocation.

=== Fixed and dynamic scene state

Use one drawing API with an explicit state policy, not independently mutable
bindings that happen to be sampled at different times.

==== Fixed content

For palettes, fixed geometry and stable cached content, record immutable content
revisions. Internally, `RecordedDraw` contains parameters, ranges and frozen
bindings, not `RenderData<T>` handles that resolve to the latest version later.

`Scene::replay` clones the recorded references. Recording A, publishing B, and
replaying the old draw must still produce A. Revisions identify stable content and
its backing, not merely a generation number followed by a lookup of current data.

==== Dynamic content

Real-time bars, segments and fields may use an explicit dynamic state slot.
Resolve each slot *once per prepared frame*, and use that complete publication for
parameters, instance ranges, axes and all resources. Multiple draws referencing
the same slot in that frame share the resolution.

A dynamic recorded draw retains the slot and content-independent placement/visible
bounds. It does not retain stale content-dependent parameters alongside bindings
that individually resolve to newer data. Intermediate publications that were never
sampled may be skipped; they are not an upload backlog.

The slot's schema, declared maximum resource/range envelope, and visible bounds
remain stable. Changing those requires scene rerecording. Actual counts may vary
inside the envelope as part of the atomic publication. Dynamic changes still need
an existing frame request/notification; latest-wins does not create a polling clock.

Once a dynamic slot has been resolved for execution, that resolved packet has the
same immutability and GPU safety requirements as fixed content. Latest-wins relaxes
which publication is selected, not whether submitted resources can be overwritten.

=== Shader composition and ABI

==== Geometry and material

A program combines geometry, a material, typed parameters/bindings, and a bounded
set of pipeline properties. Support rectangular coverage, procedural instances,
and adapters for existing paths/meshes through the same drawing model.

Geometry produces local positions and declared interpolated values. Material
functions evaluate color from those inputs, parameters and resources. Framework
entry points apply window transforms, clip, inherited opacity, geometry coverage
and the output color convention. Existing path adapters retain path coverage;
reusing a material does not automatically remove CPU path tessellation.

Custom varyings require producer/consumer layout agreement. Do not claim that
arbitrary shader fragments compose without an ABI. Use explicit standard WGSL
modules and validation; do not build a new shader language, runtime node editor,
or arbitrary render-pass callback API.

The same material should work with both a procedural bar and a compatible path.
Styles such as LED, Spectrum or Fractal Flow remain application programs and
parameters, not GPUI business enums.

Shader code is trusted application content. Do not expose unrestricted user shader
loading as part of this feature. Read-only drawing resources and framework-owned
entry points keep graphics submission and composition under renderer control.

==== Host/shader encoding

WGSL declarations plus the program description form the authoritative schema.
Use a Naga version matched to the repository's wgpu baseline to validate and
produce Rust value types, binding identifiers, layout descriptions and encoders.

The encoding contract includes:

* scalar kind/width, field offset/alignment, and total structure size;
* array and matrix stride, nested layout and runtime-array placement;
* uniform versus storage address-space rules;
* binding access/type and minimum size;
* initialized padding and checked output bounds.

`Copy`, `repr(C)`, or `Pod` alone does not establish WGSL compatibility. Encode
fields into managed storage; direct byte copying is an optimization only for
layouts proven identical. Compare actual shader layouts structurally with the
schema; a type ID, hash or matching total size alone is insufficient.

Do not upload native Rust references, pointers, `usize`/`isize`, container memory
representations, or default bool/enum representations. Use explicit fixed-width
encodings and validity masks. Zero-sized record types are not upload elements;
an empty collection is still a legitimate value. Nonfinite floating-point policy
belongs to the consumer's signal contract rather than a blanket ABI prohibition.

The current fixed schemas use explicit encoders and layout checks. Generalize tooling
only when consumer requirements justify it; postponing generation does not postpone
encoding safety. A future generator can be a small build dependency rather than
linking the runtime renderer into build scripts. Generated output belongs in Cargo's
`OUT_DIR`, with build artifacts under repository `.cache/`.

==== Program preparation

Build-time checks catch source and layout errors. The renderer creates and caches
device pipelines through the existing scene transport. Pipeline keys include the
program, binding layout, geometry adapter, relevant blend/sample/target state, and
device generation; not changing per-frame uniform values.

First-use preparation is a possible implementation, not a claim of zero startup
cost. Measure its visible latency. Evaluate renderer initialization or preparation
within the existing execution path before considering any platform-boundary change.
Do not parse source or recreate pipelines on every repaint.

Build-time shader generation does not eliminate driver compilation. No public API
may imply successful device preparation merely because a CPU description validated.

=== Publication, storage and upload

==== Update transaction

Collect edits, validate their schema/ranges, reserve finite storage, encode the
candidate, then publish one complete state. Failure or abandonment leaves the old
publication unchanged. Do not mutate backing held by a published state as part of
an operation that can still fail.

The transaction performs no I/O, asynchronous wait, business notification or
reentrant publication. Sharing and copy-on-write are internal choices, not a
public historical snapshot service. Keep only content reachable from current
owners, scene records, upload work or execution.

For drawing-only instances, a managed writer can avoid an extra application
scratch vector. Existing algorithm output may be copied or explicitly transferred.
Do not pin analysis publication slots indefinitely in pursuit of zero-copy.

==== Resource-specific storage

Small parameters can be captured and packed centrally. Frequently replaced
instance batches benefit from contiguous reusable preparation/upload regions.
Static immutable content can reuse a device copy. Large locally changing fields
may use chunked revisions or region updates with preserved old backing.

Chunking introduces metadata and GPU addressing costs. A contiguous GPU replica
may require copying unchanged regions when an old revision remains live. Account
for that work explicitly; `write_region` must not conceal unmeasured whole-field
copies. Choose the mechanism and granularity using actual update patterns.

Deduplicate uploads by resource content revision and device generation, not panel
identity or a whole-payload hash on every repaint. Different transforms of the same
shared data should not upload the payload again.

==== Upload side effects and failure isolation

Do not require every panel to update in the same frame or make one visualizer's
preparation failure cancel unrelated menus and controls. The isolation unit is a
complete resolved drawing state, which can span several draws.

Queue writes and explicit staging/copy commands are both candidates. Select by
measured upload shape and cost, not a universal transaction requirement. Before
writing, targets must be safe: a changed payload cannot overwrite storage still
needed by an existing scene or execution.

`Queue::write_buffer` and `write_texture` are not rollback operations. A scheduled
write can execute on a later submission, including one from another window using
the queue. If subsequent preparation fails, a candidate may incur wasted work,
but cannot corrupt published content. Keep its storage/staging alive until the
actual upload lifetime permits reuse. Explicit copy commands avoid this particular
queued-write side effect when an unsubmitted command buffer is discarded.

Do not advertise a state as executable until all of its required resources and
bindings are ready. A recording success is not GPU execution success. Temporary
pressure may defer that visualizer's update without queuing every missed update.
The application can retain the newest valid model and a refresh-needed marker.
A previous display may be reused only while its source and mapping remain valid;
otherwise omit the invalid content or expose its failure instead of relabeling it.

=== Scene integration and lifecycle

New records participate in GPUI's ordinary scene ordering, clipping, composition
and replay. They are not an unconditional topmost overlay. Visible bounds must
include stroke width, glow and procedural displacement. Compatible bindings and
pipelines alone do not permit reordering overlapping translucent content.

Keep scene/replay references separate from execution references. GPU completion
alone does not make a resource safe to overwrite if a scene can submit it again.
Likewise, releasing the last scene reference does not permit reusing staging that
is still being read by an upload.

Logical retirement belongs to GPUI and safe physical reclamation to WGPU. The current
retention policy is authoritative in
link:22_cache.adoc#_resource_boundaries[Resource boundaries]; generalization must
preserve that ownership rather than recreate application-specific retirement queues.

==== Hidden windows and shutdown

Hiding provides no guaranteed draw or new platform service. Stop display demand and
detach cached-scene references for content the consumer discards: dropping its model
alone cannot release replay-held CPU content. Static caches may remain, and uploads
retain data for their actual lifetime.

GPU reclamation is deferred until a later draw or renderer destruction; idle capacity
remains charged. Resume rebuilds from still-valid owned content and reconciles obsolete
resources even when the new scene has no visualizers. Close revokes window and scene
ownership without invalidating in-flight execution. No cleanup-render or polling loop
is introduced, and discarded signal history must not reappear.

==== Device and surface changes

Use the existing renderer lifecycle. An unconfigured surface is not necessarily
a lost device. Device recovery invalidates device-local pipelines and allocations
by generation. Rebuild only from still-owned valid CPU content; discarded hidden
history must not reappear. Late preparation/errors from an old generation cannot
install a new device's resources or overwrite its status.

Keep frame scheduling, presentation and native recovery integration unchanged.
If safe event-driven progress cannot be achieved with existing callbacks, report
that concrete limitation rather than silently adding platform methods or polling.

=== Palette and image semantics

`ColorRamp` represents color and alpha as a function of a normalized coordinate.
Separate its definition (stops, curve, interpolation space) from sampled views
(domain, resolution, filtering, clamping). Application-defined dB mapping,
nonlinear compression and spatial mapping remain outside the ramp itself.

CPU and GPU consumers use the same explicit definition/sampling rules. A domain
view can share data where equivalent; preserving an existing discretized result
may require a distinct bounded sampled representation. Do not assert that a
coordinate remap always reproduces a separately sampled subdomain exactly.

Numerical fields must not undergo color-space conversion. Color images and ramps
have explicit color/alpha conventions; backend BGRA/RGBA handling belongs below
the application API. Do not silently change interpolation to another color space
or add/remove premultiplication during optimization.

Generalization must preserve the distinct Spectrum, Waveform, Spectrogram and stereo
field meanings described in link:23_visuals.adoc[Visualization Rendering Design],
including per-column RMS endpoint colors, discrete Peaks and missing-time gaps.
Scalar interpolation before color mapping is not equivalent to interpolation of
mapped colors. The current field contract maps and quantizes each of four neighbors
before interpolating straight RGBA; it has no scalar-first mode. Any changed source
resolution, endpoint sampling or rounding requires an evaluated visual tradeoff.

=== Limits, pressure and acceptable approximation

Every logical resource has a finite maximum extent/record count. Physical active,
candidate, retired and pooled capacity, plus upload staging, all count toward
finite limits. Admission happens before allocation; do not evict scene-live content
to satisfy it. Device format/binding/texture limits are checked independently.

Existing consumer bounds are inputs, not a universal allocation algorithm. The
analysis-side Density three-slot publication pool remains its own contract; it
does not prescribe GPU ring depth. Do not introduce an arbitrary frequency-row cap
or shorten a supported history merely to simplify a shader.

Prototype with explicit finite experimental limits and report when they bind.
Measure live-version/region counts, payload versus allocated bytes, staging,
execution delay and idle high water. Then choose per-resource policies and product
budgets; experimental limits are not automatically shipping defaults. Measured
peaks alone are not safety bounds: exercise delayed GPU work and rapid changes.

Potentially worthwhile compromises include latest-wins updates, independent panel
refreshes, modest sampling/antialiasing differences and lower display precision.
Validate each against actual workload and perceived quality. Do not silently lower
precision, truncate data, or switch effects to make a failed allocation succeed.

Errors distinguish invalid schema/data, unsupported capability, temporary pressure,
resource limit, window closure and device failure. Temporary pressure coalesces
pending display work; it does not create an unlimited retry queue. No graphics
failure blocks or issues commands to the audio callback.

== Verification and decision gates

These are requirements for rendering changes, not claims that every historical
experiment covers every row. ABI-generation and general transaction gates apply
when introducing those proposals; current slices use fixed encoders and immutable
publication constructors. Changed consumers require their own runtime evidence:
compilation and reduced submission counts alone do not establish a performance gain.

[cols="1,3",options="header"]
|===
|Area |Required evidence
|ABI
|Offsets/strides for vectors, matrices, arrays and nested structures; uniform/storage distinction; invalid schemas rejected; padding initialized
|Fixed replay
|Record A, publish B, replay A; draw A and B in one frame without aliasing their content
|Dynamic consistency
|Publish during frame preparation; each slot resolves one complete publication for every consumer in that frame; count/axis/resource mismatches cannot occur
|Update failure
|Fail allocation or encoding between related edits; no partially published state
|Upload failure
|Inject failure after a candidate write or copy encoding; published backing remains unchanged, another window's submit cannot corrupt it, and failed candidates eventually release their charge
|Lifecycle
|Multi-panel sharing, last-consumer removal, resize, hide with no further draw, resume, close and device generation change; bounded retention and no invalid reuse
|Scene integration
|Clipping, scaling, overlap, inherited opacity, menus/tooltips over custom content, cached replay and ordinary unaffected primitives
|Visual quality
|Palette transitions, dark detail, thin lines, glow intersections, transparency, missing data and history gaps at real sizes/scales in motion
|Efficiency
|CPU construction, allocation/copy counts, upload bytes, GPU time, peak/steady memory, startup and recovery costs for equivalent workloads
|===

Use repeated measurements with variability for timing comparisons. Include static
repaints, changing data, dense LED scenes, multiple panels, resize and artificial
GPU delay. Pixel differences help locate errors but are not the sole visual
acceptance criterion. An imperceptible difference can be accepted for meaningful
performance gains; reduced draw calls or fewer source lines alone prove neither.

Follow repository checks for implemented changes: Rust changes require `make lint`
and relevant behavior tests; build/configuration/dependency changes require checks
and artifacts appropriate to the affected packages, features and linking behavior.
Exercise actual GUI behavior and affected feature branches when those are part of
the change. Documentation-only maintenance needs content, link and command checks,
not a fresh GUI run or benchmark. Keep permanent tests for consumer-visible
invariants and errors, not incidental API spelling or code
layout. Keep throwaway profiling/prototype artifacts separate from product code.
